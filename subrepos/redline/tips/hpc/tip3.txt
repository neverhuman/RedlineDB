Here’s the **Rust HPC acceleration playbook I’d use in 2026**. I’m treating “native Rust” as: Rust-first code where possible, with a separate lane for Rust bindings to unavoidable HPC substrates like CUDA, MPI, BLAS/LAPACK, RDMA, ROCm, and vendor runtimes. No list can be literally permanent because Rust HPC crates are moving fast, but this is a broad current sweep across docs, GitHub, crates, and recent community/X signals.

## The biggest breakthrough levers, ranked

**1. Change the algorithm or representation before touching micro-optimizations.** A better algorithm beats hand-tuned loops almost every time: FFT instead of direct convolution, Fast Multipole Method instead of all-pairs interactions, sparse matrices instead of dense, columnar Arrow/Polars instead of row-wise records, batched GEMM instead of scalar loops. Rust has credible building blocks here: `RustFFT` is pure Rust and SIMD-accelerated; `kifmm` is a Rust kernel-independent Fast Multipole Method framework with optional MPI support; `faer` is a high-performance dense linear algebra library; `sprs` provides compressed sparse matrix/vector storage; and Polars/DataFusion/Arrow give you columnar query execution. ([GitHub][1])

**2. Compile for the actual machine.** For intense HPC binaries, start with `opt-level = 3`, `codegen-units = 1`, LTO, `panic = "abort"`, and `-C target-cpu=native` when you do not need portable binaries. Cargo profiles expose optimization controls, Rust’s performance book explicitly recommends `codegen-units = 1`, `lto = "fat"`, alternative allocators, `panic = "abort"`, and `-C target-cpu=native` for maximum runtime speed, and `rustc` supports PGO. ([Rust Documentation][2])

```toml
# Cargo.toml
[profile.release]
opt-level = 3
codegen-units = 1
lto = "thin"          # use "fat" for final squeeze if build time is acceptable
panic = "abort"
debug = "line-tables-only"  # keep profiler-friendly symbols without full debuginfo

[profile.bench]
inherits = "release"
debug = true
```

```toml
# .cargo/config.toml
[target.x86_64-unknown-linux-gnu]
rustflags = ["-C", "target-cpu=native"]
```

**3. Build a real profiling stack first.** Use `criterion` for statistical microbenchmarks, `iai-callgrind` for stable instruction/cache-style benchmarking, `cargo-flamegraph`/`perf` for hotspots, heaptrack/DHAT/bytehound for allocation pressure, and `cargo-show-asm` to check whether the generated assembly actually vectorized. Criterion is statistics-driven, Iai-Callgrind uses Valgrind tools such as Callgrind/Cachegrind/DHAT, and Rust’s performance book lists flamegraph, heaptrack, bytehound, samply, and causal profiling tools. ([Docs.rs][3])

**4. Push memory bandwidth and cache locality before adding threads.** Use structure-of-arrays, cache blocking/tiling, preallocated workspaces, `Vec::with_capacity`, aligned chunks, chunked reductions, bitsets, compressed sparse structures, and zero-copy parsing. False sharing can destroy scaling; `CachePadded` exists specifically to prevent unrelated hot fields from living in the same cache line. ([Docs.rs][4])

**5. Use SIMD intentionally.** Stable Rust gives you `std::arch` for architecture-specific intrinsics; nightly `std::simd` is still experimental but provides portable SIMD; crates like `wide`, `pulp`, `safe_arch`, `rten-simd`, `simd-json`, `sonic-rs`, and libraries such as `RustFFT` expose SIMD in more ergonomic forms. ([Rust Documentation][5])

**6. Offload only when arithmetic intensity justifies it.** For GPUs, the exciting Rust-native frontier is moving quickly: `cuda-oxide` is an NVIDIA Labs experimental Rust-to-CUDA compiler that compiles Rust to PTX; Rust-CUDA rebooted in 2025; CubeCL lets you write GPU kernels using Rust abstractions across platforms; `cudarc` is a safe Rust wrapper around CUDA; `wgpu` gives portable compute/graphics across Vulkan/Metal/D3D12/OpenGL/WebGPU; and `rust-gpu` targets SPIR-V shaders. These are powerful, but maturity varies dramatically. ([GitHub][6])

**7. For cluster work, combine MPI/RDMA/Slurm-style scheduling with Rust ownership.** Use MPI between nodes, Rayon within a process/socket, NUMA-aware placement inside nodes, and RDMA only when message overhead dominates. `rsmpi` provides MPI bindings, `FerroMPI` is a newer MPI 4.0+ wrapper, `rust-ibverbs` exposes RDMA verbs, and HyperQueue handles large HPC workflows on Slurm/PBS-style clusters. ([Docs.rs][7])

# Rust HPC techniques that move the needle

## Compiler, linker, and build tricks

Use this as the baseline for performance builds:

```bash
RUSTFLAGS="-C target-cpu=native" cargo build --release
```

For reproducible cluster builds, build multiple CPU-specific artifacts instead of shipping one generic binary: for example, one binary for AVX2-era nodes, another for AVX-512 nodes, and another for ARM Neoverse. `target-cpu=native` is excellent for a fixed machine, but dangerous for broad distribution because the binary may use instructions unavailable on older nodes. The Rust performance book specifically recommends `-C target-cpu=native` when broad architecture support is not needed. ([Nicholas Nethercote][8])

Use **PGO** for real workloads: run an instrumented binary on representative datasets, merge the profile, then rebuild with `-C profile-use`. Rustc’s PGO support is documented in the rustc book, and it is one of the rare compiler optimizations that can improve branch-heavy, parser-heavy, query-engine, and control-flow-heavy HPC applications without changing source code. ([Rust Documentation][9])

Use **ThinLTO first, Fat LTO last**. ThinLTO often gives a strong speed/build-time tradeoff; Fat LTO may squeeze a little more in final binaries but can increase build time substantially. Cargo exposes LTO and codegen-unit profile controls. ([Rust Documentation][2])

Consider this final-release variant:

```toml
[profile.release]
opt-level = 3
codegen-units = 1
lto = "fat"
panic = "abort"
strip = "symbols"
```

Add `debug = "line-tables-only"` while optimizing so profilers can still resolve line numbers.

## Measurement and inspection

Use a full stack, not one tool:

| Need                         | Tools                                                         |
| ---------------------------- | ------------------------------------------------------------- |
| Microbenchmarks              | `criterion`, `divan`                                          |
| CI-stable performance deltas | `iai-callgrind`, `cachegrind`                                 |
| CPU flamegraphs              | `cargo-flamegraph`, Linux `perf`, `samply`                    |
| Allocation profiling         | `heaptrack`, `bytehound`, `dhat-rs`, `rust-jemalloc-pprof`    |
| Assembly/codegen inspection  | `cargo-show-asm`, Compiler Explorer, `objdump`, `llvm-mca`    |
| System counters              | `perf stat`, `perf record`, Intel VTune, AMD uProf, LIKWID    |
| GPU profiling                | Nsight Systems/Compute for CUDA, ROCm profiling tools for AMD |

Criterion aims to detect and estimate performance improvements/regressions statistically, Iai-Callgrind gives accurate Valgrind-backed measurements, and `cargo-flamegraph` generates flamegraphs for Rust/Cargo workloads. ([Docs.rs][3])

The optimization loop should be:

```text
benchmark representative workload
→ flamegraph / perf counters / allocation profile
→ inspect generated assembly if the hotspot is a tight loop
→ change one thing
→ benchmark again
→ keep only measured wins
```

## Rust-specific codegen tricks

These are the little Rust moves that often create surprisingly large wins:

| Trick                                                                                      | Why it helps                                                                                                                             |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Prefer `&[T]` / `&mut [T]` over owned `Vec<T>` in hot kernels                              | Better API, easier slicing, fewer ownership moves, often cleaner aliasing for LLVM                                                       |
| Use `split_at_mut`, `chunks_exact`, `chunks_exact_mut`, `array_chunks`, `zip`, `enumerate` | Helps remove bounds checks and expresses non-overlap                                                                                     |
| Hoist shape/length checks outside loops                                                    | Lets the inner loop avoid repeated branches                                                                                              |
| Use `debug_assert!` for invariants, not runtime checks in release                          |                                                                                                                                          |
| Prefer `fold`/`reduce` over shared mutable state                                           | Avoids locks and atomics                                                                                                                 |
| Avoid `collect()` in the middle of a pipeline                                              | Prevents temporary allocations                                                                                                           |
| Avoid `clone()` of `Vec`, `String`, `HashMap`, tensor buffers                              | Cloning heap-allocated structures usually allocates; Rust’s performance book calls this out explicitly. ([Nicholas Nethercote][10])      |
| Use `#[inline]` for tiny hot wrappers; avoid blanket `#[inline(always)]` everywhere        | Good for kernels, bad for code bloat                                                                                                     |
| Use `#[cold]` on rare error/slow paths                                                     | Keeps hot instruction cache cleaner                                                                                                      |
| Use `#[target_feature(enable = "avx2")]` / runtime dispatch for CPU-specific kernels       |                                                                                                                                          |
| Use `std::hint::black_box` in benchmarks                                                   | Prevents optimizer from deleting benchmarked work                                                                                        |
| Use `MaybeUninit` for output buffers only in carefully-audited low-level kernels           |                                                                                                                                          |
| Use `get_unchecked` only after measuring and proving bounds checks remain                  | Safe indexing can often be optimized; the Rust Performance Book discusses bounds-check elimination patterns. ([Nicholas Nethercote][11]) |

# Memory and data layout acceleration

## Highest-impact memory tactics

Use **SoA instead of AoS** when you process one field across many elements.

```rust
// Usually worse for SIMD/cache if you only touch x/y/z separately
struct Particle {
    x: f32,
    y: f32,
    z: f32,
    mass: f32,
}

// Often better for vectorized kernels
struct Particles {
    x: Vec<f32>,
    y: Vec<f32>,
    z: Vec<f32>,
    mass: Vec<f32>,
}
```

Use **AoSoA** for vector-friendly chunking:

```rust
const LANES: usize = 8;

#[repr(C, align(64))]
struct ParticleBlock {
    x: [f32; LANES],
    y: [f32; LANES],
    z: [f32; LANES],
    mass: [f32; LANES],
}
```

Use **cache blocking/tiling** for matrices, stencils, pairwise kernels, convolutions, and graph traversal. The goal is to reuse data while it is still in L1/L2/L3 rather than streaming everything repeatedly from DRAM.

Use **thread-local workspaces** instead of per-iteration allocation:

```rust
use rayon::prelude::*;

items.par_chunks(chunk_size)
    .map_init(
        || Vec::<f64>::with_capacity(4096),
        |scratch, chunk| {
            scratch.clear();
            // reuse scratch for this Rayon worker
            compute_chunk(chunk, scratch)
        },
    )
    .sum::<f64>();
```

**Underused trick:** use `Cow<'a, str>`, borrowed slices, or arena-backed strings in parsers to avoid building owned `String`s.

# CPU parallelism and NUMA

## Best CPU threading crates

| Area                   | Crates                                                                 | Notes                                                                                                                                                  |
| ---------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Data parallelism       | `rayon`                                                                | First choice for CPU-bound loops. Rayon makes sequential-to-parallel conversion simple and guarantees data-race freedom. ([GitHub][19])                |
| Work stealing / queues | `crossbeam`, `crossbeam-deque`, `crossbeam-channel`, `crossbeam-queue` | Crossbeam provides atomics, channels, work-stealing deques, queues, epoch reclamation, and scoped threads. ([Docs.rs][20])                             |
| Locks                  | `parking_lot`                                                          | Smaller/faster/more flexible Mutex/RwLock/Condvar implementations than std, according to the crate docs. ([Docs.rs][21])                               |
| Channels               | `flume`, `crossbeam-channel`, `kanal`                                  | MPMC channels; good for pipelines, but avoid in tight numerical kernels.                                                                               |
| Read-mostly sharing    | `arc-swap`, `evmap`, `left-right`                                      | `ArcSwap` provides atomic `Arc` replacement and is optimized for read-mostly scenarios. ([Docs.rs][22])                                                |
| Thread pinning         | `core_affinity`, `core_affinity2`, `hwlocality`, `affinitypool`        | Important for NUMA and latency-sensitive HPC. `hwlocality` binds to hwloc and exposes NUMA/socket/cache/core topology. ([Crates][23])                  |
| NUMA                   | `hwlocality`, `libnuma`, `numa-sys`, `rustix`/`libc` calls             | Use first-touch placement and pin workers to local memory. libnuma exposes NUMA policy; NUMA memory can have different latency/bandwidth. ([Man7][24]) |
| Thread priority        | `thread-priority`, OS-specific APIs                                    | Useful for real-time-ish pipelines and latency-critical simulations.                                                                                   |

## Rayon patterns that scale

Good:

```rust
use rayon::prelude::*;

let sum = data
    .par_chunks(4096)
    .map(|chunk| chunk.iter().map(|x| expensive(*x)).sum::<f64>())
    .sum::<f64>();
```

Better when you need scratch buffers:

```rust
let result = data
    .par_chunks(4096)
    .map_init(
        || Scratch::new(),
        |scratch, chunk| compute_with_reused_workspace(chunk, scratch),
    )
    .reduce(Output::zero, Output::combine);
```

Avoid:

```rust
// Usually terrible: shared lock in hot loop
data.par_iter().for_each(|x| {
    *global.lock().unwrap() += expensive(*x);
});
```

Use per-thread local accumulation and reduce at the end. Locks and atomics can be fine for coarse-grained coordination, but they are poison inside numerical inner loops.

## NUMA strategy for big machines

On dual-socket or multi-NUMA-node servers:

1. Start one process per NUMA node or one process per socket.
2. Pin worker threads to cores in that NUMA region.
3. First-touch initialize arrays on the same threads that will later use them.
4. Avoid one giant global allocator bottleneck.
5. Avoid cross-socket reductions until the end.
6. For MPI+threads, prefer MPI between sockets/nodes and Rayon/OpenMP-style parallelism inside a socket.

`hwlocality` is especially valuable because it exposes NUMA nodes, sockets, shared caches, cores, SMT topology, and can pin threads/memory. ([Docs.rs][25])

# SIMD and vectorization

## SIMD options in Rust

| Approach                   | Status                                  | Use when                                                                                                                                                                   |
| -------------------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auto-vectorization         | Stable                                  | Start here. Write simple, branch-light loops over slices. Inspect assembly.                                                                                                |
| `std::arch` / `core::arch` | Stable architecture-specific intrinsics | You need AVX2/AVX-512/SSE/NEON and can write target-specific kernels. `std::arch` is the gateway to architecture intrinsics and is not portable. ([Rust Documentation][5]) |
| Runtime dispatch           | Stable                                  | Write scalar fallback plus AVX2/AVX-512/NEON paths selected at runtime.                                                                                                    |
| `std::simd`                | Nightly experimental                    | Portable SIMD abstraction; docs still mark it nightly-only experimental. ([Rust Documentation][26])                                                                        |
| `wide`                     | Stable crate                            | Portable wide vector types that try to be SIMD where possible. ([GitHub][27])                                                                                              |
| `pulp`                     | Stable crate                            | Safe abstraction over SIMD with dispatch to vectorized versions. ([Crates][28])                                                                                            |
| `safe_arch`                | Stable crate                            | Safe wrappers for compile-time CPU-feature intrinsics; not runtime dispatch. ([Docs.rs][29])                                                                               |
| `rten-simd`                | Stable crate                            | Portable SIMD operations with runtime ISA dispatch. ([Docs.rs][30])                                                                                                        |

## SIMD hot-loop rules

Use these aggressively:

```rust
for (a, b) in xs.chunks_exact(8).zip(ys.chunks_exact(8)) {
    // vectorizable chunk
}
```

Prefer:

* contiguous slices;
* no virtual calls in the inner loop;
* no allocation in the inner loop;
* one or two predictable branches, not many data-dependent branches;
* precomputed constants;
* `mul_add` where numerical semantics allow FMA;
* SoA layout for gather-heavy kernels;
* chunked tail handling.

Avoid:

* `Vec<Vec<T>>` for matrices;
* maps/hash lookups inside inner numerical loops;
* iterator chains that allocate;
* branchy per-element state machines when a vectorized block parser is possible;
* tiny tasks that are parallelized before they are vectorized.

# GPU and accelerator stack

| ---------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CUDA host API from Rust                  | `cudarc`, `cust`, `rustacuda`                              | You want to launch CUDA kernels, call CUDA libraries, manage streams/memory from Rust. `cudarc` is a safe wrapper around the CUDA toolkit. ([GitHub][41])                               |
| Write CUDA kernels in Rust               | `cuda-oxide`, Rust-CUDA, `rustc_codegen_nvvm`, `cutile-rs` | Experimental but very exciting. `cuda-oxide` compiles standard Rust to PTX and is alpha; Rust-CUDA rebooted after dormancy and targets NVVM IR. ([GitHub][6])                           |

| Portable WebGPU/Vulkan/Metal/D3D compute | `wgpu`, `naga`, `vulkano`, `ash`                           | Cross-platform compute/graphics. `wgpu` runs on Vulkan, Metal, D3D12, OpenGL, WebGL2, and WebGPU. ([GitHub][43])                                                                        |
| Rust-to-SPIR-V shaders                   | `rust-gpu`                                                 | Rust as a language for GPU graphics and compute shaders. ([GitHub][44])                                                                                                                 |
| OpenCL                                   | `ocl`, `opencl3`                                           | Cross-vendor kernels with OpenCL; `ocl` exposes Rust’s OpenCL API and aims to preserve C API performance. ([Crates][45])                                                                |
| AMD ROCm/HIP                             | `rocm-rs`, `hip-sys`, CubeCL ROCm/HIP support              | AMD GPUs. ROCm is AMD’s open GPU software stack for HPC/AI workloads. ([AMD][46])                                                                                                       |
| ML/tensors                               | `candle`, `burn`, `ort`, `tract`, `safetensors`            | Inference/training/tensor workloads. Candle focuses on Rust ML performance with GPU support; Burn is a tensor/deep-learning framework optimized for numerical computing. ([GitHub][47]) |

## GPU rules that matter more than language

1. Keep data resident on the device.
2. Fuse kernels to reduce global memory traffic.
3. Batch small operations.
4. Use streams to overlap copy and compute.
5. Prefer library kernels for GEMM/FFT/convolution unless your kernel is specialized.
6. Use pinned/page-locked host memory for heavy transfers.
7. Use mixed precision when numerically acceptable.
8. Minimize host-device synchronization.
9. Avoid GPU offload for low arithmetic-intensity work.
10. Profile with Nsight/ROCm tools, not just CPU timers.

## Current “watchlist” GPU projects

`cuda-oxide` is the most interesting new item: NVIDIA Labs describes it as an experimental alpha compiler for writing CUDA SIMT kernels in pure Rust and compiling to PTX. Treat it as frontier technology, not production-stable infrastructure yet. ([GitHub][6])

Rust-CUDA is alive again after being dormant for years, but its own repo still warns to expect bugs, safety issues, and things that do not work. It is exciting, but not “just drop it into production” tooling. ([GitHub][48])

OxiCUDA showed up in recent X/GitHub searches and claims to replace the CUDA Toolkit stack in Rust, but it is extremely new. I would put it on a watchlist and validate hard before betting production workloads on it. ([X (formerly Twitter)][49])

| Tensor files                 | `safetensors`; Hugging Face describes SafeTensors as safe and fast/zero-copy for tensor storage. ([Hugging Face][55])                   |
| Serialization                | `rkyv`, `bincode`, `postcard`, `ciborium`, `capnp`, `flatbuffers`                                                                       |

Underused trick: for huge static datasets, combine `memmap2` + `rkyv`/`zerocopy`/`bytemuck` and read directly from mapped bytes. That can remove an entire “load/parse/allocate” phase.

For serious multi-node HPC, the practical architecture is usually:

```text
MPI or RDMA between nodes
+ Rayon/thread pinning within each node/socket
+ NUMA first-touch memory placement
+ Arrow/Parquet/checkpoint formats for data
+ Slurm/HyperQueue for scheduling
```

`rsmpi` bridges MPI into Rust for HPC systems, `FerroMPI` adds safe/generic MPI bindings with MPI 4.0+ features, `rust-ibverbs` exposes high-throughput/low-latency RDMA verbs, and HyperQueue simplifies large task graphs on clusters without manually submitting every Slurm/PBS task. ([Docs.rs][7])

# “People miss these” Rust HPC tricks

## 1. Use `par_chunks_mut`, not shared mutation

```rust
use rayon::prelude::*;

output
    .par_chunks_mut(block)
    .zip(input.par_chunks(block))
    .for_each(|(out, inp)| {
        kernel(inp, out);
    });
```

This gives each worker exclusive mutable slices and avoids locks entirely.

## 2. Use one allocation per phase, not one allocation per item

Bad:

```rust
let ys: Vec<Vec<f64>> = xs.iter().map(|x| compute_vec(x)).collect();
```

Better:

```rust
let mut workspace = vec![0.0; n_items * item_width];
// fill by chunk/slice
```

## 3. Replace nested `Vec<Vec<T>>` matrices

Prefer flat storage:

```rust
struct Matrix {
    data: Vec<f64>,
    rows: usize,
    cols: usize,
}

impl Matrix {
    #[inline]
    fn get(&self, r: usize, c: usize) -> f64 {
        self.data[r * self.cols + c]
    }
}
```

Better still: use `faer`, `ndarray`, or BLAS-backed crates when the matrix operations are standard.

## 4. Use bitsets for graph/frontier workloads

`HashSet<usize>` is often a disaster for graph traversals. Try `FixedBitSet`, `bitvec`, `RoaringBitmap`, or sorted `Vec<u32>` with galloping intersection.

## 5. Specialize by type and dimension

Const generics can make small kernels much faster:

```rust
fn dot<const N: usize>(a: &[f64; N], b: &[f64; N]) -> f64 {
    let mut acc = 0.0;
    for i in 0..N {
        acc += a[i] * b[i];
    }
    acc
}
```

For tiny fixed matrices/vectors, `nalgebra` with static dimensions can beat dynamic array abstractions.

## 6. Runtime-dispatch SIMD

Have scalar fallback plus CPU-specific kernels:

```rust
pub fn saxpy(a: f32, x: &[f32], y: &mut [f32]) {
    assert_eq!(x.len(), y.len());

    #[cfg(target_arch = "x86_64")]
    {
        if std::is_x86_feature_detected!("avx2") && std::is_x86_feature_detected!("fma") {
            unsafe { return saxpy_avx2_fma(a, x, y); }
        }
    }

    saxpy_scalar(a, x, y)
}

fn saxpy_scalar(a: f32, x: &[f32], y: &mut [f32]) {
    for (xi, yi) in x.iter().zip(y.iter_mut()) {
        *yi = a.mul_add(*xi, *yi);
    }
}
```

## 7. Use `ArcSwap` for read-mostly global state

For lookup tables, configurations, model snapshots, or immutable simulation parameters updated occasionally, `ArcSwap` can replace `RwLock<Arc<T>>` patterns and avoid read locks. ([Docs.rs][22])

## 8. Use mmap + zero-copy for massive static files

```rust
use memmap2::Mmap;
use std::fs::File;

let file = File::open("huge-table.bin")?;
let mmap = unsafe { Mmap::map(&file)? };
// parse/view mmap bytes without copying
```

`memmap2` maps files to byte slices, which pairs naturally with `bytemuck`, `zerocopy`, `rkyv`, Arrow, or SafeTensors. ([Docs.rs][16])

## 9. Use alternative allocators only after profiling

```rust
use mimalloc::MiMalloc;

#[global_allocator]
static GLOBAL: MiMalloc = MiMalloc;
```

Allocator swaps can help allocation-heavy services, parsers, graph builders, and schedulers, but they will not fix a bad algorithm or poor memory layout. Rust exposes `#[global_allocator]`, and `mimalloc` is a drop-in Rust global allocator wrapper. ([Rust Documentation][56])

## 10. Don’t use async for CPU compute kernels

Async helps with I/O concurrency. It usually hurts tight compute kernels. Use Rayon or dedicated pinned worker threads for CPU-bound numerical work; use async for feeding data, networking, and storage.

# A practical “max performance Rust” checklist

Use this order:

1. **Benchmark the real workload.** Add Criterion/Divan microbenchmarks only after you know the macro hotspot.
2. **Build release correctly.** `cargo build --release`, `target-cpu=native`, `codegen-units=1`, LTO, PGO.
3. **Inspect flamegraphs.** Do not optimize cold code.
4. **Kill allocations.** Preallocate, reuse scratch buffers, avoid `clone`, use arenas where lifetimes match.
5. **Fix data layout.** SoA/AoSoA, flat matrices, compressed sparse/bitset structures.
6. **Remove lock contention.** Chunk ownership, local reductions, `CachePadded`, `ArcSwap`, per-thread buffers.
7. **Vectorize.** First auto-vectorization, then `std::arch`/`wide`/`pulp`, then hand SIMD.
8. **Thread carefully.** Rayon for CPU kernels; tune chunk sizes; avoid nested oversubscription.
9. **Make it NUMA-aware.** Pin workers, first-touch memory, reduce cross-socket traffic.
10. **Use specialized libraries.** `faer`, BLAS/MKL/OpenBLAS, `RustFFT`, `sprs`, `Polars`, `DataFusion`, `kifmm`.
11. **Offload to GPU only when data movement is amortized.** Keep buffers resident and fuse kernels.
12. **Scale out.** MPI/RDMA/HyperQueue/Ballista only after single-node efficiency is strong.
13. **Lock in regressions.** Add benchmark thresholds in CI.

For the absolute highest-end Rust HPC apps, the stack I’d try first is:

```text
CPU numerical core:
  faer / ndarray / RustFFT / sprs
  + rayon
  + explicit SIMD where needed
  + target-cpu=native + PGO

Memory/data:
  SoA/AoSoA
  + memmap2
  + bytemuck/zerocopy/rkyv
  + mimalloc or jemalloc only if profiling says so

GPU:
  cudarc for production NVIDIA host-side control
  CubeCL for Rust-first multi-backend kernels
  cuda-oxide/Rust-CUDA as frontier experiments

Cluster:
  mpi or ferrompi between nodes
  + rayon inside each node/socket
  + hwlocality/libnuma for placement
  + HyperQueue for task-graph scheduling
```

The most “breakthrough” path is not a single crate. It is **algorithmic reduction + cache-friendly layout + measured compiler settings + SIMD + Rayon/NUMA + GPU only where arithmetic intensity is high**. Rust gives you a fantastic advantage here because you can encode ownership, aliasing, and thread-safety directly into the program while still reaching down to intrinsics, CUDA, MPI, RDMA, mmap, and custom allocators when the workload demands it.
