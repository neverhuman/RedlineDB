Here’s the best evidence-ranked picture I found. I’m treating “top requested” as **public-demand signal**, not an exact poll: repeated SQLite Forum threads, high-view Stack Overflow/DBA/ORM issues, Reddit/HN production discussions, extension/fork ecosystems, and official SQLite/Postgres docs. X/Quora are not fully searchable/citable in a reliable way here, so I used them only as weak directional signal; the high-confidence ranking below is based on sources that were accessible and inspectable.

SQLite itself frames the story well: it implements much of common SQL, but intentionally omits or limits some features common in server databases—officially listing limited `ALTER TABLE`, no statement-level triggers, read-only views, and no `GRANT`/`REVOKE`. ([SQLite][1])

## Details on the major gaps

### 1) Multiple concurrent writers, MVCC, row-level locks

This is the loudest and most repeated gap. SQLite’s own “when to use SQLite” page says it allows multiple simultaneous readers but only **one writer at any instant**, and advises a client/server database when many concurrent writers are needed. ([SQLite][2]) A January 2025 SQLite Forum thread asks directly why SQLite cannot have multiple writers/MVCC; the response points back to SQLite’s embedded, file-lock-based design. ([SQLite][3])

The Postgres gap is obvious: Postgres gives users MVCC, row-level locks, `SELECT ... FOR UPDATE`, concurrent write transactions, and much richer lock semantics. SQLite users often work around this with WAL mode, one writer queue, `busy_timeout`, short transactions, sharding, or routing writes through a single process. A Reddit thread from 2025 reflects the practical pain: users compare one writer connection vs. `busy_timeout`, and discuss serializing writes as a normal production pattern. ([Reddit][4])

There are forks and experiments trying to close this gap. Turso/libSQL describes SQLite’s single-writer model and `SQLITE_BUSY` as a blocker even for modest concurrent access, and notes that SQLite’s experimental `BEGIN CONCURRENT` branch has not been merged into official SQLite. ([Turso][5])

**My read:** this is the most requested “Postgres-like” SQLite feature, but also one of the least likely to land in core SQLite because it cuts against SQLite’s file-level, embedded architecture.

### 2) Replication, HA, server/network access, production ops

This is closely related to #1 but distinct. Many users do not merely want faster writes; they want **SQLite to behave operationally like a production network database** while retaining the `.db` file simplicity. SQLite’s official description emphasizes that it is in-process, serverless, and has no separate server process. ([SQLite][6]) Its own guidance says that if data is separated from the application by a network, a client/server engine is usually better. ([SQLite][2])

Public discussions repeatedly mention the gap around moving hosts, backups, containers, HA, and cross-region replication. HN users explicitly call out the complexity of configuring Litestream, rqlite, dqlite, LiteFS-like solutions, and similar tooling for high-availability SQLite. ([Hacker News][7]) Another HN discussion says SQLite is great on one VM, but migration between hosts and filesystem backup can become messy compared with a managed network database. ([Hacker News][8])

**What people want:** built-in replication, server/wire protocol, read replicas, failover, streaming backup, cloud-friendly connection semantics, and sometimes a Postgres-compatible wire protocol. The fact that libSQL/Turso, rqlite, dqlite, LiteFS, SQLite Cloud, and Litestream exist is itself strong market signal.

### 3) Full `ALTER TABLE` and painless migrations

SQLite’s DDL/migration limitations are one of the most painful day-to-day gaps. Official docs say SQLite supports only a subset of `ALTER TABLE`: rename table, rename column, add column, and drop column. Other schema changes require a manual copy-table procedure. ([SQLite][9]) For changes such as adding/removing constraints, changing types, adding `UNIQUE`, changing `NOT NULL`, or changing primary keys, SQLite documents a 12-step rebuild procedure. ([SQLite][9])

The demand signal is huge. A Stack Overflow question asking how to add a foreign key to an existing SQLite table has over 200k views; the accepted answer says you cannot use `ADD CONSTRAINT` and must recreate/copy the table. ([Stack Overflow][10]) SQLite Forum users also request smaller migration conveniences like `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`. ([SQLite][11])

**Postgres gap:** Postgres supports a far richer migration surface: `ALTER COLUMN`, add/drop constraints, change defaults, add `NOT NULL`, create/drop schemas, and so on. SQLite’s workaround is reliable but tedious: create a new table, copy data, drop old table, rename.

### 4) Better constraint handling: add/drop constraints, deferrable uniqueness, FK defaults

This is partly included in #3 but important enough to separate. Users want constraints to behave more like Postgres: add constraints later, defer constraint checks, manage constraints by name, and avoid table rebuilds for routine schema evolution.

SQLite Forum users have asked for deferred uniqueness behavior so that bulk updates like incrementing all values in a unique column do not fail row-by-row even though the final state is valid. A forum reply describes the desired behavior as delaying unique-constraint checking until commit, similar to what can be done with foreign keys. ([SQLite][12]) Separately, users complain that foreign-key enforcement is connection-level and must be enabled manually with `PRAGMA foreign_keys = ON` for each connection. ([SQLite][13])

**What people want:** Postgres-like named constraints, `ALTER TABLE ADD/DROP CONSTRAINT`, deferrable unique/exclusion constraints, database-file-level FK enforcement defaults, and smoother constraint validation.

### 5) Stronger typing and richer native types

SQLite’s flexible typing is a beloved feature for some and a constant source of production mismatches for others. Official docs say most SQL engines use static, rigid typing, while SQLite uses dynamic typing; `STRICT` tables exist, but are opt-in and table-by-table. ([SQLite][14]) The `STRICT` docs also show a much smaller type vocabulary than Postgres: `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB`, and `ANY`. ([SQLite][15])

A concrete ORM/test pain point: Django users report getting bitten when migrating from SQLite to Postgres because SQLite does not enforce `varchar` length the way Postgres does. ([Django Forum][16]) SQLite also has no separate Boolean storage class and no native date/time storage class; booleans are stored as integers, and dates/times are stored as text, real, or integer values. ([SQLite][14])

**What people want:** database-wide strictness, enforced `varchar(n)`, real Boolean/date/time/UUID types, enums, domains, arrays, composite types, and closer Postgres semantics for ORMs and dev/test parity.

### 6) Postgres-grade JSONB indexing and containment

SQLite’s JSON support has improved a lot, including JSONB. But it is not Postgres JSONB. SQLite’s own JSON docs say SQLite JSONB is not the same as PostgreSQL JSONB and does not provide O(1) lookup; most operations remain O(N). ([SQLite][17])

The recurring request is **GIN-like JSON indexing**: arbitrary key/value containment, indexing arrays, and querying unknown paths efficiently. A SQLite Forum thread asks whether one can index JSON array contents; Richard Hipp answers that ordinary SQLite indexes are one-to-one, whereas indexing array contents is many-to-one, so the answer is “probably no” without workarounds like FTS or side tables. ([SQLite][18]) HN users make the same comparison directly: SQLite lacks arbitrary JSON indexing like Postgres and can only index known expressions/paths in advance. ([Hacker News][19])

Postgres, by contrast, documents JSONB GIN operator classes such as `jsonb_ops` and `jsonb_path_ops`, including containment-style indexing behavior. ([PostgreSQL][20])

**Workarounds:** generated columns, expression indexes on known paths, trigger-maintained side tables, FTS for word-like arrays, or custom virtual tables/extensions.

### 7) Stored procedures, `CREATE FUNCTION`, procedural SQL

This is surprisingly persistent. SQLite Forum users explicitly request stored procedures/functions written in SQL and stored inside the database. ([SQLite][21]) A longer forum discussion says requests like this appear “almost every year,” with users asking for grouping statements, parameters, rollback/error handling, and reusable logic. ([SQLite][22]) Stack Overflow also has long-running demand around SQLite stored procedures, with accepted answers saying SQLite does not support them and that logic must live in client code or UDFs. ([Stack Overflow][23])

Postgres has `CREATE FUNCTION`, SQL functions, PL/pgSQL, procedural languages, overloads, set-returning functions, and security-definer functions. ([PostgreSQL][24])

**Why people ask:** reusable business logic, embedding workflow logic in the database file, multi-language apps, avoiding duplicated logic across clients, and using SQLite as more than a simple storage engine.

### 8) Materialized views / indexed views

SQLite supports ordinary views, but not materialized views. Stack Overflow questions ask how to create materialized views in SQLite; answers say they are not supported and suggest `CREATE TABLE AS SELECT` plus manual refresh. ([Stack Overflow][25]) Another Stack Overflow thread asks how to “freeze” a slow SQLite view; the workaround is to create a temp table from the view. ([Stack Overflow][26]) HN users ask the same question and get the same answer: closest is table creation/drop/recreate. ([Hacker News][27])

Postgres has `CREATE MATERIALIZED VIEW` and `REFRESH MATERIALIZED VIEW`, with materialized views persisting query results in table-like form. ([PostgreSQL][28])

**Use cases:** dashboards, cache tables, reporting, precomputed joins, expensive aggregations, and local-first apps that want indexed derived state.

### 9) Exact `DECIMAL`/`NUMERIC`

This gap appears in finance/accounting contexts. A SQLite Forum discussion says SQL-standard `NUMERIC`/`DECIMAL` decimal arithmetic is “painfully missed” in SQLite. ([SQLite][29]) SQLAlchemy discussion warns that SQLite has no lossless decimal type and that this can matter for financial apps. ([Google Groups][30])

Postgres documents exact `numeric`/`decimal` with selectable precision, suitable when exactness is required. ([PostgreSQL][31])

**Workarounds:** store cents as integers, store decimal strings, use SQLite’s decimal extension where available, or do decimal math in the application.

### 10) Native date/time/timestamp/interval/time-zone model

SQLite intentionally has no date/time storage class; date/time values are stored as text, real, or integer. ([SQLite][14]) Users still ask for better timestamp ergonomics. A forum request for `unixepoch_ms()` says working with millisecond Unix timestamps is frustrating and currently requires manual expressions and “magic constants.” ([SQLite][32])

**Postgres gap:** Postgres has real `date`, `time`, `timestamp`, `timestamptz`, and `interval` semantics. SQLite users usually choose ISO-8601 text, Unix seconds/milliseconds integers, or Julian day numbers and then standardize in app code.

### 11) Unicode, locale-aware collations, `ILIKE`, and regex

SQLite’s text behavior is another recurring global-app gap. Official docs say SQLite only understands upper/lower case for ASCII by default; Unicode case folding requires ICU. ([SQLite][33]) SQLite’s quirks page also notes that full Unicode case folding is not included by default because the tables are larger than the SQLite library itself. ([SQLite][34]) A forum thread on `upper()`/`lower()` explains the same design tradeoff and points to the ICU extension. ([SQLite][35])

Regex is similar: SQLite has `REGEXP` syntax, but no default `regexp()` function, so it normally errors unless the application supplies one. ([SQLite][33])

**What people want:** built-in `ILIKE`, Unicode-aware `NOCASE`, locale collation, natural sort, regex functions/operators, and portable binaries with ICU/PCRE-like behavior.

### 12) Postgres SQL dialect compatibility: `LATERAL`, `DISTINCT ON`, `MERGE`, `DEFAULT`, etc.

This is a large cluster of “make SQLite closer to Postgres so I can use one SQL/ORM model.”

`LATERAL` is a good example. A SQLite Forum user says that if SQLite’s `LATERAL` is compatible with PostgreSQL’s, it would be a “big win” for people using both Postgres and SQLite. ([SQLite][36]) Another ecosystem example: an Elixir/Ash discussion notes that AshPostgres supports aggregates via inner lateral joins, but AshSqlite does not. ([Elixir Programming Language Forum][37])

`DISTINCT ON` is another direct Postgres compatibility gap: SQLite’s quirks page says SQLite supports `DISTINCT` but not `DISTINCT ON`. ([SQLite][34]) `MERGE` has also been requested explicitly on the SQLite Forum after PostgreSQL added it, with a user saying it would close a big gap for multi-database apps and abstraction libraries. ([SQLite][38]) SQLite Forum users also request `DEFAULT` values inside multi-row `INSERT` value lists for better SQL compatibility and ergonomics. ([SQLite][39])

**My read:** individually these are medium or low; collectively, “Postgres-compatible SQLite” is a high-value theme.

### 13) Schemas/namespaces/search path

Postgres schemas are namespaces inside a database. PostgreSQL docs describe `CREATE SCHEMA` as creating a namespace containing tables, types, functions, and operators, with name qualification and search paths. ([PostgreSQL][40]) SQLite does not have the same model. Stack Overflow users ask whether SQLite supports Postgres-style schemas; the answer is that SQLite uses schema names for attached databases, and emulating Postgres schemas with multiple database files is usually a bad idea. ([Stack Overflow][41])

**Who cares:** multi-tenant apps, ORMs, migration tools, and apps that want Postgres-like namespacing.

### 14) Users, roles, grants, and row-level security

SQLite officially omits `GRANT` and `REVOKE`, because SQLite is an embedded database file and access control is handled through normal OS file permissions rather than database users. ([SQLite][1])

**Postgres gap:** roles, grants, privileges, schemas owned by roles, row-level security, security-definer functions, and permissioned views. This becomes more requested as people build hosted SQLite platforms or multi-user apps on top of SQLite.

### 15) Writable views and richer triggers

SQLite’s official omitted-features page says views are read-only; you cannot directly `INSERT`, `UPDATE`, or `DELETE` a view, though `INSTEAD OF` triggers can simulate this. It also says SQLite supports only `FOR EACH ROW` triggers, not `FOR EACH STATEMENT`. ([SQLite][1]) Trigger docs also note restrictions such as unsupported `ORDER BY`/`LIMIT` in trigger `UPDATE`/`DELETE` statements and no direct CTE support inside trigger statements. ([SQLite][42])

**What people want:** statement-level triggers, transition tables, richer trigger bodies, writable/updatable views, and better trigger programmability.

### 16) Arrays, enums, domains, composite/range/custom types

This is mostly a Postgres-compatibility and ORM issue. SQLite’s `STRICT` mode has a deliberately narrow set of type names. ([SQLite][15]) Postgres, by contrast, documents a broad built-in function/operator surface including array functions/operators, range/multirange functions, and user-defined functions/types. ([PostgreSQL][43])

**Workarounds:** JSON arrays, text enums with `CHECK`, generated columns, application validation, and ORM type adapters.

### 17) Larger built-in function/operator surface

Users often want common Postgres-style functions without loading extensions: `generate_series`, `date_trunc`, regex functions, `least`/`greatest`, array helpers, richer aggregates, better math/stat functions, UUID helpers, and string utilities. Postgres documents a very large built-in function/operator set and user-definable functions/operators. ([PostgreSQL][43])

SQLite can add many of these through extensions or application-defined functions, but the packaging is inconsistent across language bindings and operating systems. This is why projects like sqlean and other “batteries included” SQLite extension sets get attention.

### 18) Vector search / pgvector-like built-in support

This is a newer, fast-rising request driven by AI/local-first apps. SQLite now has an official-looking Vec1 extension page describing approximate nearest-neighbor vector search via SQLite’s virtual table interface, and third-party `sqlite-vec` has strong traction as a small cross-platform vector search extension. ([SQLite][44]) Reddit and HN discussions around `sqlite-vec` show developers looking for a robust, local, no-server vector search option for SQLite. ([Reddit][45])

**Gap:** not a universally built-in, stable, pgvector-like capability across every SQLite distribution. The gap is shrinking quickly, but it still belongs on the list.

### 19) PostGIS-class geospatial

SQLite has R-Tree, Geopoly, and SpatiaLite exists, but core SQLite is not PostGIS. SpatiaLite describes itself as a spatial extension that makes SQLite roughly comparable to PostgreSQL + PostGIS for many spatial DBMS uses. ([Gaia GIS][46])

**Demand:** strong in GIS niches, weaker in general SQLite use. Most people accept SpatiaLite as the answer, but setup, portability, and packaging remain pain points.

### 20) Parallel query / analytics / columnar-style performance

This is less of a direct SQLite Forum feature request and more of a “people choose DuckDB instead” gap. SQLite is excellent for embedded transactional storage and moderate analytics, but users who want parallel scans, columnar execution, large analytical joins, and vectorized execution often compare it with DuckDB rather than Postgres. SQLite’s own docs say that if a workload approaches terabytes or needs heavy server-style scaling, a client/server engine may be more appropriate. ([SQLite][2])

### 21) Partitioning, sharding, and large-table admin

SQLite has `ATTACH`, separate database files, and application-level sharding patterns. It does not have Postgres-style declarative partitioning, table spaces, global indexes across partitions, partition pruning, or server-side maintenance workers. Demand is lower because workloads that need this usually move away from SQLite.

### 22) CDC, changefeeds, `LISTEN`/`NOTIFY`

SQLite has update hooks and sessions/changeset extensions, but no Postgres-style `LISTEN`/`NOTIFY`, logical replication, publication/subscription, or built-in changefeed API. This comes up in local-first sync, app platforms, and edge database products more than in traditional embedded SQLite use.

### 23) Built-in statement cache / compiled statement reuse

This is lower-ranked, but real. A SQLite Forum thread proposes statement/VDBE caching; a Python SQLite wrapper author says every wrapper in every language seems to implement a statement cache and that there is “definitely a need.” ([SQLite][47])

**Why it matters:** ORMs and wrappers repeatedly prepare the same generated SQL. A built-in cache could reduce duplicated, subtly buggy cache implementations across Python, Java, C#, Node, etc.

### 24) Extension packaging and “batteries included” builds

This is less a single feature than an ecosystem gap. SQLite can do a lot via extensions—ICU, regexp, decimal, vector, CSV, FTS, SpatiaLite, custom functions—but availability varies across platforms, language bindings, mobile builds, WASM, and hosted environments. Many “feature requests” are really requests for **standardized extension availability**.

## Stale or partially solved requests to treat carefully

A lot of old online complaints are outdated. I would not rank these as current top gaps without caveats:

| Old request            | Current status                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `DROP COLUMN`          | Exists now, but full schema alteration is still limited. ([SQLite][9])                                                          |
| Strict typing          | `STRICT` tables exist, but only with a narrow type set and opt-in table semantics. ([SQLite][15])                               |
| JSONB                  | Exists in SQLite, but unlike Postgres JSONB it does not offer O(1) lookup or GIN-style indexing. ([SQLite][17])                 |
| `RIGHT`/`FULL` joins   | Modern SQLite grammar includes `RIGHT` and `FULL` join operators, so old “no full outer join” posts may be stale. ([SQLite][9]) |
| Materialized CTE hints | Not the same as persistent materialized views; users still ask for true materialized views. ([Hacker News][27])                 |

## The big product opportunity themes

The strongest opportunities cluster into four product directions:

1. **“SQLite for production web apps”**: concurrency, HA, backups, replication, network protocol, observability.
2. **“SQLite as a Postgres-compatible dev/test/local database”**: strict types, schemas, `LATERAL`, JSONB containment, Postgres functions, migrations.
3. **“SQLite as a richer embedded app platform”**: stored procedures, materialized views, functions, triggers, permissions, sync/changefeeds.
4. **“SQLite for modern local-first/AI apps”**: vector search, sync, JSON indexing, FTS/search quality, mobile/WASM extension packaging.

My overall ranking confidence is highest for the top six: **concurrent writes, production replication/server ergonomics, full migrations, stronger typing/constraints, JSONB indexing, and stored procedures**. Those show up across official docs, forum debates, Stack Overflow pain, ORMs, HN/Reddit production discussions, and active fork/extension ecosystems.
