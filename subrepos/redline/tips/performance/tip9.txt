# Recommended design upgrade: make the B-tree/index layer truly concurrent, then route reads through the raw zero-copy cursor

The section I would upgrade first is **the B-tree index subsystem**, specifically the combination of:

1. The global `structure_lock` around index writes.
2. The secondary-index scan path that still does too much allocation/materialization.
3. The lack of a first-class, high-concurrency “claim next queue item” execution path.

This is the highest-leverage upgrade because RedlineDB’s core story is already beating SQLite’s single-writer bottleneck with MVCC, row locks, a concurrent storage core, and group-commit WAL, while preserving the SQLite ABI and embedded model. The uploaded spec says exactly that: RedlineDB replaces SQLite’s single-writer WAL core with MVCC, a concurrent B-tree, group-commit WAL, and deterministic recovery.  SQLite’s own documentation still states that there can be only one writer at a time to an SQLite database, so RedlineDB’s path to winning is not “be SQLite but rewritten in Rust”; it is “make the concurrency surfaces SQLite cannot expose actually scale.” ([SQLite][1])

The current benchmark shape strongly points at the index layer. RedlineDB is already far ahead on disjoint writers and mixed OLTP at 64 threads, but it loses badly on secondary-index point and range workloads: `secondary-index-read` is reported at **16,245 qps vs SQLite 121,030 qps**, and `secondary-index-range` at **5,598 qps vs SQLite 117,088 qps**. The same table shows RedlineDB already ahead on `writers-disjoint`, `mixed-95/5`, `mixed-80/20`, and `mixed-50/50`, so the next bottleneck is not “generic writes”; it is **index write scalability plus index read efficiency**. ([GitHub][2])

The uploaded spec also explicitly names the B-tree lock as a limitation: all structural modifications are protected by a single global mutex, so even writers inserting into different leaf pages serialize. It notes that a Lehman–Yao B-link tree would eliminate this class of serialization by using right-links and high keys.  The live code matches that design: `IndexInner` contains `structure_lock: Mutex<()>`, and both insert and delete paths acquire it before mutation. ([GitHub][3])

So the proposed upgrade is:

> **Phase 12: BLINK+RAW Index Engine**
> Replace the global-lock B-tree mutation path with a B-link tree protocol using existing `right_sibling` and `high_key` fields, and make the existing raw zero-copy index cursor the default read path for secondary-index scans, counts, queue claims, and covering reads.

This is not a rewrite of the whole database. It is a targeted upgrade to the subsystem that both the spec and benchmarks identify as the biggest remaining performance gap.

---

# 1. Current-state diagnosis

## 1.1 What RedlineDB already does well

RedlineDB’s current design is already superior to SQLite for high-concurrency write workloads because it avoids SQLite’s database-level single-writer bottleneck. The architecture has MVCC, row-level locks, group-commit WAL, index undo, and a SQL layer that preserves the SQLite-ish prepare/step/execute contract. 

Current wins from the public benchmark table:

| Workload                |  RedlineDB |    SQLite |      Ratio |               |
| ----------------------- | ---------: | --------: | ---------: | ------------- |
| `writers-disjoint`, 64T |  1,256 qps |    79 qps | **15.89×** |               |
| `mixed-95/5`, 64T       | 24,763 qps | 1,680 qps | **14.74×** |               |
| `mixed-80/20`, 64T      |  6,154 qps |   405 qps | **15.21×** |               |
| `mixed-50/50`, 64T      |  2,483 qps |   160 qps | **15.55×** | ([GitHub][2]) |

That is already the right foundation.

## 1.2 Where the current design is still leaving performance on the table

The B-tree already stores `left_sibling`, `right_sibling`, and `high_key` in the page special region, which are exactly the primitives needed for a B-link style tree.  But the current implementation still protects all structural mutation under a global `structure_lock`. This means:

| Scenario                                                | Current behavior              | Problem                                                      |
| ------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------ |
| Thread A inserts key `100` into leaf L1                 | Holds global `structure_lock` | Blocks unrelated index writers                               |
| Thread B inserts key `9000000` into leaf L92            | Also needs same global lock   | Disjoint leaf, still serialized                              |
| Thread C deletes from a different index page            | Also needs same global lock   | Delete path also serializes                                  |
| Many queue workers update indexed `status` / `priority` | All touch index path          | Global structure lock and head-row lock convoy combine badly |

This is the opposite of what the rest of RedlineDB is trying to achieve. The heap has row-level locking. The transaction system has MVCC. The WAL has group commit. But the secondary-index write path still has a single choke point.

## 1.3 Secondary-index reads are also too expensive

The live code already has a raw cursor path that decodes cells in place and can avoid per-entry key allocation. `LeafCell::decode_ref` returns borrowed slices for the logical key, while the higher-level decoded entry path allocates a `Vec<u8>` for each logical key. ([GitHub][4]) The raw cursor’s rowid and count paths already walk cells directly without materializing full `LeafEntry` objects. ([GitHub][5])

That means the codebase already contains a lot of the machinery needed to close the secondary-index read gap. The upgrade is to make that machinery the default execution path, not a side path.

# 2. Proposed architecture: BLINK+RAW Index Engine

## 2.1 Design goal

Make the B-tree behave like the rest of the engine:

| Layer         | Current concurrency target              | Required index upgrade                               |
| ------------- | --------------------------------------- | ---------------------------------------------------- |
| Heap          | Disjoint rows proceed in parallel       | Disjoint index leaves proceed in parallel            |
| MVCC          | Readers do not block writers            | Index readers use latch-light/right-link traversal   |
| WAL           | Commit batching, deterministic recovery | B-link split records are crash-safe and idempotent   |
| SQL executor  | Vectorized/batched execution            | Raw index cursor returns batches without key cloning |
| Queue service | Many workers can claim jobs             | Optional queue-claim operator avoids lock convoy     |

## 2.2 Non-goals

This proposal does **not** change:

* The SQLite-compatible C ABI.
* Existing SQL semantics in default parity mode.
* MVCC tuple visibility rules.
* Index key encoding.
* Unique constraint semantics.
* WAL durability contract.
* Page size.
* Crash certification expectations.

It also does **not** require serializable isolation, predicate locks, foreign-key enforcement, or a total planner rewrite.

# 3. Core design change A: replace global index mutation lock with B-link page latching

## 3.1 Existing enabling fields

The B-tree page special region already has the key fields needed for B-link traversal:

```text
left_sibling
right_sibling
high_key
```

The current range scan already descends to a leaf and follows `right_sibling`.  The live search code also already has “move right” behavior when a searched key is greater than or equal to a page’s `high_key`. ([GitHub][3])

So the design can evolve the current B-tree; it does not need to throw it away.

## 3.2 New invariant

For every B-link page `P`:

```text
All keys physically stored in P are < P.high_key, unless P.high_key is +∞.

If a search descends to P and target_key >= P.high_key,
the search must follow P.right_sibling and repeat.

Parent pointers are allowed to be temporarily stale after a split,
because right-links and high-keys make the split reachable.
```

That last line is the big unlock. It means a child page split can become visible before the parent separator is installed. On crash or race, searches still succeed by landing on the old left page and moving right.

This follows the classic Lehman–Yao B-link-tree idea: use high keys and right links so concurrent readers/writers do not require a single global tree lock. The original paper is the canonical reference for this design. ([University of Crete][6])

## 3.3 New latch model

Replace:

```rust
structure_lock: Mutex<()>
```

with:

```rust
pub enum IndexConcurrencyMode {
    GlobalLock, // existing behavior, default during canary
    Blink,      // new behavior
}

pub struct BtreePageLatchTable {
    shards: Vec<PageLatchShard>,
}

pub struct PageLatchShard {
    latches: Mutex<HashMap<PageId, Arc<PageLatch>>>,
}

pub struct PageLatch {
    state: parking_lot_or_std_rwlock::RwLock<PageLatchState>,
}

pub struct PageLatchState {
    split_epoch: u64,
    repair_epoch: u64,
}
```

Because the product-crate dependency rules are strict, this should use `std::sync::RwLock` unless the workspace already allows `parking_lot`. The important part is not the lock implementation; it is the granularity.

### Latch types

| Latch                | Used for                               | Held across I/O? | Held across WAL fsync? |
| -------------------- | -------------------------------------- | ---------------: | ---------------------: |
| Leaf read latch      | Optional validation during read        |               No |                     No |
| Leaf write latch     | Insert/delete marker/rewrite leaf      |               No |                     No |
| Internal write latch | Insert separator / split internal page |               No |                     No |
| Root meta latch      | Root split only                        |               No |                     No |

No page latch may be held while waiting for WAL durability. Latches protect in-memory page structure, not commit durability.

## 3.4 Search algorithm

```rust
fn blink_find_leaf(root: PageId, target: &[u8]) -> Result<PageId> {
    let mut page_id = root;

    loop {
        let guard = buffer.pin(page_id)?;
        let page = guard.with_page(|p| p.read_header_and_special())?;

        if page.kind == PageKind::BtreeLeaf {
            if key_belongs_to_page(target, &page.high_key) {
                return Ok(page_id);
            }

            let right = page.right_sibling;
            drop(guard);

            if right == PageId::MAX {
                return Err(IndexCorruption::HighKeyWithoutRightSibling);
            }

            page_id = right;
            continue;
        }

        let child = internal_search_child(&guard, target)?;

        // Parent may be stale after split. Descend first.
        drop(guard);
        page_id = child;
    }
}

fn key_belongs_to_page(target: &[u8], high_key: &FenceKey) -> bool {
    high_key.is_infinity() || target < high_key.as_bytes()
}
```

Important: the parent is a hint, not a perfect routing table. The right-link/high-key invariant is authoritative.

## 3.5 Insert algorithm

```rust
fn blink_insert(tx: TxId, key: KeyBuf, row: IndexRowRef) -> Result<()> {
    loop {
        let leaf_id = blink_find_leaf(root.load(), key.as_bytes())?;
        let leaf_latch = latches.write(leaf_id)?;

        let leaf = buffer.pin_mut(leaf_id)?;

        // Validate after acquiring latch. A split may have moved the key right.
        if !leaf_accepts_key(&leaf, &key) {
            let right = leaf.right_sibling();
            drop(leaf);
            drop(leaf_latch);

            if right == PageId::MAX {
                return Err(IndexCorruption::InvalidFence);
            }

            continue;
        }

        if leaf.has_space_for(&key, &row) {
            leaf.insert_sorted(key, row, tx)?;
            wal.append(IndexInsert { tx_id: tx, ... })?;
            leaf.mark_dirty();
            return Ok(());
        }

        split_leaf_and_insert(tx, leaf_id, leaf_latch, key, row)?;
        return Ok(());
    }
}
```

The linearization point for a normal insert is the leaf mutation. The linearization point for a split is the left-page fence update described below.

## 3.6 Split algorithm

Current split behavior is globally serialized. The new split must be safe under concurrent search, concurrent insert, and crash recovery.

### Split steps

Given full leaf `L` and new key `K`:

1. Acquire write latch for `L`.
2. Validate `K < L.high_key`; otherwise release and move right.
3. Merge `K` with existing entries in memory.
4. Choose split point by bytes, not count.
5. Allocate new page `R`.
6. Initialize `R`:

   * `R.left_sibling = L.page_id`
   * `R.right_sibling = L.right_sibling`
   * `R.high_key = L.high_key`
   * `R.entries = upper_half`
7. Rewrite `L`:

   * `L.entries = lower_half`
   * `L.right_sibling = R.page_id`
   * `L.high_key = first_key(R)`
8. Append WAL for `R` page image/delta.
9. Append WAL for `L` fence/right-link update.
10. Release `L`.
11. Insert separator into parent opportunistically.
12. If parent insertion fails or crashes, background repair later installs it.

### Crash-safe ordering

The required WAL order is:

```text
1. Right page initialized
2. Left page points to right page and lowers high_key
3. Parent separator installed
```

If crash happens after step 1 but before step 2, `R` is an orphan and unreachable. It can be ignored, quarantined, or reclaimed after recovery.

If crash happens after step 2 but before step 3, the tree is still searchable: a lookup that descends to `L` and needs a key now in `R` follows `L.right_sibling`.

If crash happens after step 3, the parent has a faster route, but correctness was already established at step 2.

This preserves the redo-only recovery model and does not require an undo phase.

## 3.7 Parent separator insertion

Parent separator insertion becomes idempotent.

```rust
fn install_separator(parent_id: PageId, sep: KeyBuf, right_child: PageId) -> Result<()> {
    let parent_latch = latches.write(parent_id)?;
    let parent = buffer.pin_mut(parent_id)?;

    if parent.contains_separator_for(&sep, right_child) {
        return Ok(());
    }

    if parent.has_space_for_separator(&sep) {
        parent.insert_separator(sep, right_child)?;
        wal.append(IndexSeparatorInsert { ... })?;
        parent.mark_dirty();
        return Ok(());
    }

    split_internal_and_retry(parent_id, sep, right_child)
}
```

If there are two racing attempts to repair the same separator, only one should win. The loser observes the existing separator and returns success.

## 3.8 Delete and update behavior

To reduce risk, do **not** implement page merges in the first release.

Deletes remain logical:

```text
Index entry delete_tx = current_tx
```

That matches the existing MVCC-style index visibility model. The delete path changes only the latch scope:

| Current                         | New                               |
| ------------------------------- | --------------------------------- |
| Acquire global `structure_lock` | Locate leaf via B-link search     |
| Mark entry deleted              | Acquire leaf write latch          |
| Rewrite leaf                    | Mark entry deleted / rewrite leaf |
| Release global lock             | Release page latch                |

No sibling merge. No root shrink. No redistribution. Vacuum can compact a page under its page latch, but it must not merge pages until a later phase.

This is critical for avoiding regressions. Merges are where many concurrent B-tree implementations get complicated. Split-only B-link trees are much safer and still solve the main write-concurrency problem.

# 4. Core design change B: make `RawIndexCursor` the default secondary-index scan path

## 4.1 Problem

The secondary-index read gap is too large to explain only by B-tree write locking. The current code has both:

* An allocating path that decodes leaf entries into owned `LeafEntry` values.
* A raw path that can decode cells in place.

The owned decode path clones logical keys into `Vec<u8>`. The raw decode path can borrow from the page cell. ([GitHub][4]) The raw cursor already has direct rowid and count scanning behavior without building a full vector of leaf entries. ([GitHub][5])

## 4.2 Rule

Every planner/executor path that does **not** need to own full logical keys must use `RawIndexCursor`.

### Convert these paths first

| Query shape                                | Old path                            | New path                                       |
| ------------------------------------------ | ----------------------------------- | ---------------------------------------------- |
| `WHERE indexed_col = ?` returning heap row | Materialize index entries           | Raw cursor → rowid batch → heap batch          |
| `WHERE indexed_col BETWEEN ? AND ?`        | Materialize leaf entries            | Raw cursor range scan                          |
| `COUNT(*) WHERE indexed_col ...`           | Decode row refs / maybe materialize | Raw `count_remaining`                          |
| `ORDER BY indexed_col LIMIT K`             | Higher-level cursor                 | Raw cursor with early stop                     |
| Covering index projection                  | Clone keys where possible           | Borrow/decode projected columns from key bytes |

## 4.3 New executor interface

```rust
pub enum IndexScanProjection<'a> {
    RowRefsOnly,
    CountOnly,
    CoveringColumns {
        column_ordinals: &'a [usize],
    },
    KeysAndRows,
}

pub struct RawIndexBatch<'a> {
    pub row_refs: SmallVecOrVec<IndexRowRef>,
    pub covering_values: Option<Vec<RowBatch>>,
    pub logical_keys: Option<Vec<KeyRefOrOwned<'a>>>,
    pub rows_seen: usize,
    pub rows_visible: usize,
}
```

Avoid adding a dependency for `SmallVec` unless already allowed. A plain reusable `Vec<IndexRowRef>` with preallocated batch capacity is enough.

## 4.4 Allocation target

For rowid-only and count-only scans:

```text
Per leaf:
  0 logical_key allocations
  0 LeafEntry allocations
  0 Vec<LeafEntry>
  1 reused output Vec<IndexRowRef> per batch
```

For covering scans:

```text
Per returned row:
  allocate only final SQL value materialization
  do not allocate intermediate logical_key Vec unless required by API
```

## 4.5 Planner changes

Add a planner flag:

```rust
pub enum IndexScanEngine {
    LegacyMaterialized,
    RawRowRef,
    RawCount,
    RawCovering,
    RawOrderedLimit,
}
```

Physical plan node:

```rust
PhysicalPlan {
    index_scan_engine: Some(IndexScanEngine::RawRowRef),
    ordered_index_scan_limit: Some(k),
    covering: bool,
    ...
}
```

Routing rules:

```text
COUNT(*) + index predicate:
  RawCount

SELECT row columns + index predicate:
  RawRowRef -> heap batch fetch

SELECT only indexed columns:
  RawCovering

ORDER BY index prefix + LIMIT:
  RawOrderedLimit
```

This directly targets the current `secondary-index-read` and `secondary-index-range` losses without waiting for a full B-link writer migration.

# 5. Core design change C: opt-in queue-claim operator

The user’s queue-service concern is valid: SQLite struggles as a queue because many workers contend for one writer slot, and the “claim next available job” query often creates lock convoys.

However, RedlineDB must preserve SQLite parity by default. So this should be an **opt-in RedlineDB extension**, not a default semantic change.

## 5.1 Default parity mode

Default behavior remains SQLite-compatible:

```text
If the query says ORDER BY ... LIMIT 1,
and the first qualifying row is locked,
the engine follows normal lock/busy-timeout behavior.
```

## 5.2 Queue mode

Enable with one of:

```sql
PRAGMA redline_queue_claim = ON;
```

or Rust API:

```rust
conn.set_queue_claim_mode(QueueClaimMode::SkipLocked);
```

This is not part of SQLite compatibility mode. It is an extension for applications that explicitly want queue semantics.

## 5.3 Recognized query shape

The optimizer should recognize:

```sql
UPDATE jobs
SET status = 'running',
    claimed_by = ?,
    claimed_at = ?
WHERE id = (
    SELECT id
    FROM jobs
    WHERE status = 'ready'
    ORDER BY priority DESC, created_at ASC
    LIMIT 1
)
RETURNING *;
```

and:

```sql
DELETE FROM jobs
WHERE id = (
    SELECT id
    FROM jobs
    WHERE status = 'ready'
    ORDER BY priority DESC, created_at ASC
    LIMIT 1
)
RETURNING *;
```

## 5.4 Required index

Recommended index:

```sql
CREATE INDEX jobs_ready_idx
ON jobs(status, priority DESC, created_at ASC, id);
```

## 5.5 Physical operator

```rust
pub struct QueueClaimPlan {
    table_id: TableId,
    index_id: IndexId,
    ready_prefix: KeyPrefix,
    order_range: KeyRange,
    mutation: QueueMutation,
    return_projection: Projection,
    max_probe_rows: usize,
}
```

Execution:

```rust
fn execute_queue_claim(plan: QueueClaimPlan, tx: &mut Txn) -> Result<Option<Row>> {
    let mut cursor = RawIndexCursor::new(plan.index_id, plan.order_range, tx.snapshot());

    while let Some(row_ref) = cursor.next_row_ref()? {
        match row_locks.try_lock(plan.table_id, row_ref.row_id, tx.id) {
            TryLockResult::Acquired(guard) => {
                let row = heap.fetch_visible(row_ref, tx.snapshot())?;

                if !still_matches_ready_predicate(&row) {
                    drop(guard);
                    continue;
                }

                apply_update_or_delete(&row, plan.mutation, tx)?;
                return Ok(Some(materialize_returning(row)));
            }

            TryLockResult::WouldBlock => {
                // Queue mode only.
                // Skip locked row and try next candidate.
                continue;
            }

            TryLockResult::Dead => continue,
        }
    }

    Ok(None)
}
```

## 5.6 New RowLockManager method

```rust
pub enum TryLockResult {
    Acquired(RowLockGuard),
    WouldBlock,
    Dead,
}

impl RowLockManager {
    pub fn try_lock(&self, key: RowKey, tx_id: TxId) -> TryLockResult;
}
```

This should not affect the existing blocking lock path. It only adds a nonblocking option for queue mode.

## 5.7 Why this matters

For queue workloads, the difference is dramatic:

| Behavior                                        | Result                                         |
| ----------------------------------------------- | ---------------------------------------------- |
| All workers block on first visible ready job    | Lock convoy, low throughput, high p99          |
| Workers scan ordered index and skip locked rows | Many workers claim different jobs concurrently |
| Row lock validates before mutation              | No duplicate claims                            |
| MVCC recheck after lock                         | No stale claim                                 |

This turns RedlineDB into a credible embedded queue engine while keeping SQLite parity mode intact.

# 6. WAL and recovery design for B-link splits

The WAL design must remain conservative. The uploaded spec says RedlineDB’s durability guarantee is that a transaction is durable only if its `Commit` WAL record has been `fdatasync()`’d before `RLDB_OK`, and failpoint/recovery testing has zero tolerance for lost acknowledged commits. 

## 6.1 New WAL records

Use existing page-image/delta mechanisms first. Do **not** introduce a fragile custom WAL format until the algorithm is proven.

Minimum viable approach:

```rust
WalPayload::PageImage {
    page_id: right_page_id,
    page_lsn,
    page_bytes,
}

WalPayload::PageImage {
    page_id: left_page_id,
    page_lsn,
    page_bytes,
}

WalPayload::PageImage {
    page_id: parent_page_id,
    page_lsn,
    page_bytes,
}
```

After correctness is proven, optimize to:

```rust
WalPayload::IndexSplit {
    tx_id,
    index_id,
    left_page_id,
    right_page_id,
    old_left_high_key,
    new_left_high_key,
    right_high_key,
    moved_cells_digest,
    separator_key,
}
```

But the first production version should prefer full page images or existing safe deltas. The spec already notes page images are expensive but recovery-safe.  Correctness first.

## 6.2 Split recovery matrix

| Crash point                              | Recovered state                                                  |       Correct? |          Repair needed? |
| ---------------------------------------- | ---------------------------------------------------------------- | -------------: | ----------------------: |
| Before right page WAL                    | No split                                                         |            Yes |                      No |
| After right page WAL, before left link   | Orphan right page                                                |            Yes |      Reclaim/quarantine |
| After left link, before parent separator | Search reaches right via move-right                              |            Yes | Parent separator repair |
| After parent separator                   | Fully installed split                                            |            Yes |                      No |
| During parent cascade split              | Child reachable via right-link                                   |            Yes |  Parent/internal repair |
| During root split                        | Old root still searchable via right-link path until root install | Yes, with care |   Root repair if needed |

## 6.3 Background separator repair

Add a repair pass:

```rust
pub struct FenceRepairJob {
    index_id: IndexId,
    left_page_id: PageId,
    right_page_id: PageId,
    separator_key: KeyBuf,
    observed_epoch: u64,
}
```

When search observes a missing parent separator, or recovery finds a left/right fence without parent routing, enqueue repair.

Repair is idempotent:

```rust
fn repair_separator(job: FenceRepairJob) -> Result<()> {
    if parent_already_routes(job.separator_key, job.right_page_id) {
        return Ok(());
    }

    install_separator(parent, job.separator_key, job.right_page_id)
}
```

## 6.4 New failpoints

Add failpoints to extend the existing matrix:

| Failpoint                                      | Location                   | Purpose                   |
| ---------------------------------------------- | -------------------------- | ------------------------- |
| `index::blink_split::after_right_alloc`        | After right page allocated | Orphan page handling      |
| `index::blink_split::after_right_wal`          | Right page durable in WAL  | Crash before reachability |
| `index::blink_split::after_left_link`          | Left points to right       | Parent separator missing  |
| `index::blink_split::before_parent_insert`     | Before separator install   | Repair validation         |
| `index::blink_split::after_parent_insert`      | Separator installed        | Idempotent redo           |
| `index::blink_repair::during_separator_repair` | Repair path                | Crash-safe repair         |

Existing certification already includes index split crash coverage; this expands it for B-link-specific states.

# 7. Memory design

## 7.1 Index scan memory

The raw cursor path should make index scans mostly allocation-free.

### Current risk

```rust
Vec<LeafEntry>
LeafEntry {
    logical_key: Vec<u8>,
    ...
}
```

This is bad for range scans because every page walk can allocate and copy keys.

### New target

```rust
LeafCellRef<'page> {
    logical_key: &'page [u8],
    row: IndexRowRef,
    create_tx: TxId,
    delete_tx: TxId,
}
```

The existing code already has this style of borrowed decode. ([GitHub][4])

## 7.2 Batch reuse

Each `Statement` or execution context should own reusable buffers:

```rust
pub struct IndexScanScratch {
    row_refs: Vec<IndexRowRef>,
    covering_values: RowBatch,
    bitmap: VisibilityBitmap,
}
```

Reuse across `sqlite3_step`/`rldb_step` calls where safe.

## 7.3 Queue memory

Queue claim should never materialize a full ready-job list. It should scan the ordered index and stop on the first successfully locked candidate.

```text
Memory = O(batch_size), not O(ready_jobs)
```

# 9. Planner and executor integration

## 9.1 New planner decisions

Add a planner rule:

```text
If an index predicate can produce row refs without needing owned logical keys,
choose RawRowRef scan.

If query is COUNT(*) and all predicates are index-visible,
choose RawCount scan.

If projection is covered by index key columns,
choose RawCovering scan.

If ORDER BY matches index order and LIMIT exists,
choose RawOrderedLimit scan.

If queue-claim mode is enabled and query matches claim pattern,
choose QueueClaim operator.
```

## 9.2 Physical plan examples

### Secondary index point lookup

```sql
SELECT * FROM users WHERE email = ?;
```

Plan:

```text

  -> Projection
```

# 12. Why this should not regress existing tests

## 12.1 SQL semantics remain unchanged by default

Default mode:

```text
PRAGMA redline_queue_claim = OFF
IndexConcurrencyMode = GlobalLock or Blink with same visible results
```

No new default SQL semantics. No default skip-locked behavior. No change to SQLite ABI.

## 12.2 MVCC visibility remains unchanged

Index entries still contain:

```text
create_tx
delete_tx
```

Visibility continues to use the existing transaction status and snapshot rules. The B-link upgrade changes **how we find the leaf**, not **which entry is visible**.

## 12.3 Unique constraints remain protected

The existing `UniqueKeyLockTable` stays in front of unique-index insertion. The B-link tree does not replace unique-key locking. It only removes unrelated structural serialization.

So the TOCTOU race remains blocked:

```text
writer A inserts unique key K
writer B inserts unique key K
=> B waits on unique-key guard, then rechecks
```

## 12.4 Durability contract is unchanged

Commit still returns success only after WAL durability. The WAL coordinator’s strict durability behavior and fsynced-ack certification rule stay intact. 

The B-link split protocol is designed so every crash point leaves one of these states:

```text
No split
Unreachable orphan right page
Reachable split via right-link
Fully parent-routed split
```

All are recoverable without losing acknowledged commits.

## 12.5 Fallback mode reduces rollout risk

Keep the existing global-lock implementation behind:

```rust
IndexConcurrencyMode::GlobalLock
```

Then run every correctness test in both modes:

```text
GlobalLock result == Blink result
```

Only after certification passes should `Blink` become default.

## 12.6 No page-cell format change required at first

The leaf-cell encoding does not need to change. The key format already includes the row locator suffix, which guarantees physical uniqueness. 

The page special region already has high-key and sibling fields. So the first implementation can be mostly a concurrency/protocol change, not a format-breaking change.

If additional metadata is later needed, add it carefully:

```rust
split_epoch: u64
repair_epoch: u64
blink_flags: u16
```

and support old pages with default `0` values.

## 12.7 Point-read primary-key should not regress

Primary-key point read is currently near SQLite parity. The raw cursor and B-link changes should not add overhead to point reads because:

* B-link search only adds a high-key check.
* In the common no-split path, the search still descends normally.
* Raw cursor reduces allocation, not increases it.
* Feature flag allows rollback if point-read-pk drops.

Regression gate:

```text
point-read-pk must not regress by more than 3%.
```

## 12.8 Hot-row update may not improve, but should not regress

Hot-row update is dominated by row-lock contention, not B-tree structure lock. The benchmark already shows it trailing SQLite. ([GitHub][2])

This proposal should not claim to solve hot-row contention. It should merely avoid worsening it.

Regression gate:

```text
hot-row-update p50/p95 throughput must not regress by more than 5%.
lock timeout count must not increase.
```

A future separate upgrade could add lock wait coalescing or update combining for hot rows.

# 16. Why this is the best first upgrade

I would **not** start with the WAL, even though the uploaded spec correctly identifies the single WAL writer and group-commit delay as future bottlenecks.  WAL work is important, but current public results show RedlineDB already winning hard on multi-writer and mixed write workloads. The glaring losses are secondary-index point/range reads, and the index path is also where disjoint write scalability will hit a ceiling once heap/MVCC are doing their job. ([GitHub][2])

The B-tree/index upgrade also has an unusually good risk/reward profile:

| Reason                                                     | Why it matters                         |
| ---------------------------------------------------------- | -------------------------------------- |
| Existing page format already has right links and high keys | Less format churn                      |
| Existing raw cursor already exists                         | Lower implementation risk for read win |
| Existing benchmark suite already includes index workloads  | Easy to prove improvement              |
| Existing failpoint suite already tests crash recovery      | Extend, do not invent                  |
| Global lock is explicitly identified in spec and code      | Clear bottleneck                       |
| Queue workload benefits directly                           | Aligns with stated product goal        |

# 17. Final engineering recommendation

Build **BLINK+RAW** as the next major performance lane:

1. **Promote raw zero-copy index scans first** to attack the current secondary-index read/range losses.
2. **Introduce B-link page-latched index mutation behind a feature flag** to remove global index write serialization.
3. **Keep deletes split-only/no-merge initially** to avoid correctness risk.
4. **Use conservative WAL page images for the first B-link release**, then optimize WAL deltas later.
5. **Add opt-in queue-claim mode** so RedlineDB can be used as a high-concurrency embedded queue without breaking SQLite parity.
6. **Gate the whole rollout through the existing certification matrix plus new B-link failpoints and queue workloads.**

This gives RedlineDB the most direct path toward the stated goal: not merely “SQLite-compatible in Rust,” but a drop-in embedded SQL engine that can handle workloads SQLite structurally cannot handle well—many connections, many writers, secondary-index-heavy traffic, and queue-style claim/update loops.
