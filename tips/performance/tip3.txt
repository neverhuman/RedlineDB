According to the uploaded RedlineDB engineering spec and the live repo, the highest-leverage performance upgrade is **not** another SQL planner tweak or a WAL knob. It is the **B-tree index concurrency path**: replace the index-wide `structure_lock` with a **B-link tree / per-page latch protocol** so disjoint-key writers stop serializing on one mutex.

RedlineDB’s strategic claim is “SQLite-compatible embedded SQL, but without SQLite’s single-writer cliff.” The uploaded spec frames the engine around MVCC, row-level locks, group-commit WAL, deterministic recovery, and SQLite ABI parity.  SQLite’s own docs state that SQLite serializes writes and that WAL mode still has “only one writer at a time,” even though readers and a writer can overlap. ([SQLite][1]) RedlineDB already beats SQLite strongly on disjoint-writer and mixed OLTP benchmarks, but the repo’s README also shows honest losses on hot-row update, secondary-index read, and secondary-index range workloads. ([GitHub][2])

The problem is that RedlineDB has solved **row-level write concurrency**, but the current B-tree still contains an **index-level serialization point**. The spec explicitly says disjoint-row writers proceed in parallel at the row-lock layer, while two writers on the same B-tree path serialize on `structure_lock`.  The B-tree section is even more direct: all structural modifications are protected by `structure_lock`, and “two writers inserting into different leaf pages still serialize.”  The live code matches that: `IndexInner` contains `structure_lock: Mutex<()>`, while the same page header already has the B-link ingredients—`right` sibling and `high_key`. ([GitHub][3]) The insert/delete mutation path takes that structure mutex before descent, leaf modification, and split handling. ([GitHub][4])

## Recommendation

Upgrade `crates/kernel/src/index/` from:

> **Global-index mutex B-tree**
> one `structure_lock` serializes insert/delete/split for the whole index

to:

> **B-link concurrent B-tree**
> per-page latching, right-link/high-key “move right” navigation, non-blocking reads, local leaf writes, and parent propagation after split

This is the best next design upgrade because it directly attacks the remaining serialization point inside the “multi-writer” story. It should improve `writers-disjoint`, mixed OLTP, queue-style indexed inserts/claims, and high-connection-count write workloads without changing SQL semantics, SQLite ABI shape, MVCC visibility, row-lock behavior, or crash-recovery guarantees.

# Engineering Spec: Concurrent B-link Tree Upgrade for RedlineDB

## 1. Target subsystem

**Primary files:**

`crates/kernel/src/index/`

* `mod.rs`: `BtreeIndex`, `IndexInner`, page headers, meta handling, descent
* `mutate.rs`: insert/delete/split path
* `lookup.rs`: point lookup
* `scan.rs`: range scan wrappers
* `cursor.rs`: streaming leaf-chain cursor
* `cells.rs`: leaf/internal cell encoding
* `maintenance.rs`: vacuum/compaction

**Secondary integration files:**

`crates/kernel/src/storage/buffer.rs`

* Existing `PageGuard` and per-frame `Mutex<FrameState>` can act as the physical page latch. The buffer pool already has a frame mutex around page access and mutable page updates.  

`crates/kernel/src/wal/`

* Keep current WAL append/flush architecture.
* Add structural split page-image durability discipline.
* Preserve existing failpoint/recovery matrix style.

`crates/bench/src/`

* Add index-concurrency-specific workloads and certification gates.

---

## 2. Problem statement

RedlineDB’s MVCC and row locks allow disjoint-row writers to proceed without row-level conflict. The uploaded spec describes this as a core concurrency advantage.  However, every indexed write still must update one or more B-trees. Today the B-tree writer path takes an index-wide `structure_lock`, which serializes operations even when keys land on different leaf pages. 

That makes the B-tree the next concurrency ceiling after SQLite’s single-writer limitation.

This matters especially for queue workloads:

```sql
CREATE TABLE jobs (
  id INTEGER PRIMARY KEY,
  status TEXT,
  run_after INTEGER,
  priority INTEGER,
  payload BLOB
);

CREATE INDEX jobs_ready_idx
ON jobs(status, run_after, priority, id);
```

Queue services often do many concurrent operations like:

```sql
INSERT INTO jobs(...);
SELECT id FROM jobs
 WHERE status = 'ready' AND run_after <= ?
 ORDER BY priority, run_after
 LIMIT 1;
UPDATE jobs SET status = 'running' WHERE id = ?;
```

Even when workers touch different rows, they all update shared indexes. With a global B-tree mutation mutex, RedlineDB can outperform SQLite but still leave a lot of concurrency on the table.

---

## 3. Why this section, not WAL first?

The WAL is also a known bottleneck: the spec notes a single WAL writer thread, a pending queue, group commit delay, and a single coordinator lock.  But WAL serialization is harder to eliminate without changing commit ordering, LSN assignment, and recovery semantics. Also, the live code already has scaffolding for WAL lanes in `WalConfig`, although the engine is still single-lane by default. 

The B-tree is a better first upgrade because:

1. **The current format already has right-links and high-keys.** Those are the two main on-page structures needed for B-link navigation. ([GitHub][3])
2. **The bottleneck is explicit and isolated.** `structure_lock` appears as a single mutex in `IndexInner`, and mutation code locks it at insert/delete entry. ([GitHub][3])
3. **It compounds with every write.** Every primary-key insert, secondary-index insert, update, delete, and unique check touches an index.
4. **It does not require changing public SQL or FFI behavior.** The same `BtreeIndex` API can be preserved.
5. **It strengthens the core RedlineDB value prop.** SQLite’s official documentation says SQLite permits many connections but writes “have to take turns.” ([SQLite][1]) Removing the internal B-tree turnstile makes RedlineDB’s multi-writer claim materially stronger.

---

## 4. Proposed design

### 4.1 Replace index-global locking with page-local latching

Current:

```rust
pub(super) struct IndexInner {
    ...
    pub(super) structure_lock: Mutex<()>,
    ...
}
```

Proposed:

```rust
pub(super) struct IndexInner {
    pub(super) buffer: Arc<BufferPool>,
    pub(super) meta_page_id: PageId,
    pub(super) desc: Mutex<IndexDescriptor>,
    pub(super) unique_locks: Arc<UniqueKeyLockTable>,
    pub(super) wal: Option<Arc<WalCoordinator>>,

    // New: root changes only, not every insert/delete.
    pub(super) root_latch: Mutex<()>,

    // Optional fast root cache. Authoritative root stays on meta page.
    pub(super) root_cache: AtomicRoot,

    // Existing telemetry retained, new index-concurrency counters added.
    pub(super) range_scan_leaves_visited: AtomicU64,
    pub(super) split_count: AtomicU64,
    pub(super) move_right_count: AtomicU64,
    pub(super) parent_retry_count: AtomicU64,
}
```

Use the existing `BufferPool` frame mutex as the page latch for actual page contents. This avoids adding one lock object per page and is better for memory. `PageGuard::with_page`, `with_page_mut`, and `mutable_frame` already lock the resident frame while reading or mutating page state. 

`root_latch` is only used when the root page changes. Normal insert/delete operations do **not** take it.

### 4.2 Keep on-disk format v2 for MVP

The current page special region already includes:

```text
left_sibling
right_sibling
high_key_len
high_key bytes
```

The B-tree format also already uses physical keys with a row-locator suffix, giving every index entry a unique physical order even for non-unique indexes. 

For the MVP, do not change `INDEX_VERSION`. The implementation can reinterpret the existing fields more aggressively:

* `right_sibling`: authoritative forward link
* `high_key`: upper fence key for the page
* `left_sibling`: diagnostic/maintenance aid, not required for search correctness
* parent separators: routing accelerators, not the only correctness path

A later format v3 can add `split_epoch`, `page_flags`, or `low_key` if needed, but the first implementation should avoid a migration burden.

## 5. Core invariants

### Invariant A: Right-link chain is authoritative

At every level, pages form a sorted right-link chain. If a search descends to a page whose `high_key` proves the key belongs to the right, it moves right until the page range contains the key.

```rust
fn page_contains_key(header: &PageHeader, key: &[u8]) -> bool {
    header.high_key.is_empty() || key < header.high_key.as_slice()
}
```

### Invariant B: Parent pointers may lag, but search remains correct

After a split, the leaf/internal page pair is made reachable by the old page’s right-link before the parent separator is installed. A search that follows a stale parent pointer lands on the old page, notices `key >= high_key`, and moves right.

This is the core B-link tree property. Standard B-tree references describe Lehman-Yao-style linked tree blocks as improving concurrent access by adding a next pointer and requiring write locks only on blocks being modified. ([Wikipedia][5])

### Invariant C: Structural splits are non-transactional; entry visibility remains transactional

A page split is a physical structure change. It should not roll back when the inserting transaction rolls back. The actual index entry remains transactional because it carries `create_tx` and `delete_tx`, matching the current MVCC index visibility model. 

### Invariant D: No parent-child latch is held during parent propagation

This prevents deadlocks. Split the child, publish the right-link, release child pages, then propagate the separator upward.

### Invariant E: Deletes remain tombstone-only in v1

No concurrent page merges in this upgrade. Deletion continues to mark `delete_tx`; vacuum/maintenance can prune entries later. This avoids introducing complex merge races and preserves current MVCC visibility semantics.

## 6. Algorithms

## 6.1 Search / descent

Current `find_leaf_path` already contains the essential “move right” shape:

```rust
if !header.high_key.is_empty() && key >= header.high_key.as_slice() {
    return Ok(header.right);
}
```

The new descent should formalize this as the main protocol.

Pseudo-code:

```rust
fn find_leaf_blink(&self, key: &[u8]) -> Result<PageId> {
    let mut page_id = self.root_cache.load_or_read_meta();

    loop {
        let guard = self.inner.buffer.pin(page_id)?;

        let next = guard.with_page(|page| {
            let header = Self::read_page_header(page)?;

            // B-link move-right step.
            if !header.high_key.is_empty() && key >= header.high_key.as_slice() {
                return Ok(header.right);
            }

            if header.kind == PAGE_LEAF_KIND {
                return Ok(None);
            }

            let child = choose_child(page, &header, key)?;
            Ok(Some(child))
        })?;

        match next {
            Some(next_page_id) if next_page_id != page_id => {
                page_id = next_page_id;
                self.inner.move_right_count.fetch_add(1, Relaxed);
            }
            _ => return Ok(page_id),
        }
    }
}
```

Reads should not take `root_latch` or `structure_lock`.

---

## 6.2 Insert, no split

Fast path:

```rust
fn insert_tx_inner_blink(
    &self,
    tx_id: TxId,
    logical_key: &[u8],
    row: IndexRowRef,
    emit_wal: bool,
    lsn: Lsn,
) -> Result<()> {
    let physical = encode_physical_key(logical_key, row);

    loop {
        let leaf_id = self.find_leaf_blink(physical.as_slice())?;
        let guard = self.inner.buffer.pin(leaf_id)?;
        let mut frame = guard.mutable_frame()?;
        let page = frame.page.as_mut().ok_or(...)?;
        let header = Self::read_page_header(page)?;

        if !header.high_key.is_empty() && physical.as_slice() >= header.high_key.as_slice() {
            drop(frame);
            continue;
        }

        let mut entries = self.read_entries(page)?;
        insert_candidate_sorted(&mut entries, logical_key, row, physical, tx_id)?;

        if fits(page, &entries) {
            Self::rewrite_leaf(page, index_id, &entries, header.left, header.right, header.high_key)?;

            drop(frame);

            if emit_wal {
                let end_lsn = self.append_index_delta(tx_id, WalPayload::IndexInsert { ... })?;
                guard.mark_dirty(end_lsn)?;
            } else {
                guard.mark_dirty(lsn)?;
            }

            return Ok(());
        }

        drop(frame);

        self.split_leaf_blink(leaf_id)?;
        // Retry insert after structural split.
    }
}
```

Important change: if two writers insert into different leaves, they lock different frame mutexes and proceed in parallel. If two writers insert into the same leaf, the frame mutex serializes only that leaf.

## 6.3 Leaf split

Split should be structural first, transactional entry second.

Instead of splitting with the candidate already inserted, split existing entries to create room, then retry the actual insert. This keeps structural page images independent of the inserting transaction’s entry.

Pseudo-code:

```rust
fn split_leaf_blink(&self, left_id: PageId) -> Result<SplitResult> {
    let left_guard = self.inner.buffer.pin(left_id)?;
    let right_guard = self.inner.buffer.allocate(PageKind::BtreeLeaf, rel_id)?;

    let mut left_frame = left_guard.mutable_frame()?;
    let mut right_frame = right_guard.mutable_frame()?;

    let left_page = left_frame.page.as_mut().ok_or(...)?;
    let old_header = Self::read_page_header(left_page)?;
    let entries = self.read_entries(left_page)?;

    // Another writer may already have split this page.
    if entries_fit_with_reserve(&entries) {
        return Ok(SplitResult::AlreadySplitOrNoLongerFull);
    }

    let (left_entries, right_entries, separator) = split_by_bytes(entries);

    init_right_leaf(
        right_page,
        left_id,
        old_header.right,
        old_header.high_key.clone(),
        right_entries,
    )?;

    rewrite_left_leaf(
        left_page,
        left_entries,
        old_header.left,
        Some(right_guard.page_id()),
        separator.clone(),
    )?;

    // WAL structural page images should be non-transactional.
    let split_lsn = self.record_structural_page_images(&[
        left_guard.page_id(),
        right_guard.page_id(),
    ])?;

    left_guard.mark_dirty(split_lsn)?;
    right_guard.mark_dirty(split_lsn)?;

    drop(right_frame);
    drop(left_frame);

    self.inner.split_count.fetch_add(1, Relaxed);

    // Best-effort left-link repair for the old right sibling.
    if let Some(old_right) = old_header.right {
        self.try_repair_left_link(old_right, right_guard.page_id())?;
    }

    Ok(SplitResult {
        separator,
        left_id,
        right_id: right_guard.page_id(),
        level: 0,
    })
}
```

The correctness-critical order is:

1. Initialize the new right page.
2. Set the new right page’s right-link/high-key.
3. Set the old left page’s high-key/right-link.
4. Record structural WAL.
5. Mark both pages dirty.
6. Release page latches.
7. Propagate separator upward.

If the system crashes after step 5 but before parent propagation, search still works because stale parent descent lands on the left page and then moves right.

## 6.4 Parent separator propagation

After a child split, insert `(separator, right_child)` into the parent. Use the saved descent path as a hint, but do not trust it blindly.

```rust
fn propagate_separator(
    &self,
    parent_hint: Option<PageId>,
    level: u16,
    separator: Vec<u8>,
    right_child: PageId,
) -> Result<()> {
    let mut parent_id = match parent_hint {
        Some(id) => id,
        None => return self.create_or_update_root(level, separator, right_child),
    };

    loop {
        let guard = self.inner.buffer.pin(parent_id)?;
        let mut frame = guard.mutable_frame()?;
        let page = frame.page.as_mut().ok_or(...)?;
        let header = Self::read_page_header(page)?;

        if !header.high_key.is_empty() && separator.as_slice() >= header.high_key.as_slice() {
            let next = header.right.ok_or(Error::CorruptPage("missing blink right-link"))?;
            drop(frame);
            parent_id = next;
            self.inner.parent_retry_count.fetch_add(1, Relaxed);
            continue;
        }

        let mut entries = self.read_entries(page)?;
        insert_internal_separator_sorted(&mut entries, separator.clone(), right_child)?;

        if internal_fits(page, &entries) {
            Self::rewrite_internal(page, index_id, level, &entries, header.left, header.right, header.high_key)?;
            let lsn = self.record_structural_page_images(&[guard.page_id()])?;
            drop(frame);
            guard.mark_dirty(lsn)?;
            return Ok(());
        }

        drop(frame);

        let split = self.split_internal_blink(parent_id, level)?;
        parent_id = split.parent_hint_or_root();
        // Continue propagation upward.
    }
}
```

## 6.5 Root split

Root changes are rare and should be the only path that takes `root_latch`.

```rust
fn create_or_update_root(
    &self,
    old_level: u16,
    separator: Vec<u8>,
    right_child: PageId,
) -> Result<()> {
    let _root = self.inner.root_latch.lock().map_err(...)?;

    let meta = self.meta()?;
    let current_root = meta.root_page_id;

    // Re-check under root latch. Another writer may already have grown root.
    if root_already_covers(separator.as_slice())? {
        drop(_root);
        return self.propagate_separator(Some(current_root), old_level + 1, separator, right_child);
    }

    let new_root = self.inner.buffer.allocate(PageKind::BtreeInternal, rel_id)?;

    new_root.with_page_mut(|page| {
        init_new_root(
            page,
            left_child = current_root,
            separator,
            right_child,
            level = old_level + 1,
        )
    })?;

    let lsn = self.record_structural_page_images(&[
        self.inner.meta_page_id,
        new_root.page_id(),
    ])?;

    self.set_meta_root(new_root.page_id(), old_level + 1, TxId::ZERO, false, lsn)?;
    self.inner.root_cache.store(new_root.page_id(), old_level + 1);

    Ok(())
}
```

Root growth remains serialized, but normal index writes do not.

---

## 6.6 Delete / tombstone

Delete should no longer take the global structure mutex.

Current behavior:

* Find leaf.
* Scan for matching physical row ref.
* Set `delete_tx`.
* WAL `IndexDelete`.
* Mark dirty.

New behavior:

* Use B-link descent.
* Latch only the candidate leaf.
* If key has moved right, move right.
* If duplicate logical keys cross leaf boundaries, follow right links as current code already does.
* No page merge.
* No root change.

This keeps delete semantics almost unchanged while removing global index serialization.

## 7. WAL and recovery requirements

The crash-recovery requirement is the non-negotiable part. The spec’s failpoint and recovery matrix has zero tolerance for lost acknowledged commits.  The B-link upgrade must not weaken that.

### 7.1 Structural page images

For the MVP, structural split pages should be WALed as full `PageImage` records. That is heavier than a compact logical split record, but it is much safer and matches existing recovery patterns.

Use one of these approaches:

**Preferred MVP approach:**

```rust
WalPayload::PageImage {
    page_id,
    page_lsn,
    page_bytes,
}
```

with `tx_id = TxId::ZERO`, meaning “non-transactional structure record; redo regardless of user transaction commit.”

Reason: a page split is physical structure, not user data. The inserted entry still carries `create_tx` and is hidden unless its transaction commits. If a crash happens after a split but before the inserting transaction commits, replaying the structure is safe; the uncommitted entry is either absent because the actual insert delta never committed, or present but visibility-hidden by `create_tx`.

### 7.2 Structural WAL before dirty mark

Never mark a split page dirty until its structural page image is appended.

Required order:

```text
construct right page
rewrite left page with high_key + right_link
append structural PageImage WAL for right
append structural PageImage WAL for left
mark right dirty at structural_lsn
mark left dirty at structural_lsn
release latches
propagate parent separator
```

### 7.3 New failpoints

Add failpoints to cover every split window:

| Failpoint                                  | Location                                | Expected recovery result          |
| ------------------------------------------ | --------------------------------------- | --------------------------------- |
| `index::blink_split::after_alloc`          | after right page allocation             | no dangling child reachable       |
| `index::blink_split::after_right_init`     | right page initialized, left not linked | old tree still valid              |
| `index::blink_split::after_left_link`      | left points right, parent not updated   | search moves right and finds data |
| `index::blink_split::before_parent_insert` | child split complete, parent stale      | right-link route works            |
| `index::blink_split::after_parent_insert`  | parent updated                          | normal route works                |
| `index::blink_root::after_new_root`        | new root page written, meta not updated | old root still usable             |
| `index::blink_root::after_meta_update`     | meta points to new root                 | new root usable                   |

The existing failpoint matrix already includes index split crash coverage; this upgrade should expand that matrix around the new B-link publication sequence.

Run current certification and store baseline:

```bash

just fast

```

### Wave B — Leaf-local no-split writes

Remove `structure_lock` from the no-split insert/delete path only.

Behavior:

* Use B-link descent.
* Latch only target leaf through the existing buffer frame mutex.
* If leaf has space, rewrite leaf and return.
* If leaf is full, fall back to the existing `structure_lock` split path.

Expected benefit: large improvement for common insert/delete cases without yet taking on fully concurrent split complexity.

This wave is a safe intermediate milestone and should already improve `writers-disjoint`, because most inserts do not split.

### Wave C — B-link leaf splits

Implement concurrent leaf split publication:

* Split existing entries only.
* Publish right-link/high-key.
* Structural page images with `tx_id = ZERO`.
* Parent propagation after releasing leaf pages.
* Retry original insert.

Keep internal-page split under `root_latch` or legacy structure lock temporarily if necessary.

### Wave D — B-link internal splits and root splits

Remove the last global split fallback.

* Internal pages use same high-key/right-link rules.
* Parent propagation can recurse upward.
* Root changes use only `root_latch`.

At the end of Wave D, `structure_lock` should be deleted or retained only behind a debug/compat fallback.

## 11. Why this should not regress existing tests

### SQL parity tests

No SQL grammar, type affinity, expression evaluation, planner output, or C ABI changes are required. The public index API still returns the same `IndexRowRef` results in physical-key order. The README describes dedicated SQLite-parity tests and a differential harness; those should continue to pass because result semantics do not change. ([GitHub][2])

### MVCC visibility tests

Index entries still carry `create_tx` and `delete_tx`. Visibility continues to mirror heap tuple visibility.  The B-link upgrade only changes how pages are reached and modified, not whether an entry is visible.

### Unique constraint tests

`UniqueKeyLockTable` remains in place. The spec says it prevents the “two writers insert same unique key” TOCTOU race by locking the normalized key until commit/rollback.  B-link page concurrency does not weaken that; same-key conflicts remain serialized by the unique-key guard.

### Row-lock tests

Row locking is untouched. The spec’s row-lock matrix says same-row writers block, disjoint-row writers proceed, and writer/reader conflicts are handled by MVCC.  B-link only removes the index mutex that currently re-serializes some disjoint-row writers after the row-lock layer has allowed them through.

### Crash recovery tests

The design explicitly preserves WAL-before-dirty-page ordering and adds structural page images for split publication. Recovery already relies on WAL scan, committed transaction collection, redo, and page-LSN idempotency.  The added split failpoints should make the recovery matrix stronger, not weaker.

### Range-scan tests

The cursor already walks leaf right-links and caches the right sibling when loading each leaf.  B-link makes that right-link chain a stronger invariant. Existing range scans should see the same order, with the added benefit that a stale parent separator does not make a recently split page unreachable.

### Certification checksums

The bench harness checks row count, key XOR, and payload hash to catch missing rows, key drift, and value corruption.  This upgrade should not change logical row contents, so those checks remain valid and should remain byte-comparable for deterministic runs.

## 12. Risk register

| Risk                                              | Failure mode                                     | Mitigation                                                                                                                  |
| ------------------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| Split published but parent not updated            | Search misses right page                         | High-key/right-link move-right at every level. Add crash test after left link before parent insert.                         |
| Root split race                                   | Two roots or lost separator                      | `root_latch`; re-check meta under latch; root cache is non-authoritative.                                                   |
| Deadlock during split                             | Threads hold child then parent in opposite order | Never hold child latch while acquiring parent latch. Parent propagation happens after child release.                        |
| Stale `left_sibling`                              | Reverse chain validation fails                   | Treat right-link as authoritative; repair left-link opportunistically; adjust validation for v2 B-link mode.                |
| WAL replay sees structure without committed entry | Empty split pages remain                         | Acceptable; structure is non-transactional, entry visibility is transactional. Vacuum/maintenance can compact.              |
| Increased WAL volume during split                 | More `PageImage` records                         | Splits are infrequent relative to inserts; use full page images for MVP safety, then optimize with logical split WAL later. |
| Move-right chains grow too long                   | Search latency regression                        | Parent propagation is synchronous; add metrics and maintenance repair if move-right count exceeds threshold.                |
| Pure read overhead                                | Slight extra high-key checks                     | High-key check is cheap; target no worse than -5% on point-read and range-read gates.                                       |

## 13. Implementation acceptance criteria

The PR is not done until all of these pass:

```text
1. cargo nextest run --workspace --locked
2. just fast
3. failpoint matrix: 24/24 or expanded equivalent, zero lost acked commits
4. recovery matrix: 36/36 or expanded equivalent
5. SQL parity: no new failures
6. writers-disjoint 64T improves >= 30%
7. point-read-pk 64T regression <= 5%
8. secondary-index-read/range regression <= 5%
9. memory/RSS regression <= 10%
10. index integrity checker validates right-link chain after split storms
```

Add two hard assertions to the certification gate:

```text
index_move_right_p99_per_operation <= configured threshold
parent_propagation_pending == 0 at clean shutdown
```

## 14. Bottom line

RedlineDB already has the right macro-architecture: MVCC, row locks, group commit, redo recovery, SQLite-facing API compatibility, and a certification culture. The next major performance ceiling is that the B-tree still behaves like a single-writer subsystem inside a multi-writer engine.

The proposed B-link upgrade keeps the same page format, same MVCC visibility rules, same SQL/FFI surface, and same recovery posture, while removing the index-wide mutex from the write path. That is the cleanest next step toward making RedlineDB win harder on concurrent connects and queue-style workloads without creating a broad regression surface.
