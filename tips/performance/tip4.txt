## Recommendation: upgrade the B-tree from a global `structure_lock` to a true B-link tree

The highest-leverage design upgrade is **not** the SQL parser, not the Rust FFI, and not even the WAL first. It is the **B-tree index write path**.

RedlineDB’s stated mission is to keep the SQLite API contract while replacing SQLite’s single-writer storage core with MVCC, a concurrent B-tree, group-commit WAL, and deterministic recovery. The uploaded spec frames this as the core competitive advantage: multi-writer concurrency, crash safety, SQLite ABI compatibility, and deterministic certification.  The live GitHub README says the same: RedlineDB is a Rust-native embedded SQL engine that stays SQLite-compatible without inheriting SQLite’s concurrency cliff, and it explicitly contrasts SQLite’s single-writer WAL against RedlineDB’s MVCC, concurrent B-tree, group-commit WAL, and crash recovery. ([GitHub][1]) ([GitHub][1])

The problem is that the current B-tree implementation still has a **single global `structure_lock` over each index**. The spec says all structural modifications are protected by `structure_lock: Mutex<()>`, held across tree descent, leaf modification, and split cascade; it also states that two writers inserting into different leaf pages still serialize.  The live source confirms this: `IndexInner` contains `structure_lock: Mutex<()>`, and `insert_tx_inner` / `delete_mark_tx_inner` acquire it before proceeding. ([GitHub][2]) ([GitHub][3])

That makes the B-tree the best upgrade target because it is exactly where RedlineDB’s “multi-writer” story can silently collapse under indexed write load. SQLite WAL mode itself allows readers and writers to coexist, but because there is only one WAL file, SQLite still allows only one writer at a time. ([SQLite][4]) RedlineDB already beats SQLite hard on disjoint-writer workloads, but the benchmark table also shows weak areas around hot-row update and secondary-index read/range performance. ([GitHub][1]) Fixing the B-tree global lock is the next step toward making RedlineDB scale like a true concurrent embedded database rather than merely “less serialized than SQLite.”

# Engineering Spec: Replace B-tree `structure_lock` with B-link Tree Page Latching

## 1. Project name

**BTree-LY: Lehman-Yao B-link Index Concurrency Upgrade**

The design moves RedlineDB’s B-tree index from:

```rust
one global index mutex
    → descend tree
    → mutate leaf
    → split leaf/internal/root
    → release global lock
```

to:

```rust
short per-page latches
    → optimistic descend
    → move-right if split raced
    → mutate only target leaf/internal page
    → install parent separator after split
```

This is a classic B-link-tree direction. Lehman and Yao’s original B-tree locking work describes a B-tree variant designed for concurrent database use, and B-link-tree summaries describe the key mechanism: a right-neighbor pointer plus a high key, allowing searches and writers to move right when a concurrent split changes page ownership.  ([Flux][5])

RedlineDB is already halfway there: index pages already store `right_sibling` and `high_key`, and the live code already has `find_leaf_path` logic that checks `high_key` and follows `right` when needed.  ([GitHub][2]) The missing piece is removing the global lock and making the right-link/high-key protocol the actual concurrency mechanism.

---

## 2. Goals

The design should:

1. **Eliminate global index write serialization** for inserts/deletes targeting different leaves.
2. **Preserve SQLite API parity**: no change to SQL syntax, result sets, FFI, or public Rust API.
3. **Preserve MVCC semantics**: `create_tx` / `delete_tx` visibility remains unchanged.
4. **Preserve unique constraint correctness** through the existing `UniqueKeyLockTable`.
5. **Preserve crash safety**: committed index mutations must still be durable only after WAL durability, and recovery must still replay committed transactions only.
6. **Avoid a durable page-format migration** in the first phase by reusing existing `right_sibling`, `left_sibling`, and `high_key` fields.
7. **Improve concurrent indexed write throughput** while not regressing point reads, range scans, recovery, failpoint tests, or compatibility tests.

---

## 3. Non-goals

This change should **not** attempt to solve every known limitation at once.

It should not implement Serializable Snapshot Isolation, predicate locking, foreign keys, CHECK constraints, histograms, join reordering, parallel WAL, or variable page sizes. Those are separate workstreams. The point here is narrower: **make the existing B-tree actually concurrent under disjoint-key write load.**

It should also avoid concurrent page merge/rebalance in the first release. Deletes should continue as logical delete markers / tombstones, with vacuum handling compaction later. Concurrent merge is much easier to get wrong than concurrent split, and it is not required to remove the major insert-path serialization.

---

## 4. Current-state analysis

### 4.1 Current B-tree structure

Every index entry has a physical key:

```text
logical_key || row_id || page_id || slot || generation
```

That suffix ensures even non-unique indexes have unique physical keys, which is good for split correctness and duplicate-key runs. 

Leaf and internal pages already include:

```text
left_sibling
right_sibling
high_key
```

These are exactly the durable ingredients needed for B-link behavior. 

### 4.2 Current bottleneck

The current split algorithm updates sibling links under `structure_lock`, and the concurrent-writer section explicitly says all insert/delete/split structural modifications are protected by one `Mutex<()>`. 

The same document names this as a known limitation: B-tree `structure_lock` serializes all inserts and high write concurrency to one table; it also says a B-link tree would eliminate that lock. 

### 4.3 Why this matters for queues

Queue-like workloads are brutal for SQLite because they often combine:

```sql
INSERT INTO jobs(...)
SELECT ... WHERE status = 'ready' ORDER BY priority, created_at LIMIT 1
UPDATE jobs SET status = 'running' WHERE id = ?
DELETE FROM jobs WHERE id = ?
```

That means many concurrent writers touch both the heap and one or more indexes. RedlineDB’s row-level MVCC lets disjoint rows proceed, but if every index mutation still takes a global B-tree mutex, then high fan-in queue workloads serialize at the index layer even when row locks do not conflict.

## 5. Proposed architecture

## 5.1 Replace global index mutex with page latches

Current:

```rust
pub(super) struct IndexInner {
    buffer: Arc<BufferPool>,
    meta_page_id: PageId,
    desc: Mutex<IndexDescriptor>,
    unique_locks: Arc<UniqueKeyLockTable>,
    wal: Option<Arc<WalCoordinator>>,
    structure_lock: Mutex<()>,
    range_scan_leaves_visited: AtomicU64,
}
```

Proposed:

```rust
pub(super) struct IndexInner {
    buffer: Arc<BufferPool>,
    meta_page_id: PageId,

    // Descriptor remains small and infrequently mutated.
    desc: Mutex<IndexDescriptor>,

    // Unique key correctness remains separate from structure latching.
    unique_locks: Arc<UniqueKeyLockTable>,

    // WAL path unchanged.
    wal: Option<Arc<WalCoordinator>>,

    // Only protects root pointer / root level transitions.
    root_latch: RwLock<()>,

    // Feature flag fallback during rollout.
    legacy_structure_lock: Option<Mutex<()>>,

    // Existing and new telemetry.
    range_scan_leaves_visited: AtomicU64,
    blink_move_right_count: AtomicU64,
    blink_leaf_split_count: AtomicU64,
    blink_internal_split_count: AtomicU64,
    blink_root_split_count: AtomicU64,
    blink_parent_install_retries: AtomicU64,
    blink_latch_wait_ns: AtomicU64,
}
```

The per-page latch should live in the buffer frame, not in a side hash map, so latch memory scales with resident pages rather than total database pages.

```rust
pub struct Frame {
    page: Option<Page>,
    pin_count: AtomicUsize,
    dirty_lsn: AtomicU64,
    referenced: AtomicBool,

    // New.
    latch: RwLock<()>,
}
```

This keeps the system 100% safe Rust. No unsafe pointer protocol is required.

---

## 5.2 Latch modes

Use two latch modes:

```rust
enum LatchMode {
    Read,
    Write,
}
```

Rules:

| Operation            | Latch behavior                                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Point lookup         | read latch page briefly, copy matching entries, release                                                                          |
| Range scan           | read latch leaf briefly, copy visible candidate entries, release before yielding rows                                            |
| Insert without split | write latch target leaf only                                                                                                     |
| Delete mark          | write latch target leaf only                                                                                                     |
| Leaf split           | write latch old leaf, allocate/write new right leaf, update old leaf high-key/right-link, release, then install parent separator |
| Internal split       | write latch target internal page; root update uses `root_latch`                                                                  |
| Root split           | acquire `root_latch` write mode only for meta root update                                                                        |

Do not hold latches across user callbacks, SQL expression evaluation, WAL fsync waits, or long row materialization.

---

## 5.3 Lock ordering

To avoid deadlocks:

1. Move **down** the tree.
2. Move **right** across sibling links.
3. Never move left while holding a latch.
4. Never acquire a parent latch while still holding a child latch, except for an explicitly audited root transition path.
5. Never upgrade read latch to write latch in place. Release and retry.
6. Root latch is acquired only for root pointer/root-level transitions, not for ordinary inserts.

This gives a simple mental model:

```text
top → bottom
left → right
short latch windows only
```

# 6. Algorithms

## 6.1 Search / descent

```rust
fn find_leaf_blink(root: PageId, key: &[u8]) -> Result<SearchPath> {
    let mut page_id = root;
    let mut path = Vec::new();

    loop {
        let guard = buffer.pin(page_id)?;
        let read = guard.read_latch()?;

        let header = read.header()?;

        // B-link move-right rule.
        if !header.high_key.is_empty() && key >= header.high_key.as_slice() {
            let right = header.right.ok_or(Error::CorruptPage("missing right link"))?;
            drop(read);
            drop(guard);
            metrics.blink_move_right_count.fetch_add(1, Relaxed);
            page_id = right;
            continue;
        }

        path.push(PageHint {
            page_id,
            level: header.level,
            high_key: header.high_key.clone(),
        });

        if header.kind == PAGE_LEAF_KIND {
            return Ok(SearchPath { leaf: page_id, path });
        }

        let child = choose_child(&read, key)?;
        drop(read);
        drop(guard);

        page_id = child;
    }
}
```

This is close to what the current code already does conceptually: `find_leaf_path` checks `high_key` and follows `right` when the key no longer belongs on the current page. ([GitHub][2]) The change is that this becomes the primary concurrency protocol instead of a defensive check hidden behind a global mutex.

## 6.2 Insert without split

```rust
fn insert_tx_blink(
    &self,
    tx_id: TxId,
    logical_key: &[u8],
    row: IndexRowRef,
    emit_wal: bool,
    recovery_lsn: Lsn,
) -> Result<()> {
    let physical = encode_physical_key(logical_key, row);

    loop {
        let path = self.find_leaf_blink(self.root_page_id()?, physical.as_slice())?;
        let leaf_guard = self.inner.buffer.pin(path.leaf)?;
        let mut leaf = leaf_guard.write_latch()?;

        let header = leaf.header()?;

        if !header.high_key.is_empty() && physical.as_slice() >= header.high_key.as_slice() {
            let right = header.right.ok_or(Error::CorruptPage("leaf missing right link"))?;
            drop(leaf);
            drop(leaf_guard);
            metrics.blink_move_right_count.fetch_add(1, Relaxed);
            continue_from(right);
        }

        let mut entries = self.read_entries(&leaf)?;
        let candidate = Entry::Leaf {
            logical_key: logical_key.to_vec(),
            row,
            physical: physical.as_slice().to_vec(),
            create_tx: tx_id,
            delete_tx: TxId::ZERO,
        };

        insert_sorted_or_conflict(&mut entries, candidate, self.meta()?.uniqueness)?;

        if fits_leaf(&leaf, &entries) {
            Self::rewrite_leaf(
                &mut leaf,
                self.descriptor().index_id,
                &entries,
                header.left,
                header.right,
                header.high_key,
            )?;

            let end_lsn = if emit_wal {
                self.append_index_delta(tx_id, WalPayload::IndexInsert {
                    tx_id,
                    index_id: self.descriptor().index_id.0,
                    logical_key: logical_key.to_vec(),
                    row,
                })?
            } else {
                recovery_lsn
            };

            leaf_guard.mark_dirty(end_lsn)?;
            return Ok(());
        }

        drop(leaf);
        return self.split_leaf_and_insert_blink(path, logical_key, row, physical, tx_id, emit_wal, recovery_lsn);
    }
}
```

Critical rule: **the leaf latch is not released until the page has a correct dirty LSN.** That prevents the buffer pool from flushing a page image that recovery cannot justify from WAL.

## 6.3 Leaf split

The current split path promotes a separator to the parent immediately under the global lock. The new B-link path should make the split valid before the parent sees it.

Steps:

1. Write-latch old leaf `L`.
2. Build combined sorted entries: old entries + candidate.
3. Split into `left_entries` and `right_entries`.
4. Allocate new leaf `R`.
5. Set:

   * `R.left = L`
   * `R.right = L.right`
   * `R.high_key = L.high_key`
   * `L.right = R`
   * `L.high_key = separator`
6. Write/rewrite `R`.
7. Rewrite `L`.
8. Append WAL records for `R` and `L`.
9. Mark both pages dirty with their WAL LSN.
10. Release `L`.
11. Install separator in parent.

Pseudocode:

```rust
fn split_leaf_and_insert_blink(...) -> Result<()> {
    let left_guard = buffer.pin(leaf_id)?;
    let mut left = left_guard.write_latch()?;

    let left_header = left.header()?;
    let old_right = left_header.right;
    let old_high = left_header.high_key.clone();

    let mut entries = self.read_entries(&left)?;
    insert_candidate(&mut entries, candidate)?;

    let Split {
        left_entries,
        right_entries,
        separator,
    } = split_by_encoded_size(entries)?;

    let right_guard = buffer.allocate(PageKind::BtreeLeaf, rel_id)?;
    let mut right = right_guard.write_latch()?;

    rewrite_leaf(
        &mut right,
        index_id,
        &right_entries,
        Some(leaf_id),
        old_right,
        old_high,
    )?;

    rewrite_leaf(
        &mut left,
        index_id,
        &left_entries,
        left_header.left,
        Some(right_guard.page_id()),
        separator.clone(),
    )?;

    let right_lsn = self.record_page_image_or_delta(right_guard.page_id(), tx_id)?;
    right_guard.mark_dirty(right_lsn)?;

    let left_lsn = self.record_page_image_or_delta(leaf_id, tx_id)?;
    left_guard.mark_dirty(left_lsn)?;

    drop(right);
    drop(left);

    self.install_separator_blink(path.parent_hints(), separator, right_guard.page_id(), tx_id, emit_wal)
}
```

The important correctness point is this: once `L.high_key` and `L.right` are installed, a search that lands on old `L` can move right to `R` even if the parent separator is not installed yet. That is exactly why B-link trees are a good fit here.

## 6.4 Parent separator install

```rust
fn install_separator_blink(
    &self,
    hints: &[PageHint],
    separator: Vec<u8>,
    right_child: PageId,
    tx_id: TxId,
    emit_wal: bool,
) -> Result<()> {
    let mut parent_id = best_parent_hint_or_root(hints, &separator)?;

    loop {
        let parent_guard = buffer.pin(parent_id)?;
        let mut parent = parent_guard.write_latch()?;

        let header = parent.header()?;

        if !header.high_key.is_empty() && separator.as_slice() >= header.high_key.as_slice() {
            parent_id = header.right.ok_or(Error::CorruptPage("parent missing right link"))?;
            metrics.blink_move_right_count.fetch_add(1, Relaxed);
            continue;
        }

        let mut entries = self.read_entries(&parent)?;
        insert_internal_separator(&mut entries, separator.clone(), right_child)?;

        if fits_internal(&parent, &entries) {
            rewrite_internal(&mut parent, index_id, header.level, &entries, header.left, header.right, header.high_key)?;

            let lsn = if emit_wal {
                self.record_page_image_or_delta(parent_id, tx_id)?
            } else {
                Lsn::new(1)
            };

            parent_guard.mark_dirty(lsn)?;
            return Ok(());
        }

        drop(parent);
        drop(parent_guard);

        return self.split_internal_and_install_blink(parent_id, separator, right_child, tx_id, emit_wal);
    }
}
```

If a parent hint is stale, the algorithm follows right links or restarts from root. This should be counted:

```rust
blink_parent_install_retries += 1
```

## 6.5 Root split

Root splits remain serialized, but only root splits.

```rust
fn split_root_blink(...) -> Result<()> {
    let _root = self.inner.root_latch.write()?;

    let current_root = self.meta()?.root_page_id;

    // Verify root still needs split after acquiring root latch.
    if !root_still_matches_expected(current_root, expected_root) {
        return retry_from_root();
    }

    let new_root = buffer.allocate(PageKind::BtreeInternal, rel_id)?;

    // Install left child + separator + right child.
    rewrite_new_root(...)?;

    let root_lsn = self.record_page_image_or_delta(new_root.page_id(), tx_id)?;
    new_root.mark_dirty(root_lsn)?;

    self.set_meta_root(new_root.page_id(), old_level + 1, tx_id, emit_wal, root_lsn)
}
```

This preserves correctness while removing the common-case serialization. Root splits are rare compared with leaf insertions.

## 6.6 Delete path

Phase 1 should **not** merge pages.

Current delete mark behavior should become:

```rust
fn delete_mark_tx_blink(...) -> Result<()> {
    let physical = encode_physical_key(logical_key, row);

    loop {
        let path = find_leaf_blink(root, physical.as_slice())?;
        let leaf_guard = buffer.pin(path.leaf)?;
        let mut leaf = leaf_guard.write_latch()?;

        let header = leaf.header()?;
        if !header.high_key.is_empty() && physical.as_slice() >= header.high_key.as_slice() {
            continue_right(header.right);
        }

        let mut entries = read_entries(&leaf)?;
        mark_matching_entry_delete_tx(&mut entries, tx_id, visibility)?;

        rewrite_leaf(&mut leaf, index_id, &entries, header.left, header.right, header.high_key)?;

        let lsn = append_index_delta(IndexDelete { ... })?;
        leaf_guard.mark_dirty(lsn)?;
        return Ok(());
    }
}
```

No merge. No left sibling acquisition. No deadlock trap.

Vacuum can compact a single leaf under that leaf’s write latch. Cross-page merge can be a later phase after the split protocol is proven.

# 7. WAL and recovery design

## 7.1 Keep WAL semantics unchanged

Do **not** introduce parallel WAL in this change. The current WAL design has a single coordinator state with `reserved_lsn`, `written_lsn`, `durable_lsn`, and a pending queue; group commit drains pending records and `fdatasync()`s the segment. 

That single WAL writer is a known future bottleneck, but changing the WAL and B-tree simultaneously would make failures much harder to isolate. The B-tree lock is earlier in the write path, so remove that first.

## 7.2 Split logging

For the first implementation, use existing WAL mechanisms:

* `IndexInsert`
* `IndexDelete`
* `PageImage`
* `PageDelta` where already available / safe

The spec already has WAL payload variants for `IndexInsert`, `IndexDelete`, `Commit`, and `PageImage`; `PageDelta` is reserved. 

For Phase 1, correctness beats WAL size. Use `PageImage` for split structural changes if delta semantics are not fully ready. Later, replace split page images with compact deltas.

## 7.3 Redo-only recovery compatibility

Recovery already collects committed transactions, applies heap/index/page-image records for committed transactions, and skips uncommitted transaction IDs. 

The B-link split protocol must obey this rule:

```text
No structural page update may become checkpoint-flushable unless its WAL record has an LSN.
```

Therefore:

1. Mutate page under write latch.
2. Append WAL.
3. Set page LSN / dirty LSN.
4. Release latch.

If the process crashes before commit, recovery skips uncommitted index mutations. If the process crashes after commit, the commit record is durable and all prior index WAL records must be durable because commit is appended after them and `flush_until(commit_lsn)` waits for durability. The spec states the transaction is durable only when its commit WAL record is `fdatasync()`’d before `RLDB_OK`.

# 8. Correctness invariants

Add an index validator specifically for B-link invariants:

```rust
pub struct BlinkValidationReport {
    pages_seen: usize,
    leaf_pages: usize,
    internal_pages: usize,
    right_link_edges: usize,
    high_key_errors: Vec<PageId>,
    right_link_cycles: Vec<PageId>,
    parent_coverage_gaps: Vec<PageId>,
    duplicate_physical_keys: Vec<Vec<u8>>,
}
```

Required invariants:

1. **Leaf order:** all physical keys inside a leaf are strictly sorted.
2. **Physical uniqueness:** no duplicate full physical key exists.
3. **High-key bound:** for every page with non-empty `high_key`, all keys on that page are `< high_key`.
4. **Right-link bound:** if `L.right = R`, then keys in `R` are `>= L.high_key`.
5. **Right-link acyclicity:** following right links at a level never cycles.
6. **Parent separator compatibility:** parent separators may lag only transiently in memory; after a committed operation and recovery, every child must be discoverable either through parent descent or right-link movement.
7. **Visibility unchanged:** `create_tx` and `delete_tx` visibility rules produce the same logical index contents as before.
8. **Unique keys unchanged:** unique logical keys still require `UniqueKeyLockTable` ownership before insert.

# 10. Expected outcomes

These are directional expectations, not benchmark claims until measured.

## 10.1 Write throughput

For indexed, disjoint-key write workloads, I would expect:

| Workload                           | Expected impact                                                               |
| ---------------------------------- | ----------------------------------------------------------------------------- |
| Disjoint inserts, one index        | **2×–6× RedlineDB improvement** if `structure_lock` is currently hot          |
| Disjoint inserts, multiple indexes | **larger improvement**, because each index currently serializes independently |
| Mixed 80/20 and 50/50 OLTP         | **1.2×–2×** depending on write/index share                                    |
| Queue claim/update/delete          | **major p99 improvement** when jobs map to different leaves                   |
| Same hot row update                | little improvement; still row-lock bound                                      |
| Same hot index leaf                | limited improvement; leaf latch becomes expected bottleneck                   |
| Point-read PK                      | no intended regression                                                        |
| Pure secondary-index range scan    | not fully solved; may need cursor/page-layout work later                      |

The live benchmark table already shows RedlineDB strongly ahead of SQLite on multi-writer workloads but weak on secondary-index read/range and hot-row-update. ([GitHub][1]) This B-tree change is primarily a **write-concurrency** upgrade; it should also reduce reader p99 under concurrent index splits, but it is not a complete secondary-index read-performance redesign.

## 10.2 Memory

Expected memory cost is low:

```text
per resident buffer frame: one RwLock + small counters/metadata
persistent page format: unchanged in Phase 1
per operation: short path Vec<PageHint>
```

For a 64k-frame buffer pool, the latch overhead should be on the order of a few MiB, not hundreds of MiB. No per-row lock table is added for index pages.

## 10.3 Concurrency / connections

This should let more concurrent connections make useful progress when they are inserting/updating different indexed keys. It does not change the C ABI thread-safety contract, but it improves the engine underneath a pool of one-connection-per-thread clients.

## 10.4 Durability

Durability should not regress because the commit protocol remains unchanged: the transaction is acknowledged only after the commit WAL record is durable.  The failpoint/recovery matrix should be extended, not weakened.

---

# 11. Why this should not regress other tests

## SQL compatibility

No parser, planner, executor, or FFI signatures change. SQLite-compatible behavior remains the same because this only changes index-page concurrency.

## MVCC visibility

Index entries still carry `create_tx` and `delete_tx`, and the entry visibility function continues to mirror heap tuple visibility.  No snapshot rules change.

## Unique constraints

The existing unique-key lock remains in front of unique inserts. The spec says this guard prevents the race where two writers both see no duplicate and insert the same key.  The B-link page latch only protects page structure; it does not replace logical unique-key serialization.

## Crash recovery

Recovery continues to redo committed WAL records and skip uncommitted transaction IDs.  The B-link protocol must add more crash windows to the matrix, but the recovery model itself does not need to change.

## Read performance

Point reads gain a few extra high-key checks but lose global writer interference. Range scans already follow right siblings, and B-link keeps that model. The implementation should copy leaf entries under a short read latch and release before row materialization, so long scans do not block writers for the duration of the scan.

## Hot-row contention

Hot-row update is not expected to improve much because that workload is correctly limited by row locking. That is not a regression; it is the right bottleneck.

# 12. Rollout plan

## Phase 0 — Instrument current lock

Before changing behavior, add counters around the existing `structure_lock`:

```rust
index_structure_lock_wait_ns
index_structure_lock_hold_ns
index_structure_lock_contention_count
index_split_count
index_insert_count
```

Run current certification and store the baseline.

## Phase 1 — Add page latch API

Add read/write latches to buffer frames and expose safe APIs:

```rust
FrameGuard::with_page_read_latched(...)
FrameGuard::with_page_write_latched(...)
```

No B-tree behavior change yet.

## Phase 2 — Read path uses B-link latches

Convert `find_leaf_path`, point lookup, and range scan to use page read latches and move-right logic. Keep legacy global write lock for mutations.

## Phase 3 — Concurrent no-split leaf insert

Allow concurrent inserts into different safe leaves. Splits still fall back to legacy `structure_lock`.

This phase should already show whether latch overhead regresses point reads.

## Phase 4 — Concurrent leaf splits

Implement B-link leaf split and parent separator install. Add failpoints around every split stage.

## Phase 5 — Internal/root splits

Remove legacy split fallback for internal pages. Keep only root-level serialization.

## Phase 6 — Delete mark and vacuum compaction

Convert delete-mark path to per-leaf write latches. Keep page merge disabled.

## Phase 7 — Default-on

Enable `blink_index` by default after:

```text
cargo test --workspace
compat suite
recovery matrix
failpoint matrix
certification workloads
cross-engine SQLite differential tests
```

Keep `legacy_structure_lock` behind a feature flag for one release cycle.

---

# 13. Final decision

The key section to upgrade is:

```text
crates/kernel/src/index/
```

Specifically:

```text
index/mod.rs      -> IndexInner, page header handling, search path
index/mutate.rs   -> insert, delete_mark, split path
index/cursor.rs   -> range scan latch behavior
storage/buffer.rs -> per-frame latch API
bench/            -> new B-link stress/failpoint workloads
```

The reason is simple: RedlineDB’s big promise is **multi-writer SQLite compatibility**, but the current B-tree still has a single global index structure mutex. Removing that mutex with a B-link protocol gives the best performance upside while keeping WAL, MVCC, SQL, FFI, and recovery semantics stable.
