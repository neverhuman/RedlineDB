## Recommendation: upgrade the B-tree index from a global-mutex B-tree to a per-page-latched B-link tree

The single highest-leverage section to upgrade is **`crates/kernel/src/index/`**, specifically the B-tree mutation path. RedlineDB’s overall architecture is already pointed in the right direction: safe Rust, MVCC, row-level write concurrency, group-commit WAL, deterministic recovery, and SQLite ABI compatibility. The spec says the engine’s goal is to keep the SQLite API contract while replacing SQLite’s single-writer storage core with MVCC, concurrent indexing, group commit, and deterministic crash recovery. 

The weakness is that the current B-tree still has a **single `structure_lock: Mutex<()>` per index**, and both insert and delete-mark paths acquire it before doing descent, leaf modification, and split/parent work. The public source confirms `IndexInner` contains `structure_lock`, and `insert_tx_inner` plus `delete_mark_tx_inner` acquire it before proceeding. ([GitHub][1]) The uploaded spec is even more explicit: all structural modifications are protected by that one lock, and two writers inserting into different leaf pages still serialize. 

That means RedlineDB currently beats SQLite’s single-writer WAL on disjoint writes **despite** a global index bottleneck, not because the index layer is fully concurrent. The README reports strong write/mixed workload wins, but also honest losses on hot-row update and secondary-index workloads; for example, writers-disjoint at 64 threads is listed as 15.89× SQLite, while secondary-index-range is only 0.048× SQLite and secondary-index-read is 0.13×. ([GitHub][2])

My proposed upgrade is:

> **Replace `BtreeIndex.inner.structure_lock` with a Lehman-Yao-style B-link tree protocol using page-level latches, existing right-sibling links, high keys, optimistic move-right search, and crash-safe split installation.**

This is the right next move because the current page format already has most of the B-link ingredients: leaf/internal page headers include `left`, `right`, and `high_key`, and the source defines `PAGE_RIGHT_OFF` and `PAGE_HIGH_KEY_OFF` in the B-tree special region. ([GitHub][1]) The classic B-link-tree approach uses right links and high keys so search and insert can move right when a split races with traversal, avoiding a global tree lock; summaries of Lehman-Yao describe the key idea as adding a right-neighbor pointer and high key so concurrent operations can remain correct with very limited write locking. ([Flux][3])

# Engineering spec: RedlineDB B-link Index Concurrency Upgrade

## 1. Goal

Make the B-tree index mutation path scale with independent keys and independent leaves.

Today:

```text
all index writers for one index
        ↓
single structure_lock
        ↓
tree descent + leaf update + split cascade
        ↓
release
```

Target:

```text
writer A on leaf 100 ── page latch leaf 100 ── commit index delta
writer B on leaf 884 ── page latch leaf 884 ── commit index delta
writer C on leaf 200 ── page latch leaf 200 ── commit index delta
```

The global index mutex should disappear from normal insert/delete/compaction paths. Writers should conflict only when they touch the same leaf, adjacent split boundary, same parent during separator propagation, or the same unique key. The existing `UniqueKeyLockTable` must remain in place for unique constraints, because it prevents two concurrent writers from both seeing “no duplicate” and inserting the same unique key. 

## 2. Non-goals

This change should **not** attempt to solve every known limitation at once.

It should not change SQL semantics, FFI ABI, MVCC visibility rules, row-lock behavior, `UniqueKeyLockTable`, statement caching, or planner cost modeling. It should not introduce page merges yet. It should not promise that a true single hot row will beat SQLite; hot-row update is fundamentally a row-lock convoy, and the current README already shows hot-row-update remains weak relative to SQLite. ([GitHub][2])

It should also not rewrite the WAL subsystem in this phase. WAL may become the next ceiling, because the spec notes a single WAL writer and one pending `VecDeque` can saturate under many small transactions.  But the index global lock is a cleaner, more local first upgrade.

## 3. Current problem statement

### 3.1 The B-tree contradicts the “multi-writer” promise at the index layer

The engine can let two disjoint-row writers proceed at the row-lock/MVCC layer, but once they update an index, they serialize behind `structure_lock`. The spec says two writers on disjoint rows do not conflict at the row-lock layer, but two writers on the same B-tree path serialize through `structure_lock`. 

This is most damaging for:

1. Queue workloads where many workers claim different rows but update the same status/time/priority index.
2. Insert-heavy tables with primary-key and secondary indexes.
3. Mixed OLTP workloads where index updates elongate p99 latency.
4. Many-connection workloads where the connection count is high but useful write progress collapses behind one index mutex.
5. Secondary-index maintenance, especially when updates delete old keys and insert new keys.

### 3.2 The current implementation already hints at the B-link design

The insert path already contains a defensive high-key check: if the chosen leaf says the candidate belongs to a sibling, it retries descent. ([GitHub][4]) Delete-mark also walks right when duplicates of the logical key may continue on the right sibling. ([GitHub][4]) Those are the right conceptual primitives; they just sit behind a global lock today.

## 4. Proposed architecture

### 4.1 Replace `structure_lock` with explicit page-latch discipline

Change:

```rust
pub(super) structure_lock: Mutex<()>,
```

to either remove it entirely or keep it only as a debug-only fallback behind a feature flag:

```rust
pub(super) index_mode: IndexConcurrencyMode,

pub enum IndexConcurrencyMode {
    GlobalMutexCompat,   // temporary rollback/debug path
    BLinkPageLatch,      // new default
}
```

Use the existing buffer frame pin/mutable-frame mechanism as the primary page latch if it already provides exclusive mutable access. If the buffer layer cannot provide stable read/write page guards, add a small `IndexPageLatch` layer keyed by `PageId`:

```rust
struct IndexPageLatchTable {
    shards: [Mutex<HashMap<PageId, Arc<IndexPageLatch>>>; 64],
}

struct IndexPageLatch {
    latch: RwLock<()>,
    split_epoch: AtomicU64,
}
```

No new persistent data is required for latches. This is an in-memory concurrency-control layer only.

### 4.2 Use B-link invariants

Every B-tree page must maintain:

```text
page.high_key = exclusive upper bound for keys that belong on this page
page.right    = sibling page to consult when search_key >= high_key
```

For the rightmost page at a level:

```text
high_key = empty / infinity
right    = None
```

Search invariant:

```text
A search may land on an old page after a concurrent split.
If search_key >= page.high_key and page.right != None,
move right until the key belongs.
```

Split invariant:

```text
A split is visible to readers/writers as soon as the left page points to the new right page.
The parent separator can be installed later.
```

This is the key reason B-link trees work: parent updates no longer have to be globally synchronized with child splits.

### 4.3 Preserve the current physical key format

Do not change:

```text
KeyBuf = logical_key || row_id || page_id || slot || generation
```

The current physical-key suffix is already excellent. It makes duplicate keys totally ordered, makes split midpoints well-defined, and prevents non-unique index duplicates from becoming ambiguous. 

This is a huge advantage for the B-link upgrade: duplicate-heavy queue/status indexes can split on physical keys without needing special duplicate chains.

## 5. New algorithms

### 5.1 Search/read path

New helper:

```rust
fn find_leaf_blink(&self, key: &[u8]) -> Result<PageId> {
    let mut page_id = self.root_page_id_relaxed()?;

    loop {
        let guard = self.pin_read(page_id)?;
        let header = Self::read_page_header(guard.page())?;

        if !header.high_key.is_empty()
            && key >= header.high_key.as_slice()
            && let Some(right) = header.right
        {
            drop(guard);
            page_id = right;
            continue;
        }

        if header.kind == PAGE_LEAF_KIND {
            return Ok(page_id);
        }

        let child = self.choose_child(guard.page(), key)?;
        drop(guard);
        page_id = child;
    }
}
```

Read path rules:

1. Readers may take a read latch briefly while copying entries from a page.
2. Readers never take a global index lock.
3. Range scan follows right links as it does today.
4. If a split moves the key range while a reader is in flight, the reader sees either the old page then moves right, or the new parent path and lands directly on the new page.
5. Range scan should copy page entries into a short-lived local vector, release the page latch, then apply MVCC visibility. This prevents long scans from blocking writers.

### 5.2 Insert fast path: no split

Current fast path under global lock:

```text
lock structure_lock
descend to leaf
rewrite leaf
append IndexInsert WAL
mark dirty
unlock structure_lock
```

New fast path:

```rust
fn insert_tx_inner_blink(...) -> Result<()> {
    let physical = encode_physical_key(logical_key, row);

    loop {
        let leaf_id = self.find_leaf_blink(physical.as_slice())?;

        let leaf = self.pin_write(leaf_id)?;
        let header = Self::read_page_header(leaf.page())?;

        if self.key_belongs_right(&header, physical.as_slice()) {
            let right = header.right.ok_or(Error::CorruptPage("missing right link"))?;
            drop(leaf);
            continue;
        }

        let mut entries = self.read_entries(leaf.page())?;
        let candidate = Entry::Leaf { ... };

        insert_sorted(&mut entries, candidate)?;

        if fits(leaf.page(), &entries) {
            Self::rewrite_leaf(...)?;
            let end_lsn = self.append_index_delta(tx_id, WalPayload::IndexInsert { ... })?;
            leaf.mark_dirty(end_lsn)?;
            return Ok(());
        }

        drop(leaf);
        return self.split_leaf_and_insert_blink(...);
    }
}
```

Key behavior:

1. Only the target leaf is write-latched.
2. Writers on different leaves run concurrently.
3. If a concurrent split redirects the key, retry/move right.
4. Unique constraints remain guarded by `UniqueKeyLockTable`; no change.

### 5.3 Insert slow path: leaf split

Split order must be crash-safe and concurrency-safe.

Recommended split sequence:

```text
1. Write-latch old leaf L.
2. Build sorted entries = old entries + candidate.
3. Split entries into left_entries and right_entries.
4. Allocate new right leaf R.
5. Write-latch R.
6. Initialize R:
   R.entries  = right_entries
   R.high_key = old_L.high_key
   R.right    = old_L.right
   R.left     = L
7. Rewrite L:
   L.entries  = left_entries
   L.high_key = separator
   L.right    = R
8. WAL/page-image order:
   a. R page image / delta
   b. L page image / delta
9. Release R and L.
10. Insert separator into parent.
```

Important invariant:

```text
L.right = R must become visible before the parent separator is required for correctness.
```

So even if parent insertion lags, readers and writers can still find `R` by landing on `L`, comparing against `L.high_key`, and moving right.

### 5.4 Parent separator insertion

Parent insertion should be re-search based, not dependent on a stale path.

Current split path can pass a parent path captured during descent. With concurrent splits, that path may no longer be reliable. The B-link version should use:

```rust
fn insert_parent_separator_blink(
    level: u16,
    separator: Vec<u8>,
    right_child: PageId,
) -> Result<()> {
    loop {
        let parent_id = self.find_parent_candidate(level + 1, &separator)?;
        let parent = self.pin_write(parent_id)?;
        let header = Self::read_page_header(parent.page())?;

        if key_belongs_right(&header, &separator) {
            let right = header.right.unwrap();
            drop(parent);
            continue;
        }

        insert_internal_cell(parent, separator, right_child)?;

        if parent_fits {
            wal_parent_delta_or_image(...)?;
            parent.mark_dirty(...)?;
            return Ok(());
        }

        let promoted = split_internal_page_blink(parent, separator, right_child)?;
        drop(parent);

        if split_was_root {
            install_new_root(...)?;
            return Ok(());
        }

        separator = promoted.separator;
        right_child = promoted.right_page;
    }
}
```

Parent insertion rules:

1. Lock only one parent page at a time.
2. Move right if parent’s high key says separator belongs elsewhere.
3. If parent splits, publish right-link/high-key first, then propagate upward.
4. Root split uses a short `root_latch` or `meta_latch`, not the old global index lock.

### 5.5 Root split

Root split is the only operation that should serialize at index level.

Add:

```rust
root_latch: Mutex<()>,
root_page_id_cache: AtomicU64,
root_level_cache: AtomicU16,
```

Root split algorithm:

```text
1. Acquire root_latch.
2. Re-read meta root; verify root still needs split.
3. Allocate new root.
4. Install left child and separator/right child.
5. WAL page image for new root.
6. WAL/meta update for root pointer/root level.
7. Publish root cache.
8. Release root_latch.
```

Root splits are rare. Serializing them is acceptable.

### 5.6 Delete-mark path

Do **not** implement page merge yet.

Current delete-mark is MVCC tombstoning of index entries, not physical page removal. That is good for concurrency. The new path should:

1. Find leaf via `find_leaf_blink`.
2. Write-latch only that leaf.
3. Move right if the logical/physical key may continue to a sibling.
4. Mark `delete_tx`.
5. Append `IndexDelete` WAL payload.
6. Mark leaf dirty.

No merge means no sibling underflow protocol, no delete-side structural hazards, and much lower risk of correctness regression.

### 5.7 Compaction/vacuum path

`compact_leaf_page` and `prune_committed_deletes_before` should write-latch one leaf page at a time. They should not acquire a global structure lock.

Rules:

1. Never compact a page that is currently being split.
2. Re-read header after acquiring latch.
3. Preserve `left`, `right`, and `high_key`.
4. Never move live entries across leaf boundaries during compaction.
5. Do not merge pages in this phase.

This keeps vacuum local and safe.

## 6. WAL and crash-recovery requirements

The existing recovery model is redo-only: committed mutations are replayed, uncommitted transactions are ignored, and page redo is skipped when `page_lsn >= record.lsn`.  The B-link split must be compatible with that model.

### 6.1 WAL record options

Lowest-risk path:

```text
Keep using PageImage records for split-touched pages.
Use existing IndexInsert/IndexDelete deltas for non-split insert/delete.
```

For a leaf split:

```text
PageImage(R)
PageImage(L)
IndexInsert(tx_id, key, row)
```

For parent insertion:

```text
PageImage(parent)
```

For root split:

```text
PageImage(new_root)
PageImage(meta)
```

This is not the most WAL-efficient design, but it is the least risky. The spec already notes `PageImage` is expensive but safe and idempotent.  Optimize to compact `IndexSplit` records later after correctness is locked down.

### 6.2 Required split crash invariants

A committed split must recover into one of these valid states:

| Recovered state                              |                                                       Valid? | Why |
| -------------------------------------------- | -----------------------------------------------------------: | --- |
| Neither L nor R split visible                |                              Yes, if transaction uncommitted |     |
| R exists but unreachable                     | Yes, if uncommitted; vacuum/page allocator can reclaim later |     |
| L points to R, parent missing separator      |                               Yes, B-link move-right finds R |     |
| L points to R and parent has separator       |                                   Yes, normal complete split |     |
| Parent points to R but L does not point to R |                                                       **No** |     |

The forbidden state is prevented by WAL/apply order: right page first, left page with right-link second, parent separator third.

### 6.3 New failpoints

Add failpoints specifically for split interleavings:

```text
index::split::after_alloc_right
index::split::after_write_right_before_link_left
index::split::after_link_left_before_parent
index::split::after_parent_before_commit
index::root_split::after_new_root_before_meta
index::root_split::after_meta_before_publish
```

These should extend the current crash matrix, which already includes index split crash injection and synced-ack durability gates. 

## 7. Data-structure changes

### 7.1 `IndexInner`

Proposed:

```rust
pub(super) struct IndexInner {
    pub(super) buffer: Arc<BufferPool>,
    pub(super) meta_page_id: PageId,
    pub(super) desc: Mutex<IndexDescriptor>,
    pub(super) unique_locks: Arc<UniqueKeyLockTable>,
    pub(super) wal: Option<Arc<WalCoordinator>>,

    // Replace global structure_lock:
    pub(super) root_latch: Mutex<()>,
    pub(super) root_page_id_cache: AtomicU64,
    pub(super) root_level_cache: AtomicU16,

    pub(super) stats: IndexStatsAtomic,
}
```

`structure_lock` can remain temporarily behind `#[cfg(feature = "index_global_mutex_compat")]`.

### 7.2 `IndexStats`

Expand from only range-scan leaves visited to:

```rust
pub struct IndexStats {
    pub range_scan_leaves_visited: u64,
    pub insert_leaf_latch_wait_ns: u64,
    pub insert_parent_latch_wait_ns: u64,
    pub split_count: u64,
    pub root_split_count: u64,
    pub move_right_count: u64,
    pub insert_retries: u64,
    pub max_split_chain_len: u64,
    pub global_structure_lock_acquires: u64, // must be 0 in new mode
}
```

This matters because the certification harness already surfaces performance counters and process metrics; index-latch counters should be added to the same reporting path so we can prove the bottleneck moved instead of guessing.

### 7.3 Page format

Minimal version:

```text
No persistent format change required.
```

The page special region already stores right sibling and high key. Source constants confirm `PAGE_RIGHT_OFF`, `PAGE_HIGH_KEY_LEN_OFF`, and `PAGE_HIGH_KEY_OFF` exist. ([GitHub][1])

Optional safer version:

```rust
pub const INDEX_VERSION: u16 = 3;

new special fields:
- split_epoch: u64
- flags: u16
```

I would avoid a format bump unless the current special region truly needs a persisted split marker. The best design is to make split correctness depend on page contents and WAL order, not on extra recovery flags.

## 8. Correctness invariants

### 8.1 Ordering invariant

For every page `P`:

```text
all keys in P < P.high_key, unless P.high_key == infinity
```

For every right link:

```text
if P.right = R, then P.high_key <= first_key(R)
```

For physical keys:

```text
logical_key || row_ref_suffix is total order
```

### 8.2 Reachability invariant

Every committed key must be reachable by either:

```text
root descent
```

or:

```text
root descent to stale left sibling + one or more right-link moves
```

### 8.3 Split invariant

After split publication:

```text
left.high_key = separator
left.right = right_page_id
right.high_key = old_left.high_key
right.right = old_left.right
```

Parent separator insertion may lag, but must never precede left-link publication in WAL recovery order.

### 8.4 MVCC invariant

Index entry visibility remains unchanged:

```text
create_tx must be visible
delete_tx must not be visible
```

This preserves snapshot isolation behavior and does not alter SQL semantics.

### 8.5 Unique invariant

Unique-key locking remains unchanged:

```text
unique logical key lock is acquired before probing/inserting
guard is held until commit/rollback
```

This prevents the duplicate-insert race independently of B-tree latching.

## 9. Performance expectations

### 9.1 Where performance should improve

Expected improvements:

| Workload                                | Expected effect                                                                                      |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `WritersDisjoint`                       | Higher throughput once index updates no longer serialize globally                                    |
| queue claim/update workloads            | More workers can claim different rows concurrently when claims touch indexed status/priority columns |
| `MixedOLTP-80/20` and `MixedOLTP-50/50` | Lower p95/p99 latency from shorter index critical sections                                           |
| secondary-index write maintenance       | Better scaling for update/delete/insert on independent keys                                          |
| connection-limit benchmark              | More active connections can make useful progress before lock convoying                               |

A realistic first target is **1.5×–2.5× current RedlineDB throughput** on indexed disjoint-writer workloads at 32–64 threads, assuming WAL does not become the next bottleneck. I would not claim this will fix pure secondary-index-read parity by itself; the README’s secondary-index-read/range losses likely include scan, visibility, heap-fetch, and planner/executor costs beyond mutation locking. ([GitHub][2])

### 9.2 Where performance will not improve

This will not materially improve:

```text
many writers updating one row
```

That remains a row-lock convoy.

It will not fix:

```text
bad plans from missing histograms
```

The spec lists histogram-free cardinality estimation as a separate SQL planner limitation. 

It will not fix:

```text
single WAL writer saturation
```

If this B-link upgrade works, WAL may become the next dominant ceiling under many tiny commits. The spec already identifies the single WAL writer, group-commit delay, and pending queue as known limitations. 

## 10. Why this should not regress other tests

### 10.1 SQL parity should not regress

The change is inside the kernel index implementation. It does not change parser behavior, SQL result types, C ABI symbols, parameter binding, row encoding, or SQLite surface behavior. Existing SQLite parity tests should see identical rows.

### 10.2 MVCC visibility should not regress

The index entry format already stores `create_tx` and `delete_tx`, and this change does not modify visibility rules. The range scan and point lookup should still filter index entries exactly as before. 

### 10.3 Unique constraints should not regress

The `UniqueKeyLockTable` stays in front of unique inserts. The B-link implementation changes physical page concurrency, not logical uniqueness.

### 10.4 Crash safety should not regress

The existing recovery contract is WAL-first and redo-idempotent. A transaction is durable only when the commit WAL record is fdatasync’d before returning OK.  The split protocol respects this by logging page images/deltas in an order where a recovered tree is always searchable, even if parent separator installation lags behind left/right link installation.

### 10.5 Memory should not regress meaningfully

The cheapest version uses existing buffer-frame guards as page latches. That adds almost no persistent memory. If a latch table is required, make it lazy and sharded, keyed only by resident or recently touched `PageId`, with cleanup on eviction. The target overhead should be:

```text
< 128 bytes per resident index page
< 1 KB per index for root cache/stats
zero extra bytes per tuple
zero extra bytes per index entry
```

### 10.6 Read performance should not regress

Readers should not wait behind a global writer lock. They may briefly take page read latches while copying entries, but they should release before MVCC filtering and heap fetch. In mixed workloads, this should reduce reader p99 stalls caused by index writers.

## 11. Implementation plan

### Phase 0 — observability before changing behavior

Add counters around current `structure_lock`:

```text
structure_lock_wait_ns
structure_lock_hold_ns
structure_lock_acquire_count
structure_lock_contention_count
insert_split_count
delete_mark_count
```

Gate: prove that indexed disjoint writers spend meaningful time waiting on `structure_lock`.

### Phase 1 — page-latched read/search path

Implement:

```rust
find_leaf_blink()
move_right_if_needed()
copy_leaf_entries_for_scan()
```

Keep `structure_lock` enabled for writers. This phase proves the new search logic agrees with the old path.

Tests:

```text
old_find_leaf_path == new_find_leaf_blink
point lookup equivalence
range scan equivalence
duplicate-key split lookup equivalence
```

### Phase 2 — insert fast path without global lock

Enable no-split inserts under leaf write latch only.

Gate:

```text
global_structure_lock_acquires == 0 for no-split insert workload
all index integrity tests pass
all SQL DML tests pass
```

### Phase 3 — leaf split without global lock

Implement split publication:

```text
right page image
left page image with right link/high key
parent separator insertion
```

Add failpoints.

Gate:

```text
crash at every split failpoint
recover
PRAGMA integrity_check / internal index validation
row_count/key_xor/payload_hash stable
```

The spec’s certification uses row count, key XOR, and payload hash to detect missing rows, wrong keys, and value corruption; reuse that exact strategy for split stress. 

### Phase 4 — parent/internal split

Implement internal-page B-link split and separator propagation.

Gate:

```text
height >= 3 randomized insert/delete tests
concurrent inserts across many key ranges
concurrent duplicate-heavy inserts
range scans during split storm
```

### Phase 5 — root split

Add `root_latch` and root cache.

Gate:

```text
root split under 64 concurrent writers
crash before/after meta update
recovery opens index and validates all entries
```

### Phase 6 — delete-mark and compaction without global lock

Convert delete-mark, compact, and prune to page-latched paths.

Gate:

```text
update/delete workloads
vacuum/prune workloads
range scan during prune
rollback with index undo
```

### Phase 7 — remove compatibility mode

After certification stability:

```text
remove index_global_mutex_compat
remove structure_lock from production IndexInner
keep debug assertion that no global lock path is used
```

```text

force duplicate-key leaf splits
verify:
- point lookup returns all committed rows
- range scan sees complete duplicate run
- delete-mark can find entries across right siblings
```

This is essential because RedlineDB’s physical key suffix is a major differentiator; the B-link protocol must preserve duplicate-key correctness.

```text
thread A: long range scan
thread B: inserts/splits inside scan range
thread C: deletes/tombstones inside scan range
```

Verify snapshot visibility:

```text
reader sees exactly its snapshot
not partial future rows
not missing committed-before-snapshot rows
```

```text
- parent latch wait

- move-right count
- WAL fdatasync count
- pwrite count
- RSS
```

The current README says mixed and disjoint-writer workloads scale well to 64 threads but hit a 128-thread cross-core scaling cliff. ([GitHub][2]) This upgrade should specifically test whether the cliff is index lock contention or something later in the pipeline, such as WAL or buffer-frame contention.

## 14. Rollout risk and mitigation

| Risk                                            | Mitigation                                                                      |
| ----------------------------------------------- | ------------------------------------------------------------------------------- |
| Hard-to-debug split race                        | Keep `index_global_mutex_compat` feature until certification passes             |
| Parent separator lost or duplicated             | Use page-image WAL during first implementation; optimize deltas later           |
| Reader sees partial split                       | Publish right page then left right-link/high-key before parent                  |
| Duplicate-key range scan misses entries         | Stress duplicate logical key + physical suffix split cases                      |
| Root split race                                 | Serialize only root split with `root_latch`                                     |
| Memory increase from latches                    | Prefer existing buffer guards; if latch table needed, allocate lazily           |
| WAL amplification worsens during split storms   | Accept initially for safety; measure; later add compact `IndexSplit` WAL record |
| Secondary-index pure-read still loses to SQLite | Treat as separate executor/planner/index-scan optimization lane                 |

## 15. Expected outcome

After this upgrade, RedlineDB’s concurrency story becomes much cleaner:

```text
MVCC allows disjoint row writes.
RowLockManager only blocks same-row conflicts.
UniqueKeyLockTable only blocks same-unique-key conflicts.
B-link index only blocks same-leaf/split-boundary conflicts.
WAL group commit batches durable commits.
```

That is the architecture RedlineDB needs if it wants to be credible as a high-concurrency SQLite replacement for queues and embedded services. The current design already has the right storage and recovery foundation; the B-tree mutation lock is the most obvious “still SQLite-like serialization point” left in the hot path.

My final recommendation: **make the B-link index upgrade the next major performance lane, before rewriting WAL or planner internals.** It is local enough to implement and certify, but important enough to materially improve high-connection, disjoint-writer, and queue-claim workloads.
