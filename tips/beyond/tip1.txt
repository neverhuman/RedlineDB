Here’s the ranked “requested SQLite gaps” backlog I would take seriously after a broad scan of public SQLite forum threads, Stack Overflow, GitHub issues, HN/Reddit-style discussions, ORM issues, and Postgres-parity conversations. I’m not going to pretend I literally read every X/Quora/forum post on the internet; public search/indexing for X and Quora is patchy. The ranking below is based on recurring public demand signals, Stack Overflow view/vote signals where available, SQLite’s own omitted-feature docs, and how often a gap appears when people compare SQLite with PostgreSQL.

SQLite’s own framing matters: the project explicitly says SQLite is not trying to be a client/server database like PostgreSQL; it emphasizes local, embedded simplicity, while client/server engines emphasize scalability, concurrency, centralization, and control. Many “missing features” below are therefore deliberate tradeoffs, not accidental omissions. ([SQLite][1])

## Ranked list of requested SQLite features/gaps

|   Rank | Requested feature / gap                                                                                         | What people are asking for                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Why it matters / Postgres gap                                                                                                                                                                                                                                                          |
| -----: | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|  **1** | **More write concurrency: multiple writers, row-level locks, `SELECT … FOR UPDATE`, queue-friendly locking**    | The most common pain cluster is “database is locked,” one-writer bottlenecks, row-level locking, job queues, and transactional work where unrelated rows should not block one another. Public demand signals are very strong: a Stack Overflow “database is locked” question shows 216k views, SQLite forum users ask about row-level locking, and SQLite’s own docs steer high-concurrency write workloads toward client/server systems. ([Stack Overflow][2])                            | PostgreSQL’s MVCC/row-locking model enables many concurrent writers, `FOR UPDATE`, `SKIP LOCKED`, job queues, and long-running transactions with less global contention. This is the single biggest “SQLite as primary app DB” blocker.                                                |
|  **2** | **Full `ALTER TABLE` / migration ergonomics**                                                                   | People want `ALTER COLUMN`, change/drop constraints, add/drop primary keys, change defaults and types, add constraints, `DROP CONSTRAINT`, `ADD COLUMN IF NOT EXISTS`, and fewer table-rebuild migrations. SQLite officially supports only a limited subset of `ALTER TABLE`; its docs describe the 12-step table-rebuild procedure for broader schema changes. A Stack Overflow `ALTER COLUMN` question has 172k views, and Reddit/ORM issues still surface migration pain. ([SQLite][3]) | PostgreSQL has much richer DDL. This is especially painful for ORMs, test suites, production migrations, and apps that evolve schemas frequently.                                                                                                                                      |
|  **3** | **Stored procedures, SQL-defined functions, variables, and parameterized views**                                | Users repeatedly ask for stored procedures/functions written in SQL rather than C/app code; related requests include variables, reusable database logic, parameterized views, and procedural blocks. The SQLite forum has direct “please add stored functions/procedures” requests, and Stack Overflow has long-running SQLite stored-procedure questions. ([SQLite][4])                                                                                                                   | PostgreSQL has PL/pgSQL, SQL functions, procedures, `DO` blocks, security-definer functions, etc. SQLite’s usual answer is “put that in the host language,” but that breaks down when multiple apps/languages share one database file or when users want logic stored with the schema. |
|  **4** | **Richer and stricter type system**                                                                             | Common asks: real `BOOLEAN`, `DATE`, `TIME`, `TIMESTAMP WITH TIME ZONE`, `INTERVAL`, `UUID`, `DECIMAL/NUMERIC`, enums/domains, custom types, better strictness defaults, and fewer surprising implicit conversions. SQLite uses dynamic typing; `STRICT` tables exist, but allowed strict types are limited to `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB`, and `ANY`. SQLite also has no separate Boolean or date/time storage class. ([SQLite][5])                                          | PostgreSQL’s typed model catches more bugs and maps more cleanly to application schemas. This gap is especially visible when developers prototype in SQLite and later port to Postgres.                                                                                                |
|  **5** | **Full Unicode case folding, collations, `ILIKE`/`CITEXT`-like behavior**                                       | Users want Unicode-aware case-insensitive search/sort by default, not just ASCII behavior. SQLite’s own quirks page says `upper()`/`lower()` only handle ASCII by default and full Unicode case folding requires ICU-enabled builds. ([SQLite][6])                                                                                                                                                                                                                                         | PostgreSQL can use collations and extensions such as `citext`. This is a major issue for apps with non-English text, names, search boxes, and case-insensitive uniqueness.                                                                                                             |
|  **6** | **Built-in server/remote/replication/distributed mode**                                                         | People want “SQLite, but remotely accessible,” plus replication, failover, edge replicas, managed backups, and safer multi-host usage. SQLite’s docs say it is embedded/local and that client/server systems can be better for networked or high-concurrency workloads; HN/Reddit discussions repeatedly frame SQLite as great until you need multi-client writes, remote access, or host migration. ([SQLite][1])                                                                         | PostgreSQL is built around networked clients, server processes, replication, roles, backups, and operations. The market has responded with LiteFS, Turso/libSQL, Cloudflare D1, SQLite Cloud, etc., but those are not “core SQLite.”                                                   |
|  **7** | **Users, roles, `GRANT`/`REVOKE`, row-level security, fine-grained permissions**                                | Users ask for auth, admin/user permissions, fine-grained access control, and RLS-like policies. SQLite’s omitted-features page explicitly says `GRANT` and `REVOKE` are not implemented because SQLite is an embedded database that relies on OS file permissions. Forum discussions on role-based authorization and “SQLite with Fido” show the demand and the mismatch with SQLite’s single-user model. ([SQLite][3])                                                                    | PostgreSQL has roles, grants, schemas, security-definer functions, and row security policies. ([PostgreSQL][7])                                                                                                                                                                        |
|  **8** | **Postgres-like JSONB, arrays, and nested-data indexing**                                                       | SQLite has JSON and JSONB, but users want PostgreSQL-grade JSONB behavior: fast object/array lookup, deep indexing, GIN-like indexes, richer operators, arrays, `array_agg`, `unnest`, and clean ORM portability. SQLite’s docs explicitly say its JSONB is not binary-compatible with PostgreSQL JSONB and does not claim O(1) lookup; most SQLite JSONB operations are O(N). ([SQLite][8])                                                                                               | PostgreSQL’s JSONB, arrays, operators, and indexes are a big reason people use it as an application database rather than just relational storage.                                                                                                                                      |
|  **9** | **Schemas/namespaces/search path**                                                                              | Users ask whether SQLite supports schemas in the PostgreSQL sense, especially for multi-tenant apps or multiple tables with the same logical names. Knex users have also requested multiple schemas with SQLite or hit portability issues with schema-qualified table names. ([Stack Overflow][9])                                                                                                                                                                                         | PostgreSQL schemas are a namespace and permissions boundary; SQLite has `main`, `temp`, and attached databases, but not the same schema model/search-path semantics.                                                                                                                   |
| **10** | **Materialized views and refresh semantics**                                                                    | Users want cached query results, `CREATE MATERIALIZED VIEW`, `REFRESH MATERIALIZED VIEW`, incremental refresh, and automatic refresh strategies. PostgreSQL materialized views persist results in a table-like form, while SQLite users generally emulate this with tables, triggers, or app code. ([PostgreSQL][10])                                                                                                                                                                      | This is a common analytics/reporting/performance feature. It is especially attractive in SQLite because local apps often need fast derived views without a heavy server.                                                                                                               |
| **11** | **Writable/updatable views and complete trigger support**                                                       | SQLite’s official omitted-features page says views are read-only, though `INSTEAD OF` triggers can emulate writes, and that SQLite supports row triggers but not statement triggers. The trigger docs also state that SQLite supports only `FOR EACH ROW`, not `FOR EACH STATEMENT`. ([SQLite][3])                                                                                                                                                                                         | PostgreSQL supports richer trigger models and updatable views/rules in more cases. This matters for audit logs, derived writes, validation, and compatibility with generated SQL.                                                                                                      |
| **12** | **Data-modifying CTEs and `RETURNING` usable as a relation**                                                    | Users want `WITH moved AS (DELETE/UPDATE/INSERT … RETURNING …) SELECT/INSERT … FROM moved`, which works in PostgreSQL-like workflows. SQLite forum threads show that `INSERT … RETURNING` works by itself but not inside CTEs/subqueries. ([SQLite][11])                                                                                                                                                                                                                                   | This enables compact, atomic “modify and then use the modified rows” SQL, audit logging, archiving, move-between-table operations, and ORM portability.                                                                                                                                |
| **13** | **SQL `MERGE`**                                                                                                 | Users ask for PostgreSQL/standard-style `MERGE` to conditionally insert/update/delete from a source relation. A SQLite forum request explicitly frames it as closing a gap with PostgreSQL 15 and abstraction libraries; PostgreSQL docs describe `MERGE` as a single statement for conditional `INSERT`, `UPDATE`, or `DELETE`. ([SQLite][12])                                                                                                                                            | SQLite has UPSERT, but `MERGE` is broader and more portable for ETL/sync workloads.                                                                                                                                                                                                    |
| **14** | **`LATERAL` joins / `CROSS APPLY`**                                                                             | SQLite has had active forum work/discussion around LATERAL; users cite PostgreSQL compatibility and use cases such as “top N rows per left-side row,” avoiding repeated expressions, and table-valued functions. ([SQLite][13])                                                                                                                                                                                                                                                            | PostgreSQL’s `LATERAL` is powerful for per-row subqueries, JSON expansion, top-N-per-group, and complex report queries.                                                                                                                                                                |
| **15** | **`DEFAULT` as an expression/value in `INSERT`/`UPDATE`**                                                       | Users want `INSERT INTO t(a,b,c) VALUES (10, DEFAULT, DEFAULT)` and `UPDATE t SET col = DEFAULT`. SQLite forum discussion shows Richard Hipp noting that PostgreSQL, MySQL, SQL Server, and Oracle support this, and that SQLite “probably should too,” though it is a substantial change. ([SQLite][14])                                                                                                                                                                                  | It improves bulk inserts, generated SQL, partial record construction, and cross-database compatibility.                                                                                                                                                                                |
| **16** | **Postgres convenience syntax: `DISTINCT ON`, `WITH ORDINALITY`, more `generate_series`-style table functions** | SQLite’s quirks page explicitly says SQLite supports `DISTINCT` but not PostgreSQL’s `DISTINCT ON`; forum users also ask about order/ordinality semantics comparable to Postgres `WITH ORDINALITY`. ([SQLite][6])                                                                                                                                                                                                                                                                          | These are not foundational features, but they reduce SQL rewrites for apps that support both SQLite and Postgres.                                                                                                                                                                      |
| **17** | **Advanced indexes: `INCLUDE`, GIN/GiST/BRIN-like families, trigram indexes, JSON/array indexes**               | Users ask for PostgreSQL-style `INCLUDE` columns on unique covering indexes; a SQLite forum request says this would bring parity with PostgreSQL and avoid index+table I/O. Trigram-index requests also appear, often framed around PostgreSQL’s `pg_trgm`. ([SQLite][15])                                                                                                                                                                                                                 | SQLite has many useful indexing features, but Postgres has a much broader index-method ecosystem for search, JSON, ranges, geospatial-like patterns, and huge tables.                                                                                                                  |
| **18** | **Vector search / embeddings in core or a blessed extension**                                                   | This has become a newer, very current request area: users want SQLite to act like a local-first vector database for RAG, semantic search, and edge AI. The SQLite forum has a dense-vector-search thread; `sqlite-vec`, SQLite-Vector, Turso vector search, and LangChain integrations show strong ecosystem demand, but it is extension-led rather than core. ([SQLite][16])                                                                                                              | PostgreSQL has the widely used `pgvector` ecosystem. For SQLite, the request is usually “make vector search portable, easy, and official-feeling.”                                                                                                                                     |
| **19** | **Sequences and richer identity-column semantics**                                                              | Users sometimes want standalone sequences, shared counters across tables, `GENERATED … AS IDENTITY`, and behavior closer to PostgreSQL sequences. A Stack Overflow SQLite sequence question asks for IDs unique across multiple tables; PostgreSQL documents identity columns as generated from implicit sequences. ([Stack Overflow][17])                                                                                                                                                 | SQLite’s `INTEGER PRIMARY KEY`/rowid model is simple and fast, but not equivalent to Postgres sequences or identity columns.                                                                                                                                                           |
| **20** | **Planner statistics portability, richer `EXPLAIN ANALYZE`, and optimizer controls**                            | Advanced users ask for ways to reproduce production query plans locally and manage/import statistics. A 2026 SQLite forum request asks for something analogous to PostgreSQL 18’s stats-restore functions. ([SQLite][18])                                                                                                                                                                                                                                                                  | Postgres exposes extensive planner statistics and plan inspection. SQLite is simpler, but production users increasingly want repeatable planning, diagnostics, and tuning tools.                                                                                                       |
| **21** | **A larger built-in “standard library” of SQL functions**                                                       | Common asks include `stddev`, `variance`, richer math functions, regex, split/string table-valued functions, aggregates, and utility functions. SQLite forum posts ask for native math, variance/stddev, and split functions; Stack Overflow has a 47k-view standard-deviation question. ([SQLite][19])                                                                                                                                                                                    | PostgreSQL ships a broad function catalog and supports extensions. SQLite can add functions via host language or loadable extensions, but users want more batteries included.                                                                                                          |
| **22** | **Full-text search upgrades: ranking, stemming, trigram/fuzzy search, easier search indexes**                   | SQLite FTS is powerful, but people still ask about ranking, trigram search, fuzzy matching, and more Postgres-like search capabilities. Stack Overflow has a long-running SQLite FTS ranking question; the SQLite forum has a trigram-index request explicitly inspired by PostgreSQL. ([Stack Overflow][20])                                                                                                                                                                              | PostgreSQL’s `tsvector`, `pg_trgm`, dictionaries, ranking, and extension ecosystem make search more integrated.                                                                                                                                                                        |
| **23** | **Default-on foreign keys and stricter SQL mode**                                                               | Users often want SQLite to reject more “dubious SQL” by default: foreign keys on by default, stricter `GROUP BY`, fewer double-quoted-string surprises, stricter primary-key null behavior, and strict tables by default. SQLite’s quirks page documents foreign-key enforcement being off by default, permissive typing, non-standard aggregate behavior, and other compatibility quirks. ([SQLite][6])                                                                                   | PostgreSQL’s strictness catches bugs earlier. SQLite preserves legacy compatibility, which is good for existing apps but surprising for new apps.                                                                                                                                      |
| **24** | **Partitioning / table inheritance / large-table management**                                                   | This is a weaker SQLite request signal, but it appears in Postgres-comparison discussions for time-series, multi-tenant, and very large tables. PostgreSQL users rely on partitioning/inheritance-like patterns for big data and tenant isolation; SQLite users usually shard into separate files instead. ([Reddit][21])                                                                                                                                                                  | Not a natural SQLite-core feature, but it is a Postgres gap people notice when using SQLite for analytics or local caches with huge tables.                                                                                                                                            |
| **25** | **Encryption-at-rest in core**                                                                                  | Users ask for encrypted SQLite files without adopting SQLCipher, SEE, wrapper-specific hacks, or app-level encryption. SQLite forum and HN discussions show recurring interest; SQLCipher is a standalone fork that adds full database encryption. ([SQLite][22])                                                                                                                                                                                                                          | PostgreSQL usually relies on OS/storage/TLS/KMS layers and has server-side operational security patterns. SQLite’s “database is a file” model makes app-level encryption demand especially visible.                                                                                    |
| **26** | **Better remote-file / network-filesystem behavior**                                                            | Users want safe high-performance access to SQLite on NAS/SMB/remote filesystems, or a first-class remote proxy model. SQLite’s model is file-based; forum/GitHub discussions often end up building TCP proxy layers because direct remote file access can be slow or risky. ([GitHub][23])                                                                                                                                                                                                 | PostgreSQL’s network protocol solves this class of problem directly.                                                                                                                                                                                                                   |
| **27** | **Better vacuum/space-management ergonomics**                                                                   | Users ask why files do not shrink automatically, how to reclaim space, and how to avoid expensive `VACUUM` behavior. SQLite’s `VACUUM` docs say it copies the database into a temporary file and can require up to twice the database size in free disk space. ([SQLite][24])                                                                                                                                                                                                              | Postgres has its own vacuum complexity, but SQLite users often expect deleted rows to immediately shrink a single-file database.                                                                                                                                                       |
| **28** | **psql-like admin/introspection ergonomics**                                                                    | SQLite CLI is capable, but users often want richer meta-commands, introspection, explain tooling, scriptability, and a canonical “admin console” experience closer to `psql`. SQLite’s CLI docs show rich output modes and dot commands, while PostgreSQL’s `psql` docs describe extensive meta-command/script support. ([SQLite][25])                                                                                                                                                     | This is tooling rather than core engine, but it matters for production adoption.                                                                                                                                                                                                       |
| **29** | **More portable ORM/query-builder behavior**                                                                    | Many feature requests are not about one SQL feature; they are about making generated SQL portable between SQLite and Postgres. Examples include schemas, materialized views, migrations, returning-in-CTEs, default values, LATERAL, and SQL grammar differences. Knex and Laravel issues show this pattern clearly. ([GitHub][26])                                                                                                                                                        | SQLite is widely used in tests/dev, while Postgres is used in production. The closer SQLite can mimic Postgres SQL, the less conditional ORM code people need.                                                                                                                         |
| **30** | **Date/time semantics closer to Postgres**                                                                      | Lower-volume but real requests include transaction-stable `now`, timestamp/time-zone precision, and less surprising date/time storage. SQLite has no dedicated date/time storage class; a SQLite forum thread discusses differences between SQLite and PostgreSQL around `'now'` stability. ([SQLite][5])                                                                                                                                                                                  | PostgreSQL has rich temporal types and stable timestamp semantics. SQLite’s flexible text/real/integer model is lightweight but requires app discipline.                                                                                                                               |

## The clearest top tier

The strongest, most repeated requests are:

1. **Concurrent writers / row-level locking / “database is locked” relief.** This is the biggest blocker for people trying to use SQLite as a primary web/app database instead of Postgres.
2. **Full schema migrations.** SQLite’s limited `ALTER TABLE` creates real pain for ORMs and evolving apps.
3. **Stored procedures / SQL-defined reusable logic.** The demand is persistent, even though it cuts against SQLite’s host-language philosophy.
4. **Stricter/richer typing.** `STRICT` tables helped, but users still want Postgres-like date/time, UUID, decimal, arrays, enums, domains, and fewer coercion surprises.
5. **Unicode/collation/search improvements.** This one is easy to underestimate until you build multilingual products.
6. **Security/roles/RLS and network/server/replication features.** These are highly requested, but they also most directly conflict with SQLite’s embedded design.

## Features people ask for that SQLite partially has already

A few older complaints are now partly outdated. SQLite now has `DROP COLUMN` but with important restrictions; it has `STRICT` tables, but with a small allowed type set; it has JSONB, but not PostgreSQL-compatible JSONB or O(1)-style lookup; it has `RETURNING`, but not as a CTE/subquery relation; it has FTS, but people still want richer ranking/trigram/fuzzy behavior. ([SQLite][27])

## My practical ranking by product opportunity

If someone were building “SQLite++” or a Postgres-compatible SQLite layer, the highest-value roadmap would be:

**First:** better migrations, concurrent-writer primitives, SQL-defined functions/procedures, Unicode collations, and a strict/typed profile.

**Second:** Postgres-portability syntax: data-modifying CTEs, `LATERAL`, `MERGE`, `DEFAULT` in values, schemas/namespaces, `DISTINCT ON`, and `WITH ORDINALITY`.

**Third:** optional advanced modules: vector search, materialized views, JSON/array indexing, RLS-like policy hooks, encryption-at-rest, and a larger function/extension standard library.

The big strategic tension is that the most requested features are also the ones most likely to make SQLite less SQLite-like. The sweet spot would be optional, opt-in features that preserve the tiny embedded default while making “SQLite as a local-first/Postgres-adjacent application database” much easier.
