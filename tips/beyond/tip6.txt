Here’s the best signal-weighted ranking I’d use in 2026. I sampled official SQLite docs and forum threads, Stack Overflow/DBA, GitHub issues/projects, Hacker News/Reddit-style discussions, and indexed X/forum material. Caveat: there is no official SQLite “most requested features” leaderboard, and large parts of X/Quora are not reliably crawlable or indexable, so this is a qualitative ranking by repeated public demand, size of pain, and Postgres-gap importance.

SQLite is also a moving target: the current SQLite homepage lists **3.53.1, released May 5, 2026**, and 3.53.0 recently added more `ALTER TABLE` support, including adding/removing `NOT NULL` and `CHECK` constraints. So a few old “missing feature” complaints are now partly stale. ([SQLite][1])

## Ranked feature gaps people ask for

### 1. True multi-writer concurrency / MVCC-like write scaling

**Demand: very high. Postgres gap: huge.**

This is the single biggest recurring pain once people push SQLite beyond local/single-writer workloads. SQLite is excellent at embedded/local storage, but the core design still centers on many readers and limited writer concurrency. SQLite’s own docs say it supports “unlimited” simultaneous readers but only one writer at a time, and recommend client/server databases for many concurrent writers or many machines directly accessing the same database. ([SQLite][2])

People ask for variations of this constantly: multiple writers, fewer `database is locked` errors, MVCC, row-level/page-level write isolation, a mainline `BEGIN CONCURRENT`, or Turso/libSQL-like behavior in core. In the SQLite forum, a 2025 thread explicitly asks for “out of the box ability to have multiple writers,” while responses point to WAL limits, the experimental `BEGIN CONCURRENT` branch, and the reality that SQLite is not a server database. ([SQLite][3])

**Typical asks:**

* Multiple concurrent writers.
* Safer long-running writes.
* Less global write-locking.
* Mainline support for `BEGIN CONCURRENT`.
* MVCC semantics closer to Postgres.
* Better lock diagnostics.

**Current workaround:** WAL mode, short transactions, application-level write queues, sharding, libSQL/Turso, dqlite/rqlite, LiteFS/Litestream, or moving to Postgres.

---

### 2. Built-in client/server or remote access mode

**Demand: very high. Postgres gap: huge.**

A closely related but distinct ask is: “Can SQLite be accessed over the network like Postgres?” The canonical answer is no: SQLite is an embedded library and database file format, not a network server. SQLite’s docs explicitly warn against many clients on a network filesystem because of latency, locking bugs, and potential corruption risk. ([SQLite][2])

This shows up in DBA/Stack Overflow discussions and tool feature requests. A DBA StackExchange answer notes that SQLite has no network endpoint and that a Postgres-style server is more appropriate for high-concurrency networked applications. A 2025 SQLiteStudio GitHub request asked for TCP-based remote SQLite querying because SMB/network-share access was dramatically slower. ([Database Administrators Stack Exchange][4])

**Typical asks:**

* A built-in SQLite server daemon.
* Postgres wire-protocol compatibility.
* HTTP API access to SQLite.
* Safe remote GUI browsing.
* Better behavior over SMB/NFS/cloud mounts.

**Current workaround:** Datasette, LiteFS, rqlite, dqlite, Turso/libSQL, application APIs, `sqlite3` over SSH, or just Postgres.

---

### 3. More complete, migration-friendly `ALTER TABLE`

**Demand: very high. Postgres gap: very large.**

This is one of the most visible developer-productivity gaps. SQLite’s own `ALTER TABLE` docs say support remains limited: rename table, rename column, add column, and drop column. For many other schema changes, the documented method is still the classic create-copy-drop-rename rebuild procedure. ([SQLite][5])

The 2026 release improved this by allowing addition/removal of `NOT NULL` and `CHECK` constraints, which removes some historical pain. But many common operations still feel clumsy compared with Postgres: altering column type, changing defaults, reordering columns, adding/dropping foreign-key constraints, modifying primary keys, and doing safe constraint migrations without table rebuilds. ([SQLite][6])

**Typical asks:**

* `ALTER COLUMN TYPE`.
* `ALTER COLUMN SET/DROP DEFAULT`.
* `ADD/DROP CONSTRAINT`, especially foreign keys.
* Easier primary-key and unique-constraint changes.
* Less need for table rebuilds.
* Better ORM migration compatibility.

**Current workaround:** ORM “batch mode,” migration libraries, `CREATE TABLE new AS SELECT...`, dump/reload, or using tools like `sqlite-utils`.

---

### 4. Stronger native type system and Postgres-like data types

**Demand: very high. Postgres gap: very large.**

SQLite’s flexible typing is beloved by some users and hated by others. Officially, SQLite has storage classes like `NULL`, `INTEGER`, `REAL`, `TEXT`, and `BLOB`; booleans are integers, dates/times are stored as text/real/integer values, and `VARCHAR(n)` length is not enforced. ([SQLite][7])

A lot of requests are not merely “make SQLite statically typed.” They are more subtle: support common type names and semantics in `STRICT` tables, real `BOOLEAN`, real `DATE`/`TIMESTAMP`, exact `DECIMAL/NUMERIC`, enums, arrays, intervals, ranges, custom types, and stricter defaults. Forum users have specifically asked for `BOOLEAN` mapping in strict tables, better strict-mode defaults, and exact decimal handling for money-like ORM use cases. ([SQLite][8])

Postgres has a much richer native type system: booleans, dates, timestamps, intervals, JSON/JSONB, money, arrays, enums, ranges, composite types, and user-defined types. That gap matters especially for teams using SQLite in dev/test and Postgres in production. ([PostgreSQL][9])

**Typical asks:**

* Native `BOOLEAN`.
* Native `DATE`, `TIME`, `TIMESTAMP`, `INTERVAL`.
* Exact `DECIMAL`/`NUMERIC`.
* Enforced `VARCHAR(n)`.
* `ENUM`.
* Arrays.
* Custom/user-defined SQL types.
* “Strict by default” mode.

**Current workaround:** `STRICT` tables, `CHECK` constraints, generated columns, app-level validation, ORMs, decimal extensions, or using Postgres when exact typing matters.

---

### 5. Built-in encryption at rest

**Demand: high. Postgres gap: medium, but SQLite-specific pain is high.**

Because SQLite databases are often single files copied between devices, embedded in apps, synced to cloud storage, or shipped with mobile/desktop software, file-level encryption is a frequent request. SQLite has an official SQLite Encryption Extension, but it is licensed/commercial; the public SQLite core cannot read or write encrypted database files by itself. ([SQLite][10])

**Typical asks:**

* Built-in encrypted database files.
* Open, bundled SQLCipher-like support.
* Per-database password/key API.
* Better encrypted backups.
* Encryption support in default drivers.

**Current workaround:** SQLCipher, SQLite SEE, OS/full-disk encryption, app-layer encryption, or custom VFS implementations.

---

### 6. Postgres-like JSONB indexing and faster JSON document operations

**Demand: high and rising. Postgres gap: large.**

SQLite now has JSONB, but it is not Postgres JSONB. SQLite’s docs say its JSONB format is not binary-compatible with Postgres and that most operations are still O(N), not O(1). ([SQLite][11])

The most common request is not merely “support JSON”; SQLite already has good JSON functions. The ask is **arbitrary JSON indexing**: GIN-like indexes, containment queries, existence queries, jsonpath indexing, and document-style lookup performance closer to Postgres. Community comments often point out that SQLite expression indexes work if you know the exact JSON path in advance, but they do not replace generalized multi-key JSON indexing. ([Hacker News][12])

Postgres JSONB supports GIN indexes for containment, key existence, and jsonpath-style queries, which is the comparison people usually have in mind. ([PostgreSQL][13])

**Typical asks:**

* GIN-like indexes for JSON.
* Index arbitrary keys and nested paths.
* Fast `@>`-style containment.
* Better jsonpath query support.
* O(1)-ish JSONB key lookup.
* Multi-valued indexes for JSON arrays.

**Current workaround:** generated columns + indexes, expression indexes, FTS tricks, manual side tables, extensions, or Postgres.

---

### 7. Full Unicode-aware text handling and collations

**Demand: high. Postgres gap: large for international apps.**

SQLite’s built-in `NOCASE` collation is ASCII-only. Official docs explain that full Unicode case folding is not attempted in core partly because the required tables are large and Unicode case rules change. ([SQLite][7])

This gap shows up whenever people build multilingual search, case-insensitive login/email matching, sorting, `lower()`/`upper()` behavior, accent-insensitive search, or natural-language text tools. A SQLite forum thread has a user saying they cannot search properly when text is not English, and Richard Hipp explains the library-size and Unicode-version tradeoffs. ([SQLite][14])

**Typical asks:**

* Unicode `NOCASE`.
* Unicode-aware `lower()` / `upper()`.
* Built-in ICU support.
* `ILIKE`.
* Accent-insensitive comparison.
* Locale-aware sort order.
* Natural sort.

**Current workaround:** ICU extension, custom collations, normalized shadow columns, app-level normalization, FTS tokenizers.

---

### 8. Stored procedures, SQL-defined functions, and procedural language support

**Demand: high but divisive. Postgres gap: large.**

A long-running request is the ability to define stored procedures or SQL functions inside the database, rather than registering C/application functions. Forum users have explicitly asked for stored functions/procedures similar to MariaDB/Postgres-style server databases. The counterargument from SQLite regulars is that many stored-procedure benefits are about reducing client/server round trips, while SQLite is in-process. ([SQLite][15])

Still, the ask persists because stored logic helps with:

* Shared logic across languages.
* Migrations.
* Auditing.
* Replicated/distributed SQLite deployments.
* Encapsulation.
* Reducing ORM/application duplication.

**Typical asks:**

* `CREATE FUNCTION ... LANGUAGE SQL`.
* `CREATE PROCEDURE`.
* Variables and control flow.
* Packaged database-side business logic.
* SQL macros.
* Trigger-adjacent reusable functions.

**Current workaround:** application-defined functions, loadable extensions, triggers, views, C/Rust extensions, or external projects that emulate stored procedures.

---

### 9. Materialized views

**Demand: medium-high. Postgres gap: large for analytics/caching.**

SQLite has views, but not true materialized views. Stack Overflow answers still state plainly that SQLite does not support materialized views; users emulate them with tables refreshed by triggers or jobs. ([Stack Overflow][16])

Postgres has `CREATE MATERIALIZED VIEW` and `REFRESH MATERIALIZED VIEW`, which gives users a familiar model for cached query results. ([PostgreSQL][17])

**Typical asks:**

* `CREATE MATERIALIZED VIEW`.
* `REFRESH MATERIALIZED VIEW`.
* Incremental refresh.
* Indexes on materialized views.
* Trigger-maintained materialized views.

**Current workaround:** manual summary tables, triggers, scheduled refresh, `CREATE TABLE AS SELECT`, or app-side caching.

---

### 10. Schemas/namespaces inside a database

**Demand: medium-high. Postgres gap: large for multi-module apps.**

SQLite uses `main`, `temp`, and attached databases as schema-like qualifiers, but it does not have Postgres-style schemas/namespaces inside one database. Stack Overflow discussions answer this by saying SQLite “schema names” are attached database names, not Postgres-like namespaces. ([Stack Overflow][18])

Postgres schemas let users organize objects under names like `sales.orders`, `auth.users`, and `analytics.events`, with ownership, search paths, and permissions. ([PostgreSQL][19])

**Typical asks:**

* `CREATE SCHEMA`.
* `schema.table` namespaces in one file.
* `search_path`.
* Easier modularization.
* Multi-tenant namespaces.
* Avoiding table-name prefixes.

**Current workaround:** table prefixes, attached databases, separate SQLite files, or Postgres.

---

### 11. Data-modifying CTEs and composable `RETURNING`

**Demand: medium-high among advanced SQL users. Postgres gap: significant.**

SQLite supports `RETURNING`, but a frequent advanced request is to use `INSERT/UPDATE/DELETE ... RETURNING` as a table-producing expression inside a CTE or subquery. In a forum thread, Richard Hipp states that DML statements cannot be used in subqueries, while users explain audit-log and pipeline use cases. ([SQLite][20])

Postgres allows auxiliary statements in `WITH`, including `INSERT`, `UPDATE`, `DELETE`, and `MERGE`, which makes multi-step mutation pipelines much easier. ([PostgreSQL][21])

**Typical asks:**

* `WITH inserted AS (INSERT ... RETURNING ...) SELECT ...`.
* Use `RETURNING` output in another insert.
* Audit-log pipelines.
* Chained mutations.
* Table-valued DML expressions.

**Current workaround:** temporary tables, multiple statements in transactions, app-side capture of returned rows.

---

### 12. Richer built-in function library: date/time, regex, math, arrays, statistics

**Demand: medium-high. Postgres gap: broad.**

SQLite intentionally keeps the core small, but many users want more Postgres-like built-ins. Date/time handling is especially common: transaction-stable `now`, timezone handling, interval arithmetic, parsing/formatting, date truncation, and richer extraction. Forum users have compared SQLite’s `now` semantics with Postgres and asked for transaction-stable behavior. ([SQLite][22])

Community discussions also mention missing array support, thinner date manipulation, regex extraction/replacement, and common utility functions that Postgres users expect out of the box. ([Hacker News][23])

**Typical asks:**

* `date_trunc`.
* Timezone-aware timestamps.
* Transaction-stable `now()`.
* Better interval arithmetic.
* Regex match/extract/replace.
* Array functions.
* More math/statistical aggregates.
* More string utilities.

**Current workaround:** extensions, user-defined functions, application code, sqlean-like extension bundles.

---

### 13. `LATERAL` joins / `APPLY`

**Demand: medium among SQL power users and ORM authors. Postgres gap: meaningful.**

This is not a mass-market request, but it comes up repeatedly among people writing complex SQL or porting from Postgres. SQLite has had a `lateral-join` branch, and forum users have given concrete use cases like top-N-per-row queries and Postgres compatibility. ([SQLite][24])

**Typical asks:**

* `LATERAL` subqueries.
* `CROSS APPLY` / `OUTER APPLY`.
* Cleaner correlated subqueries in `FROM`.
* Better ORM compatibility.

**Current workaround:** correlated subqueries, window functions, CTE rewrites, temp tables.

---

### 14. Users, roles, `GRANT`/`REVOKE`, and row-level security

**Demand: medium. Postgres gap: huge, but intentionally outside SQLite’s normal design.**

SQLite’s official “omitted features” page lists `GRANT` and `REVOKE` as unsupported because SQLite relies on normal filesystem permissions. ([SQLite][25])

That is fine for embedded apps, but not for multi-user query surfaces, dashboards, local-first sync tools, hosted SQLite, or AI/agent systems that expose SQL. Forum users have asked about role-based or row-level authorization, and answers point toward views, authorizer callbacks, triggers, and application-level enforcement. ([SQLite][26])

Postgres row-level security is much more formal: policies can restrict which rows are visible or modifiable by role and command. ([PostgreSQL][27])

**Typical asks:**

* `CREATE ROLE`.
* `GRANT` / `REVOKE`.
* Row-level security.
* Column-level permissions.
* Read-only users.
* Policy-based access.

**Current workaround:** OS permissions, separate DB files, views, triggers, `sqlite3_set_authorizer`, app-layer ACLs, hosted wrappers.

---

### 15. Native replication, change data capture, sync, and high availability

**Demand: medium, rising with local-first apps. Postgres gap: large.**

SQLite’s core does not provide Postgres-style logical replication, CDC slots, read replicas, failover, or server-side streaming. In a SQLite forum thread, a user asks for host-to-host transaction replication and change tracking; responses point out that distributed replication is outside SQLite’s core purpose. ([SQLite][28])

Postgres-style CDC/logical replication streams row changes and supports selective replication and integration patterns that SQLite users often want for sync, audit, and distributed systems. ([PlanetScale][29])

**Typical asks:**

* Built-in replication.
* Change feeds.
* Logical decoding-style API.
* Conflict resolution.
* Multi-primary sync.
* Read replicas.
* Point-in-time recovery.

**Current workaround:** WAL tailing, session extension, LiteFS, Litestream, rqlite, dqlite, Turso/libSQL, custom sync layers.

---

### 16. Richer trigger support and writable views

**Demand: medium. Postgres gap: moderate.**

SQLite’s omitted-features page lists no `FOR EACH STATEMENT` triggers and says views are read-only, although `INSTEAD OF` triggers can emulate writes to views. ([SQLite][25])

**Typical asks:**

* Statement-level triggers.
* More predictable trigger ordering.
* Transition tables.
* Directly updatable views.
* More Postgres-like trigger semantics.

**Current workaround:** row-level triggers, `INSTEAD OF` triggers on views, app logic.

---

### 17. SQL-standard DML conveniences: `MERGE`, `DEFAULT` in `VALUES`, `TRUNCATE`, comments

**Demand: medium. Postgres gap: moderate.**

These are smaller, but they appear often in portability complaints.

One concrete SQLite forum feature request asks for column-level `DEFAULT` inside `INSERT ... VALUES`, such as inserting default values for some columns without omitting them from the column list. ([SQLite][30])

Postgres also has `MERGE`, which performs conditional insert/update/delete-style logic after joining source and target rows. SQLite has UPSERT, but not full SQL `MERGE`. ([PostgreSQL][31])

**Typical asks:**

* `DEFAULT` as a value expression in `INSERT`.
* `MERGE`.
* `TRUNCATE`.
* `COMMENT ON TABLE/COLUMN`.
* `DISTINCT ON`.
* `NULLS FIRST/LAST` parity in all contexts.
* More Postgres-compatible syntax.

**Current workaround:** omit columns, use UPSERT, use metadata tables for comments, emulate `MERGE` with multiple statements.

---

### 18. Foreign keys enabled and strictness defaults

**Demand: medium. Postgres gap: small-to-medium, but developer pain is real.**

SQLite supports foreign keys, but enforcement historically has been off by default unless enabled per connection or compiled differently. Forum users have asked why foreign-key enforcement is not stored as a database-file default, and community discussions repeatedly warn newcomers to enable it. ([SQLite][32])

**Typical asks:**

* Foreign keys on by default.
* Per-database setting persisted in the file.
* A “strict SQLite edition.”
* Strict tables by default.
* Safer defaults for production.

**Current workaround:** `PRAGMA foreign_keys = ON` on every connection, compile-time options, connection wrappers, ORM settings.

---

### 19. Standalone sequences and richer identity behavior

**Demand: low-medium. Postgres gap: moderate.**

SQLite has `rowid`, `INTEGER PRIMARY KEY`, and `AUTOINCREMENT`, but not standalone sequence objects like Postgres `CREATE SEQUENCE`. Postgres sequences are independent schema objects that generate numeric values. ([PostgreSQL][33])

This matters for multi-table numbering, custom ID allocation, and portability from Postgres/Oracle-style schemas.

**Typical asks:**

* `CREATE SEQUENCE`.
* `nextval()` / `currval()`.
* Identity columns closer to SQL standard.
* Shared counters across tables.

**Current workaround:** sequence tables, triggers, application-side ID generation, UUIDs.

---

### 20. Geospatial features closer to PostGIS

**Demand: low-medium overall, high in GIS niches. Postgres gap: huge.**

SQLite has SpatiaLite and R-Tree support, but users comparing to PostGIS often want richer geospatial features in a more standard/bundled way. SpatiaLite is powerful, but PostGIS remains the reference point for advanced GIS workloads. ([Gaia GIS][34])

**Typical asks:**

* PostGIS-like spatial types.
* More built-in geometry/geography functions.
* Raster/point-cloud-like capabilities.
* Easier extension packaging.
* Better multi-user GIS workflows.

**Current workaround:** SpatiaLite, GeoPackage, app-level GIS libraries, PostGIS.

---

### 21. Vector search / ANN in core

**Demand: emerging, currently medium in AI apps but not classic SQLite community-wide.**

This has grown quickly because SQLite is attractive for local AI apps. Projects such as `sqlite-vec` provide vector search as an extension, but people increasingly ask whether vector similarity search should be first-class or easier to bundle. ([GitHub][35])

**Typical asks:**

* Vector column type.
* Approximate nearest neighbor indexes.
* Cosine/dot/L2 search.
* Hybrid FTS + vector search.
* Easier extension distribution.

**Current workaround:** `sqlite-vec`, `sqlite-vss`, external vector DBs, Postgres with pgvector.

---

### 22. More advanced indexes and query execution features

**Demand: low-medium from general users, high from performance experts. Postgres gap: broad.**

SQLite has many useful index features, but Postgres has a much wider set: GIN, GiST, BRIN, hash indexes, advanced operator classes, parallel query, richer statistics, and more planner options. SQLite users usually do not request all of these by name, but they surface indirectly as JSON indexing, full-text ranking, complex analytics, geospatial, and large-query performance requests.

**Typical asks:**

* GIN/GiST-like index families.
* Multi-valued indexes.
* Better statistics.
* More join algorithms.
* Parallel query execution.
* Better plans for analytical workloads.

**Current workaround:** expression indexes, partial indexes, covering indexes, FTS5, R-Tree, manual denormalization, or Postgres/DuckDB for analytics.

---

### 23. Better extension packaging and “batteries included” distributions

**Demand: low-medium but very practical.**

Many missing features exist as extensions: ICU, SQLCipher, SpatiaLite, decimal math, regex, vector search, UUID functions, extra math/string functions. The recurring complaint is that shipping extensions across macOS, Windows, Linux, iOS, Android, Python, Node, Rust, Go, WASM, and serverless environments can be painful.

**Typical asks:**

* Official extension registry.
* Easier extension loading in constrained runtimes.
* A “SQLite batteries included” distribution.
* Standard bundles for ICU, regex, decimal, crypto, UUID, vector, spatial.
* Better language-driver support.

**Current workaround:** sqlean-like bundles, static linking, platform-specific builds, libSQL/Turso distributions, custom compiled SQLite.

---

### 24. Better admin, observability, and operational tooling

**Demand: lower as a core feature, but common among teams operationalizing SQLite.**

Once SQLite is used in production services, people want Postgres-like operational affordances: lock visibility, active queries, replication health, slow-query logs, remote inspection, online backups, and GUI tooling. This is often less a request for SQLite core and more a request for the ecosystem. The SQLiteStudio remote-access request is a good example: the pain is operational, not SQL syntax. ([GitHub][36])

**Typical asks:**

* Better lock/debug introspection.
* Slow-query logging.
* Production monitoring.
* Remote browser/GUI support.
* Easier online backup and restore UX.
* Better migration/backup tooling.

**Current workaround:** application metrics, `sqlite3_trace_v2`, backup API, custom logs, Datasette, GUI tools, external wrappers.

---

## Features that people still mention but are partly outdated

A few old “SQLite lacks X” claims should be treated carefully now:

**RIGHT and FULL OUTER JOIN** should not be ranked as a major current missing feature. SQLite’s current grammar includes `RIGHT` and `FULL` join operators. ([SQLite][5])

**Adding/removing `NOT NULL` and `CHECK` constraints** is no longer fully missing as of SQLite 3.53.0, though broader constraint and column alteration remains much more limited than Postgres. ([SQLite][6])

**JSON support** is not missing; SQLite has JSON functions and JSONB. The real remaining gap is Postgres-like JSONB indexing, containment, and lookup performance. ([SQLite][11])

## The practical top 10

My condensed ranking:

1. **True multi-writer concurrency / MVCC**
2. **Client/server or safe remote access mode**
3. **More complete `ALTER TABLE` and migrations**
4. **Stronger native types and strict-mode ergonomics**
5. **Built-in encryption at rest**
6. **Postgres-like JSONB indexing**
7. **Unicode-aware text/collation/search**
8. **Stored procedures / SQL-defined functions**
9. **Materialized views**
10. **Schemas/namespaces**

The strategic pattern is pretty clear: SQLite users are not mostly asking for obscure SQL bells and whistles. They are asking for the features that appear when SQLite is used as “almost Postgres”: more concurrent writes, remote access, safer migrations, stronger types, richer indexing, international text, and production-grade operational features.
