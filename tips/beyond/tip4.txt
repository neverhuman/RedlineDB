## Bottom line

The **most requested missing SQLite features** are clustered around one big theme: people love SQLite’s zero-admin, single-file model, but they increasingly want it to behave more like a small PostgreSQL for web apps, multi-user apps, reactive apps, and ORM-backed apps.

I ranked the list below by **observed demand across public SQLite Forum threads, StackOverflow, Reddit/Hacker News-style discussions, current docs, web-visible X results, and Postgres-comparison discussions**. This is not a literal census of every post on the internet. Quora pages were not accessible to my browsing tool, and X search is only partly visible, so I weighted them lightly. The strongest signals came from the **SQLite Forum**, **StackOverflow**, **Reddit/HN**, official docs, and recurring ORM/framework pain points.

One important freshness note: SQLite is currently at **3.53.1**, released May 5, 2026, and 3.53.0 recently improved `ALTER TABLE` by allowing adding/removing `NOT NULL` and `CHECK` constraints, so some older migration complaints are partly obsolete. ([SQLite][1])

# Ranked list of requested SQLite gaps

## 1. More write concurrency: multiple writers, row-level locks, `SELECT … FOR UPDATE`

**Demand level: extremely high.** This is the most recurring gap whenever people compare SQLite with PostgreSQL for web apps, queues, collaborative apps, job systems, and write-heavy services.

SQLite’s official model is clear: separate connections can read and write, but **writes are serialized**; “there can only be a single writer at a time,” and write-capable connections “have to take turns.” ([SQLite][2]) WAL mode helps because readers and a writer can proceed concurrently, but the WAL documentation still says there can only be **one writer at a time**. ([SQLite][3])

What people ask for:

| Requested feature                       | What they really want                                 |
| --------------------------------------- | ----------------------------------------------------- |
| Multiple concurrent writers             | Less `database is locked`, better web-server behavior |
| Row-level locks                         | PostgreSQL-like concurrent updates to different rows  |
| `SELECT … FOR UPDATE`                   | Safe job-queue / reservation / inventory patterns     |
| `FOR NO KEY UPDATE`, `SKIP LOCKED`      | Queue consumers, background workers                   |
| `BEGIN CONCURRENT` in mainstream SQLite | Optimistic multi-writer transactions                  |
| Better busy handling                    | Fewer surprising lock failures under load             |

Evidence is broad: a 2025 SQLite Forum thread directly asks why SQLite cannot have multiple writers, StackOverflow has long-running high-view concurrency questions, and public discussion keeps revisiting `SELECT … FOR UPDATE` as a missing feature. ([SQLite][4]) PostgreSQL, by contrast, documents row-level locks and `SELECT FOR UPDATE` / related lock modes as normal concurrency tools. ([PostgreSQL][5])

**Why SQLite lacks it:** SQLite’s design is embedded, file-based, and serverless: it reads/writes ordinary disk files directly rather than coordinating through a long-running server process. ([SQLite][6])

**Likelihood in core SQLite:** Low to medium. Some experimental/forked approaches exist, but true PostgreSQL-style row-locking would be a major architectural change.

---

## 2. Stored procedures / stored functions / procedural SQL

**Demand level: very high.** This is one of the most explicit feature requests on the SQLite Forum.

People ask for:

| Requested feature                      | PostgreSQL analogue                                                                |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| `CREATE PROCEDURE`                     | `CREATE PROCEDURE`, `CALL`                                                         |
| SQL-language stored functions          | `CREATE FUNCTION … LANGUAGE SQL`                                                   |
| Procedural language                    | PL/pgSQL-like blocks, variables, loops                                             |
| Persistent database-side routines      | Reusable business logic inside the DB                                              |
| Procedure parameters and return values | PostgreSQL functions/procedures                                                    |
| Transactional procedures               | PostgreSQL procedures can perform transaction control in top-level `CALL` contexts |

The SQLite Forum has direct threads titled “Feature request: Stored Procedures” and “Request: stored functions/procedures.” Users argue that application-side functions are not equivalent when the same database is used by apps written in multiple languages, because business logic must be duplicated in Python, C, PHP, etc. ([SQLite][7]) PostgreSQL officially supports `CREATE PROCEDURE` and `CALL`. ([PostgreSQL][8])

**Why SQLite lacks it:** SQLite assumes the host application is the procedural language. Also, adding a procedural runtime would increase size, complexity, and security surface.

**Likelihood in core SQLite:** Medium-low. A minimalist SQL-procedure feature has been discussed, but a full PL/pgSQL equivalent seems unlikely.

## 3. Built-in replication, HA, sync, network access, and “server mode”

**Demand level: very high, but often outside SQLite’s core philosophy.**

A huge modern SQLite trend is: “I want SQLite’s simplicity, but I also want production-database deployment properties.” This shows up in discussions around LiteFS, Turso/libSQL, rqlite, Litestream, PocketBase, Rails/SQLite deployments, and “SQLite for web apps.”

People ask for:

| Requested feature                   | What people want                               |
| ----------------------------------- | ---------------------------------------------- |
| Native replication                  | Read replicas, failover, multi-node durability |
| Network-accessible SQLite           | Connect like PostgreSQL over TCP               |
| Managed SQLite                      | Cloud-hosted SQLite with backups and scaling   |
| Multi-primary or distributed writes | Fewer single-node constraints                  |
| Streaming WAL / WAL archiving       | Postgres-like operational durability           |
| Point-in-time recovery              | Production ops comfort                         |
| Cross-host concurrent access        | Use one database across services/machines      |

The official design explains why this is not native: SQLite is an in-process, serverless library and has no separate server process. ([SQLite][6]) WAL mode also explicitly does not work over network filesystems because all processes must be on the same host. ([SQLite][3]) Public discussion around moving from SQLite to PostgreSQL, or wrapping SQLite with replication/network services, consistently centers on this gap. ([GitHub][9])

**Why SQLite lacks it:** This is essentially a different product category. SQLite is closer to “a database file plus library” than “a server database.”

**Likelihood in core SQLite:** Low. More likely via forks/extensions/services: libSQL/Turso, LiteFS, Litestream, rqlite, dqlite, mvSQLite-like projects.

---

## 4. More complete `ALTER TABLE` and migration support

**Demand level: very high.** Developers hit this constantly through ORMs and migrations.

SQLite now supports more DDL than it used to, including table/column rename, add/drop column, and as of 3.53.0, adding/removing `NOT NULL` and `CHECK` constraints. ([SQLite][1]) But the official docs still describe SQLite’s `ALTER TABLE` as limited, and common operations often require a create-copy-drop-rename rebuild pattern. ([SQLite][10])

People still ask for:

| Requested feature                                  | Current pain                          |
| -------------------------------------------------- | ------------------------------------- |
| Change column type                                 | Often requires table rebuild          |
| Change default expression                          | Often requires schema surgery/rebuild |
| Add/drop primary key                               | Requires rebuild                      |
| Add/drop unique constraint                         | Requires rebuild                      |
| Add/drop foreign key constraint                    | Often rebuild/manual schema editing   |
| Reorder columns                                    | Requires rebuild                      |
| Rename/move across schemas                         | Not supported in the PostgreSQL sense |
| Safer migration primitives                         | Avoid `PRAGMA writable_schema` hacks  |
| `ALTER COLUMN TYPE`, `SET DEFAULT`, `DROP DEFAULT` | PostgreSQL-style migration ergonomics |

Official docs list restrictions on `ADD COLUMN`, including no `PRIMARY KEY`/`UNIQUE`, restricted defaults, and other limitations. ([SQLite][10]) `DROP COLUMN` also fails if the column is primary key, unique, indexed, referenced by constraints, used in generated columns, triggers, views, and more. ([SQLite][10]) StackOverflow has long-running, high-view questions around “alter column” and “modify column” in SQLite, which is strong evidence of persistent developer demand. ([Stack Overflow][11])

**Likelihood in core SQLite:** Medium. SQLite has been slowly adding DDL capability, so more incremental improvements are plausible.

## 5. `LISTEN` / `NOTIFY`, cross-connection events, and database change notifications

**Demand level: high and growing.** This appears in reactive UI, local-first apps, pub/sub, cache invalidation, and background worker use cases.

People ask for:

| Requested feature                    | Use case                                   |
| ------------------------------------ | ------------------------------------------ |
| PostgreSQL-style `LISTEN` / `NOTIFY` | Notify clients after table changes         |
| Cross-connection notifications       | One process sees another process’s changes |
| Trigger-based notification           | Emit messages from triggers                |
| Payload-bearing events               | Send row/table IDs or small JSON payloads  |
| Same-host pub/sub                    | Often enough for local apps                |
| Avoid polling                        | Reactive UI and caches                     |

A SQLite Forum user explicitly asked for a pub/sub mechanism and said PostgreSQL’s `LISTEN/NOTIFY` would suit their needs; they wanted to update a UI when another client inserts a record, and noted that polling is undesirable. ([SQLite][12]) PostgreSQL officially supports asynchronous notification through `LISTEN` and `NOTIFY`, including optional payloads. ([PostgreSQL][13])

**Why SQLite lacks it:** SQLite has no central server process to route notifications across clients. There are hooks such as update hooks, but they are not the same as durable cross-process pub/sub.

**Likelihood in core SQLite:** Medium-low. Same-process hooks exist; cross-process notifications would need careful OS-specific design.

---

## 6. Materialized views and incremental view maintenance

**Demand level: high.** This is frequently requested by people doing analytics, dashboards, expensive joins, search indexes, and precomputed summaries.

SQLite has ordinary views, but they are read-only unless you attach `INSTEAD OF` triggers; it does not have PostgreSQL-style materialized views. The official omitted-features page says views are read-only, though `INSTEAD OF` triggers can make them writable. ([SQLite][14]) StackOverflow has recurring questions on creating materialized views in SQLite. ([Stack Overflow][15]) PostgreSQL materialized views persist query results in table-like form. ([PostgreSQL][16])

People ask for:

| Requested feature             | Desired behavior                     |
| ----------------------------- | ------------------------------------ |
| `CREATE MATERIALIZED VIEW`    | Store results of expensive queries   |
| `REFRESH MATERIALIZED VIEW`   | Recompute on demand                  |
| `REFRESH … CONCURRENTLY`      | Avoid blocking readers               |
| Incremental maintenance       | Update only affected rows            |
| Refresh-on-commit             | Oracle-like / trigger-like freshness |
| Indexes on materialized views | Fast dashboard/search queries        |

**Why SQLite lacks it:** You can simulate materialized views with tables plus triggers, but the database does not provide a first-class object or refresh planner.

**Likelihood in core SQLite:** Medium-low. Manual tables/triggers are “good enough” for many SQLite use cases, but demand is real.

## 7. Stronger native data types: true `DECIMAL`, datetime, UUID, boolean, enum, arrays, richer `STRICT`

**Demand level: high.** This is one of the biggest PostgreSQL-to-SQLite mismatch areas, especially for ORMs.

SQLite intentionally uses flexible typing and says flexible typing is a feature, not a bug; `STRICT` tables exist for rigid type enforcement, but SQLite’s core type set remains small. ([SQLite][17])

People ask for:

| Requested type/feature               | Why                                 |
| ------------------------------------ | ----------------------------------- |
| True `DECIMAL` / `NUMERIC`           | Money, accounting, exact arithmetic |
| `TIMESTAMP WITH TIME ZONE`           | Safer time handling                 |
| `DATE`, `TIME`, `INTERVAL`           | ORM compatibility                   |
| `BOOLEAN` as real type               | Cleaner schemas                     |
| `UUID`                               | App identifiers                     |
| `ENUM`                               | Constrained symbolic values         |
| `ARRAY`                              | PostgreSQL compatibility            |
| JSON type in `STRICT` mode           | Enforced JSON validity              |
| Domain types                         | Reusable validated types            |
| More semantic type names in `STRICT` | Avoid losing ORM meaning            |

A SQLite Forum post specifically calls it a pity that SQLite does not implement true `DECIMAL`/`NUMERIC`, because binary floats are not precise for commercial calculations. ([SQLite][18]) Another 2025 forum request asks for official array support, while acknowledging that PostgreSQL’s full array system may be overkill. ([SQLite][19]) Forum users have also requested a JSON type in `STRICT` mode. ([SQLite][20]) PostgreSQL documents selectable-precision decimal numeric types. ([PostgreSQL][21])

**Likelihood in core SQLite:** Medium for small `STRICT` enhancements; low for a full PostgreSQL-like type system.

## 8. Better Unicode, collations, and PostgreSQL-like `ILIKE`

**Demand level: high, especially for international apps.**

SQLite’s built-in case handling is ASCII-oriented in important places. Forum discussions note that `upper()`/`lower()` are ASCII-only by default and that full Unicode case-folding tables are large; ICU can be used as an extension. ([SQLite][22])

People ask for:

| Requested feature               | Why                                           |
| ------------------------------- | --------------------------------------------- |
| Built-in Unicode `NOCASE`       | Correct search/sort outside ASCII             |
| `COLLATE UNICODE`               | Locale-aware comparisons                      |
| Built-in `ILIKE`                | PostgreSQL compatibility                      |
| Case-insensitive Unicode `LIKE` | Search Cyrillic, Greek, Turkish, Polish, etc. |
| Accent-insensitive comparisons  | Search UX                                     |
| Better default collation story  | Less extension work                           |

A 2024 SQLite Forum thread shows a user moving from PostgreSQL over ODBC to SQLite and failing on the missing `ILIKE` operator. ([SQLite][23]) Another forum feature request asks for Unicode collation because `COLLATE NOCASE` handles only ASCII. ([SQLite][24])

**Likelihood in core SQLite:** Medium-low. SQLite has historically avoided bundling large Unicode tables; ICU remains the likely answer.

## 9. Permissions, roles, `GRANT` / `REVOKE`, and row-level security

**Demand level: medium-high, but mostly from people trying to use SQLite as a multi-user server database.**

SQLite officially omits `GRANT` and `REVOKE`, explaining that permissions are handled through normal filesystem permissions rather than inside the database. ([SQLite][14]) PostgreSQL, by contrast, has roles, privileges, and row-level security policies. ([PostgreSQL][25])

People ask for:

| Requested feature                | Why                              |
| -------------------------------- | -------------------------------- |
| `GRANT` / `REVOKE`               | App-level multi-user permissions |
| Roles                            | SaaS / admin / read-only access  |
| Row-level security               | Tenant isolation                 |
| Column-level permissions         | Expose limited data              |
| `SECURITY DEFINER`-like routines | Controlled privileged operations |
| Database users                   | Avoid relying only on app code   |

**Why SQLite lacks it:** Without a server process enforcing identity, database-internal permissions are hard to make meaningful. Anyone with file access can generally copy or inspect the DB file.

**Likelihood in core SQLite:** Low.

## 10. More PostgreSQL-compatible SQL syntax: `DEFAULT` in `VALUES`, `MERGE`, `DISTINCT ON`, richer aggregates/windows

**Demand level: medium-high.** This is a collection of smaller but highly irritating compatibility gaps.

One concrete SQLite Forum feature request asks for per-column `DEFAULT` in `INSERT` values, e.g. `INSERT INTO t VALUES (DEFAULT, ?, DEFAULT)`. Richard Hipp commented that PostgreSQL, MySQL, SQL Server, and Oracle support this, so SQLite probably should too, but that it would require substantial parser/code-generator changes. ([SQLite][26])

People ask for:

| Feature                                           | Postgres / SQL gap                            |
| ------------------------------------------------- | --------------------------------------------- |
| `DEFAULT` inside `VALUES`                         | Use default per column/per row                |
| `MERGE`                                           | Standard upsert/update/delete merge logic     |
| `DISTINCT ON`                                     | PostgreSQL shortcut for “first row per group” |
| `FILTER` on more window functions                 | Cleaner analytics queries                     |
| `IGNORE NULLS` for `first_value` / `last_value`   | Time-series and sparse data                   |
| More aggregate `ORDER BY` parity                  | PostgreSQL-style aggregate control            |
| More complete `FETCH FIRST` / SQL-standard syntax | Portability                                   |
| `UPDATE … FROM` parity edge cases                 | Migration from PostgreSQL                     |
| More complete `RETURNING` behavior parity         | ORMs                                          |

SQLite Forum users have asked for `FILTER` on `first_value()` / `last_value()`, `IGNORE NULLS`-like behavior, and aggregate ordering patterns familiar from PostgreSQL. ([SQLite][27]) PostgreSQL also supports `MERGE` as a standard conditional insert/update/delete command. ([PostgreSQL][28])

**Likelihood in core SQLite:** Medium. The `DEFAULT` request in particular seems plausible because it is a syntax/compatibility feature rather than an architectural change.

| Types         | `UUID`, `JSONB`, `DECIMAL`, arrays, timestamps |
| DDL           | `ALTER COLUMN`, constraints, schemas           |
| SQL syntax    | `ILIKE`, `DISTINCT ON`, `MERGE`, `DEFAULT`     |
| Concurrency   | `FOR UPDATE`, `SKIP LOCKED`                    |
| Procedures    | Functions/procedures                           |
| Introspection | Catalog differences                            |

This is visible in migration and framework discussions where people want SQLite simplicity first, then the ability to switch to PostgreSQL as traffic or complexity grows. ([ClassicPress Forums][33])

**Likelihood in core SQLite:** Medium for small syntax features; low for full PostgreSQL compatibility.

# What is most likely to be added soon?

My read:

**Most plausible incremental additions:**

1. `DEFAULT` inside `INSERT … VALUES`.
2. More `ALTER TABLE` enhancements.
3. More JSON functions and stricter JSON typing options.
4. More CLI/diagnostic improvements.
5. More PostgreSQL-compatible syntax where it does not alter SQLite’s architecture.

**Least likely in core SQLite:**

1. True multi-writer row-level MVCC.
2. Native server mode.
3. Built-in replication/HA.
4. PostgreSQL-style roles/RLS.
5. Full stored-procedure language.
6. Full Unicode collation tables bundled by default.

The biggest pattern is this: **SQLite users are not mostly asking for exotic SQL features; they are asking for SQLite to cross the boundary from embedded database into small-server PostgreSQL territory.** SQLite’s maintainers often resist exactly those changes because the embedded, tiny, stable, serverless design is the point.
