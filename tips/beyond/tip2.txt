## Ranked SQLite feature-request gaps, most requested → least requested

I treated this as a **public-signal ranking**, not a literal census of every post on the internet. X and Quora are hard to use as comprehensive archives, so I weighted durable sources more heavily: official SQLite docs and forum threads, Stack Overflow question volume, ORM/provider issue patterns, Reddit/HN/GitHub discussions, and direct Postgres feature comparisons.

Two important recent corrections: **RIGHT JOIN / FULL OUTER JOIN should no longer be counted as missing**; SQLite added them in 3.39.0. Also, **SQLite 3.53.0, released April 9, 2026, added ALTER TABLE support for adding/removing NOT NULL and CHECK constraints**, and 3.53.1 followed on May 5, 2026 with fixes. That narrows the ALTER TABLE gap, but does not eliminate it. ([SQLite][1])

---

# 1. Full ALTER TABLE / migration ergonomics

**Demand signal: extremely high.** This is probably the most requested SQLite gap overall because it hits nearly every app that evolves its schema.

People repeatedly ask for Postgres-like migration operations: `ALTER COLUMN TYPE`, `ALTER COLUMN SET/DROP DEFAULT`, `ADD/DROP FOREIGN KEY`, `ADD/DROP UNIQUE`, `ADD/DROP PRIMARY KEY`, `ADD COLUMN IF NOT EXISTS`, column positioning such as `AFTER`, and easier constraint changes. The evidence is strong: high-volume Stack Overflow questions cover modifying columns, dropping `NOT NULL`, adding foreign keys to existing tables, and adding constraints; those questions collectively have hundreds of thousands of views. ([Stack Overflow][2])

**Current SQLite status:** better than it used to be, but still limited. SQLite now supports rename table, rename column, add column, drop column, and as of 3.53.0 adding/removing `NOT NULL` and `CHECK` constraints. But official docs still describe SQLite ALTER TABLE as a limited subset, and many arbitrary changes require the classic recreate/copy/drop/rename/rebuild sequence. ADD COLUMN still cannot add a primary key or unique constraint, has restrictions around defaults, foreign keys, and generated columns, and DROP COLUMN fails if the column participates in indexes, constraints, triggers, views, generated columns, or keys. ([SQLite][3])

**Why people want it:** ORMs and migration tools have to special-case SQLite; teams using SQLite in production want safe, idempotent, automated migrations instead of table rebuild recipes. Microsoft’s EF Core provider, for example, documents many schema operations that require rebuilds or are unsupported in SQLite. ([Microsoft Learn][4])

**Postgres gap:** Postgres has a much richer `ALTER TABLE` surface and catalog-based schema machinery. SQLite stores schema as SQL text, which makes ALTER operations harder; the docs explicitly call this out as the reason ALTER is tricky. ([SQLite][3])

---

# 2. Stored procedures, stored functions, variables, and procedural SQL

**Demand signal: extremely high.** This is probably the biggest single named feature request.

The canonical Stack Overflow question “Creating stored procedure in SQLite” has very high visibility, and SQLite forum threads keep returning to stored procedures and SQL-defined functions. Users ask for `CREATE PROCEDURE`, `CREATE FUNCTION`, variables, control flow, error handling, reusable business logic, and transaction blocks stored in the database. ([Stack Overflow][5])

**Current SQLite status:** SQLite does not have Postgres-style stored procedures or a built-in procedural language. You can register user-defined functions from the host application, use triggers, use views, use C extensions, or generate SQL in application code, but you cannot store a PL/pgSQL-like routine inside the database.

**Why people want it:** multi-language applications do not want to duplicate database-side logic in Go, Python, Node, Java, etc. Forum users explicitly argue that stored routines would let them group statements, parameterize logic, maintain logic in one place, and perform ordered operations that triggers do not express cleanly. ([SQLite][6])

**Why SQLite resists it:** SQLite is embedded, so the host application is “near” the database; unlike client/server databases, there is no network round trip to avoid. Forum responses also note that adding a procedural language would be a large design and maintenance burden. ([Stack Overflow][5])

---

# 3. Better write concurrency: multiple writers, row-level locking, MVCC-like behavior

**Demand signal: extremely high, especially from web/backend users.**

This is the classic “SQLite vs Postgres” complaint: SQLite is excellent for many read-heavy workloads, but it serializes writes. Official SQLite material says there can only be one writer at a time; WAL allows readers and a writer to coexist, but still only one writer. ([SQLite][7])

**What users ask for:** concurrent writes, row-level locking, less `SQLITE_BUSY`, better writer queuing, a mainline version of experimental concurrency branches, and fewer surprises when many threads/processes write at once. SQLite forum threads discuss “many threads/processes write,” WAL3, begin-concurrent/WAL2, and experimental high-concurrency backends such as Hctree. ([SQLite][8])

**Postgres gap:** Postgres is built around multi-user, multi-session concurrent writes with MVCC. SQLite’s single-writer design is simpler, smaller, and robust, but it is the first major scaling wall for server-style workloads.

**Workarounds today:** WAL mode, short transactions, `busy_timeout`, one writer queue, a single writer process, retry logic, sharding by database file, or SQLite-derived projects such as libSQL/Turso. But users keep asking for this in core because the workaround changes application architecture.

---

# 4. Richer type system and stronger Postgres-style type fidelity

**Demand signal: very high.** This is a broad cluster rather than one feature.

SQLite uses dynamic typing: values have storage classes, and most columns can store most value types. STRICT tables, added in 3.37.0, help, but they only allow a small set of datatype names: `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB`, and `ANY`. SQLite also has no dedicated date/time datatype; it stores dates as text, Julian day numbers, or Unix timestamps. ([SQLite][9])

**What users ask for most:**

* exact `DECIMAL` / `NUMERIC(p,s)` arithmetic
* native date, time, timestamp, interval, and timezone-aware types
* `UUID`
* `BOOLEAN` as a stricter logical type
* enums, domains, custom types
* arrays and ranges
* unsigned integers, 128-bit integers, big integers
* better affinity behavior for ORMs and cross-database portability

Microsoft’s EF Core SQLite provider documents practical type gaps around `DateTimeOffset`, `decimal`, `TimeSpan`, and `ulong`, including limited comparison/order behavior. Community issues also ask for exact decimal and 128-bit numeric support. ([Microsoft Learn][4])

**Postgres gap:** Postgres has user-defined types, domains, arrays, ranges, enums, rich numeric types, and more. Official Postgres docs expose `CREATE TYPE`, `CREATE DOMAIN`, and array support as first-class features. ([PostgreSQL][10])

---

# 5. Materialized views / indexed views / refreshable precomputed queries

**Demand signal: high.**

People ask for materialized views when regular SQLite views are too slow and they want a query result physically stored and refreshed. Stack Overflow questions explicitly ask how to create materialized views in SQLite; the answer is essentially: SQLite does not support them, and you must create a table yourself and refresh it manually. ([Stack Overflow][11])

**Current SQLite status:** no native `CREATE MATERIALIZED VIEW`, no `REFRESH MATERIALIZED VIEW`, no dependency-aware refresh system.

**Workarounds:** create a table from a query, refresh it manually, maintain it with triggers, or use application-side caching.

**Postgres gap:** Postgres has `CREATE MATERIALIZED VIEW` and `REFRESH MATERIALIZED VIEW`; the database owns the object type and refresh semantics. ([PostgreSQL][12])

---

# 6. Schemas/namespaces, sequences, identity columns, and database-generated concurrency tokens

**Demand signal: high, especially from ORMs and apps porting from Postgres.**

SQLite has attached databases, but not Postgres-style schemas/namespaces inside a database. It also does not have independent `CREATE SEQUENCE` objects. EF Core’s SQLite provider explicitly notes that schemas, sequences, and database-generated concurrency tokens are unsupported. ([Microsoft Learn][4])

**What users ask for:** `schema.table` namespaces, `CREATE SCHEMA`, `CREATE SEQUENCE`, identity columns closer to Postgres, better autoincrement semantics, and database-generated row-version/concurrency tokens.

**Postgres gap:** Postgres has `CREATE SCHEMA`, `CREATE SEQUENCE`, identity columns backed by sequence-like behavior, and many schema-qualified object types. ([PostgreSQL][10])

---

# 7. Users, roles, GRANT/REVOKE, and row-level security

**Demand signal: high in multi-user applications; low in embedded/local apps.**

SQLite does not implement SQL `GRANT` and `REVOKE`; the official “omitted features” page says access permissions are handled through normal filesystem permissions. SQLite also lacks Postgres-style roles, policies, and row-level security. ([SQLite][13])

**What users ask for:** database users, roles, table privileges, column privileges, row-level policies, tenant isolation, and read/write controls inside the DB rather than only in app code.

**Postgres gap:** Postgres supports `GRANT`, `REVOKE`, roles, and row-level security policies that can vary by user and command. ([PostgreSQL][14])

**SQLite reality:** for an embedded database file, OS-level permissions make sense. But as people use SQLite in server, edge, local-first, and multi-tenant contexts, the lack of internal authorization becomes more painful.

---

# 8. LISTEN/NOTIFY-style pub/sub, database notifications, and change data capture

**Demand signal: medium-high and rising.**

Users ask for a Postgres-like way to notify clients when database changes happen. A SQLite forum thread explicitly describes wanting SQLite to act as a pub/sub broker and says Postgres `LISTEN/NOTIFY` fits the use case well; the user had tried hooks, triggers, file notifications, and polling, but wanted to avoid polling. ([SQLite][15])

**Current SQLite status:** there are update hooks in C APIs, triggers, changelog tables, polling, and the session extension for changesets/patchsets. But there is no SQL-level `LISTEN` / `NOTIFY` equivalent that wakes listeners with payloads. ([SQLite][16])

**Postgres gap:** Postgres has asynchronous notifications via `LISTEN` and `NOTIFY`, where listening sessions receive notifications and optional payloads. ([PostgreSQL][17])

---

# 9. Built-in replication, read replicas, sync, HA, and conflict resolution

**Demand signal: medium-high, much higher now than a decade ago.**

SQLite core is a single-file embedded database, not a distributed database. But the ecosystem demand is obvious: Litestream, LiteFS, rqlite, libSQL/Turso, and other projects exist largely to add replication, backup, HA, or distributed behavior around SQLite. Litestream is described as a tool for making SQLite apps recoverable from object storage; LiteFS replicates SQLite across a cluster for HA and lower latency; rqlite positions itself as a distributed database built on SQLite. ([Fly.io][18])

**What users ask for:** read replicas, streaming replication, automatic failover, offline sync, conflict-free multi-device sync, cloud backup, and safe distributed writes.

**Current SQLite status:** the official session extension can produce changesets and patchsets and apply them to another database, which helps with sync tooling, but it is not a full HA/replication system. ([SQLite][16])

**Postgres gap:** Postgres has a large replication/logical decoding/HA ecosystem and is naturally server-oriented. SQLite users increasingly want the deployment simplicity of SQLite plus the durability and replication ergonomics of server databases.

---

# 10. JSONB parity: document indexing, containment operators, and JSON_TABLE-style querying

**Demand signal: medium-high.**

SQLite’s JSON support is strong for its size, and newer SQLite versions use an internal JSONB representation for efficiency in many JSON functions. But the feature requests tend to target Postgres-style document querying: indexable containment, GIN-like indexes, path indexes, key-existence operators, and SQL/JSON table projection. ([SQLite][19])

**Current SQLite status:** JSON is mostly function-based. You can use expression indexes over `json_extract(...)`, generated columns, and partial indexes, but there is no Postgres-style `jsonb_ops` / `jsonb_path_ops` GIN index family, no native containment operator equivalent with the same index behavior, and no full `JSON_TABLE` parity. Community posts ask how to index JSON columns for fast queries. ([Reddit][20])

**Postgres gap:** Postgres has JSONB GIN operator classes for efficient key/key-value/path containment and SQL/JSON query features including `JSON_TABLE`. ([PostgreSQL][21])

---

# 11. Unicode-aware collations, case-insensitive search, and REGEXP out of the box

**Demand signal: medium-high.**

SQLite’s default `LIKE` case-insensitivity only covers ASCII; Unicode characters beyond ASCII are case-sensitive by default. The docs say the ICU extension can add enhanced Unicode behavior, but it is not the default built-in experience. SQLite also reserves `REGEXP` syntax but does not provide a regexp function by default. ([SQLite][22])

**What users ask for:** Unicode `LOWER`/`UPPER`, Unicode case folding, locale-aware collations, accent-insensitive comparisons, built-in regex, and better multilingual search defaults. Community issues and discussions repeatedly mention ASCII-only case-insensitive behavior and requests for ICU/collation support. ([SQLite][23])

**Why it is not trivial:** Unicode case folding and collations are large, evolving, locale-dependent, and can affect index correctness. SQLite historically keeps this optional through ICU rather than making the core larger.

---

# 12. Updatable views, statement-level triggers, and richer trigger semantics

**Demand signal: medium.**

SQLite views are read-only by default; writes can be simulated with `INSTEAD OF` triggers. The official omitted-features page also lists lack of statement-level triggers: SQLite only supports row-level triggers. ([SQLite][13])

**What users ask for:** naturally updatable views, `WITH CHECK OPTION`, statement-level triggers, more trigger timing options, richer transition-table semantics, and view insert/update/delete behavior closer to Postgres.

**Postgres gap:** Postgres has richer view and trigger machinery, including updatable-view behavior in many cases and more trigger varieties.

**Workaround:** use `INSTEAD OF` triggers, but that makes view updates manual and verbose. Requests show up in GUI/database-browser projects too, where users expect to edit rows through views. ([GitHub][24])

---

# 13. Advanced index types: GIN, GiST, SP-GiST, BRIN, operator classes

**Demand signal: medium.**

SQLite already has useful indexing features: normal B-tree indexes, expression indexes, partial indexes, and FTS virtual tables. But users coming from Postgres often miss specialized index access methods for JSON, arrays, full-text, geospatial, nearest-neighbor, range, and huge append-only tables. ([SQLite][25])

**What users ask for:** GIN-like indexes for JSON/arrays/text, GiST-like extensibility, BRIN-like indexes for very large ordered tables, custom operator classes, and better planner support for specialized predicates.

**Postgres gap:** Postgres supports multiple index methods including B-tree, Hash, GiST, SP-GiST, GIN, BRIN, and Bloom, with operator classes for data-type-specific indexing. ([PostgreSQL][26])

---

# 14. Declarative partitioning and large-table management

**Demand signal: medium-low, but important for analytics-scale users.**

SQLite does not have native declarative table partitioning. Users can manually shard tables, use attached databases, or create routing views/triggers, but not Postgres-style `PARTITION BY` table definitions.

**Postgres gap:** Postgres supports declarative partitioning, where one logical table is divided into partitions. ([PostgreSQL][27])

**Why people ask:** time-series data, logs, event stores, archival tables, and mobile/local apps with large append-only datasets.

**Why it is lower ranked:** once a workload needs true partitioning, many teams are already willing to use Postgres, DuckDB, ClickHouse, or another system.

---

# 15. SQL dialect conveniences and Postgres compatibility sugar

**Demand signal: medium.**

This is a grab bag, but it comes up constantly in porting and migration work.

Common requests include:

* `CREATE OR REPLACE VIEW`
* more `IF EXISTS` / `IF NOT EXISTS`, especially `ADD COLUMN IF NOT EXISTS`
* `TRUNCATE`
* more complete `ALTER VIEW`
* `COMMENT ON`
* `MERGE`
* `DISTINCT ON`
* `RETURNING` already exists, but users still ask for broader Postgres compatibility
* column placement such as `ADD COLUMN ... AFTER ...`

Stack Overflow and GitHub discussions show recurring demand for `CREATE OR REPLACE VIEW`, `TRUNCATE`, and `ADD COLUMN IF NOT EXISTS`. ([Stack Overflow][28])

**Current SQLite status:** some of these are intentionally omitted because SQLite favors a small grammar and simple storage model. Some can be emulated with `DROP` + `CREATE`, `DELETE`, migration introspection, or application logic.

---

# 16. Built-in database encryption / password-protected database files

**Demand signal: medium, especially for desktop/mobile apps.**

SQLite core does not include free built-in full-database encryption. The official SQLite Encryption Extension exists, but it is an add-on; SQLCipher is a popular separate encrypted SQLite fork/extension. ([SQLite][29])

**What users ask for:** “password-protect my SQLite database,” transparent AES encryption, encrypted local app data, encrypted backups, and a core-supported way to ship encrypted SQLite without commercial licensing or third-party builds. Stack Overflow and SQLite forum discussions reflect this exact demand. ([Stack Overflow][30])

**Why it is lower ranked:** serious users often adopt SQLCipher, SEE, OS-level encryption, or application-level encryption. But for app developers, this remains a highly visible gap.

---

# 17. Client/server mode, network protocol, pooling, and server management

**Demand signal: medium, but philosophically contentious.**

People periodically ask for SQLite “but with a server,” connection pooling, remote access, and multi-client coordination. This is really a request to turn SQLite into something closer to Postgres while keeping SQLite’s simplicity.

**Current SQLite status:** SQLite is embedded. There is no official SQLite server daemon, network wire protocol, role system, or connection-pooling server. Projects such as rqlite, LiteFS, libSQL/Turso, and application-specific wrappers exist because demand is real. ([rqlite][31])

**Why it is not higher:** many maintainers and experienced users treat this as outside SQLite’s core mission. When you need a true client/server database, Postgres is usually the answer.

---

# 18. Foreign key ergonomics: enabled-by-default, persistent enforcement, easier FK changes

**Demand signal: medium.**

SQLite supports foreign keys, but they are famously controlled by `PRAGMA foreign_keys`, and users repeatedly trip over the fact that enforcement must be enabled per connection. Forum and Stack Overflow threads ask why FK support is not simply persistent or enabled by default. ([SQLite][32])

**What users ask for:** foreign keys on by default, file-level persistence of enforcement, easier `ADD CONSTRAINT FOREIGN KEY`, easier FK introspection, and safer defaults for ORMs.

**Overlap with rank #1:** adding/dropping foreign keys after table creation is one of the biggest ALTER TABLE pain points.

---

# 19. Full-text-search parity with Postgres search

**Demand signal: medium-low because SQLite already has FTS5.**

SQLite’s FTS5 module is powerful and widely used; it provides full-text-search virtual tables. ([SQLite][33])

**What users still ask for:** richer language dictionaries, ranking controls, stemming/tokenizer defaults, trigram/fuzzy search, better integration with normal tables, easier indexing of generated content, and Postgres-like text-search configuration.

**Postgres gap:** Postgres full-text search has `tsvector`, `tsquery`, ranking, highlighting/display helpers, dictionaries, and configuration concepts built into the server. ([PostgreSQL][34])

**Why it is lower ranked:** SQLite has a credible built-in answer already; the gap is about ergonomics and advanced language tooling, not total absence.

---

# 20. GIS / spatial SQL parity

**Demand signal: lower in general SQLite discussions, high in geospatial niches.**

SQLite does not ship with PostGIS-like spatial functionality in core. SpatiaLite extends SQLite with full spatial SQL capabilities, while PostGIS extends Postgres for geospatial storage, indexing, and querying. ([GaiaGIS][35])

**What users ask for:** geometry/geography types, spatial indexes, coordinate transformations, distance predicates, and GeoJSON handling in core.

**Why it is lower ranked:** SpatiaLite covers much of the niche, and adding full GIS would make SQLite core much larger.

---

# 21. Cross-database views and better ATTACH-database composition

**Demand signal: low-medium.**

SQLite supports `ATTACH`, but schema objects have limitations around attached databases. Users occasionally want durable views that reference attached databases, cross-database constraints, cross-database triggers, and more composable multi-file database designs.

**Why people ask:** they want modular database files, plugin architectures, local-first apps with separate datasets, or read-only reference databases attached to writable app databases.

**Why it is lower ranked:** common, but not nearly as visible as ALTER TABLE, stored procedures, concurrency, or types.

---

# 22. Extension and package ecosystem improvements

**Demand signal: low-medium but important to power users.**

SQLite supports loadable extensions, virtual tables, C APIs, and extension functions, but users sometimes want a more Postgres-like extension ecosystem: `CREATE EXTENSION`, versioned extension packages, dependency metadata, portable installation, and sometimes syntax extensibility.

**Postgres gap:** Postgres has first-class extension commands and a large ecosystem of extensions. SQLite has excellent low-level extensibility, but not the same package-management experience.

---

# 23. Idempotent migrations, procedural migration scripts, and database-level application locks

**Demand signal: low-medium, mostly from ORM users.**

This overlaps with ALTER TABLE and stored procedures, but it is distinct. EF Core documents that SQLite lacks a procedural language, which complicates idempotent migration scripts, and notes that SQLite has no built-in application-lock primitive. ([Microsoft Learn][4])

**What users ask for:** safe “run this migration only if needed” scripts, advisory locks, migration locks, procedural `IF` blocks, and database-native migration guards.

**Postgres gap:** Postgres has procedural `DO` blocks, advisory locks, richer catalogs, and server-side mechanisms that make robust migrations easier.

---

# 24. More built-in scalar, aggregate, math, regex, and decimal functions

**Demand signal: low-medium.**

SQLite has a strong core function set, and extensions can add more. But users still ask for built-in regex, richer math/statistical aggregates, exact decimal arithmetic, date/time niceties, and Postgres-compatible functions.

**Current status:** `REGEXP` syntax exists but no regexp function is provided by default; users must define one. SQLite’s date/time functions are useful, but there is no dedicated date/time datatype. ([SQLite][22])

**Why it is lower ranked:** extension loading and application-defined functions solve many cases, but portability suffers.

---

# 25. Administrative observability, monitoring, and server-style operations

**Demand signal: low compared with the above.**

Users coming from Postgres sometimes want richer built-in observability: active sessions, lock views, query statistics, slow query logging, replication lag, server metrics, and administrative dashboards.

**SQLite reality:** because SQLite is embedded, many of these responsibilities live in the host application rather than the database engine. SQLite has `EXPLAIN`, `EXPLAIN QUERY PLAN`, pragmas, tracing/profiling APIs, and compile/runtime diagnostics, but not a server catalog of live sessions like Postgres.

---

## Features people still mention, but should not be counted as current missing gaps

* **RIGHT JOIN and FULL OUTER JOIN:** added in SQLite 3.39.0. ([SQLite][1])
* **STRICT tables:** added in SQLite 3.37.0, though strict typing is still much narrower than Postgres typing. ([SQLite][9])
* **DROP COLUMN:** now exists, but with many dependency restrictions. ([SQLite][3])
* **Expression indexes and partial indexes:** SQLite supports both, so the real gap is specialized index families such as GIN/GiST/BRIN, not basic expression or partial indexes. ([SQLite][25])
* **JSON support generally:** SQLite has substantial JSON support; the missing piece is Postgres-like JSONB indexing/operators/query ergonomics. ([SQLite][19])
* **Full-text search generally:** SQLite has FTS5; the gap is deeper language/search configuration parity. ([SQLite][33])

---

## My condensed top 10

1. **Full ALTER TABLE / migrations**
2. **Stored procedures and SQL-defined functions**
3. **Multiple concurrent writers / row-level locking**
4. **Richer type system: decimal, UUID, dates, arrays, enums, domains**
5. **Materialized views**
6. **Schemas, sequences, identity/concurrency tokens**
7. **GRANT/REVOKE, roles, row-level security**
8. **LISTEN/NOTIFY and change notifications**
9. **Replication, HA, and sync**
10. **Postgres-like JSONB indexing and document-query operators**

The big pattern is clear: people love SQLite’s deployment model, but the most requested missing features are the ones that would let SQLite behave more like **“embedded Postgres”** without giving up its tiny, zero-config, single-file nature. The tension is that many of these requests directly conflict with what makes SQLite SQLite.
