Here’s the evidence-weighted ranking I’d use. I treated this as a public-demand map, not a literal census: X/Quora/private Discords and many forum archives are not fully indexable, so I weighted sources I could verify: SQLite’s own docs and forum, Stack Overflow, GitHub/Hacker News ecosystem signals, and current PostgreSQL/SQLite docs.

The big pattern is wonderfully clear: the most requested “missing SQLite features” are usually requests to make SQLite behave like **a tiny, embeddable Postgres** without losing the single-file/serverless magic. That collides with SQLite’s stated design: SQLite is serverless, embedded, file-based, and its own docs say it solves a different problem than client/server systems like PostgreSQL. ([SQLite][1])

## Ranked feature gaps, most requested to least

### 1. More concurrent writes: multiple writers, row-level locking, official `BEGIN CONCURRENT`, fewer `SQLITE_BUSY` failures

This is the strongest and most repeated ask. People want SQLite to support many writers at once, row-level or page-level locking, MVCC-like writer concurrency, official `BEGIN CONCURRENT`/WAL2 support, and fewer cases where a second writer blocks or fails.

SQLite today allows many readers but only one writer at a time; its FAQ explicitly contrasts this with PostgreSQL/MySQL/Oracle-style engines that generally allow multiple processes to write at once. Official forum threads repeatedly ask for multiple writers, row-level locking, or official support for `BEGIN CONCURRENT`. Stack Overflow has a very large, old, highly viewed concurrency thread because this is one of the first pain points developers hit when they try to use SQLite for server workloads. PostgreSQL’s row-level locks and `SELECT FOR UPDATE` are the obvious comparison point. ([SQLite][2])

**What people are asking for:**

* Multiple simultaneous writers.
* Row-level locking or page-level conflict detection.
* Official `BEGIN CONCURRENT` / WAL2 support.
* `SELECT FOR UPDATE`, `SKIP LOCKED`, queue/job-table semantics.
* Better busy handling and lock diagnostics.
* More predictable behavior under web-server concurrency.

**Why it ranks #1:** it appears across official SQLite forums, Stack Overflow, and real production architecture discussions. It is also the biggest Postgres-vs-SQLite practical gap for server-side applications.

---

### 2. Built-in replication, sync, HA, read replicas, failover, and CDC/change streams

The second-biggest ask is “SQLite, but replicated.” People want streaming WAL replication, live read replicas, simple failover, backup to object storage, changefeeds, and APIs that make local-first or multi-node sync straightforward.

SQLite does not include built-in streaming replication. A forum request explicitly asks for master/slave-style transaction replication with low overhead and failover, while ecosystem projects such as Litestream, LiteFS, and rqlite exist largely because people keep wanting Postgres-like operational properties around SQLite. Litestream/LiteFS documentation frames the problem directly: SQLite’s embedded nature is wonderful, but the database can live and die with one server unless external replication tooling is added. ([SQLite][3])

**What people are asking for:**

* Built-in WAL streaming replication.
* Read replicas.
* Primary failover.
* Durable change data capture.
* Conflict-free local-first sync.
* A stable low-level “what changed?” API.
* Easier cloud backup/restore.

**Why it ranks #2:** SQLite’s popularity for “small web app on one box,” edge apps, and local-first apps has made replication tooling a whole ecosystem. This is probably the biggest product opportunity around SQLite, even if it is not obviously a fit for SQLite core.

---

### 3. More complete `ALTER TABLE` and easier schema migrations

This remains a major request, though it has improved recently. SQLite 3.53.0, released in April 2026, added new `ALTER TABLE` capabilities for adding/removing `NOT NULL` and `CHECK` constraints. That narrows the gap, but people still want much more Postgres-like migration support. ([SQLite][4])

SQLite’s own docs still describe direct schema alteration as limited: many changes require rebuilding a table, editing schema text carefully, or following a multi-step migration procedure. Dropping columns has many restrictions, and operations such as changing data types, changing defaults, adding/removing primary keys, adding/removing unique constraints, reordering columns, or modifying foreign-key structure are not as ergonomic as in Postgres. ([SQLite][5])

**What people are asking for:**

* `ALTER COLUMN TYPE`.
* `ALTER COLUMN SET/DROP DEFAULT`.
* Add/drop primary keys and unique constraints.
* Add/drop/modify foreign-key constraints more directly.
* Safer column drops.
* Column reordering.
* Migration ergonomics closer to Postgres, MySQL, and SQL Server.

**Why it ranks #3:** almost every serious application eventually hits migrations. This is a huge practical gap for ORMs, migration tools, and teams moving between Postgres and SQLite.

---

### 4. Stored procedures, stored functions, variables, and SQL routines

A very common request is some form of `CREATE PROCEDURE`, `CREATE FUNCTION`, variables, procedural SQL, or parametric database-side routines. SQLite does not support stored procedures in the Postgres/MySQL sense; the usual answer is to implement logic in the host application or register user-defined functions from the application language. ([SQLite][6])

The SQLite forum has multiple threads asking for stored procedures or stored functions. Supporters argue that SQLite is often used as a standalone data engine and that stored routines would let people centralize logic, reuse multi-statement operations, and reduce duplicated application code. Skeptics point out that the traditional client/server argument for stored procedures—avoiding network round trips—is much weaker for SQLite because the database is in-process. ([SQLite][7])

**What people are asking for:**

* `CREATE PROCEDURE`.
* SQL-language `CREATE FUNCTION`.
* Variables and control flow.
* Parametric views/macros.
* Reusable database-side business logic.
* Better pure-SQL scripting.

**Why it ranks #4:** demand is persistent and visible, especially among people who use SQLite beyond “simple embedded storage.”

---

### 5. Materialized views, indexed views, and incremental view maintenance

People want `CREATE MATERIALIZED VIEW`, `REFRESH MATERIALIZED VIEW`, indexed views, and incremental maintenance of expensive derived queries. PostgreSQL supports materialized views as stored query results that can be refreshed; SQLite has ordinary views but no native materialized-view syntax. ([PostgreSQL][8])

SQLite forum users explicitly ask how to materialize views or maintain expensive derived results. One concurrency-related forum request describes a product need to maintain materialized views and diffs over large expensive queries. In SQLite today, the common workaround is manual: create a table, populate it from a query, refresh it yourself, or maintain it with triggers. ([SQLite][9])

**What people are asking for:**

* `CREATE MATERIALIZED VIEW`.
* Refreshable materialized views.
* Incremental view maintenance.
* Indexed views.
* Declarative caching of expensive joins/aggregations.
* Change diffs for derived query results.

**Why it ranks #5:** this comes up whenever SQLite is used for analytics, dashboards, local search indexes, or expensive denormalized projections.

---

### 6. Cross-connection `LISTEN`/`NOTIFY`, pub/sub, durable event queues, and database-change notifications

This is a rising request. Developers want SQLite to notify other processes or connections when data changes, similar to PostgreSQL’s `LISTEN`/`NOTIFY`. PostgreSQL lets sessions listen on channels and receive notifications from `NOTIFY`; SQLite has hooks, but not a built-in cross-connection notification bus. ([PostgreSQL][10])

A SQLite forum user asked for pub/sub or event streaming because polling many times per second was undesirable. The response highlights the architectural challenge: SQLite has no centralized server process that knows about all connections. The interest is also visible in ecosystem experiments such as Honker, which advertises Postgres-like `NOTIFY`/`LISTEN` semantics for SQLite and drew notable Hacker News discussion. ([SQLite][11])

**What people are asking for:**

* `LISTEN` / `NOTIFY`.
* Cross-process change notifications.
* Durable event queues.
* Triggered notifications after commits.
* No-poll reactive apps.
* Pub/sub channels backed by SQLite.

**Why it ranks #6:** this is increasingly important for local-first apps, desktop apps, reactive web servers, and “SQLite as an app backend” designs.

---

### 7. More powerful JSON/JSONB: whole-document indexes, containment operators, JSONPath, GIN-like indexing

SQLite has JSON support, and since 3.45.0 it has JSONB: SQLite’s internal binary parse-tree representation, designed to be smaller and faster than text JSON. But SQLite’s JSONB is not PostgreSQL JSONB, and it does not provide the same indexing/operator ecosystem. ([SQLite][12])

The common request is Postgres-style JSONB power: containment operators, key-existence operators, JSONPath querying, and especially generalized indexes over arbitrary JSON documents. SQLite users can index known JSON paths with expression indexes, but that is different from indexing an entire JSON document for flexible containment/key/path queries. ([SQLite][13])

**What people are asking for:**

* GIN-like indexes over JSON documents.
* JSON containment operators like Postgres `@>`.
* Key-existence operators.
* JSONPath indexing.
* Multi-valued indexes for arrays/objects.
* Faster arbitrary-path JSON querying.

**Why it ranks #7:** JSON is now a default modeling tool for many apps. SQLite has improved a lot here, but Postgres still feels much more powerful for semi-structured data.

---

### 8. Richer type system: UUID, decimal, date/time, boolean, enum, array, stricter typing

This is a huge Postgres-migration friction point. SQLite intentionally uses flexible typing; it has no separate Boolean or DateTime storage class, and `STRICT` tables exist but only allow a narrow set of type names such as `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB`, and `ANY`. ([SQLite][14])

The demand signal is broad: Stack Overflow questions about UUIDs, enums, and arrays in SQLite have very high view counts, and ORMs often need special-case handling for UUID, decimal/money, datetime, enum, and array-like fields. ([Stack Overflow][15])

**What people are asking for:**

* Native `UUID`.
* Exact `DECIMAL` / `NUMERIC`.
* `DATE`, `TIME`, `TIMESTAMP`, `TIMESTAMPTZ`.
* Native `BOOLEAN`.
* `ENUM`.
* `ARRAY`.
* Better transaction-stable `now` semantics.
* Strict typing by default or a stronger strict mode.

**Why it ranks #8:** this is one of the most visible differences for application developers moving between SQLite and Postgres.

---

### 9. Full Unicode case-insensitive search, collations, indexed `LIKE`, and `ILIKE`

SQLite’s default case-insensitive behavior is ASCII-oriented. The FAQ says full Unicode case-folding tables would substantially increase library size, and it suggests ICU or custom functions/collations for applications that need full Unicode support. ([SQLite][2])

Users still ask for a native `COLLATE UNICODE`, Unicode-aware `NOCASE`, indexed Unicode-insensitive `LIKE`, and something like Postgres `ILIKE`. A forum thread specifically complains that Unicode-aware indexed case-insensitive search should be easier and that ICU/custom approaches do not fully solve the indexed `LIKE` problem in a simple built-in way. ([SQLite][16])

**What people are asking for:**

* Unicode `NOCASE`.
* `ILIKE`.
* Indexed Unicode-insensitive `LIKE`.
* Better locale-aware collations.
* Built-in case-folding functions.
* Fewer ICU/custom-extension requirements.

**Why it ranks #9:** this matters a lot for international apps, search boxes, contact databases, and mobile/desktop apps.

---

### 10. A built-in server mode or network protocol: “SQLite, but client/server when needed”

This is slightly different from replication or concurrency. Some people want to keep SQLite’s file format and simplicity while adding a server process, network protocol, connection pooling, shared cache coordination, auth, or a Postgres-like deployment mode.

SQLite’s docs explicitly describe it as serverless: there is no intermediary server process, and a separate server can coordinate finer-grained locking and better concurrency. The docs also say client/server databases are better when many client programs send SQL over a network or when many concurrent writers are expected. ([SQLite][17])

**What people are asking for:**

* Optional SQLite server daemon.
* Network wire protocol.
* Remote SQL access.
* Centralized connection coordination.
* Easier multi-process/multi-host deployment.
* “Postgres-lite” operational mode.

**Why it ranks #10:** many asks for concurrency, notifications, auth, and replication are really asking for a coordinator. But adding one would change SQLite’s fundamental design.

---

### 11. Users, roles, `GRANT`/`REVOKE`, permissions, and row-level security

SQLite omits `GRANT` and `REVOKE`; its docs explain that access control is normally handled through operating-system file permissions because SQLite reads and writes an ordinary disk file. ([SQLite][18])

PostgreSQL has rich role-based privileges and row-level security policies, so this becomes a clear gap when developers try to use SQLite in multi-tenant or end-user-facing deployments. PostgreSQL’s docs show `GRANT` privileges across tables, schemas, functions, and roles, and row security policies can restrict which rows users can read or modify. ([PostgreSQL][19])

**What people are asking for:**

* Database users and roles.
* `GRANT` / `REVOKE`.
* Row-level security.
* Column-level privileges.
* Tenant isolation policies.
* Auditable access-control semantics.

**Why it ranks #11:** it is a major Postgres feature gap, but demand is weaker than concurrency/replication because many SQLite deployments are single-user or application-mediated.

---

### 12. Modern safety defaults: foreign keys on by default, stricter primary keys, stricter mode by default

SQLite supports foreign keys, but enforcement must be enabled; the docs say it is disabled by default for backward compatibility. SQLite also has historical quirks around flexible typing, primary keys that can contain `NULL` except in specific cases, and permissive type behavior. ([SQLite][20])

`STRICT` tables help, but they are opt-in and still intentionally limited. Many Postgres users want a “modern SQLite mode” where foreign keys, strict typing, and stricter SQL behavior are default. ([SQLite][21])

**What people are asking for:**

* `PRAGMA foreign_keys=ON` by default.
* `STRICT` tables by default.
* More Postgres-like primary-key `NOT NULL` behavior.
* Safer defaults for new databases.
* Fewer legacy compatibility surprises.

**Why it ranks #12:** this is less flashy than replication, but it is one of the most common “SQLite footgun” complaints.

---

### 13. Data-modifying CTEs and composable `RETURNING`

SQLite supports `RETURNING`, but users want to use `INSERT ... RETURNING`, `UPDATE ... RETURNING`, or `DELETE ... RETURNING` as subqueries or CTEs the way they can in PostgreSQL.

A SQLite forum thread shows a user attempting to pipe `INSERT ... RETURNING` into another operation; Richard Hipp replies that DML statements cannot be used in subqueries, while the user argues this would simplify audit logs and pure-SQL workflows. ([SQLite][22])

**What people are asking for:**

* `WITH x AS (INSERT ... RETURNING ...) SELECT ...`.
* Chaining DML operations.
* Capturing `RETURNING` rows into another insert.
* Fewer client round trips.
* Audit-log patterns in pure SQL.

**Why it ranks #13:** this is a common Postgres compatibility gap for SQL-heavy developers.

---

### 14. `LATERAL` joins / `CROSS APPLY`

Developers ask for `LATERAL` joins because they make correlated derived tables cleaner and more efficient. Forum discussion around SQLite `LATERAL` support includes users explaining that it would avoid repeated calculations, enable cleaner recursive-query patterns, and improve compatibility with PostgreSQL and SQL Server. ([SQLite][23])

**What people are asking for:**

* `JOIN LATERAL`.
* `CROSS APPLY`-style behavior.
* Cleaner correlated subqueries.
* Better portability from Postgres.
* Easier reuse of calculated expressions.

**Why it ranks #14:** important for advanced SQL users, less important for typical CRUD apps.

---

### 15. SQL `MERGE`

People ask whether SQLite will add SQL `MERGE`, especially now that PostgreSQL has it. Forum users argue it would close a compatibility gap and help abstraction libraries avoid database-specific update/upsert code. ([SQLite][24])

**What people are asking for:**

* Standard SQL `MERGE`.
* Multi-branch upsert/update/delete logic.
* Cross-database DDL/DML compatibility.
* Fewer ORM dialect special cases.

**Why it ranks #15:** SQLite has `UPSERT`, but `MERGE` is broader and more portable for some workloads.

---

### 16. Native arrays, `UNNEST`, and built-in `split()` table-valued functions

SQLite lacks native array types like PostgreSQL arrays. Users ask for `ARRAY`, `UNNEST`, `string_to_array`, or at least a built-in `split()` table-valued function. One SQLite forum discussion explicitly compares Postgres `unnest(string_to_array(...))` with what users wish SQLite had. ([SQLite][25])

**What people are asking for:**

* Native arrays.
* `UNNEST`.
* `split()` returning rows.
* Easier handling of delimited values.
* Better compatibility with Postgres array workflows.

**Why it ranks #16:** visible, but often workaroundable with JSON arrays, recursive CTEs, or application code.

---

## Important “not gaps anymore” or “partly fixed” items

A lot of older online complaints are now stale. I would not count these as fully missing anymore:

* **JSONB exists now**, but not with PostgreSQL’s operator/indexing power. SQLite JSONB arrived in 3.45.0. ([SQLite][12])
* **`DROP COLUMN` exists**, but with significant restrictions. ([SQLite][5])
* **Some constraint alteration improved in 2026**: SQLite 3.53.0 added support for adding/removing `NOT NULL` and `CHECK` constraints via `ALTER TABLE`. ([SQLite][4])
* **`RETURNING` exists**, but it is not composable like PostgreSQL data-modifying CTEs. ([SQLite][22])
* **`STRICT` tables exist**, but they are opt-in and much narrower than a full Postgres-like type system. ([SQLite][21])

## My strongest conclusion

The top five demand clusters are:

1. **More write concurrency**
2. **Replication/sync/HA**
3. **Better migrations / fuller `ALTER TABLE`**
4. **Stored procedures/functions**
5. **Materialized views**

Those are the most repeated, highest-friction gaps between “SQLite as an embedded database” and “SQLite as a small Postgres replacement.”

The most commercially interesting extension/product opportunities are probably **replication/sync**, **change notifications**, **materialized-view maintenance**, **Postgres-like JSON indexing**, and **Unicode/search tooling**. The hardest to add to SQLite core itself is almost certainly **multi-writer row-level concurrency**, because that cuts directly against the file-based/serverless architecture that makes SQLite so small, reliable, and portable.
