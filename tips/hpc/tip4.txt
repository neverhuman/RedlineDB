This is a fantastic rabbit hole. Here’s the Rust HPC acceleration map I’d use in 2026: big breakthrough tactics first, then the lesser-known crates and runtime tricks that can compound into C/C++-class performance.

Rust is absolutely viable for serious HPC when you treat it like a systems/HPC language: optimize the build, control layout, profile continuously, use SIMD/GPU/distributed runtimes when the workload justifies it, and avoid “safe but accidental” overhead in hot loops. NERSC’s Rust-for-HPC docs describe Rust as performance-focused and capable of C++-like speeds, and Rust HPC experiments such as HPCCG-in-Rust show Rayon/MPI-based Rust implementations approaching C++ performance on real HPC kernels. ([NERSC Documentation][1])

## The biggest breakthrough levers

| Priority | Move                                          | What to do in Rust                                                                                                                                                                                                                                                                                                              |
| -------: | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|        1 | **Measure first**                             | Use `perf`, FlameGraph, Samply, VTune, AMD uProf, Criterion, Divan, Iai-Callgrind, DHAT, Heaptrack. Rust’s Performance Book explicitly recommends profiler-driven work; `perf` can use hardware counters and tools like Hotspot/Firefox Profiler to view results. ([Nicholas Nethercote][2])                                    |
|        2 | **Compile like an HPC binary**                | Use `--release`, `opt-level=3`, `lto`, `codegen-units=1`, `target-cpu=native` or explicit target features, and profile-guided optimization. Cargo profiles control optimization/debug settings; rustc supports PGO, and `codegen-units=1` can improve optimization quality at the cost of build time. ([Rust Documentation][3]) |
|        3 | **PGO + BOLT**                                | Use `cargo-pgo` for PGO and post-link BOLT workflows when the binary is hot-path heavy. This is one of the most underused Rust performance moves because it optimizes for the real workload, not a synthetic one. ([Crates][4])                                                                                                 |
|        4 | **Data layout before code cleverness**        | Prefer contiguous arrays, structure-of-arrays, packed hot fields, precomputed strides, and cache-line-aware partitioning. Most HPC Rust speedups come from cache behavior before “unsafe.”                                                                                                                                      |
|        5 | **Avoid accidental allocation**               | Reuse buffers, reserve capacity, avoid per-element `String`/`Vec`, use arenas/bump allocators, inline small vectors, and measure allocations with Divan or DHAT. Divan has an `AllocProfiler`; DHAT is a Rust heap-profiling crate inspired by Valgrind DHAT. ([Nikolai Vazquez][5])                                            |
|        6 | **Use the right allocator**                   | Try `mimalloc`, `tikv-jemallocator`, `snmalloc-rs`, or `rpmalloc` for allocation-heavy codes. `mimalloc` has a Rust wrapper usable as a drop-in global allocator. ([GitHub][6])                                                                                                                                                 |
|        7 | **Exploit SIMD**                              | Use `std::arch` intrinsics for stable explicit SIMD, `pulp`, `wide`, `rten-simd`, or nightly `std::simd`. `std::arch` exposes vendor intrinsics; portable `std::simd` is still nightly-only under `portable_simd`. ([Rust Documentation][7])                                                                                    |
|        8 | **Runtime CPU dispatch**                      | Build AVX2/AVX-512/NEON/SVE/WASM kernels separately and dispatch at startup with `is_x86_feature_detected!` or a crate like `pulp`/`rten-simd`. `rten-simd` advertises safe portable APIs plus runtime dispatch to the best available ISA. ([Docs.rs][8])                                                                       |
|        9 | **Parallelize with chunking, not tiny tasks** | Use Rayon, Fork Union, or custom scoped pools; partition into cache-sized chunks; reduce per-thread then merge. Rayon is the default Rust data-parallel workhorse and is designed to convert sequential iterators into parallel ones while preserving data-race safety. ([GitHub][9])                                           |
|       10 | **Pin threads and respect NUMA**              | Use `hwlocality`, `core_affinity`, Folo, or `numaperf`; first-touch allocate per NUMA node; avoid cross-socket chatter. `hwlocality` binds to hwloc for topology, CPU pinning, and NUMA memory awareness; `numaperf` targets topology, pinning, memory placement, scheduling, and observability. ([Docs.rs][10])                |
|       11 | **Kill false sharing**                        | Use `crossbeam::utils::CachePadded`, per-thread accumulators, and cache-line-aligned counters. Crossbeam’s docs call out cache-line invalidation and `CachePadded` as a mitigation. ([Docs.rs][11])                                                                                                                             |
|       12 | **Remove bounds checks safely**               | Prefer iterators, `chunks_exact`, `array_chunks`, `zip`, `split_at_mut`, and shape prevalidation before hot loops. Rust’s Performance Book calls out bounds checks in slices/vectors and shows safe patterns that let LLVM remove them. ([Nicholas Nethercote][12])                                                             |
|       13 | **Use proven kernels**                        | Don’t hand-roll GEMM, FFT, sort, compression, dataframe execution, or query engines unless that is the project. Use `faer`, `matrixmultiply`, `RustFFT`, `Polars`, `DataFusion`, `lz4_flex`, `zstd`, etc.                                                                                                                       |
|       14 | **Zero-copy everything possible**             | Use `memmap2`, Arrow buffers, `rkyv`, `zerocopy`, `bytemuck`, borrowed parsing, and avoid deserialize-copy-transform-copy pipelines. `rkyv` is a zero-copy deserialization framework; `memmap2` exposes memory-mapped buffers as slice-like mappings. ([GitHub][13])                                                            |
|       15 | **GPU offload only when transfer math works** | Use CUDA-specific crates for NVIDIA, or CubeCL/wgpu/rust-gpu for cross-platform GPU compute. CubeCL and Burn are especially interesting right now for Rust-native GPU/CPU kernel work. ([GitHub][14])                                                                                                                           |
|       16 | **Scale out with MPI/PGAS/RDMA**              | Use `mpi`/`rsmpi`, Lamellar, HDF5/netCDF/Zarr, and RDMA/UCX bindings when you leave one node. Lamellar is an async tasking runtime for HPC with PGAS-style distributed arrays/active messages. ([GitHub][15])                                                                                                                   |
|       17 | **Inspect generated code**                    | Use `cargo-show-asm`, godbolt, `cargo asm`, LLVM IR, and `perf annotate`. `cargo-show-asm` can display assembly, LLVM IR, MIR, and WASM for Rust code. ([GitHub][16])                                                                                                                                                           |
|       18 | **Optimize branches and cold paths**          | Move errors/logging/rare cases out of the hot loop; use `#[cold]`, `#[inline]`, `#[inline(always)]` only after measuring; avoid virtual dispatch in inner loops unless monomorphization cost is worse.                                                                                                                          |
|       19 | **Make CI catch regressions**                 | Use Criterion baselines, Iai-Callgrind in stable CI, hyperfine for whole-program benchmarks, and codspeed-like workflows. Criterion stores statistical info and detects regressions; Iai-Callgrind uses Valgrind Callgrind/Cachegrind-style measurements suitable for consistent CI runs. ([Bheisler][17])                      |
|       20 | **Use algorithmic wins before micro-wins**    | Radix sort, blocked algorithms, sparse formats, FFT/FMM, approximate nearest neighbor, streaming query execution, and fused kernels routinely beat micro-optimizing scalar loops.                                                                                                                                               |

## A strong `Cargo.toml` / `.cargo/config.toml` starting point

Use this only for non-portable, host-specific HPC binaries. For binaries distributed to many CPUs, build per target or use runtime dispatch.

```toml
# Cargo.toml
[profile.release]
opt-level = 3
lto = "thin"          # also test "fat"
codegen-units = 1
panic = "abort"
debug = "line-tables-only"
strip = "symbols"

[profile.bench]
opt-level = 3
lto = "thin"
codegen-units = 1
debug = true
```

```toml
# .cargo/config.toml
[build]
rustflags = [
  "-C", "target-cpu=native"
]
```

Then test variants:

```bash
RUSTFLAGS="-C target-cpu=native" cargo build --release
RUSTFLAGS="-C target-cpu=native -C target-feature=+avx2,+fma" cargo build --release
cargo pgo build
```

`target-cpu=native` is powerful but non-portable. If the binary might run on older CPUs, prefer runtime dispatch or build separate artifacts.

## SIMD and vectorization stack

Use SIMD in layers:

1. Let LLVM auto-vectorize simple loops.
2. Structure data to make vectorization obvious.
3. Use explicit SIMD wrappers.
4. Use ISA-specific kernels for truly hot paths.

| Tool                    | Best use                                                                                                         |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **`std::arch`**         | Stable vendor intrinsics for x86/x86_64/ARM/WASM etc.; maximum control, more `unsafe`. ([Rust Documentation][7]) |
| **nightly `std::simd`** | Portable SIMD API, still under the `portable_simd` nightly feature. ([Rust Documentation][36])                   |
| **`pulp`**              | Safe abstraction over SIMD with runtime dispatch; very useful for writing multi-ISA kernels. ([Docs.rs][37])     |
| **`rten-simd`**         | Safe portable SIMD APIs and runtime dispatch to AVX2/Neon/WASM where available. ([Docs.rs][8])                   |
| **`wide`**              | Portable wide-vector types. Good when you want a simpler API than raw intrinsics. ([Lib.rs][38])                 |
| **`simd-json`**         | Rust port of simdjson-style JSON parsing with Serde compatibility. ([GitHub][39])                                |
| **`sonic-rs`**          | Fast Rust JSON library based on SIMD. ([GitHub][40])                                                             |

Hidden SIMD trick: build a scalar reference kernel, an AVX2 kernel, an AVX-512 kernel, and a NEON/SVE kernel, then dispatch once at startup. That avoids runtime feature checks inside the loop.

```rust
#[inline]
fn dot_scalar(a: &[f32], b: &[f32]) -> f32 {
    a.iter().zip(b).map(|(x, y)| x * y).sum()
}

#[cfg(target_arch = "x86_64")]
fn dot(a: &[f32], b: &[f32]) -> f32 {
    if std::is_x86_feature_detected!("avx2") {
        unsafe { dot_avx2(a, b) }
    } else {
        dot_scalar(a, b)
    }
}

#[cfg(target_arch = "x86_64")]
#[target_feature(enable = "avx2")]
unsafe fn dot_avx2(a: &[f32], b: &[f32]) -> f32 {
    // Use std::arch intrinsics or delegate to a SIMD crate.
    dot_scalar(a, b)
}
```

## Parallelism, synchronization, and NUMA

| Library / technique                         | Why it matters                                                                                                                                                                                                                 |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`rayon`**                                 | The default for CPU data parallelism: `par_iter`, `par_chunks`, parallel reductions, custom thread pools. ([GitHub][9])                                                                                                        |
| **`crossbeam`**                             | Atomics, queues, epoch memory, scoped threads, channels, `CachePadded`. ([GitHub][41])                                                                                                                                         |
| **`parking_lot`**                           | Often faster/smaller lock primitives than `std::sync` for lock-heavy code. ([Lib.rs][42])                                                                                                                                      |
| **`dashmap`**                               | Concurrent hashmap with an ergonomic API similar to `HashMap`. ([GitHub][43])                                                                                                                                                  |
| **`scc`**                                   | High-performance async/concurrent containers; current crates.io listing describes async and sync interfaces. Note: the GitHub repo result says archived Jan. 2026, so check maintenance status before adopting. ([Crates][44]) |
| **`evmap`**                                 | Lock-free/eventually consistent read-heavy map design. ([GitHub][45])                                                                                                                                                          |
| **`flume` / `kanal` / `crossbeam-channel`** | Fast MPMC channel families; benchmark with your message size and contention pattern. `flume` is a safe fast MPMC channel; `kanal` targets fast sync/async CSP-style channels. ([GitHub][46])                                   |
| **`hwlocality`**                            | Rust bindings to hwloc for CPU topology, pinning, and NUMA memory awareness. ([Docs.rs][10])                                                                                                                                   |
| **Folo / `many_cpus`**                      | Hardware-aware Rust runtime ideas for processor and memory topology. ([GitHub][47])                                                                                                                                            |
| **`numaperf`**                              | NUMA-aware toolkit for topology, pinning, memory placement, scheduling, and observability. ([Docs.rs][48])                                                                                                                     |
| **Fork Union**                              | OpenMP-style scoped thread-pool approach with low-latency/NUMA-aware goals; good to investigate for HPC fork-join workloads. ([GitHub][49])                                                                                    |

Great Rayon pattern:

```rust
use rayon::prelude::*;

fn update_grid(grid: &mut [f64], old: &[f64]) {
    grid.par_chunks_mut(4096)
        .zip(old.par_chunks(4096))
        .for_each(|(out, inp)| {
            for (o, x) in out.iter_mut().zip(inp) {
                *o = x.sin() + x.cos();
            }
        });
}
```

Avoid:

* pushing to a shared `Mutex<Vec<_>>` inside `par_iter`
* global atomic counters on every element
* nested Rayon pools without controlling oversubscription
* tiny tasks that are smaller than scheduling overhead
* cross-socket writes to shared cache lines

Use per-thread/per-chunk accumulation and reduce at the end.

## Memory, allocation, layout, zero-copy

| Tool / crate               | Use it for                                                                                                                                                      |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`MaybeUninit`**          | Construct arrays/buffers without unnecessary initialization; official docs show “out-pointer” patterns that avoid unnecessary moves. ([Rust Documentation][50]) |
| **`bumpalo`**              | Fast bump allocation when many objects die together; bump allocation is basically pointer check/update. ([GitHub][51])                                          |
| **`smallvec`**             | Inline small arrays with heap spillover; improves locality and reduces allocator traffic when common sizes fit inline. ([Docs.rs][52])                          |
| **`arrayvec` / `tinyvec`** | Fixed-capacity or small-vector alternatives for avoiding heap allocation.                                                                                       |
| **`compact_str`**          | Small string optimization; useful for metadata-heavy pipelines. ([GitHub][53])                                                                                  |
| **`slotmap`**              | Stable keys with O(1) insert/access/removal; useful for graph/mesh/entity pools. ([GitHub][54])                                                                 |
| **`memmap2`**              | Memory-mapped files as slice-like buffers for huge datasets and zero-copy-ish file access. ([Docs.rs][55])                                                      |
| **`rkyv`**                 | Zero-copy serialization/deserialization; excellent for read-mostly persisted data. ([GitHub][13])                                                               |
| **`zerocopy`**             | Safe zero-copy conversion between byte sequences and typed structures. ([GitHub][56])                                                                           |
| **`bytemuck`**             | Safe casting utilities for plain-data types and slices. ([Docs.rs][57])                                                                                         |
| **`mmap-sync`**            | Cloudflare project for concurrent mmap-backed data access, wait-free synchronization, and zero-copy deserialization. ([GitHub][58])                             |

Allocator swap example:

```rust
use mimalloc::MiMalloc;

#[global_allocator]
static GLOBAL: MiMalloc = MiMalloc;
```

Preallocation pattern:

```rust
let mut buf = Vec::<f64>::with_capacity(n);
buf.resize(n, 0.0);

// Better for repeated phases:
let mut scratch = vec![0.0; n];
for step in 0..steps {
    scratch.fill(0.0);
    // reuse scratch
}
```

`MaybeUninit` is powerful but should be isolated behind safe APIs. Avoid old `mem::uninitialized`; Rust docs mark that path deprecated in favor of `MaybeUninit`. ([public-docs.ferrocene.dev][59])

## Hashing, maps, and lookup speed

Rust’s default `HashMap` is secure, not the fastest possible choice. For compute workloads with trusted keys, pick the hasher intentionally.

| Tool                            | Best use                                                                                                                                                       |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`rustc-hash` / `FxHashMap`**  | Very fast, lower-quality hash; Rust Performance Book notes it is especially fast for integer keys and used inside rustc workloads. ([Nicholas Nethercote][60]) |
| **`ahash`**                     | Fast general-purpose hash map hasher, often a great default for trusted high-throughput maps. ([Nicholas Nethercote][60])                                      |
| **`foldhash`**                  | Fast non-cryptographic, minimally DoS-resistant hash designed for computational uses like hash maps and bloom filters. ([GitHub][61])                          |
| **`nohash-hasher` / `nohash`**  | Integer keys where hashing can be bypassed; `IntMap` uses `NoHashHasher` to perform no hashing for integer domains. ([Docs.rs][62])                            |
| **`xxhash-rust` / `twox-hash`** | Fast non-cryptographic hashing; xxHash is designed to run near RAM-speed limits. ([GitHub][63])                                                                |
| **`hashbrown`**                 | SwissTable-derived hashmap implementation; useful if you need lower-level control or no-std-ish behavior.                                                      |

Rule of thumb: for dense integer IDs, use `Vec<T>` or `Vec<Option<T>>` before any hash map. For sparse trusted keys, try `ahash`/`foldhash`/`rustc-hash`. For untrusted external keys, keep DoS resistance in mind.

## Data engines, Arrow, analytics, query execution

| Library              | Why it matters                                                                                                                                                                        |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Polars**           | Extremely fast Rust dataframe/query engine; supports eager/lazy APIs, streaming larger-than-RAM execution, query optimization, multithreading, SIMD, and Arrow memory. ([GitHub][64]) |
| **DataFusion**       | Extensible query engine in Rust built around Apache Arrow memory. Excellent when you need SQL/plans/operators rather than just arrays. ([GitHub][65])                                 |
| **Arrow / arrow-rs** | Columnar in-memory data representation; a critical zero-copy format for analytics, IPC, Parquet, and vectorized compute. ([GitHub][66])                                               |
| **Parquet crates**   | Use column pruning, predicate pushdown, row-group sizing, and Arrow integration for throughput.                                                                                       |
| **`object_store`**   | Data lake / cloud-object-store access patterns; useful for distributed analytics stacks.                                                                                              |
| **`zarrs`**          | Worth checking for chunked scientific arrays/Zarr workflows.                                                                                                                          |

For tabular HPC/data workloads, Polars or DataFusion often beats handcrafted loops because they bring query planning, columnar layout, predicate pushdown, vectorization, and parallel execution.

## “People miss these” Rust HPC tricks

### 1. Use `chunks_exact` and `zip` to help LLVM

```rust
fn saxpy(a: f32, x: &[f32], y: &mut [f32]) {
    assert_eq!(x.len(), y.len());

    for (yi, xi) in y.iter_mut().zip(x.iter()) {
        *yi += a * *xi;
    }
}
```

This often optimizes better than repeated `y[i]`/`x[i]` indexing because the iterator shape proves bounds relationships.

### 2. Pre-split mutable slices instead of fighting the borrow checker

```rust
let (left, right) = data.split_at_mut(mid);
// process left and right independently, possibly in Rayon scopes
```

This creates non-overlapping mutable regions that Rust and LLVM can reason about.

### 3. Reduce per-thread, then merge

Bad:

```rust
// hot loop contends on one atomic
counter.fetch_add(1, Ordering::Relaxed);
```

Better:

```rust
let total: usize = data.par_chunks(4096)
    .map(|chunk| chunk.iter().filter(|x| predicate(x)).count())
    .sum();
```

### 4. Pad hot atomics and counters

```rust
use crossbeam_utils::CachePadded;
use std::sync::atomic::{AtomicU64, Ordering};

struct Counters {
    hits: CachePadded<AtomicU64>,
    misses: CachePadded<AtomicU64>,
}
```

This avoids independent counters bouncing the same cache line.

### 5. Use `#[cold]` for error/reporting slow paths

```rust
#[cold]
fn bad_shape() -> ! {
    panic!("shape mismatch")
}

fn kernel(a: &[f64], b: &[f64]) {
    if a.len() != b.len() {
        bad_shape();
    }
    // hot path
}
```

### 6. Don’t let logging poison the hot path

Use counters, sampling, or aggregate diagnostics outside the loop. Even disabled formatting can leak into performance if you build strings before checking log level.

### 7. Convert AoS to SoA

Often worse:

```rust
struct Particle {
    x: f32,
    y: f32,
    z: f32,
    vx: f32,
    vy: f32,
    vz: f32,
}
Vec<Particle>
```

Often better for vectorized compute:

```rust
struct Particles {
    x: Vec<f32>,
    y: Vec<f32>,
    z: Vec<f32>,
    vx: Vec<f32>,
    vy: Vec<f32>,
    vz: Vec<f32>,
}
```

### 8. Separate hot and cold fields

Keep fields used in the inner loop together. Move IDs, metadata, strings, diagnostics, and optional data elsewhere.

### 9. Use `f32` intentionally

Many scientific codes default to `f64`. If the math tolerates `f32` or mixed precision, memory bandwidth and SIMD width can improve dramatically.

### 10. Prefer batch APIs

One call over 1 million values beats 1 million calls over one value. Design Rust APIs around slices, chunks, and views.

### 11. Use prefetch only after evidence

Rust exposes nightly `prefetch_read_data`; docs describe it as an intrinsic that may no-op if unsupported. Hardware prefetchers are already good, so use software prefetch only after profiler evidence. ([Rust Documentation][98])

### 12. Avoid generic abstraction in the final inner loop unless it monomorphizes cleanly

Traits and generics are fine when monomorphized. Trait objects, callbacks, iterators with complex adapters, or dynamic dispatch inside the hottest loop need measurement.

### 13. Fuse passes

Three passes over a huge array can be slower than one fused pass even if each pass is clean. This is why GPU tensor frameworks and query engines focus heavily on fusion.

### 14. Make shape/stride checks once

Validate dimensions outside the loop, then call a small internal kernel that assumes valid shapes.

### 15. Know when `unsafe` helps — and when it doesn’t

`unsafe` can remove bounds checks, express alignment, use intrinsics, and manage uninitialized memory. It does not fix bad layout, random memory access, poor algorithm choice, or cross-socket false sharing.

## Workload-specific recommendations

### Dense linear algebra

Start with `faer`. Use `ndarray` if N-dimensional array ergonomics matter. Use `ndarray-linalg` + OpenBLAS/MKL if external native libraries are acceptable. Use `matrixmultiply` for GEMM-like internals.

### Stencils, PDEs, CFD, simulation grids

Use SoA layout, ghost-cell padding, blocked tiles, Rayon over tiles, NUMA first-touch allocation, `CachePadded` reductions, and explicit SIMD for inner stencil kernels.

### Sparse solvers / graph-like numerical work

Use CSR/CSC layouts, `sprs`, custom index-width choices, prefetch-friendly ordering, partitioning, and per-thread scratch buffers. Reordering can beat micro-optimization.

### FFT/DSP

Use `RustFFT`/`realfft`; pre-plan transforms, reuse buffers, and batch transforms to amortize setup and improve cache locality.

### Particle/N-body

Use `kiddo` for k-d tree lookup, `kifmm` for fast multipole methods, SoA particle arrays, Morton/Hilbert ordering, and chunked pair evaluation.

### Dataframes / analytics

Use Polars first. Use DataFusion when you need a query engine, SQL, custom logical/physical plans, or Arrow-native integration.

### ML/tensors

Use Burn/CubeCL for Rust-native tensor/GPU exploration, Candle for compact inference/training workflows, `cudarc` for CUDA-specific kernels, and `tch-rs` when libtorch/PyTorch ecosystem compatibility matters.

### Cluster HPC

Use MPI for conventional HPC, Lamellar for Rust-native PGAS/tasking experiments, Rayon inside each rank, and HDF5/netCDF/Zarr/Arrow/Parquet for data.

## The underused “breakthrough” combo

For a single-node CPU HPC code, the stack I’d try first is:

```text
Criterion/Divan + perf
→ release profile: opt=3, lto=thin/fat, codegen-units=1, target-cpu=native
→ SoA layout + chunked contiguous loops
→ Rayon par_chunks + per-thread scratch/reductions
→ CachePadded for shared counters
→ mimalloc/jemalloc if allocation-heavy
→ explicit SIMD via pulp/rten-simd/std::arch
→ PGO + BOLT
→ hwlocality/numaperf for pinning and NUMA
```

For a GPU-capable code:

```text
CPU reference kernel
→ batch/fuse operations
→ measure transfer/computation ratio
→ CubeCL/Burn for portable Rust-native GPU kernels
→ cudarc/cust for NVIDIA-specific kernels
→ double buffering + pinned/mapped memory where backend supports it
→ keep data resident on device across multiple kernels
```

For distributed HPC:

```text
Rayon inside rank
→ MPI or Lamellar across nodes
→ NUMA-aware per-rank memory placement
→ Arrow/HDF5/Zarr/Parquet data layout
→ RDMA/UCX only when MPI/storage layers are not enough
```

## A final caution that matters

The fastest Rust HPC code usually looks “boring”: slices, arrays, explicit layouts, batch APIs, preallocated scratch buffers, few branches, few allocations, measured parallelism, and carefully selected libraries. The advanced magic is less about sprinkling `unsafe` everywhere and more about making the compiler, memory hierarchy, SIMD units, GPU, and scheduler all see the same simple structure.
