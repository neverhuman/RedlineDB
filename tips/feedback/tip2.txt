# 1. Fix secondary-index range/count/covering scans

## Benchmarks targeted

```text
secondary-index-range       0.048×
secondary-index-count       Phase 11 gate target/floor exists, raw results missing
covered-range-cold/warm     Phase 11 gate target/floor exists, raw results missing
secondary-index-ordered-limit related
```

## Key issue

The range-scan code has several good Phase 11 starts, but the low Phase 10 number makes sense after reading the code.

The workload is:

```sql
SELECT COUNT(*) FROM kv WHERE tenant BETWEEN ?1 AND ?2
```

from `crates/bench/src/workload.rs`.

The SQL executor has a `COUNT(*)` fast path in `crates/sql/src/exec/select_top.rs`, and `crates/sql/src/exec/index_batch.rs` has `execute_index_count_range`. That is promising, but raw Phase 11 results are missing, so the improvement is not proven in this archive.

For non-count range scans, the current path still commonly does this:

1. Use the B-tree index to collect row IDs.
2. Materialize a `Vec<RowId>`.
3. Heap-load rows later.
4. Heap recheck batching tries to group by `IndexRowRef.tuple.page_id`.
5. But SQL index entries use a synthetic tuple pointer: page `0`, slot `0`.

The smoking gun is in `crates/sql/src/exec/index_dml.rs`:

```rust
pub(crate) fn synthetic_row_ref(rowid: RowId) -> IndexRowRef {
    IndexRowRef::with_row_id(
        rowid,
        TuplePtr::new_with_generation(PageId(0), 0, PageGeneration::ONE),
    )
}
```

So the grouping logic in `index_batch.rs` is mostly fake for SQL indexes. It groups everything by page 0, which cannot improve heap locality.

The second issue is cursor prefetch. `IndexCursor` has prefetch logic, but `RawIndexCursor`, which is used by count/covering/ordered fast paths, lacks the same warm-leaf reuse/prefetch machinery. The README explicitly calls this out: large secondary-index range scans lack prefetch and warm-leaf reuse.

## Proposed change

Implement three pieces together:

1. **Store real heap tuple back-pointers in SQL index entries.**
   Replace synthetic `TuplePtr(PageId(0), slot 0)` with the actual tuple pointer produced by heap insert/update.

2. **Make range scans stream batches instead of materializing all row IDs.**
   Return rows through a streaming runtime or callback so large range scans do not allocate huge `Vec<RowId>` and then perform a second pass.

3. **Add RawIndexCursor prefetch/warm-leaf reuse.**
   Mirror `IndexCursor`’s prefetch hints inside `RawIndexCursor`, because the fast count/covering paths use raw cursor APIs.

## Code example: heap writes should return the tuple pointer

Right now `PageBackedHeap::insert_for_relation` and `update_for_relation` return `Result<()>`, even though internally `append_tuple` already returns `TuplePtr`.

Change that API to surface the pointer.

```rust
// crates/kernel/src/engine/page_heap.rs

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub struct RelationWriteResult {
    pub rel_id: RelId,
    pub row_id: RowId,
    pub tuple: TuplePtr,
}

pub fn insert_for_relation(
    &self,
    tx_id: TxId,
    rel_id: RelId,
    row_id: RowId,
    payload: Vec<u8>,
    lsn: Lsn,
) -> Result<RelationWriteResult> {
    let rel_id = if rel_id == RelId::ZERO { self.rel_id } else { rel_id };

    advance_atomic_past(&self.next_row, row_id.0);

    let wal_payload = if lsn != Lsn::ZERO {
        Some(WalPayload::HeapInsert {
            tx_id,
            rel_id,
            row_id,
            payload: payload.clone(),
        })
    } else {
        None
    };

    let tuple = TupleVersion::new(row_id, rel_id, tx_id, payload);
    let ptr = self.append_tuple(tx_id, row_id, tuple, lsn, wal_payload)?;

    self.set_head(row_id, ptr)?;
    self.set_relation_head(rel_id, row_id, ptr)?;

    Ok(RelationWriteResult {
        rel_id,
        row_id,
        tuple: ptr,
    })
}

pub fn update_for_relation(
    &self,
    tx_id: TxId,
    snapshot: &Snapshot,
    tx_status: &ConcurrentTxStatus,
    target: RelationWriteTarget,
    payload: Vec<u8>,
    lsn: Lsn,
) -> Result<RelationWriteResult> {
    let rel_id = if target.rel_id == RelId::ZERO {
        self.rel_id
    } else {
        target.rel_id
    };

    let current = self.visible_tuple_for_write_in_relation(
        tx_id,
        snapshot,
        tx_status,
        RelationWriteTarget {
            rel_id,
            row_id: target.row_id,
        },
    )?;

    let ptr = self.append_update_version_returning_ptr(
        tx_id,
        rel_id,
        target.row_id,
        payload,
        current,
        lsn,
    )?;

    Ok(RelationWriteResult {
        rel_id,
        row_id: target.row_id,
        tuple: ptr,
    })
}

fn append_update_version_returning_ptr(
    &self,
    tx_id: TxId,
    rel_id: RelId,
    row_id: RowId,
    payload: Vec<u8>,
    current: TupleVersion,
    lsn: Lsn,
) -> Result<TuplePtr> {
    let wal_payload = if lsn != Lsn::ZERO {
        Some(WalPayload::HeapUpdate {
            tx_id,
            rel_id,
            row_id,
            payload: payload.clone(),
        })
    } else {
        None
    };

    let mut before = current.clone();
    before.end_tx = tx_id;

    let undo_ptr = self.append_undo(
        tx_id,
        row_id,
        UndoRecord {
            kind: UndoKind::UpdateBeforeImage,
            tx_id,
            row_id,
            prev_undo: current.undo_head,
            before_image: before.encode()?,
        },
        lsn,
    )?;

    let mut next = TupleVersion::new(row_id, rel_id, tx_id, payload);
    next.undo_head = undo_ptr;

    let ptr = self.append_tuple(tx_id, row_id, next, lsn, wal_payload)?;
    self.set_head(row_id, ptr)?;
    self.set_relation_head(rel_id, row_id, ptr)?;

    Ok(ptr)
}
```

```rust
#[allow(clippy::too_many_arguments)]
pub(crate) fn maintain_indexes_on_update(
    engine: &Engine,
    tx: &Txn,
    table: &TableDef,
    old_values: &[SqlValue],
    new_values: &[SqlValue],
    old_rowid: RowId,
    new_rowid: RowId,
    old_tuple: TuplePtr,
    new_tuple: TuplePtr,
) -> Result<()> {
    for index in &table.indexes {
        let Some(handle) = open_index_handle(engine, index) else {
            continue;
        };

        let old_key = build_index_key(index, old_values);
        let new_key = build_index_key(index, new_values);

        if old_key.bytes == new_key.bytes && old_rowid == new_rowid {
            continue;
        }

        let old_row = row_ref_for_tuple(old_rowid, old_tuple);
        let new_row = row_ref_for_tuple(new_rowid, new_tuple);

        handle.delete_mark_tx_visible(
            engine.tx_status(),
            tx.snapshot(),
            Some(tx.id()),
            tx.id(),
            &old_key.bytes,
            old_row,
        )?;

        handle.insert_tx(tx.id(), &new_key.bytes, new_row)?;
    }

    Ok(())
}
```

Once this is in place, the page grouping in `process_recheck_batch` becomes real instead of synthetic.

## Code example: add prefetch to `RawIndexCursor`

The exact field names should match `crates/kernel/src/index/cursor.rs`, but the shape should be this:

```rust
// crates/kernel/src/index/cursor.rs

pub struct RawIndexCursor {
    handle: Arc<BtreeIndex>,
    range: KeyRange,
    view: SnapshotView,
    current_leaf: Option<PageId>,
    right_link: Option<PageId>,
    entry_idx: usize,
    entries: Vec<LeafEntry>,
    counters: Option<Arc<Phase11Counters>>,
    prefetch_hints_emitted: u64,
}

impl RawIndexCursor {
    fn load_current_leaf(&mut self) -> Result<()> {
        let Some(page_id) = self.current_leaf else {
            self.entries.clear();
            self.right_link = None;
            return Ok(());
        };

        let guard = self.handle.buffer().pin(page_id)?;

        guard.with_page(|page| {
            self.entries.clear();

            let leaf = decode_leaf(page)?;
            self.right_link = leaf.right_link;

            for entry in leaf.entries {
                if self.range.contains(entry.logical_key()) {
                    self.entries.push(entry);
                }
            }

            Ok(())
        })?;

        if let Some(next) = self.right_link {
            self.prefetch_hint(next);
        }

        Ok(())
    }

    fn prefetch_hint(&mut self, page_id: PageId) {
        self.prefetch_hints_emitted += 1;

        if let Some(counters) = &self.counters {
            counters
                .cursor_prefetch_hints
                .fetch_add(1, std::sync::atomic::Ordering::Relaxed);
        }

        self.handle.buffer().prefetch(page_id);
    }

    fn advance_to_right_link(&mut self) -> Result<bool> {
        let Some(next) = self.right_link else {
            self.current_leaf = None;
            self.entries.clear();
            return Ok(false);
        };

        self.current_leaf = Some(next);
        self.entry_idx = 0;
        self.load_current_leaf()?;

        Ok(true)
    }
}
```

# 2. Fix `secondary-index-read`: ordered point lookup with `ORDER BY k LIMIT 1`

## Benchmark targeted

```text
secondary-index-read: 0.13×
```

The workload query is:

```sql
SELECT k, v FROM kv WHERE tenant = ?1 ORDER BY k LIMIT 1
```

This should be an easy index point/range path:

1. `tenant = ?1` gives a point lookup on the secondary index leading column.
2. `k` is the rowid alias / primary key.
3. B-tree secondary index entries already include rowid as a suffix.
4. `ORDER BY k LIMIT 1` can stop after the first visible rowid in that tenant bucket.
5. Only one heap fetch is needed for `v`.

The code has a partial shortcut in `select_top.rs` / `index_batch.rs`: a single-key index plus `ORDER BY` rowid alias and `Point` match can use `execute_index_probe_with_limit`. That is the right direction, but it needs hardening and proof.

## Key issue

Current risks:

1. The ordered-limit path is executor-local and not clearly exposed as a planned access path.
2. `execute_index_range_scan_ordered` returns rowids from `RawIndexCursor` without heap recheck.
3. The path still heap-loads the row later, which is unavoidable for `v` unless both SQLite and RedlineDB use a fair covering index.
4. There is not enough benchmark telemetry proving this path was actually hit during `secondary-index-read`.

## Proposed change

Promote the ordered-limit shortcut into a first-class access path with instrumentation:

```text
AccessPath::IndexOrderedLimit {
    index_id,
    probe_kind: Point,
    order_kind: RowidSuffixAsc,
    limit,
}
```

Then make the execution path:

```text
Raw index cursor -> visible rowid batch -> heap recheck until N visible rows -> return rowid(s)
```

For this benchmark, `N = 1`.

## Code example: make order satisfaction explicit

```rust
// crates/sql/src/exec/index_access.rs

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub(crate) enum IndexOrderSatisfaction {
    None,
    LeadingKeyAsc,
    RowidSuffixAsc,
}

pub(crate) fn order_satisfied_by_index(
    table: &TableDef,
    index: &IndexDef,
    probe: &IndexProbe,
    order_by: &[OrderByExpr],
) -> IndexOrderSatisfaction {
    if order_by.is_empty() {
        return IndexOrderSatisfaction::None;
    }

    // Case used by:
    // SELECT k, v FROM kv WHERE tenant = ? ORDER BY k LIMIT 1
    //
    // tenant index layout: tenant || rowid suffix
    // Equality on tenant means the remaining physical order is rowid.
    if index.keys.len() == 1
        && matches!(probe, IndexProbe::Point { .. })
        && order_by_rowid_alias(table, order_by)
    {
        return IndexOrderSatisfaction::RowidSuffixAsc;
    }

    if covering_order_satisfies(index, order_by) {
        return IndexOrderSatisfaction::LeadingKeyAsc;
    }

    IndexOrderSatisfaction::None
}
```

## Code example: heap-rechecked ordered limit

```rust
// crates/sql/src/exec/index_batch.rs

pub(super) fn execute_ordered_probe_with_heap_recheck(
    engine: &Engine,
    tx: &mut Txn,
    table: &Arc<TableDef>,
    index: &IndexDef,
    start: &[u8],
    end: &[u8],
    limit: usize,
) -> Result<Vec<RowId>> {
    let Some(handle) = open_handle(engine, index) else {
        return Ok(Vec::new());
    };

    let counters = engine.phase11_counters();
    counters
        .ordered_limit_path_hits
        .fetch_add(1, AtomicOrdering::Relaxed);

    let snapshot = tx.snapshot().clone();
    let owner = Some(tx.id());
    let view = SnapshotView::visible(engine.tx_status(), &snapshot, owner);
    let range = KeyRange::half_open(start, end);

    let mut cursor =
        RawIndexCursor::open_with_counters(&handle, range, view, Some(&*counters))?;

    let mut out = Vec::with_capacity(limit);
    let mut batch = Vec::with_capacity(MAX_BATCH);

    while out.len() < limit {
        batch.clear();

        match cursor.next_rowid_batch(&mut batch, MAX_BATCH)? {
            CursorYield::End => break,
            CursorYield::Batch(_) => {
                for entry in &batch {
                    if visible_in_relation(engine, tx, table, entry.row_id)? {
                        out.push(entry.row_id);

                        if out.len() == limit {
                            break;
                        }
                    }
                }
            }
        }
    }

    cursor.close();

    counters
        .ordered_limit_rows_returned
        .fetch_add(out.len() as u64, AtomicOrdering::Relaxed);

    Ok(out)
}
```

It will not make RedlineDB faster than SQLite by itself because the query still loads `v` from the heap, but it should remove unnecessary range materialization/sorting and make the path much closer to SQLite’s “seek tenant bucket, return first rowid” behavior.

# 3. Fix hot-row and hot-counter update paths

## Benchmarks targeted

```text
hot-row-update:     0.44×
hot-counter-update: Phase 11 baseline/gate, raw result missing
```

## Key issue

The benchmark query for `hot-row-update` is:

```sql
UPDATE kv SET v = ?1, version = version + 1 WHERE k = ?2
```

with `k = 0`.

The benchmark query for `hot-counter-update` is:

```sql
UPDATE hot_counter SET counter = counter + 1 WHERE pk = ?1
```

The code path in `crates/sql/src/exec/tail.rs` is expensive under single-row contention:

1. Locate target rowid.
2. `lock_row_for_relation`.
3. Reload the row.
4. Recheck predicate.
5. Evaluate assignments.
6. Run constraints.
7. Encode the new payload.
8. Call `engine.update_for_relation`.
9. `engine.update_for_relation` locks the row again.
10. Maintain indexes.

The double lock is visible:

```text
tail.rs:
  lock_row_for_relation(...)

engine/mod.rs:
  update_for_relation(...)
    lock_row_in_rel(...)
```

The second lock is reentrant, but it still burns time in the lock table under heavy contention.

There is also a WAL combiner module, but it is not integrated into runtime commit/update flow. The workplan calls the semantic combiner deferred.

## Proposed change

Split hot-row work into two levels:

### 3A. Safe improvements for general `hot-row-update`

These apply to the blob update benchmark without changing semantics:

1. Add `Engine::update_for_relation_locked` so SQL can update after it already acquired the row lock.
2. Avoid rebuilding index keys when assignment columns do not intersect any index key columns.
3. Use a contention-aware wait/backoff path instead of a tight rollback/yield retry loop.
4. Add lock-wait and hot-row telemetry to the benchmark artifact.

### 3B. Narrow commutative-delta fast path for `hot-counter-update`

This should **not** be applied to the general blob-writing `hot-row-update`. It is only safe for shapes like:

```sql
UPDATE t SET counter = counter + ? WHERE pk = ?
```

where:

```text
counter is INTEGER
counter is not indexed
rowid/pk predicate identifies exactly one row
no RETURNING
no trigger
no foreign-key side effect
no generated column/check expression depending on counter, unless rechecked
autocommit or otherwise proven safe
```

## Code example: skip index work when UPDATE cannot affect indexes

Right now `maintain_indexes_on_update` builds old and new keys for every index before discovering they are equal. Add an assignment mask.

```rust
// crates/sql/src/exec/index_dml.rs

pub(crate) fn update_touches_index(
    index: &IndexDef,
    touched_attnums: &FixedBitSet,
    rowid_changed: bool,
) -> bool {
    if rowid_changed {
        return true;
    }

    index.keys.iter().any(|key| match key.source {
        IndexKeySource::Column { attnum } => touched_attnums.contains(attnum as usize),
    })
}

#[allow(clippy::too_many_arguments)]
pub(crate) fn maintain_indexes_on_update(
    engine: &Engine,
    tx: &Txn,
    table: &TableDef,
    old_values: &[SqlValue],
    new_values: &[SqlValue],
    old_rowid: RowId,
    new_rowid: RowId,
    old_tuple: TuplePtr,
    new_tuple: TuplePtr,
    touched_attnums: &FixedBitSet,
) -> Result<()> {
    let rowid_changed = old_rowid != new_rowid;

    for index in &table.indexes {
        if !update_touches_index(index, touched_attnums, rowid_changed) {
            continue;
        }

        let Some(handle) = open_index_handle(engine, index) else {
            continue;
        };

        let old_key = build_index_key(index, old_values);
        let new_key = build_index_key(index, new_values);

        if old_key.bytes == new_key.bytes && !rowid_changed {
            continue;
        }

        handle.delete_mark_tx_visible(
            engine.tx_status(),
            tx.snapshot(),
            Some(tx.id()),
            tx.id(),
            &old_key.bytes,
            row_ref_for_tuple(old_rowid, old_tuple),
        )?;

        handle.insert_tx(
            tx.id(),
            &new_key.bytes,
            row_ref_for_tuple(new_rowid, new_tuple),
        )?;
    }

    Ok(())
}
```

For the `kv` benchmark table, the secondary index is on `tenant`, while `hot-row-update` updates `v` and `version`. This means index maintenance can be skipped without even building `tenant` keys.

## Code example: narrow commutative counter recognizer

```rust
pub(crate) struct CounterDeltaShape {
    pub table: Arc<TableDef>,
    pub rowid: RowId,
    pub column_attnum: usize,
    pub delta: i64,
}

pub(crate) fn match_counter_delta_update(
    stmt: &UpdateStatement,
    bindings: &BoundParams,
    table: Arc<TableDef>,
) -> Result<Option<CounterDeltaShape>> {
    // Required shape:
    // UPDATE table SET col = col + <integer> WHERE pk = <bound/integer>
    //
    // Reject:
    // - multiple assignments
    // - expression using another column
    // - non-integer delta
    // - no exact pk/rowid equality
    // - indexed target column
    // - RETURNING/triggers/FK side effects until supported safely.

    if stmt.assignments.len() != 1 {
        return Ok(None);
    }

    let assignment = &stmt.assignments[0];

    let Some(column_attnum) = table.column_attnum(&assignment.column) else {
        return Ok(None);
    };

    if table.indexes.iter().any(|idx| index_uses_attnum(idx, column_attnum)) {
        return Ok(None);
    }

    let Some(delta) = parse_self_plus_integer_delta(&assignment.expr, &assignment.column, bindings)? else {
        return Ok(None);
    };

    let Some(rowid) = parse_exact_rowid_predicate(&stmt.where_clause, bindings, &table)? else {
        return Ok(None);
    };

    Ok(Some(CounterDeltaShape {
        table,
        rowid,
        column_attnum,
        delta,
    }))
}
```

## Code example: execute counter delta in SQL while keeping kernel SQL-agnostic

The kernel should not learn SQL value encoding. Keep SQL decode/encode in SQL, but use the new locked update API.

```rust
// crates/sql/src/exec/commutative_update.rs

pub(crate) fn try_execute_counter_delta(
    conn: &mut SqlConnection,
    stmt: &UpdateStatement,
    bindings: &BoundParams,
) -> Result<Option<ExecutionResult>> {
    let table = conn.catalog().resolve_table(&stmt.table)?;

    let Some(shape) = match_counter_delta_update(stmt, bindings, Arc::clone(&table))? else {
        return Ok(None);
    };

    let result = with_write_tx(conn, |conn, tx| {
        let engine = conn.engine();

        engine.lock_row_for_relation(tx, shape.table.rel_id, shape.rowid)?;

        let payload = engine
            .load_table_row_by_rowid(tx, shape.table.rel_id, shape.rowid)?
            .ok_or(Error::NotVisible)?;

        let mut values = decode_sql_row(&shape.table, &payload)?;

        let current = values[shape.column_attnum]
            .as_i64()
            .ok_or_else(|| Error::Type("counter delta requires INTEGER".into()))?;

        let next = current
            .checked_add(shape.delta)
            .ok_or_else(|| Error::IntegerOverflow)?;

        values[shape.column_attnum] = SqlValue::Integer(next);

        let new_payload = encode_sql_row(&shape.table, &values)?;

        engine.update_for_relation_locked(
            tx,
            shape.table.rel_id,
            shape.rowid,
            new_payload,
        )?;

        Ok(build_dml_execution_result(1, Vec::new(), false))
    })?;

    Ok(Some(result))
}
```

This version improves lock/update overhead but does not yet combine multiple logical increments. The next step is integrating `WalCombiner` so multiple deltas can be merged physically while still preserving logical transaction acknowledgements and recovery.

## Expected impact

For `hot-row-update`, the realistic first target is reducing overhead around the unavoidable single-row serialization. This should improve the 0.44× number but probably will not make it beat SQLite.

For `hot-counter-update`, a true commutative-delta path can be much larger, because `counter = counter + 1` is mergeable. That path should be proven separately and not conflated with arbitrary blob writes.

# 4. Fix HNSW low-M recall

## Benchmark targeted

```text
HNSW recall@10 ≥ 0.95 at M=16
```

The workplan says:

```text
M=32, efC=200, recall@10=0.9526 at efS=64
HNSW recall@10 ≥ 0.95 at M=16 is deferred/current impl needs M=32
```

The benchmark workload currently sets:

```rust
params.m = 16;
params.m_max0 = 32;
params.ef_construction = 128;
params.ef_search = 96;
```

The ignored recall test asserts success with `M=32`, not `M=16`, so the low-M target is not actually locked down by a passing test.

## Key issue found in code

There is a likely HNSW topology bug in `crates/kernel/src/vector/hnsw/builder.rs`.

`extend_candidates` is called while linking a specific layer, but it expands candidates using **layer 0 neighbors**:

```rust
let nbrs: Vec<u32> = graph
    .neighbors_at(cand_id, 0)
    .map(|s| s.to_vec())
    .unwrap_or_default();
```

That is wrong for upper layers. A candidate at layer 2 should be expanded through layer 2 neighbors, not layer 0 neighbors.

Worse, neither `select_neighbors_heuristic` nor `back_link_with_pruning` filters candidates by whether they actually live at the current layer. And `Graph::set_neighbors_at` will extend a node’s `neighbors` vector even if that node’s assigned `layer` is lower:

```rust
while node.neighbors.len() <= layer as usize {
    node.neighbors.push(Vec::new());
}
node.neighbors[layer as usize] = list;
```

That means the builder can create upper-layer adjacency lists for nodes that were not assigned to those upper layers. This violates the standard HNSW layer invariant and can distort search quality. Before tuning `ef_construction`, this invariant needs to be fixed and tested.

## Proposed change

1. Add graph-layer invariant checks.
2. Make `extend_candidates` layer-aware.
3. Filter neighbor candidates by `graph.layer_of(id) >= layer`.
4. Prevent reciprocal backlinks to nodes below the current layer.
5. Then tune M=16 using deterministic sweeps:

   * `ef_construction = 128, 200, 300, 400`
   * `ef_search = 64, 96, 128`
6. Update the benchmark default only after the sweep proves the lowest-cost setting that reaches recall@10 ≥ 0.95.

## Code example: layer-aware candidate extension

```rust
// crates/kernel/src/vector/hnsw/builder.rs

fn node_lives_at_layer(graph: &Graph, id: u32, layer: u8) -> Result<bool> {
    Ok(graph.layer_of(id)? >= layer)
}

fn extend_candidates(
    graph: &Graph,
    metric: Metric,
    query: &[f32],
    candidates: &[(f32, u32)],
    cap: usize,
    layer: u8,
) -> Result<Vec<(f32, u32)>> {
    use std::collections::HashSet;

    let mut seen = HashSet::with_capacity(candidates.len() * 4);
    let mut out = Vec::with_capacity(candidates.len() * 4);

    for (d, id) in candidates {
        if !node_lives_at_layer(graph, *id, layer)? {
            continue;
        }

        if seen.insert(*id) {
            out.push((*d, *id));
        }
    }

    let cap_ext = cap * 4;
    let originals: Vec<u32> = out.iter().map(|(_, id)| *id).collect();

    'outer: for cand_id in originals {
        // Critical fix: use the current layer, not layer 0.
        let nbrs = graph.neighbors_at(cand_id, layer)?.to_vec();

        for nb in nbrs {
            if !node_lives_at_layer(graph, nb, layer)? {
                continue;
            }

            if !seen.insert(nb) {
                continue;
            }

            let d = metric.distance(query, graph.vector_of(nb)?)?;
            out.push((d, nb));

            if out.len() >= cap_ext {
                break 'outer;
            }
        }
    }

    out.sort_by(|a, b| a.0.total_cmp(&b.0));
    Ok(out)
}
```

```rust
)?;
```

## Code example: filter selected neighbors by layer

```rust
fn select_neighbors_heuristic(
    graph: &Graph,
    metric: Metric,
    _query: &[f32],
    query_owner: u32,
    candidates: &[(f32, u32)],
    cap: usize,
    layer: u8,
) -> Result<Vec<u32>> {
    let mut sorted: Vec<(f32, u32)> = Vec::new();

    for (dist, id) in candidates {
        if *id == query_owner {
            continue;
        }

        if graph.layer_of(*id)? < layer {
            continue;
        }

        sorted.push((*dist, *id));
    }

    sorted.sort_by(|a, b| a.0.total_cmp(&b.0));

    let mut result = Vec::with_capacity(cap);
    let mut overflow = Vec::new();

    for (d_to_q, cand) in &sorted {
        if result.len() >= cap {
            break;
        }

        let cand_vec = graph.vector_of(*cand)?.to_vec();
        let mut admit = true;

        for r in &result {
            let d_to_r = metric.distance(&cand_vec, graph.vector_of(*r)?)?;

            if d_to_r < *d_to_q {
                admit = false;
                break;
            }
        }

        if admit {
            result.push(*cand);
        } else {
            overflow.push(*cand);
        }
    }

    while result.len() < cap && !overflow.is_empty() {
        result.push(overflow.remove(0));
    }

    Ok(result)
}
```

## Code example: prevent illegal backlinks

```rust
fn back_link_with_pruning(
    graph: &mut Graph,
    metric: Metric,
    nb: u32,
    layer: u8,
    new_id: u32,
    cap: usize,
) -> Result<()> {
    // Critical guard: do not create layer-N adjacency on a node whose
    // assigned maximum layer is below N.
    if graph.layer_of(nb)? < layer {
        return Ok(());
    }

    if graph.layer_of(new_id)? < layer {
        return Ok(());
    }

    let mut nb_list = graph.neighbors_at(nb, layer)?.to_vec();

    if !nb_list.contains(&new_id) {
        nb_list.push(new_id);
    }

    if nb_list.len() <= cap {
        graph.set_neighbors_at(nb, layer, nb_list)?;
        return Ok(());
    }

    let nb_vec = graph.vector_of(nb)?.to_vec();

    let mut scored = Vec::with_capacity(nb_list.len());
    for cand in &nb_list {
        if graph.layer_of(*cand)? < layer {
            continue;
        }

        let d = metric.distance(&nb_vec, graph.vector_of(*cand)?)?;
        scored.push((d, *cand));
    }

    scored.sort_by(|a, b| a.0.total_cmp(&b.0));

    let pruned = select_neighbors_heuristic(
        graph,
        metric,
        &nb_vec,
        nb,
        &scored,
        cap,
        layer,
    )?;

    graph.set_neighbors_at(nb, layer, pruned)
}
```

```rust
use std::sync::Arc;

use memmap2::Mmap;

use crate::Result;

use super::sectors::{decode_node, SectorLayout};
use super::{DiskAnnParams, DiskAnnRowId};

pub(crate) enum DiskAnnStore {
    InMemory(InMemoryGraph),
    Mmap(MmapGraph),
}

pub(crate) struct InMemoryGraph {
    pub vectors: Vec<Vec<f32>>,
    pub neighbors: Vec<Vec<u32>>,
    pub row_ids: Vec<DiskAnnRowId>,
}

pub(crate) struct MmapGraph {
    mmap: Arc<Mmap>,
    layout: SectorLayout,
    dim: usize,
    len: usize,
}

pub(crate) struct NodeView<'a> {
    pub row_id: DiskAnnRowId,
    pub vector: &'a [f32],
    pub neighbors: &'a [u32],
}

impl MmapGraph {
    pub(crate) fn open(
        path: &Path,
        dim: usize,
        params: DiskAnnParams,
        len: usize,
    ) -> Result<Self> {
        let file = std::fs::File::open(path)?;
        let mmap = unsafe { Mmap::map(&file)? };

        let layout = SectorLayout::for_params(dim, params.max_degree)?;

        let expected_len = layout.sector_size * len;
        if mmap.len() < expected_len {
            return Err(crate::Error::CorruptPage("diskann mmap file too short"));
        }

        Ok(Self {
            mmap: Arc::new(mmap),
            layout,
            dim,
            len,
        })
    }

    pub(crate) fn node(&self, id: u32) -> Result<NodeView<'_>> {
        let idx = id as usize;

        if idx >= self.len {
            return Err(crate::Error::CorruptPage("diskann node id out of bounds"));
        }

        let start = idx * self.layout.sector_size;
        let end = start + self.layout.sector_size;
        let sector = &self.mmap[start..end];

        let decoded = decode_node(sector, &self.layout, self.dim)?;

        Ok(NodeView {
            row_id: decoded.row_id,
            vector: decoded.vector,
            neighbors: decoded.neighbors,
        })
    }
}
```

## Code example: graph-access trait for searcher

```rust
// crates/kernel/src/vector/diskann/searcher.rs

pub(crate) trait GraphAccess {
    fn len(&self) -> usize;
    fn entry(&self) -> u32;
    fn row_id(&self, node: u32) -> Result<DiskAnnRowId>;
    fn distance(&self, node: u32, query: &[f32]) -> Result<f32>;
    fn neighbors<'a>(&'a self, node: u32, scratch: &'a mut Vec<u32>) -> Result<&'a [u32]>;
}

pub(crate) fn search<G: GraphAccess>(
    graph: &G,
    query: &[f32],
    k: usize,
    beam_width: usize,
) -> Result<Vec<SearchHit>> {
    let mut visited = HashSet::new();
    let mut frontier = BinaryHeap::new();
    let mut candidates = BinaryHeap::new();
    let mut scratch = Vec::new();

    let entry = graph.entry();
    let entry_dist = graph.distance(entry, query)?;

    frontier.push(MinCandidate {
        dist: entry_dist,
        node: entry,
    });

    while let Some(candidate) = frontier.pop() {
        if !visited.insert(candidate.node) {
            continue;
        }

        candidates.push(MaxCandidate {
            dist: candidate.dist,
            node: candidate.node,
        });

        while candidates.len() > beam_width {
            candidates.pop();
        }

        let neighbors = graph.neighbors(candidate.node, &mut scratch)?;

        for &nb in neighbors {
            if visited.contains(&nb) {
                continue;
            }

            let dist = graph.distance(nb, query)?;
            frontier.push(MinCandidate { dist, node: nb });
        }
    }

    let mut hits = candidates.into_sorted_vec();
    hits.truncate(k);

    hits.into_iter()
        .map(|hit| {
            Ok(SearchHit {
                row_id: graph.row_id(hit.node)?,
                distance: hit.dist,
            })
        })
        .collect()
}
```

## Code example: benchmark should use mmap path

```rust
// crates/bench/src/workload.rs

let built = DiskAnnIndex::build(DISKANN_DIM, &vectors, &row_ids, params)?;
let sectors = built.to_sectors()?;

let temp = tempfile::TempDir::new()?;
let sector_path = temp.path().join("diskann.sectors");

std::fs::write(&sector_path, &sectors)?;

let index = Arc::new(DiskAnnIndex::from_mmap_file(
    &sector_path,
    DISKANN_DIM,
    params,
    built.entry(),
    rows,
)?);

let mut stats = BTreeMap::new();
stats.insert("vector_recall_at_10".to_owned(), serde_json::json!(recall));
stats.insert("vector_candidates".to_owned(), serde_json::json!(64));
stats.insert("vector_index_kind".to_owned(), serde_json::json!("diskann"));
stats.insert("diskann_storage".to_owned(), serde_json::json!("mmap"));
stats.insert(
    "diskann_sector_bytes".to_owned(),
    serde_json::json!(sectors.len() as u64),
);
```

## Important safety note

`sectors.rs` currently decodes vector bytes into `&[f32]` using alignment-sensitive logic. With mmap this is probably okay if each sector starts page-aligned and the vector offset is 4-byte aligned, but it should be explicitly asserted. Safer options:

1. Make `SectorLayout` guarantee `vector_offset % 4 == 0`.
2. Add a test that all mmap node vectors are aligned.
3. If alignment ever becomes uncertain, decode f32 values into a scratch buffer instead of returning borrowed `&[f32]`.

## Expected impact

This is unlikely to change recall, but it will make the `vector-ann-search-disk` benchmark honest. Right now the “disk” workload proves serialization but not disk-resident search. Mmap also makes memory usage and page-fault behavior measurable, which the current in-memory `std::fs::read` path hides.

# Priority order

I would implement in this order:

1. **Restore benchmark configs/artifact discipline.**
   Without this, nobody can prove the numbers moved.

2. **Secondary-index range/count/covering fix.**
   This targets the worst ratio: `secondary-index-range` at 0.048×.

3. **Secondary-index-read ordered-limit fast path.**
   This targets the cleanest single-query regression: `secondary-index-read` at 0.13×.

4. **Hot-row general overhead reduction, then hot-counter commutative path.**
   Fix double-lock/index-maintenance overhead first; only then wire semantic delta combining.

5. **HNSW layer-invariant fix before parameter tuning.**
   The layer-0 expansion bug should be corrected before any M=16 recall sweep.

6. **DiskANN mmap.**
   Important for honesty of the vector disk benchmark; less directly tied to the published low SQLite ratios.

The biggest exact code issue I would hand to another agent first is the **SQL index `TuplePtr` problem**. The code has a batching optimization that groups heap rechecks by page, but SQL indexes currently store every tuple pointer as page 0 / slot 0. That makes the optimization structurally unable to help the low range-scan benchmarks until index entries carry real heap locations.
