# Key finding before performance work: one fast-path correctness risk

The most important technical finding is not just performance-related.

The current SQL fast paths can use an index range without proving that **all predicates are consumed by the index**.

The risky paths are in:

* `crates/sql/src/exec/select_top.rs`
* `crates/sql/src/exec/index_access.rs`
* `crates/sql/src/exec/index_batch.rs`

The current `COUNT(*)` fast path recognizes a query like:

```sql
SELECT COUNT(*) FROM kv WHERE tenant BETWEEN ?1 AND ?2
```

and routes it to an index-only count through `execute_index_count_range`.

That is exactly what we want for `secondary-index-range`.

But the current matcher appears to return only the usable leading index range. It does **not** carry a residual predicate contract. That means a query like this is dangerous:

```sql
SELECT COUNT(*)
FROM kv
WHERE tenant BETWEEN 1 AND 4
  AND version = 999;
```

The index on `tenant` can satisfy the `tenant BETWEEN` part, but not `version = 999`. If the fast path counts the index range without rechecking `version`, it can return the wrong answer.

The same category applies to covering index range scans and ordered-limit scans. This must be fixed before relying on the fast paths for benchmark wins.

## Concrete implementation guidance

### Step 1: extend `IndexAccessMatch`

Current logic returns a match but does not sufficiently prove residual safety. Add explicit consumed-predicate metadata.

A concrete shape:

```rust
// crates/sql/src/exec/index_access.rs

#[derive(Debug, Clone)]
pub(crate) struct IndexAccessMatch {
    pub index_id: IndexId,
    pub index_name: String,
    pub key_parts: Vec<SqlValue>,
    pub access: IndexAccessKind,

    // New:
    pub conjunct_count: usize,
    pub consumed_conjuncts: Vec<usize>,
    pub equality_prefix_len: usize,
}

impl IndexAccessMatch {
    pub(crate) fn consumes_all_conjuncts(&self) -> bool {
        self.consumed_conjuncts.len() == self.conjunct_count
    }

    pub(crate) fn has_residual_predicate(&self) -> bool {
        !self.consumes_all_conjuncts()
    }

    pub(crate) fn consumed_set_contains(&self, idx: usize) -> bool {
        self.consumed_conjuncts.iter().any(|seen| *seen == idx)
    }
}
```

Then change predicate flattening to preserve conjunct positions.

Instead of only flattening into expressions:

```rust
let conjuncts = flatten_and(selection);
```

use something like:

```rust
#[derive(Clone)]
struct IndexedConjunct<'a> {
    ordinal: usize,
    expr: &'a Expr,
}

fn flatten_and_indexed<'a>(expr: &'a Expr, out: &mut Vec<IndexedConjunct<'a>>) {
    match expr {
        Expr::Binary { op: BinaryOp::And, left, right } => {
            flatten_and_indexed(left, out);
            flatten_and_indexed(right, out);
        }
        other => {
            let ordinal = out.len();
            out.push(IndexedConjunct { ordinal, expr: other });
        }
    }
}
```

When the matcher consumes `tenant BETWEEN ?1 AND ?2`, mark that conjunct consumed. When it consumes `tenant = ?1`, mark that conjunct consumed. If the selection includes `version = 999`, leave it unconsumed.

### Step 2: make index-only count require no residual

In `select_top.rs`, the index-only count path should only fire when the index match consumes the entire selection.

Shape:

```rust
// crates/sql/src/exec/select_top.rs

fn try_count_star_index_range(
    conn: &Connection,
    tx: &Tx,
    plan: &SelectPlan,
    source: &TableSource,
    snapshot: SnapshotView,
) -> Result<Option<Vec<Vec<SqlValue>>>> {
    if !is_simple_count_star(plan) {
        return Ok(None);
    }

    let Some(selection) = plan.selection.as_ref() else {
        return Ok(None);
    };

    let Some(matched) = try_match_index_access(conn, source, selection)? else {
        return Ok(None);
    };

    // Critical correctness guard.
    if matched.has_residual_predicate() {
        return Ok(None);
    }

    let count = execute_index_count_range(
        conn.engine(),
        tx,
        source.relation_id,
        &matched,
        snapshot,
    )?;

    conn.engine()
        .benchmark_stats()
        .index_count_path_hits
        .fetch_add(1, Ordering::Relaxed);

    Ok(Some(vec![vec![SqlValue::Integer(count as i64)]]))
}
```

This should be the only heap-free `COUNT(*)` path.

If a query has residual predicates, either:

1. Fall back to heap recheck, or
2. Add a residual-aware count path that scans the index but checks qualifying rows.

Do **not** use the pure index-only count if residual predicates remain.

# Change 2: Fix secondary-index ordered `LIMIT` and add a fair covering-index read path

## Benchmarks improved

Primary:

* `secondary-index-read`

Secondary:

* `secondary-index-ordered-limit`
* `queue-mixed`
* `covered-range-warm`
* `covered-range-cold`

## Current benchmark query

`secondary-index-read` in `crates/bench/src/workload.rs:320-327` runs:

```sql
SELECT k, v FROM kv WHERE tenant = ?1 ORDER BY k LIMIT 1
```

The schema has only:

```sql
CREATE INDEX kv_tenant_idx ON kv(tenant)
```

This means the current index is **not covering** for `v`.

Because `k INTEGER PRIMARY KEY` is effectively the rowid, the index can use tenant equality and rowid order to find the first `k`, but it still needs a heap fetch to get `v`.

That puts RedlineDB in a weaker position than SQLite’s mature btree executor.

## Current fast path

`crates/sql/src/exec/select_top.rs` contains an ordered-limit fast path.

For a one-key index and `ORDER BY` rowid alias, it can use:

```rust
execute_index_probe_with_limit(...)
```

That is good for:

```sql
WHERE tenant = ?
ORDER BY k
LIMIT 1
```

because duplicate `tenant` index entries are ordered by rowid / primary key.

## Main issues

There are three important issues.

### Issue A: the fast path must be proven active

If RedlineDB misses the ordered-limit path, the fallback can do something much worse:

1. Fetch all rowids for the tenant.
2. Heap-load them.
3. Sort/order.
4. Take one row.

That would explain a large gap.

So add counters and tests proving this query hits the ordered-limit path.

### Issue B: current index is not covering

The query returns `v`, but `v` is not in `kv_tenant_idx`.

A fair covering benchmark should use the same covering index on both engines:

```sql
CREATE INDEX kv_tenant_k_v_idx ON kv(tenant, k, v);
```

Then this query can be answered entirely from the index:

```sql
SELECT k, v
FROM kv
WHERE tenant = ?1
ORDER BY k
LIMIT 1;
```

### Issue C: covering-order logic needs equality-prefix awareness

For an index like:

```sql
CREATE INDEX kv_tenant_k_v_idx ON kv(tenant, k, v);
```

and query:

```sql
WHERE tenant = ?
ORDER BY k
LIMIT 1
```

the order is not the first index column. It is the first column **after the equality prefix**.

The planner should understand:

* `tenant = ?` consumes index key position `0`.
* Remaining index order is by `k`, then `v`, then rowid.
* Therefore `ORDER BY k LIMIT 1` is satisfied by the index range.

The current `covering_order_satisfies` logic appears too narrow. It mostly checks the first index key or rowid alias. It needs equality-prefix-aware suffix ordering.

### Step 2: make order satisfaction equality-prefix-aware

Example implementation shape:

```rust
// crates/sql/src/exec/select_top.rs

fn index_order_satisfies_after_equality_prefix(
    table: &TableMeta,
    index: &IndexMeta,
    matched: &IndexAccessMatch,
    order_by: &[OrderExpr],
) -> bool {
    if order_by.is_empty() {
        return true;
    }

    let mut key_pos = matched.equality_prefix_len;

    for order in order_by {
        if order.desc {
            return false;
        }

        let Some(order_col) = order_expr_column_name(&order.expr) else {
            return false;
        };

        // Case 1: ORDER BY rowid / INTEGER PRIMARY KEY alias.
        if table.is_rowid_alias(&order_col) {
            // Rowid order is available after all explicit index keys.
            // For single-key duplicate ranges like idx(tenant), rowid is the tiebreaker.
            return key_pos >= index.keys.len()
                || index.keys[key_pos..].is_empty();
        }

        // Case 2: ORDER BY next index key after equality prefix.
        let Some(index_key) = index.keys.get(key_pos) else {
            return false;
        };

        if !same_column(table, index_key.column_id, &order_col) {
            return false;
        }

        key_pos += 1;
    }

    true
}
```

The important rule:

```text
WHERE a = ?
ORDER BY b
```

is satisfied by:

```text
INDEX(a, b, ...)
```

because `a` is fixed.

# Change 3: Make index range scanning truly streaming and make prefetch non-blocking

## Benchmarks improved

Primary:

* `secondary-index-range`
* `covered-range-cold`
* `covered-range-warm`
* `secondary-index-count`

Secondary:

* `secondary-index-read`
* `secondary-index-ordered-limit`
* queue-style workloads using state indexes

## Current code path

Index scans use cursor code in:

* `crates/kernel/src/index/cursor.rs`
* `crates/sql/src/exec/index_batch.rs`

There are two cursor styles:

1. `IndexCursor`, which decodes a whole leaf into owned `Vec<LeafEntry>`.
2. `RawIndexCursor`, which avoids some allocation and can decode by reference.

The `COUNT(*)` and covering paths already use `RawIndexCursor`, which is good.

However, `BufferPool::prefetch` in `crates/kernel/src/storage/buffer.rs` appears to do a synchronous cold `pin` if the page is not resident. That means the cursor’s “prefetch” can actually block the scanning thread.

For a range benchmark, blocking prefetch is not really prefetch. It can serialize I/O or pollute timing.

## Key issues

1. `RawIndexCursor::count_remaining` is the right primitive for index-only count.
2. `BufferPool::prefetch` should not synchronously block the scanning thread on a cold page.
3. Heap recheck batching currently allocates a `HashMap` per batch and calls visibility checks row by row.
4. Batch sizes are fixed and conservative. The index count/range workloads should be able to use larger batches or full-leaf loops.

## Concrete implementation guidance

### Step 1: split blocking pin from non-blocking prefetch

Current behavior is approximately:

```rust
pub fn prefetch(&self, page_id: PageId) {
    if self.try_resident(page_id) {
        return;
    }

    // Bad for scanner: this can block.
    let _guard = self.pin(page_id);
}
```

Replace with a non-blocking enqueue API.

Shape:

```rust
// crates/kernel/src/storage/buffer.rs

pub enum PrefetchResult {
    AlreadyResident,
    Enqueued,
    QueueFull,
    Disabled,
}

impl BufferPool {
    pub fn try_prefetch(&self, page_id: PageId) -> PrefetchResult {
        if self.is_resident(page_id) {
            self.stats.prefetch_hits.fetch_add(1, Ordering::Relaxed);
            return PrefetchResult::AlreadyResident;
        }

        match self.prefetch_queue.try_push(page_id) {
            Ok(()) => {
                self.stats.prefetch_enqueued.fetch_add(1, Ordering::Relaxed);
                PrefetchResult::Enqueued
            }
            Err(_) => {
                self.stats.prefetch_dropped.fetch_add(1, Ordering::Relaxed);
                PrefetchResult::QueueFull
            }
        }
    }
}
```

Then a background worker or existing heap lane should perform the blocking pin:

```rust
fn prefetch_worker(pool: Arc<BufferPool>, rx: Receiver<PageId>) {
    while let Ok(page_id) = rx.recv() {
        if !pool.is_resident(page_id) {
            let _ = pool.pin(page_id);
        }
    }
}
```

The key requirement: the scanner thread should not block just because it tried to prefetch the next leaf.

### Step 2: in `RawIndexCursor`, prefetch one or two leaves ahead but never block

In `crates/kernel/src/index/cursor.rs`:

```rust
fn emit_prefetch_hint(&mut self, page_id: PageId) {
    if let Some(pool) = self.buffer_pool.as_ref() {
        match pool.try_prefetch(page_id) {
            PrefetchResult::AlreadyResident => self.stats.prefetch_hits += 1,
            PrefetchResult::Enqueued => self.stats.prefetch_enqueued += 1,
            PrefetchResult::QueueFull => self.stats.prefetch_dropped += 1,
            PrefetchResult::Disabled => {}
        }
    }
}
```

When a leaf is loaded and has `right_link`, enqueue that right link. If the page has a known next-next link after decoding the current leaf header, enqueue that too.

### Step 3: avoid per-batch heap grouping allocations

In `crates/sql/src/exec/index_batch.rs`, `process_recheck_batch` groups tuples by page using a fresh `HashMap`.

For batch sizes like 256, a sorted vector is often cheaper and more predictable:

```rust
fn process_recheck_batch(
    engine: &Engine,
    tx: &Tx,
    relation: RelationId,
    batch: &mut [IndexTuple],
    snapshot: SnapshotView,
) -> Result<Vec<RowId>> {
    batch.sort_unstable_by_key(|tuple| (tuple.page_id, tuple.slot_id));

    let mut out = Vec::with_capacity(batch.len());
    let mut i = 0;

    while i < batch.len() {
        let page_id = batch[i].page_id;
        let mut j = i + 1;

        while j < batch.len() && batch[j].page_id == page_id {
            j += 1;
        }

        // Ideal next step:
        // pin heap page once, visibility-check all slots on that page.
        for tuple in &batch[i..j] {
            if engine.visible_in_relation(tx, relation, tuple.row_id, snapshot)? {
                out.push(tuple.row_id);
            }
        }

        i = j;
    }

    Ok(out)
}
```

The next improvement is a page-local visibility helper that pins the heap page once and checks all slots in that page.


# Change 4: Split hot-row from hot-counter, then implement a real commutative integer-delta path

## Benchmarks improved

Primary:

* `hot-counter-update`

Secondary:

* `hot-row-update`, indirectly through telemetry and lock optimizations
* `commit-storm-batched`
* mixed write-heavy workloads

## Current benchmark

`hot-row-update` in `crates/bench/src/workload.rs:404-414` runs:

```sql
UPDATE kv
SET v = ?1, version = version + 1
WHERE k = ?2
```

with `k = 0`.

This is not safely commutative because `v = ?1` is an arbitrary last-writer-wins blob assignment. You cannot combine 64 concurrent updates into one delta without changing the final `v` semantics.

There is also a separate `hot-counter-update` workload in `crates/bench/src/workload.rs:1223-1269`:

```sql
UPDATE hot_counter
SET counter = counter + 1
WHERE pk = ?1
```

That is the right benchmark for commutative combining.

## Current write path

The SQL update executor is in `crates/sql/src/exec/tail.rs`.

The core update path:

1. Finds target rows.
2. Locks the row.
3. Reloads the fresh row after lock.
4. Rechecks predicate.
5. Evaluates assignments.
6. Applies constraints/index changes.
7. Updates heap.
8. Commits.

The row lock implementation is in `crates/kernel/src/engine/lock.rs`. It is FIFO and wakes one waiter.

The commit path in `crates/kernel/src/engine/mod.rs` has a useful detail: in the common strict path without schema/index handle changes, it publishes the commit and releases locks before flushing the WAL. So the confirmed hot-row gap is not simply “row lock held across fsync.” It is more likely row-lock convoying plus per-statement update/WAL overhead.

There is a `crates/kernel/src/wal/combiner.rs`, but it is currently design-level. It is opt-in, disabled by default, and not integrated into the SQL update path as a real semantic delta execution mode.

## Key issues

1. Do not apply commutative combining to the existing `hot-row-update` benchmark. It is not semantically safe.
2. Add/promote `hot-counter-update` as the benchmark for semantic combining.
3. Implement a SQL-level detector for `counter = counter + constant`.
4. Implement a kernel-level delta apply path with checked integer overflow.
5. Make WAL/recovery preserve every committed transaction’s durability semantics.

## Concrete implementation guidance

### Step 1: add a semantic update detector

In the SQL update executor, detect this exact safe pattern:

```sql
UPDATE t
SET counter = counter + ?
WHERE pk = ?
```

Required safety constraints:

* Single target table.
* Single target row by primary key / rowid equality.
* Updated column is an integer column.
* Assignment is `col = col + constant` or `col = col - constant`.
* No updated indexed column, unless index maintenance supports the delta path.
* No `RETURNING` requiring intermediate values.
* No triggers.
* No residual predicate that could become false after combining unless it is rechecked correctly.
* Overflow is checked.
* Transaction isolation remains correct.

Example shape:

```rust
// crates/sql/src/exec/tail.rs

#[derive(Debug, Clone)]
struct IntegerDeltaUpdate {
    relation_id: RelationId,
    row_id: RowId,
    column_id: ColumnId,
    delta: i64,
}

fn detect_integer_delta_update(
    plan: &UpdatePlan,
    bindings: &[SqlValue],
    table: &TableMeta,
) -> Option<IntegerDeltaUpdate> {
    // 1. Exactly one assignment.
    let assignment = plan.assignments.single()?;

    // 2. Assignment shape: col = col + literal_or_param.
    let (lhs_col, rhs_col, delta) = parse_additive_assignment(assignment, bindings)?;

    if lhs_col != rhs_col {
        return None;
    }

    // 3. WHERE shape: pk = param/literal.
    let row_id = extract_exact_rowid_equality(&plan.selection, table, bindings)?;

    // 4. The target column must not require secondary index maintenance.
    if table.column_is_indexed(lhs_col) {
        return None;
    }

    // 5. Column type / affinity guard.
    if !table.column_is_integer_affinity(lhs_col) {
        return None;
    }

    Some(IntegerDeltaUpdate {
        relation_id: table.relation_id,
        row_id,
        column_id: lhs_col,
        delta,
    })
}
```

Then at the top of `execute_update`:

```rust
if let Some(delta) = detect_integer_delta_update(plan, bindings, table) {
    if conn.engine().wal_config().semantic_combiner {
        return execute_integer_delta_update(conn, tx, delta);
    }
}
```

### Step 2: implement the engine delta apply API

Add something like:

```rust
// crates/kernel/src/engine/mod.rs

pub fn apply_integer_delta_for_relation(
    &self,
    tx: &mut Tx,
    relation_id: RelationId,
    row_id: RowId,
    column_id: ColumnId,
    delta: i64,
) -> Result<()> {
    self.lock_row_for_relation(tx, relation_id, row_id)?;

    let current = self.read_column_for_update(tx, relation_id, row_id, column_id)?;
    let current_i64 = current.as_i64_checked()?;

    let next = current_i64
        .checked_add(delta)
        .ok_or(Error::IntegerOverflow)?;

    self.write_column_for_update(
        tx,
        relation_id,
        row_id,
        column_id,
        SqlValue::Integer(next),
    )?;

    tx.record_semantic_delta(CombinableDelta {
        rel_id: relation_id,
        row_id,
        column: column_id,
        delta,
    });

    Ok(())
}
```

This does not yet reduce row-lock contention by itself. It first creates a semantically clean path.

### Step 3: batch deltas before the row lock

To actually improve `hot-counter-update`, the combiner needs to combine waiting deltas before every transaction individually grabs the row lock.

One implementation direction:

```rust
pub struct PendingDeltaGroup {
    key: DeltaKey,
    waiters: Vec<DeltaWaiter>,
    sum: i64,
}

pub struct DeltaWaiter {
    tx_id: TxId,
    delta: i64,
    durable_ack: oneshot::Sender<Result<CommitReceipt>>,
}
```

For identical `(relation_id, row_id, column_id)`:

1. Threads submit deltas.
2. Combiner sums compatible deltas with checked arithmetic.
3. One worker takes the row lock.
4. It applies the total delta once.
5. WAL records either:

   * one combined physical update plus a list of transaction commit records, or
   * individual semantic delta records that recovery replays deterministically.

Do not acknowledge durability to a transaction until its commit record is durable under the selected sync mode.

### Step 4: preserve correctness in WAL/recovery

A safe WAL shape:

```rust
enum WalPayload {
    Commit {
        tx_id: TxId,
        commit_csn: Csn,
        records: Vec<WalRecord>,
    },

    SemanticDelta {
        relation_id: RelationId,
        row_id: RowId,
        column_id: ColumnId,
        delta: i64,
    },

    CombinedSemanticDelta {
        relation_id: RelationId,
        row_id: RowId,
        column_id: ColumnId,
        total_delta: i64,
        member_tx_ids: Vec<TxId>,
    },
}
```

Recovery must satisfy:

```text
Applying tx1(+1), tx2(+1), tx3(+1)
is equivalent to applying combined(+3)
and marking tx1, tx2, tx3 committed.
```

### Step 5: keep `hot-row-update` honest

For `hot-row-update`, optimize only general overhead:

* Better lock wait telemetry.
* Less statement/update allocation.
* Possibly row-local update fast path for primary-key exact update.
* Group commit tuning.

But do not fold the blob assignment.

## Expected benchmark impact

For `hot-row-update`, expect modest improvement unless the benchmark semantics are changed.

For `hot-counter-update`, a real combiner can produce a major improvement because all threads are incrementing the same integer. That is the benchmark where RedlineDB can plausibly beat SQLite.

Target outcomes:

* `hot-row-update`: move from `0.44x` to maybe `0.6x-1.0x` with general overhead reduction.
* `hot-counter-update`: target multi-x improvement over the uncombined path.

```rust
pub fn search(&self, query: &[f32], k: usize, ef: usize) -> Result<Vec<SearchHit>> {
    let live_ratio = self.live_ratio_estimate();
    let tombstone_penalty = if live_ratio < 0.95 {
        ((k as f64 / live_ratio.max(0.1)).ceil() as usize).saturating_sub(k)
    } else {
        0
    };

    let internal_k = k + tombstone_penalty;
    let internal_ef = ef.max(internal_k * 4);

    let candidates = self.search_layer(query, self.entry_point, internal_ef, 0)?;

    Ok(candidates
        .into_iter()
        .filter(|hit| self.is_live(hit.node_id))
        .take(k)
        .collect())
}
```

## Concrete DiskANN mmap implementation guidance

The current `from_sectors(&loaded, ...)` API forces the benchmark to load the whole file into memory.

Introduce a sector reader abstraction.

```rust
// crates/kernel/src/vector/diskann/sectors.rs

pub trait SectorReader: Send + Sync + 'static {
    fn sector_count(&self) -> usize;
    fn read_sector(&self, sector_id: u64) -> Result<&[u8]>;
}
```

Memory implementation:

```rust
pub struct MemorySectorReader {
    bytes: Arc<[u8]>,
    sector_size: usize,
}

impl SectorReader for MemorySectorReader {
    fn sector_count(&self) -> usize {
        self.bytes.len() / self.sector_size
    }

    fn read_sector(&self, sector_id: u64) -> Result<&[u8]> {
        let start = sector_id as usize * self.sector_size;
        let end = start + self.sector_size;
        Ok(&self.bytes[start..end])
    }
}
```

Mmap implementation:

```rust
pub struct MmapSectorReader {
    mmap: memmap2::Mmap,
    sector_size: usize,
}

impl MmapSectorReader {
    pub fn open(path: &Path, sector_size: usize) -> Result<Self> {
        let file = std::fs::File::open(path)?;
        let mmap = unsafe { memmap2::MmapOptions::new().map(&file)? };
        Ok(Self { mmap, sector_size })
    }
}

impl SectorReader for MmapSectorReader {
    fn sector_count(&self) -> usize {
        self.mmap.len() / self.sector_size
    }

    fn read_sector(&self, sector_id: u64) -> Result<&[u8]> {
        let start = sector_id as usize * self.sector_size;
        let end = start + self.sector_size;
        Ok(&self.mmap[start..end])
    }
}
```

Then make `DiskAnnIndex` generic over the reader:

```rust
pub struct DiskAnnIndex<R: SectorReader> {
    reader: R,
    layout: DiskAnnLayout,
    metric: VectorMetric,
    // cache, beam width, entry point, etc.
}
```

The disk benchmark should become:

```rust

```

