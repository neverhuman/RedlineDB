You should build Phase 6 as a **planner + statistics + physical-operator upgrade** that sits cleanly above your Phase 5 SQL executor and below the public API. The goal is not to clone SQLite’s optimizer exactly; the goal is to beat it where RedlineDB has structural advantages: MVCC concurrency, multiple writers, Rust-native memory control, hash joins, richer stats, and deterministic bounded execution.

SQLite’s own optimizer docs frame the core problem correctly: a single SQL statement can have many possible implementations, and the planner’s job is to minimize disk I/O and CPU overhead. SQLite’s `EXPLAIN QUERY PLAN` exposes useful high-level concepts like `SCAN`, `SEARCH`, covering indexes, and temp B-tree sorting; RedlineDB should expose a similar explain surface, even if the internals are more modern. ([SQLite][1])

## Phase 6 target

By the end of Phase 6, RedlineDB should have:

1. **Persistent table, column, and index statistics**
2. **A cost-based optimizer**
3. **Index/range/covering-index access-path selection**
4. **Join-order optimization**
5. **Physical operators for nested-loop, indexed nested-loop, hash join, sort, aggregate, grouping, and range scans**
6. **Memory-bounded execution**
7. **Plan inspection**
8. **Regression tests that compare plans, row counts, memory usage, and SQLite results**
9. **A performance harness that explains why a query is fast or slow**

The most important architectural choice: **Phase 6 should not make the executor clever by accident.** The optimizer should explicitly choose physical operators, access paths, orderings, memory budgets, and spill behavior. Execution should be dumb, fast, measurable, and predictable.

# 2. Core principle: stable snapshots of stats

Planning must be concurrent and lock-light.

Do **not** let query planning grab catalog/storage locks for long periods. Instead:

```rust
pub struct PlannerInputs {
    pub catalog: Arc<CatalogSnapshot>,
    pub stats: Arc<StatsSnapshot>,
    pub config: Arc<OptimizerConfig>,
    pub schema_version: SchemaVersion,
    pub stats_epoch: StatsEpoch,
}
```

Each statement plans against a frozen view:

```rust
let inputs = PlannerInputs {
    catalog: session.catalog_snapshot(),
    stats: db.stats_snapshot(),
    config: db.optimizer_config(),
    schema_version: session.schema_version(),
    stats_epoch: db.stats_epoch(),
};
```

Stats updates should use RCU-style replacement:

```rust
// Conceptual.
pub struct StatsManager {
    current: arc_swap::ArcSwap<StatsSnapshot>,
    epoch: AtomicU64,
}

impl StatsManager {
    pub fn snapshot(&self) -> Arc<StatsSnapshot> {
        self.current.load_full()
    }

    pub fn publish(&self, next: StatsSnapshot) {
        self.epoch.fetch_add(1, Ordering::Release);
        self.current.store(Arc::new(next));
    }
}
```

This gives you:

* no global planner lock
* deterministic plans per stats epoch
* cheap plan-cache invalidation
* safe concurrent `ANALYZE`
* clean benchmark reproducibility

SQLite’s `ANALYZE` gathers stats into internal tables used by the optimizer, and its docs note that stats are not automatically updated every time data changes; RedlineDB should use the same explicit-stats idea, but add staleness counters and optional background refresh. ([SQLite][2])

## Sampling strategy

Do **not** full-scan huge tables by default. Use adaptive sampling:


Use:

1. exact full scan for small tables
2. page-level sampling for large heap tables
3. index leaf sampling for indexes
4. reservoir sampling for values
5. HyperLogLog for NDV
6. Misra-Gries / Space-Saving for most common values
7. equi-depth histograms for ordered scalar values

## Pure Rust HyperLogLog sketch

```rust
#[derive(Clone)]
pub struct Hll {
    p: u8,
    registers: Vec<u8>,
}

impl Hll {
    pub fn new(p: u8) -> Self {
        let m = 1usize << p;
        Self { p, registers: vec![0; m] }
    }

    pub fn insert_hash(&mut self, hash: u64) {
        let idx = (hash >> (64 - self.p)) as usize;
        let w = hash << self.p;
        let rank = w.leading_zeros() as u8 + 1;
        self.registers[idx] = self.registers[idx].max(rank);
    }

    pub fn estimate(&self) -> f64 {
        let m = self.registers.len() as f64;
        let alpha = match self.registers.len() {
            16 => 0.673,
            32 => 0.697,
            64 => 0.709,
            _ => 0.7213 / (1.0 + 1.079 / m),
        };

        let sum: f64 = self.registers
            .iter()
            .map(|&r| 2.0_f64.powi(-(r as i32)))
            .sum();

        alpha * m * m / sum
    }
}
```

For production, add small-range correction and deterministic hash seeding. Use one hash implementation across stats and hash joins to avoid duplicate code.

## MCV sketch

```rust
pub struct SpaceSaving<T> {
    capacity: usize,
    counters: HashMap<T, Counter>,
}

#[derive(Clone, Copy)]
struct Counter {
    count: u64,
    error: u64,
}
```

For each value:

* if present: increment
* if space: insert
* else replace min counter with new value at `min + 1`, error `min`

This gives approximate heavy hitters without retaining all values.

## SARGability rules

For Phase 6, support:

```text
col = constant
col = outer_col
col IN (...)
col > constant
col >= constant
col < constant
col <= constant
col BETWEEN low AND high
col IS NULL
col IS NOT NULL
LIKE 'prefix%'
```

Do **not** initially treat arbitrary expressions as indexable unless Phase 4/5 added expression indexes.

## Composite index rule

For index `(a, b, c, d)`:

```text
a = ? AND b = ? AND c > ? AND d = ?
```

usable as:

```text
equality prefix: a, b
range column: c
residual: d = ?
```

Once you hit the first range column, later columns are normally not usable for narrowing the seek range, though they can still help covering/projection.

# 8. Selectivity estimation

## Equality

```rust
fn estimate_eq(col: &ColumnStats, value: &ScalarValue) -> f64 {
    if let Some(mcv) = col.mcv.iter().find(|m| &m.value == value) {
        return mcv.frequency;
    }

    let null_frac = col.null_count as f64 / col_total_rows(col);
    let non_null_frac = 1.0 - null_frac;

    let ndv = match col.distinct_estimate {
        DistinctEstimate::Exact(n) => n.max(1) as f64,
        DistinctEstimate::HyperLogLog { estimate, .. } => estimate.max(1.0),
    };

    let mcv_mass: f64 = col.mcv.iter().map(|m| m.frequency).sum();
    let remaining_mass = (non_null_frac - mcv_mass).max(0.0);
    let remaining_ndv = (ndv - col.mcv.len() as f64).max(1.0);

    remaining_mass / remaining_ndv
}
```

## Range

Use histogram CDF:

```rust
fn estimate_range(col: &ColumnStats, low: Option<&ScalarValue>, high: Option<&ScalarValue>) -> f64 {
    let Some(hist) = &col.histogram else {
        return 0.333; // conservative default
    };

    let low_cdf = low.map(|v| hist.cdf(v)).unwrap_or(0.0);
    let high_cdf = high.map(|v| hist.cdf(v)).unwrap_or(1.0);

    (high_cdf - low_cdf).clamp(0.0, 1.0)
}
```

## AND

Naive multiplication often underestimates. Use dampening:

```rust
fn combine_and(mut sels: Vec<f64>) -> f64 {
    sels.sort_by(|a, b| a.partial_cmp(b).unwrap());

    let mut out = 1.0;
    let mut damp = 1.0;

    for sel in sels {
        out *= sel.powf(damp);
        damp *= 0.75;
    }

    out.clamp(0.0, 1.0)
}
```

## OR

Use inclusion/exclusion, with caps:

```rust
fn combine_or(a: f64, b: f64) -> f64 {
    (a + b - a * b).clamp(0.0, 1.0)
}
```

## Joins

For equality join:

```text
rows(left ⋈ right on l.k = r.k)
≈ left_rows * right_rows / max(ndv(l.k), ndv(r.k))
```

with MCV correction later.

```rust
fn estimate_eq_join(left_rows: f64, right_rows: f64, left_ndv: f64, right_ndv: f64) -> f64 {
    let denom = left_ndv.max(right_ndv).max(1.0);
    (left_rows * right_rows / denom).max(1.0)
}
```

Candidate generation:

```rust
pub fn enumerate_access_paths(
    table: TableId,
    required: &RequiredProps,
    predicates: &PredicateSet,
    catalog: &CatalogSnapshot,
    stats: &StatsSnapshot,
    coster: &Coster,
) -> Vec<AccessPath> {
    let mut out = Vec::new();

    out.push(coster.table_scan(table, required, predicates, catalog, stats));

    if let Some(pk) = catalog.primary_key_index(table) {
        if let Some(path) = coster.index_path(table, pk, required, predicates, catalog, stats) {
            out.push(path);
        }
    }

    for index in catalog.indexes_on_table(table) {
        if let Some(path) = coster.index_path(table, index.id, required, predicates, catalog, stats) {
            out.push(path);
        }
    }

    if let Some(path) = maybe_multi_index_or(table, predicates, catalog, stats, coster) {
        out.push(path);
    }

    prune_dominated_access_paths(out)
}
```

## Dominance pruning

Drop a candidate if another candidate has:

* lower cost
* same or lower estimated rows
* same or better ordering
* same or better covering
* same required columns

```rust
fn prune_dominated_access_paths(mut paths: Vec<AccessPath>) -> Vec<AccessPath> {
    let mut keep = Vec::new();

    'outer: for i in 0..paths.len() {
        for j in 0..paths.len() {
            if i == j {
                continue;
            }

            if dominates(&paths[j], &paths[i]) {
                continue 'outer;
            }
        }
        keep.push(paths[i].clone());
    }

    keep
}
```

This is critical. Without pruning, join enumeration explodes.

# 10. Covering-index reads

A covering index path is valid when every required output column is available from the index entry.

```rust
fn is_covering(
    index: &IndexMeta,
    required_cols: &ColumnSet,
    table_pk: &[ColumnId],
) -> bool {
    required_cols.iter().all(|col| {
        index.key_columns.contains(&col)
            || index.include_columns.contains(&col)
            || table_pk.contains(&col)
    })
}
```

Physical execution:

```text
covering index scan:
  index leaf -> decode required columns -> return row

non-covering index scan:
  index leaf -> row_id -> heap fetch -> MVCC visibility recheck -> return row
```

Because RedlineDB uses MVCC, **index entries may be stale**. Every non-covering secondary-index path must heap-recheck visibility and predicate correctness.

```rust
pub struct IndexScanExec {
    index: IndexHandle,
    heap: Option<HeapHandle>,
    bounds: RuntimeIndexBounds,
    required_cols: ColumnSet,
    residual: CompiledPredicate,
    covering: bool,
}

impl ExecOperator for IndexScanExec {
    fn next_batch(&mut self, out: &mut RowBatch) -> Result<usize> {
        out.clear();

        while out.len() < out.capacity() {
            let Some(entry) = self.index.next_visible_candidate(&self.bounds)? else {
                break;
            };

            if self.covering {
                let row = entry.decode_covering(&self.required_cols)?;
                if self.residual.eval(&row)? {
                    out.push(row);
                }
            } else {
                let rid = entry.row_id();
                let Some(row) = self.heap.as_ref().unwrap().fetch_visible(rid)? else {
                    continue; // stale index entry
                };

                if self.residual.eval(&row)? {
                    out.push(row);
                }
            }
        }

        Ok(out.len())
    }
}
```

# 11. Order tracking and sort avoidance

Add physical ordering properties:

```rust
#[derive(Clone, Debug)]
pub struct Ordering {
```

An index on:

```sql
CREATE INDEX idx ON orders(customer_id, created_at DESC);
```

can satisfy:

```sql
WHERE customer_id = ?

```

because equality on the prefix leaves the suffix ordered.

Implement:

```rust
fn index_provides_ordering(
    index: &IndexMeta,
    bounds: &IndexBounds,
    required_order: &Ordering,
) -> bool {
    let skipped_prefix = bounds.equality_prefix.len();

    let remaining_index_order = index.key_columns
        .iter()
        .skip(skipped_prefix)
        .map(|k| k.order_key());

    ordering_prefix_satisfies(remaining_index_order, required_order.keys.iter())
}
```

If not satisfied, insert one of:

```rust
PhysicalPlan::Sort
PhysicalPlan::TopN
```

`TopN` is important for:

```sql
ORDER BY created_at DESC LIMIT 20
```

Do not fully sort one million rows for a limit of 20.

```rust
pub enum PhysicalSortKind {

    ExternalMergeSort,

```

SQLite’s explain output explicitly calls out temp B-tree usage for `ORDER BY`, `GROUP BY`, and `DISTINCT`; RedlineDB should show equivalent sort/materialization nodes and separately profile their rows, memory, and spill bytes. ([SQLite][3])

# 12. Join-order optimization

SQLite’s docs say it implements joins as nested loops and frames join planning as choosing loop order and indexes. That is a good compatibility mental model, but RedlineDB should go further by adding hash joins and memory-bounded hash aggregation. ([SQLite][4])

## Phase 6 join strategy

Support:

```rust
pub enum JoinMethod {
    NestedLoop,
    IndexNestedLoop {
        inner_index: IndexId,
    },
    HashJoin {
        build_side: BuildSide,
    },
    MergeJoin,
}
```

Prioritize:

1. indexed nested-loop for OLTP joins
2. hash join for larger equality joins
3. merge join when both sides already ordered
4. nested loop only for tiny inputs or non-equality predicates

## Left-deep DP for up to 12 tables

For embedded workloads, a left-deep DP optimizer is a strong start.

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash)]
pub struct RelSet(u128);

pub struct JoinMemo {
    best: HashMap<RelSet, Vec<PlanAlternative>>,
}

pub struct PlanAlternative {
    pub rels: RelSet,
    pub plan: PhysicalPlanRef,
    pub props: PhysicalProps,
}
```

Algorithm:

```rust
pub fn optimize_joins(
    base: Vec<BaseRelationAlternatives>,
    predicates: &JoinPredicateGraph,
    required: &RequiredProps,
    ctx: &OptContext,
) -> PhysicalPlanRef {
    let n = base.len();
    assert!(n <= 128);

    let mut memo = JoinMemo::new();

    for (i, alternatives) in base.into_iter().enumerate() {
        let set = RelSet(1u128 << i);
        memo.insert(set, alternatives.into_plan_alternatives(set));
    }

    for size in 2..=n {
        for subset in subsets_of_size(n, size) {
            let mut candidates = Vec::new();

            // left-deep: previous subset + one new table
            for inner_idx in subset.members() {
                let inner = RelSet(1u128 << inner_idx);
                let outer = subset.remove(inner_idx);

                let Some(outer_alts) = memo.get(outer) else { continue; };
                let Some(inner_alts) = memo.get(inner) else { continue; };

                for outer_plan in outer_alts {
                    for inner_plan in inner_alts {
                        if !predicates.has_join_or_cross_allowed(outer, inner) {
                            continue;
                        }

                        candidates.extend(enumerate_join_methods(
                            outer_plan,
                            inner_plan,
                            predicates.between(outer, inner),
                            required,
                            ctx,
                        ));
                    }
                }
            }

            memo.insert(subset, prune_join_alternatives(candidates, ctx));
        }
    }

    let all = RelSet((1u128 << n) - 1);
    choose_best_final(memo.get(all).unwrap(), required, ctx)
}
```

## N-best alternatives, not one

Keep multiple alternatives per relation set because one plan may be slightly more expensive but preserves useful ordering.

```rust
pub struct OptimizerConfig {
    pub max_alternatives_per_group: usize, // e.g. 8
    pub max_join_tables_exact_dp: usize,   // e.g. 12
    pub enable_hash_join: bool,
    pub enable_merge_join: bool,
    pub enable_auto_index: bool,
}
```

Prune by:

* cost
* output ordering
* estimated rows
* memory
* interesting orderings
* required final order

SQLite’s NGQP uses an N-nearest-neighbor-style approach for hard join-order cases; for RedlineDB, use exact DP for small joins and an N-best/beam approach once tables exceed the exact threshold. ([SQLite][4])

```rust
    fn build_hash_table(&mut self) -> Result<()> {
        let mut batch = RowBatch::with_capacity(self.config.batch_rows);

        while self.build.next_batch(&mut batch)? != 0 {
            for row in batch.rows() {
                let encoded = self.encode_build_row(row)?;
                let hash = hash_join_key(row, &self.build_keys)?;
```

# 17. Memory tracking

Every physical operator gets a child memory tracker.

```rust
pub struct MemoryTracker {
    limit: usize,
    used: AtomicUsize,
}

impl MemoryTracker {
    pub fn try_reserve(&self, bytes: usize) -> Result<MemoryReservation> {
        let mut current = self.used.load(Ordering::Relaxed);

        loop {
            let next = current.checked_add(bytes).ok_or(Error::OutOfMemory)?;

            if next > self.limit {
                return Err(Error::MemoryLimitExceeded {
                    requested: bytes,
                    used: current,
                    limit: self.limit,
                });
            }

            match self.used.compare_exchange_weak(
                current,
                next,
                Ordering::AcqRel,
                Ordering::Relaxed,
            ) {
                Ok(_) => return Ok(MemoryReservation { tracker: self, bytes }),
                Err(actual) => current = actual,
            }
        }
    }
}
```


# 19. Costing access paths

## Table scan

```rust
fn cost_table_scan(
    table: &TableMeta,
    stats: &TableStats,
    predicates: &PredicateSet,
    constants: &CostConstants,
) -> CostedRows {
    let selectivity = estimate_predicates(predicates, stats);
    let rows_in = stats.live_tuple_count as f64;
    let rows_out = (rows_in * selectivity).max(1.0);

    let pages = stats.page_count as f64;

    let io = pages * constants.seq_page_read;
    let cpu = rows_in * constants.cpu_tuple
        + rows_in * predicates.len() as f64 * constants.cpu_predicate;

    CostedRows {
        rows: rows_out,
        cost: Cost {
            startup: 0.0,
            total: io + cpu,
            cpu,
            seq_io: io,
            ..Cost::default()
        },
    }
}
```

## Index range scan

```rust
fn cost_index_range_scan(
    table_stats: &TableStats,
    index_stats: &IndexStats,
    bounds: &IndexBounds,
    covering: bool,
    residual_count: usize,
    constants: &CostConstants,
) -> CostedRows {
    let selectivity = estimate_index_bounds(index_stats, bounds);
    let entries = (index_stats.entry_count as f64 * selectivity).max(1.0);

    let descent = index_stats.height as f64 * constants.btree_descent_per_level;

    let leaf_pages = estimate_leaf_pages(index_stats, entries);
    let index_io = descent + leaf_pages * constants.seq_page_read;

    let heap_io = if covering {
        0.0
    } else {
        // Adjust using clustering factor.
        let random_fetches = entries * index_stats.clustering_factor;
        random_fetches * constants.random_page_read
    };

    let cpu = entries * constants.cpu_tuple
        + entries * residual_count as f64 * constants.cpu_predicate
        + if covering { 0.0 } else { entries * constants.mvcc_recheck };

    CostedRows {
        rows: entries,
        cost: Cost {
            startup: descent,
            total: index_io + heap_io + cpu,
            cpu,
            random_io: heap_io,
            seq_io: index_io,
            ..Cost::default()
        },
    }
}
```

# 20. Automatic transient indexes

SQLite can create automatic indexes for some query shapes; RedlineDB should support this only under strict conditions and explain it clearly. SQLite’s profiling docs expose automatic-index creation as a separate profiled operation, which is a good model. ([SQLite][5])

```rust
fn should_build_auto_index(c: &AutoIndexCandidate, constants: &CostConstants) -> bool {
    let build = c.estimated_build_rows * constants.cpu_hash
        + c.estimated_build_rows * log2(c.estimated_build_rows).max(1.0) * constants.cpu_compare;

    let no_index_probe = c.estimated_probe_count * c.estimated_build_rows * constants.cpu_predicate;

    let indexed_probe = c.estimated_probe_count
        * log2(c.estimated_build_rows).max(1.0)
        * constants.cpu_compare;

    indexed_probe + build < no_index_probe * 0.75
}
```

# 23. Optimizer pipeline

The whole pipeline should look like this:

```rust
pub fn optimize_statement(
    stmt: BoundStatement,
    inputs: PlannerInputs,
) -> Result<PreparedPhysicalPlan> {
    let logical = lower_bound_to_logical(stmt)?;

    let normalized = normalize_logical(logical)?;

    let required = derive_required_props(&normalized)?;

    let predicates = extract_predicates(&normalized)?;

    let optimized_logical = pushdown_and_simplify(normalized, &predicates)?;

    let physical = match optimized_logical {
        LogicalPlan::Scan(..) => optimize_single_relation(...)?,
        LogicalPlan::Join(..) => optimize_join_graph(...)?,
        _ => optimize_general(...)?,
    };

    let final_plan = enforce_required_properties(physical, &required)?;

    validate_plan(&final_plan)?;

    Ok(PreparedPhysicalPlan {
        plan: final_plan,
        schema_version: inputs.schema_version,
        stats_epoch: inputs.stats_epoch,
        param_sensitivity: derive_param_sensitivity(&final_plan),
    })
}
```

# 27. The “beat SQLite” strategy for Phase 6

Do not try to beat SQLite everywhere immediately. Beat it deliberately in places where RedlineDB can be structurally better.

## Where RedlineDB should win

### Concurrent read/write workloads

Your storage design already targets multiple sessions over one engine without SQLite’s single-writer ceiling. Phase 6 helps by making writers/readers touch fewer pages through better index selection and covering scans.

### Hash joins

SQLite join planning is fundamentally nested-loop based according to its own docs. RedlineDB adding hash joins gives it a real advantage on medium/large equality joins. ([SQLite][4])

### Covering secondary indexes with MVCC-aware recheck

For read-heavy embedded OLTP, covering indexes avoid heap fetches and reduce latch pressure.

### Memory-bounded sort/hash

SQLite is extremely good, but RedlineDB can make memory use more explicit and testable from day one.

### Better plan observability

Expose estimated-vs-actual rows early. This makes optimizer regressions much easier to catch.

---

# 28. Important design choices I would avoid

## Do not build a Cascades optimizer yet

A full Cascades/memo optimizer is powerful but expensive to get right. For Phase 6:

```text
rule-based logical rewrites
+
access-path enumeration
+
left-deep DP / beam join search
+
physical property enforcement
```

That is enough to become dangerous.

## Do not make stats auto-update synchronously

Never update histograms on every write. Use cheap modification counters and explicit/background analyze.

## Do not parallelize every query

Parallel scans and joins can help large analytical queries, but embedded OLTP often gets worse with too much parallelism. Add parallel execution behind a threshold:

```rust
pub struct ParallelConfig {
    pub enable_parallel_scan: bool,
    pub enable_parallel_hash_join: bool,
    pub min_rows_for_parallel: u64,
    pub max_workers_per_query: usize,
}
```

Default conservative.

## Do not hide spills

Every spill should be visible in `EXPLAIN ANALYZE`.

## Do not overfit to SQLite plans

Compare results and performance. Do not require identical plans.

# 29. Minimal Rust skeleton

A compact but real optimizer skeleton could look like this:

```rust
pub struct Optimizer {
    inputs: PlannerInputs,
    coster: Coster,
}

impl Optimizer {
    pub fn optimize(&self, stmt: BoundStatement) -> Result<PhysicalPlan> {
        let logical = lower_bound_statement(stmt)?;
        let logical = normalize_logical(logical)?;
        let required = derive_required_props(&logical);
        let predicates = extract_predicates(&logical)?;

        let plan = self.optimize_logical(&logical, &required, &predicates)?;
        let plan = self.enforce_props(plan, &required)?;

        Ok(plan)
    }

    fn optimize_logical(
        &self,
        logical: &LogicalPlan,
        required: &RequiredProps,
        predicates: &PredicateSet,
    ) -> Result<PhysicalPlan> {
        match logical {
            LogicalPlan::Scan(scan) => {
                self.optimize_scan(scan, required, predicates)
            }
            LogicalPlan::Join(join) => {
                self.optimize_join(join, required, predicates)
            }
            LogicalPlan::Aggregate(agg) => {
                self.optimize_aggregate(agg, required, predicates)
            }
            LogicalPlan::Sort(sort) => {
                self.optimize_sort(sort, required, predicates)
            }
            LogicalPlan::Project(project) => {
                let child_required = required_for_project(project, required);
                let child = self.optimize_logical(&project.input, &child_required, predicates)?;
                Ok(PhysicalPlan::Project(ProjectPlan::new(child, project.exprs.clone())))
            }
            LogicalPlan::Filter(filter) => {
                let child = self.optimize_logical(&filter.input, required, predicates)?;
                Ok(PhysicalPlan::Filter(FilterPlan::new(child, filter.predicate.clone())))
            }
            LogicalPlan::Limit(limit) => {
                let mut child_required = required.clone();
                child_required.limit = Some(limit.count);
                let child = self.optimize_logical(&limit.input, &child_required, predicates)?;
                Ok(PhysicalPlan::Limit(LimitPlan::new(child, limit.count)))
            }
            _ => todo!("remaining logical nodes"),
        }
    }

    fn optimize_scan(
        &self,
        scan: &LogicalScan,
        required: &RequiredProps,
        predicates: &PredicateSet,
    ) -> Result<PhysicalPlan> {
        let paths = enumerate_access_paths(
            scan.table,
            required,
            predicates,
            &self.inputs.catalog,
            &self.inputs.stats,
            &self.coster,
        );

        let best = paths
            .into_iter()
            .min_by(|a, b| {
                a.cost.score(&self.inputs.config.cost_weights)
                    .partial_cmp(&b.cost.score(&self.inputs.config.cost_weights))
                    .unwrap()
            })
            .ok_or(Error::NoAccessPath)?;

        Ok(lower_access_path(best))
    }
}
```

# 30. Definition of done for Phase 6

Phase 6 is “done” when these are true:

```text
ANALYZE persists table, column, and index stats.

The optimizer chooses between table scans, index seeks, range scans,
covering index scans, sort, TopN, indexed nested-loop joins, hash joins,
hash aggregate, and streaming aggregate.

EXPLAIN QUERY PLAN shows the chosen strategy.

EXPLAIN ANALYZE shows estimated rows, actual rows, loops, time, memory,
spill bytes, and scan details.

All supported SQL result tests pass against SQLite.

Plan regression tests are deterministic for fixed schema/stats.

Memory ceiling tests prove sort/hash/join operators respect configured budgets.

Benchmarks prove at least:
  - indexed point/range reads are competitive,
  - covering-index reads are excellent,
  - large equality joins benefit from hash join,
  - concurrent workloads do not regress due to optimizer locks.
```

The simplest “brilliant” version is not a giant academic optimizer. It is:

```text
persistent stats
clean predicate analysis
excellent access-path enumeration
good-enough selectivity
left-deep DP joins
hash join
covering scans
sort avoidance
memory-bounded temp operators
great EXPLAIN ANALYZE
ruthless regression benchmarks
```

That is the Phase 6 I would build.
