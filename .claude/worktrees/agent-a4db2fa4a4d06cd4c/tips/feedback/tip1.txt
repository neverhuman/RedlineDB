# 1. Fix `secondary-index-read`: exploit the implicit rowid suffix of secondary indexes

## Benchmark targeted

`secondary-index-read` at 64 threads: **0.13×**.

The workload is:

```rust
SELECT k, v FROM kv WHERE tenant = ?1 ORDER BY k LIMIT 1
```

from `crates/bench/src/workload.rs:320-324`.

The benchmark schema creates only this index:

```sql
CREATE INDEX kv_tenant_idx ON kv(tenant)
```

in `crates/bench/src/engine/redline.rs:52-58` and the equivalent SQLite setup in `crates/bench/src/engine/sqlite.rs:90-99`.

## Root issue

This query should be cheap even with only `kv_tenant_idx ON kv(tenant)`.

In RedlineDB’s B-tree, a secondary-index physical key is:

```rust
logical_key || row_id || tuple page/slot/generation
```

That is visible in `crates/kernel/src/index/mod.rs:696-700`:

```rust
pub fn encode_physical_key(logical_key: &[u8], row: IndexRowRef) -> KeyBuf {
    let mut key = KeyBuf::new();
    key.extend_logical(logical_key);
    key.append_row_ref_suffix(row);
    key
}
```

and the rowid suffix is big-endian sortable at `crates/kernel/src/index/mod.rs:90-97`.

Because `k INTEGER PRIMARY KEY` is the rowid alias, the physical order inside one `tenant = ?` prefix is already:

```text
tenant, rowid/k
```

So:

```sql
WHERE tenant = ? ORDER BY k LIMIT 1
```

can be satisfied by reading the **first visible entry in the tenant prefix**, then loading one heap row for `v`.

Current code does not recognize this. The current `covering_order_satisfies()` only checks whether `ORDER BY` matches the **first logical index key**:

```rust
// crates/sql/src/exec/select_top.rs:719-748
fn covering_order_satisfies(index, table, order_by) -> bool {
    ...
    let Some(first_key) = index.keys.first() else { return false; };
    ...
}
```

And `try_ordered_index_limit_path()` only recognizes a rowid suffix case for a **point lookup**, not for the common prefix-range case:

```rust
// crates/sql/src/exec/select_top.rs:801-823
if matched.index.keys.len() == 1
    && order_by_rowid_alias(table, &plan.order_by)
    && matches!(matched.probe, index_access::IndexProbe::Point { .. })
{
    ...
}

if !matches!(matched.probe, index_access::IndexProbe::Range { .. }) {
    return Ok(None);
}
if !covering_order_satisfies(&matched.index, table, &plan.order_by) {
    return Ok(None);
}
```

For `tenant = ?`, `try_match_index_access()` returns a prefix `Range`, not a `Point`, so the executor falls through. It then does this expensive path:

1. Use the tenant index to collect **all rowids for the tenant**.
2. Load every matching heap row.
3. Top-K sort by `k`.
4. Return one row.

That path is in `table_rows_for_select()` and `order_and_project_rows()` in `crates/sql/src/exec/select_top.rs:402-476`.

SQLite is almost certainly winning this benchmark because it knows the rowid suffix order of secondary indexes and can stop at the first row.

## Key change

Teach the planner/executor that an equality-bound index prefix is ordered by:

```text
remaining logical index keys, then implicit rowid suffix
```

For the current benchmark:

```text
index:       (tenant) + implicit rowid
predicate:  tenant = ?
ORDER BY:   k / rowid alias
LIMIT:      1
```

This should become an ordered index range scan with hard early stop at `LIMIT + OFFSET`.

```rust
// crates/sql/src/exec/index_access.rs

fn equality_prefix_values(
    conjuncts: &[&Expr],
    table: &TableDef,
    index: &IndexDef,
    bindings: &[Option<SqlValue>],
) -> Vec<SqlValue> {
    let mut values = Vec::new();

    for key in &index.keys {
        let IndexKeySource::Column { attnum } = key.source;
        let column = attnum as usize;

        match first_constant_eq_for_column(conjuncts, table, column, bindings) {
            Some(value) if !matches!(value, SqlValue::Null) => values.push(value),
            _ => break,
        }
    }

    values
}
```

Now add ordering recognition that skips equality-bound prefix columns and accepts the implicit rowid suffix.

```rust
// crates/sql/src/exec/select_top.rs

fn ordered_index_scan_satisfies(
    table: &Arc<redlinedb_kernel::catalog::TableDef>,
    matched: &index_access::IndexAccessMatch,
    order_by: &[OrderByExpr],
) -> bool {
    use redlinedb_kernel::catalog::{IndexKeySource, SortDir};

    if order_by.is_empty() {
        return true;
    }

    let mut key_pos = matched.equality_prefix_len;

    for order in order_by {
        let ascending = order.options.asc.unwrap_or(true);
        if !ascending {
            // No reverse cursor yet.
            return false;
        }

        if key_pos < matched.index.keys.len() {
            let key = &matched.index.keys[key_pos];

            let IndexKeySource::Column { attnum } = key.source;
            let Some(order_ord) = order_expr_column_ordinal_for_table(&order.expr, table) else {
                return false;
            };

            if order_ord != attnum as usize {
                return false;
            }

            if key.sort_dir != SortDir::Asc {
                return false;
            }

            key_pos += 1;
            continue;
        }

        // After all logical index keys, leaf physical order is rowid.
        // This is the missing case for:
        //   index (tenant), WHERE tenant = ?, ORDER BY k LIMIT 1
        // when k is INTEGER PRIMARY KEY / rowid alias.
        if order_by_rowid_alias_expr(table, &order.expr) {
            key_pos += 1;
            continue;
        }

        return false;
    }

    true
}
```

Helper for rowid alias expression:

```rust
fn order_by_rowid_alias_expr(
    table: &Arc<redlinedb_kernel::catalog::TableDef>,
    expr: &Expr,
) -> bool {
    let name = match expr {
        Expr::Identifier(ident) => ident.value.as_str(),
        Expr::CompoundIdentifier(parts) => {
            let Some(last) = parts.last() else { return false; };
            last.value.as_str()
        }
        _ => return false,
    };

    name.eq_ignore_ascii_case("rowid")
        || name.eq_ignore_ascii_case("_rowid_")
        || name.eq_ignore_ascii_case("oid")
        || table
            .rowid_alias_column
            .and_then(|alias| table.columns.get(alias as usize))
            .is_some_and(|col| col.folded.as_ref().eq_ignore_ascii_case(name))
}
```

Then change `try_ordered_index_limit_path()`:

```rust
// crates/sql/src/exec/select_top.rs

fn try_ordered_index_limit_path(
    conn: &Connection,
    tx: &mut Txn,
    plan: &SelectPlan,
    bindings: &[Option<SqlValue>],
    table: &Arc<redlinedb_kernel::catalog::TableDef>,
    limit: usize,
    offset: usize,
) -> Result<Option<Vec<RowId>>> {
    if plan.order_by.is_empty() || limit == usize::MAX {
        return Ok(None);
    }

    let Some(matched) =
        index_access::try_match_index_access(conn.engine(), table, &plan.selection, bindings)
    else {
        return Ok(None);
    };

    if index_access::open_handle(conn.engine(), &matched.index).is_none() {
        return Ok(None);
    }

    if !ordered_index_scan_satisfies(table, &matched, &plan.order_by) {
        return Ok(None);
    }

    let take = limit.saturating_add(offset);

    let rowids = index_access::execute_index_probe_with_limit(
        conn.engine(),
        tx,
        table,
        &matched.index,
        &matched.probe,
        Some(take),
    )?;

    Ok(Some(rowids))
}
```

# 2. Fix `secondary-index-range`: rerun Phase 11 count fast path, then add raw-cursor prefetch and narrow-index selection

## Benchmark targeted

`secondary-index-range` at 64 threads: **0.048×**.

The workload is:

```rust
SELECT COUNT(*) FROM kv WHERE tenant BETWEEN ?1 AND ?2
```

from `crates/bench/src/workload.rs:329-340`.

## Important discovery

The current archive already contains a Phase 11 fast path that appears designed to fix this benchmark:

```rust
// crates/sql/src/exec/select_top.rs:33-66

    && let Some(matched) = index_access::try_match_index_access(...)
    && let index_access::IndexProbe::Range { start, end } = &matched.probe
{
    let count = index_access::execute_index_count_range(...)?;
    fast_path_rows = Some(vec![vec![SqlValue::Integer(count)]]);
}
```

That calls:

```rust
// crates/sql/src/exec/index_batch.rs:190-210
execute_index_count_range(...)
```

which uses:

```rust
// crates/kernel/src/index/cursor.rs:708-783
RawIndexCursor::count_remaining()
```

This is a major code change relative to the reported Phase 10 number. Since the raw Phase 11 benchmark results are not in the archive, the first action is to rerun the exact comparison before optimizing further. The published 0.048× number may already be stale for this code.

## Remaining issues after rerun

Even with the count fast path, the raw cursor still has two problems.

### Issue A: `RawIndexCursor` does not prefetch

The normal `IndexCursor` has prefetch plumbing, but the raw count/covering cursor does not have equivalent next-leaf prefetch. The `RawIndexCursor` count path pins one leaf at a time:

```rust
// crates/kernel/src/index/cursor.rs:723
let guard = self.index.inner.buffer.pin(leaf_id)?;
```

It then reads `header.right`, processes the page, and only then advances.

### Issue B: current `BufferPool::prefetch()` is synchronous on cold pages

`BufferPool::prefetch()` claims to be advisory, but on a cold page it calls `pin()` directly:

```rust
// crates/kernel/src/storage/buffer.rs:212-221
counters.prefetch_misses.fetch_add(1, Ordering::Relaxed);
if let Ok(_guard) = self.pin(page_id) {
    // Drop the guard immediately
}
```

That can block the cursor on the exact I/O it is supposed to hide. For cold range scans, this is not real read-ahead; it is a synchronous extra pin.

### Issue C: if a covering composite index is later added, count must still prefer the narrow `(tenant)` index

The existing index matcher returns the first usable index:

```rust
// crates/sql/src/exec/index_access.rs:117-121
// Take the first index that fits
for index in &table.indexes {
    ...
}
```

For `COUNT(*) WHERE tenant BETWEEN ? AND ?`, the best index is the narrowest index on `tenant`, not a wider covering index. If we later add a `(tenant, k, v)` benchmark index for a read-specific lane, the count fast path must not accidentally choose the wider index.

## Key change

Add query-shape-aware index selection and real raw-cursor read-ahead.

## Detailed implementation sketch: query-shape index scoring

Add a hinted matcher instead of always taking the first index.

```rust
// crates/sql/src/exec/index_access.rs

#[derive(Debug, Clone, Copy)]
pub(crate) enum IndexAccessPurpose {
    General,
    CountStar,
    OrderedLimit,
    CoveringProjection,
}

pub(crate) struct IndexAccessHints<'a> {
    pub purpose: IndexAccessPurpose,
    pub order_by: &'a [OrderByExpr],
    pub projection: &'a [SelectItem],
}

pub(crate) fn try_match_index_access_with_hints(
    engine: &Engine,
    table: &Arc<TableDef>,
    selection: &Option<Expr>,
    bindings: &[Option<SqlValue>],
    hints: IndexAccessHints<'_>,
) -> Option<IndexAccessMatch> {
    let expr = selection.as_ref()?;
    let conjuncts = flatten_top_level_and(expr);

    let mut best: Option<(i64, IndexAccessMatch)> = None;

    for index in &table.indexes {
        if index.meta_page_id.is_none() || engine.index_handle(index.index_id).is_none() {
            continue;
        }

        let Some(candidate) = match_one_index(index, table, &conjuncts, bindings) else {
            continue;
        };

        let score = score_index_candidate(table, &candidate, hints);

        if best.as_ref().is_none_or(|(best_score, _)| score > *best_score) {
            best = Some((score, candidate));
        }
    }

    best.map(|(_, candidate)| candidate)
}
```

Scoring rule:

```rust
fn score_index_candidate(
    table: &TableDef,
    candidate: &IndexAccessMatch,
    hints: IndexAccessHints<'_>,
) -> i64 {
    let mut score = 0_i64;

    match candidate.kind {
        IndexProbeKind::PointLookup => score += 10_000,
        IndexProbeKind::RangeScan => score += 5_000,
    }

    // More equality-bound prefix is usually better.
    score += (candidate.equality_prefix_len as i64) * 500;

    match hints.purpose {
        IndexAccessPurpose::CountStar => {
            // For COUNT(*), prefer leaf density. Wider keys reduce fanout.
            score -= estimated_index_key_width(&candidate.index) as i64;
            score -= (candidate.index.keys.len() as i64) * 100;
        }
        IndexAccessPurpose::OrderedLimit => {
            if ordered_index_scan_satisfies(table, candidate, hints.order_by) {
                score += 20_000;
            }
        }
        IndexAccessPurpose::CoveringProjection => {
            if projection_is_covered_by_index(table, &candidate.index, hints.projection) {
                score += 15_000;
            }
        }
        IndexAccessPurpose::General => {}
    }

    score
}
```

Then the count fast path should call with `CountStar`:

## Detailed implementation sketch: nonblocking raw-cursor prefetch

First, do not make `BufferPool::prefetch()` synchronously call `pin()` on cold pages. Add a true nonblocking method.

```rust
// crates/kernel/src/storage/buffer.rs

pub fn prefetch_nonblocking(&self, page_id: PageId, counters: &Phase11Counters) {
    let shard_idx = self.shard_idx(page_id);

    let resident = match self.shards[shard_idx].try_lock() {
        Ok(shard) => shard.contains_key(&page_id),
        Err(_) => {
            counters.prefetch_misses.fetch_add(1, Ordering::Relaxed);
            return;
        }
    };

    if resident {
        counters.prefetch_hits.fetch_add(1, Ordering::Relaxed);
        return;
    }

    counters.prefetch_misses.fetch_add(1, Ordering::Relaxed);

    // Do not call pin() here.
    // Queue the load onto a bounded prefetch worker, or drop the hint.
    //
    // The first implementation can be conservative:
    //   - bounded queue
    //   - de-duplicate in-flight page IDs
    //   - one or two worker threads per buffer pool
    //   - never evict dirty pages just for prefetch
    let _ = self.prefetch_queue.try_enqueue(page_id);
}
```

Then wire it into `RawIndexCursor`.

```rust
// crates/kernel/src/index/cursor.rs

impl<'idx> RawIndexCursor<'idx> {
    fn prefetch_leaf(&self, page_id: Option<PageId>) {
        let Some(page_id) = page_id else { return; };
        let Some(counters) = self.counters else { return; };

        self.index
            .inner
            .buffer
            .prefetch_nonblocking(page_id, counters);
    }
}
```

Inside `count_remaining()`, after reading the header:

```rust
let batch_result = guard.with_page(|page| {
    let header = BtreeIndex::read_page_header(page)?;
    next_leaf = header.right;

    // Schedule the next leaf before processing the current leaf,
    // so I/O can overlap with CPU visibility checks.
    self.prefetch_leaf(next_leaf);

    ...
    Ok(())
});
```

For better read-ahead, prefetch the next-next leaf too by peeking at the next leaf header when resident, but do not block if not resident.

`secondary-index-range` should move substantially once the COUNT fast path is measured. After that, real nonblocking prefetch matters most for cold-cache and wider range windows. The current Phase 10 0.048× number should not be treated as current until the Phase 11 code is rerun.

# 3. Fix `hot-row-update`: skip unnecessary index work, then add a safe hot-row combiner

## Benchmark targeted

`hot-row-update` at 64 threads: **0.44×**.

The workload is:

```rust
UPDATE kv SET v = ?1, version = version + 1 WHERE k = ?2
```

with `k = 0`, from `crates/bench/src/workload.rs:404-412`.

## Root issue

The row lock manager is not the obvious bottleneck anymore. It already has targeted FIFO handoff:

```rust
// crates/kernel/src/engine/lock.rs:16-19
// Each waiter owns its own Condvar so the holder can wake exactly the next-in-line waiter
```

and the unlock path uses `notify_one()`:

```rust
// crates/kernel/src/engine/lock.rs:160-163
if let Some(next) = state.waiters.front().cloned() {
    next.notify_one();
}
```

The expensive path is the SQL/autocommit update pipeline. Every operation does:

1. Begin read-committed transaction.
2. Resolve target rowid.
3. Lock hot row.
4. Reload fresh row.
5. Evaluate assignments.
6. Apply affinity and constraints.
7. Check unique constraints.
8. Encode row payload.
9. Heap update.
10. Call index update maintenance.
11. Commit and wait for durability.

That is in `crates/sql/src/exec/tail.rs:357-450` and `crates/sql/src/exec/mod.rs:274-342`.

The WAL combiner is not actually wired to mutations. `WalConfig::semantic_combiner` exists, but `grep` only finds combiner use in `combiner.rs`; the manager does not consume `CombinableDelta`. The workplan also calls semantic combiner deferred.

## Low-risk change first: skip index maintenance when no indexed column changed

`hot-row-update` changes only `v` and `version`. The only benchmark index is `tenant`. The rowid `k` is unchanged. Current code still calls:

```rust
maintain_indexes_on_update(...)
```

which loops indexes and builds old/new index keys before discovering they are equal:

```rust
// crates/sql/src/exec/index_dml.rs:177-188
let old_key = build_index_key(index, old_values);
let new_key = build_index_key(index, new_values);
if old_key.bytes == new_key.bytes && old_rowid == new_rowid {
    continue;
}
```

Avoid this call entirely when assigned columns cannot affect any index key and the rowid is unchanged.

Existing files:

## High-impact change: safe SQL-level hot-row combiner

WAL-level semantic combining alone is not enough, because the heap MVCC row still gets updated once per SQL transaction. The effective change is a **SQL-level combiner** for very narrow, provably safe update shapes.

Start with two exact shapes:

```sql
UPDATE hot_counter SET counter = counter + 1 WHERE pk = ?
```

and then:

```sql
UPDATE kv SET v = ?, version = version + 1 WHERE k = ?
```

The second shape is safe only under these restrictions:

```text
single rowid equality predicate
no RETURNING
no triggers
no foreign-key side effects
no rowid change
no indexed column assignment
version assignment is exactly version = version + positive constant
v assignment is constant or bound parameter, not row-dependent
all queued statements are concurrent; callers are acknowledged only after the combined commit
```

For a batch of N concurrent `hot-row-update` operations on the same row:

```text
version := old_version + N
v       := last queued v
```

Then every queued caller gets `rows_affected = 1` after the single combined commit. This is equivalent to a serial order in which the queued writes run back-to-back with no externally visible reads between them.

## Code example: shape detection

```rust
// crates/sql/src/exec/hot_update.rs

pub(crate) struct HotRowCandidate {
    pub table: Arc<TableDef>,
    pub rowid: RowId,
    pub version_col: usize,
    pub payload_col: Option<usize>,
    pub payload_value: Option<SqlValue>,
    pub version_delta: i64,
}

pub(crate) fn detect_hot_row_candidate(
    plan: &UpdatePlan,
    bindings: &[Option<SqlValue>],
) -> Result<Option<HotRowCandidate>> {
    if plan.returning.is_some() {
        return Ok(None);
    }

    let Some(rowid) = selection_rowid_eq(&plan.table, &plan.selection, bindings)? else {
        return Ok(None);
    };

    let assigned: std::collections::BTreeSet<usize> =
        plan.assignments.iter().map(|(ord, _)| *ord).collect();

    if assignment_touches_index_key_or_rowid(&plan.table, &assigned) {
        return Ok(None);
    }

    let mut version_col = None;
    let mut version_delta = None;
    let mut payload_col = None;
    let mut payload_value = None;

    for (ordinal, expr) in &plan.assignments {
        let col_name = plan.table.columns[*ordinal].folded.as_ref();

        if col_name.eq_ignore_ascii_case("version") {
            if let Some(delta) = parse_col_plus_const(expr, &plan.table, *ordinal, bindings)? {
                version_col = Some(*ordinal);
                version_delta = Some(delta);
            } else {
                return Ok(None);
            }
            continue;
        }

        if col_name.eq_ignore_ascii_case("v") {
            // Accept only constant/bind RHS so the queued job can capture it
            // without reading the current row.
            let value = eval_constant_update_rhs(expr, bindings)?;
            payload_col = Some(*ordinal);
            payload_value = Some(value);
            continue;
        }

        return Ok(None);
    }

    let Some(version_col) = version_col else { return Ok(None); };
    let Some(version_delta) = version_delta else { return Ok(None); };

    if version_delta <= 0 {
        return Ok(None);
    }

    Ok(Some(HotRowCandidate {
        table: Arc::clone(&plan.table),
        rowid,
        version_col,
        payload_col,
        payload_value,
        version_delta,
    }))
}
```

## Code example: coordinator

```rust
// crates/sql/src/exec/hot_update.rs

#[derive(Debug, Clone, PartialEq, Eq, Hash)]
struct HotRowKey {
    rel_id: u64,
    rowid: u64,
    version_col: usize,
    payload_col: Option<usize>,
}

struct HotRowJob {
    candidate: HotRowCandidate,
    reply: std::sync::mpsc::Sender<Result<ExecutionResult>>,
}

pub(crate) struct HotUpdateCoordinator {
    queues: dashmap::DashMap<HotRowKey, Arc<HotRowQueue>>,
    max_batch: usize,
    max_delay: Duration,
}

impl HotUpdateCoordinator {
    pub(crate) fn submit(
        &self,
        conn: &Connection,
        candidate: HotRowCandidate,
    ) -> Result<ExecutionResult> {
        let key = HotRowKey {
            rel_id: candidate.table.relation_id.0,
            rowid: candidate.rowid.0,
            version_col: candidate.version_col,
            payload_col: candidate.payload_col,
        };

        let queue = self
            .queues
            .entry(key.clone())
            .or_insert_with(|| Arc::new(HotRowQueue::new()))
            .clone();

        let (tx, rx) = std::sync::mpsc::channel();

        let became_owner = queue.push(HotRowJob {
            candidate,
            reply: tx,
        });

        if became_owner {
            self.drain_as_owner(conn, key, queue);
        }

        rx.recv()
            .map_err(|_| Error::TransactionState("hot update coordinator dropped reply"))?
    }

    fn drain_as_owner(
        &self,
        conn: &Connection,
        key: HotRowKey,
        queue: Arc<HotRowQueue>,
    ) {
        loop {
            let jobs = queue.drain_up_to(self.max_batch, self.max_delay);

            if jobs.is_empty() {
                queue.release_owner();
                if queue.is_empty() {
                    self.queues.remove(&key);
                    return;
                }
                if !queue.try_become_owner() {
                    return;
                }
                continue;
            }

            let result = apply_hot_row_batch(conn, &jobs);

            for job in jobs {
                let _ = job.reply.send(result.clone());
            }
        }
    }
}
```

## Code example: apply one physical update for N logical updates

```rust
fn apply_hot_row_batch(
    conn: &Connection,
    jobs: &[HotRowJob],
) -> Result<ExecutionResult> {
    let first = &jobs[0].candidate;
    let batch_len = jobs.len() as i64;
    let total_delta = jobs
        .iter()
        .map(|job| job.candidate.version_delta)
        .try_fold(0_i64, |acc, delta| acc.checked_add(delta).ok_or_else(|| {
            Error::TransactionState("hot row version delta overflow")
        }))?;

    with_write_tx(conn, |_session, tx| {
        conn.engine()
            .lock_row_for_relation(tx, first.table.relation_id, first.rowid)?;

        let Some(fresh) =
            load_table_row_by_rowid(conn.engine(), tx, &first.table, first.rowid)?
        else {
            return Ok(ExecutionResult {
                affected_rows: 0,
                returned_rows: Vec::new(),
                runtime: RuntimeState::Done,
            });
        };

        let mut values = fresh.values.clone();

        let old_version = match values.get(first.version_col) {
            Some(SqlValue::Integer(v)) => *v,
            _ => return Err(Error::Type("hot row version column must be INTEGER".into())),
        };

        values[first.version_col] = SqlValue::Integer(
            old_version
                .checked_add(total_delta)
                .ok_or_else(|| Error::TransactionState("hot row version overflow"))?,
        );

        if let Some(payload_col) = first.payload_col {
            // Last queued update wins, matching serial order by queue order.
            let last_payload = jobs
                .last()
                .and_then(|job| job.candidate.payload_value.clone())
                .ok_or_else(|| Error::TransactionState("missing hot row payload"))?;
            values[payload_col] = last_payload;
        }

        let payload = encode_sql_row(first.table.table_id.0, &values)?;

        conn.engine().update_for_relation(
            tx,
            first.table.relation_id,
            first.rowid,
            payload,
        )?;

        Ok(ExecutionResult {
            affected_rows: batch_len as usize,
            returned_rows: Vec::new(),
            runtime: RuntimeState::Done,
        })
    })
}
```

For the public SQL result, each caller should receive `affected_rows = 1`, not the batch length. The coordinator can apply the batch length internally and reply with a per-job result.

## Tests required

1. `64` concurrent updates to `hot_counter` produce final counter `64`.
2. `64` concurrent `hot-row-update` operations produce final `version = old + 64`.
3. Every caller receives `rows_affected = 1`.
4. No fast path with `RETURNING`.
5. No fast path if an indexed column is assigned.
6. No fast path if rowid changes.
7. Crash/failpoint test: if callers are acknowledged, recovered final version includes their count.
8. Concurrent reader test: readers either see old state before the batch or final state after the batch, never an impossible partial payload/version combination.

## Expected impact

The low-risk skip-index-maintenance change reduces per-update CPU overhead. The combiner is the real throughput change: it converts a convoy of N independent hot-row updates into one physical heap update and one durable commit group. This is the change most likely to move `hot-row-update` above SQLite, but it needs correctness proof and should start behind an opt-in flag.

# Priority order

1. **Implement implicit rowid-suffix ordered LIMIT for `secondary-index-read`.**
   This is the cleanest high-impact fix. It directly targets the 0.13× benchmark and should not require schema changes.

2. **Rerun `secondary-index-range` with the current Phase 11 count fast path.**
   The archive already contains code that likely invalidates the old 0.048× number. Measure first, then optimize raw-cursor prefetch.

3. **Add index-selection scoring.**
   This prevents future composite/covering indexes from hurting count scans and ensures ordered-limit queries choose the right index.

4. **Apply hot-row low-risk CPU cuts, then build an opt-in combiner.**
   Skip unchanged-index maintenance immediately. Then implement the hot-row/hot-counter combiner behind a flag with crash/recovery proof.

5. **Add direct rowid SELECT fast path.**
   This improves point-read constant overhead and protects mixed read-heavy workloads.

The top two changes should move the worst read-side gaps. The hot-row combiner is the hardest and riskiest, but it is the likely path to move `hot-row-update` from “trails SQLite” to “competitive or better.”
