# RedlineDB External Audit Report

## Executive Summary

I unpacked and audited the uploaded repository archive at commit `3d7c72f`. This report supersedes my earlier source-only response that was based on the public repository view. I was able to inspect the codebase directly, but I could not run the full requested test and benchmark suite because the repository requires Rust `1.95.0`, and this environment could not download that toolchain or crates from the network. With `RUSTUP_TOOLCHAIN=stable`, local `cargo 1.85.0` could run `cargo fmt --check` successfully. `./scripts/check_file_sizes.sh` returned success but warned that these files exceed the project size threshold: `crates/kernel/src/index/mod.rs`, `crates/sql/src/exec.rs`, and `crates/sql/tests/sql_smoke.rs`. `cargo check --workspace --locked --offline` failed because dependencies such as `crc32fast` were not present in the local cache.

No benchmark headline claims are validated by this audit. Everything below is based on direct source inspection of the uploaded tree plus official SQLite and systems references for expected behavior.

### Top 10 blockers

1. **RedlineDB is not currently safe to market as SQLite-compatible.** It is a promising Rust embedded database with a SQLite-like subset, but SQL behavior, C ABI behavior, PRAGMAs, transaction semantics, and tooling are far short of SQLite drop-in expectations.
2. **`CREATE INDEX` backfill appears to index the wrong column bytes for existing SQL rows.** SQL row encoding prepends `table_id`, but kernel backfill reads `attnum` directly from the raw record. This can make indexes built on non-empty tables inconsistent with later probes and DML.
3. **Explicit `NULL` values are replaced by column defaults.** SQLite applies a column default when no explicit value is supplied, not when the user explicitly inserts `NULL`. RedlineDB currently conflates those cases.
4. **Index mutations are physically applied outside kernel transaction rollback.** The code comments acknowledge that SQL-side index page changes are repaired by best-effort undo; that is not strong enough for crash safety or unique-index correctness.
5. **`SELECT ALL` is parsed as `DISTINCT`.** This is a direct wrong-result bug.
6. **Ordinary SQL can panic the engine.** Integer division/modulo by zero uses Rust `/` and `%` without zero checks.
7. **Core SQLite expression behavior is wrong.** CAST, numeric coercion, string concatenation, scalar functions, NULL propagation, scalar subqueries, correlated subqueries, and rowid semantics diverge materially.
8. **Conflict algorithms are not SQLite-compatible.** `ABORT`, `FAIL`, `ROLLBACK`, `IGNORE`, and `REPLACE` require distinct statement and transaction semantics; RedlineDB currently collapses or only partially implements them.
9. **The C ABI has serious compatibility and safety gaps.** `sqlite3_prepare_v2`/`rldb_prepare_v2` mishandles `nByte` and tail semantics; several FFI entry points dereference null pointers; `sqlite3_exec` is not multi-statement compatible.
10. **Benchmark/proof lanes are not yet sufficient to support performance or crash-safety claims.** The failpoint verifier checks row counts rather than exact recovered contents, index consistency, or catalog digests; the connection-limit workload has a throughput accounting bug.

### Top 10 opportunities

1. **Move index maintenance into kernel transaction/WAL machinery.** Adopt MVCC-visible index entries or WAL-logged index intents instead of SQL-side physical undo.
2. **Build a SQLite differential conformance suite for the supported subset.** Every supported SQL construct should be compared against SQLite, including result rows, errors, types, and C API behavior.
3. **Implement statement journals/savepoints.** This unlocks correct conflict algorithms, triggers, foreign keys, and `SAVEPOINT`/`ROLLBACK TO`.
4. **Implement a real `PRAGMA integrity_check`.** It should validate catalog, heap, WAL, page metadata, unique constraints, and every table/index equivalence.
5. **Add vectorized scan/filter/project/aggregate execution.** DuckDB’s vectorized model processes fixed-size vectors/DataChunks, commonly 2048 rows, and is a proven architecture for high-throughput scans. ([DuckDB][1])
6. **Add JSON text functions and binary JSONB.** SQLite itself now has JSONB stored as BLOBs, primarily to avoid repeated parse/render overhead. ([SQLite][2])
7. **Add vector types and indexes.** Start with exact flat SIMD scan, then HNSW for approximate nearest-neighbor search; HNSW is a strong established graph-based ANN baseline. ([arXiv][3])
8. **Design for high concurrent connection counts explicitly.** Add group commit, lock wait telemetry, hot-key queues, reader epoch management, and backpressure.
9. **Make the FFI compile common SQLite-using libraries.** Focus first on `open/open_v2`, `prepare_v2`, `step`, `reset`, `finalize`, `bind_*`, `column_*`, `exec`, busy handlers, error codes, and backup APIs.
10. **Publish only artifact-backed benchmark claims.** Each claim should be tied to raw JSON, host metadata, Docker digest, git SHA, binary hash, integrity output, and latency distributions.

### Is RedlineDB currently safe to market as SQLite-compatible?

**No.** The accurate positioning today is:

> RedlineDB is an experimental 100% Rust embedded database with a SQLite-like SQL/API subset.

“SQLite-compatible” or “SQLite drop-in replacement” would overstate the current source. SQLite compatibility is not just accepting similar syntax; it requires matching behavior for dynamic typing, defaults, rowids, conflict algorithms, transactions, PRAGMAs, C API lifetimes, C API errors, and common shell/tool workflows. SQLite documents dynamic typing as value-associated rather than container-associated, and many RedlineDB expression paths do not yet follow that model. ([SQLite][4])

## P0 Findings

### Finding 1: `CREATE INDEX` backfill appears to index the wrong SQL column for existing rows

* **Severity:** P0

* **Area:** Index correctness, wrong query results, unique constraint correctness

* **Files/lines:**

  * `crates/sql/src/exec/expr.rs:1161-1167` encodes SQL rows as `[table_id, col0, col1, ...]`.
  * `crates/sql/src/exec/expr.rs:1170-1190` decodes by reading `table_id` at slot `0` and user columns from slot `1..`.
  * `crates/kernel/src/engine/mod.rs:970-980` backfills index keys using `record.value_at(&scratch, attnum as usize)`.
  * `crates/kernel/src/catalog/ops.rs:638-654` sets `attnum` to the table column ordinal.
  * `crates/sql/src/exec/index_dml.rs:86-104` DML index maintenance uses decoded user-column vectors, so it does not include the `table_id` prefix.

* **Reproduction:**

```sql
CREATE TABLE t(a INTEGER, b TEXT);
INSERT INTO t VALUES(5, 'x');
CREATE INDEX ix_t_a ON t(a);

EXPLAIN QUERY PLAN SELECT * FROM t WHERE a = 5;
SELECT * FROM t WHERE a = 5;
```

Also test:

```sql
CREATE TABLE u(a INTEGER);
INSERT INTO u VALUES(1), (1);
CREATE UNIQUE INDEX ux_u_a ON u(a);
```

* **Expected:** `CREATE INDEX` on a non-empty table should build keys from user column `a`. A subsequent indexed lookup on `a = 5` should find the existing row. A unique index created on duplicate existing values should reject duplicates.
* **Actual from source:** Existing-row backfill reads physical record slot `attnum`, but SQL rows have `table_id` at slot `0`. For `attnum = 0`, backfill indexes `table_id`, not column `a`. Later DML and probes use decoded user-column values. That means backfilled keys and future keys can disagree.
* **Why it matters:** This is a severe index-corruption and wrong-result risk. An index built on existing data may not match table scans, and a unique index may enforce uniqueness on the wrong bytes during backfill.
* **Suggested fix:** Centralize SQL heap-row decoding for index-key construction. In the immediate patch, use `record.value_at(&scratch, 1 + attnum as usize)` in `backfill_index`. Better: decode with the same SQL decoder used by DML, then call the same `build_index_key` path.
* **Tests to add:**

```sql
CREATE TABLE t(a INTEGER, b TEXT);
INSERT INTO t VALUES(5,'x'),(6,'y');
CREATE INDEX ix ON t(a);
SELECT * FROM t WHERE a=5;
-- Force index and force scan if the planner allows; digests must match.
```

Also add non-empty `CREATE UNIQUE INDEX`, multi-column index, nullable unique index, descending index, and crash-after-backfill tests.

### Finding 2: Explicit `NULL` is replaced by column `DEFAULT`

* **Severity:** P0

* **Area:** SQL correctness, SQLite compatibility, data correctness

* **Files/lines:** `crates/sql/src/exec/tail.rs:547-575`

* **Reproduction:**

```sql
CREATE TABLE t(a INTEGER DEFAULT 7, b TEXT DEFAULT 'x');
INSERT INTO t(a, b) VALUES(NULL, NULL);
SELECT typeof(a), a, typeof(b), b FROM t;
```

* **Expected:** SQLite uses a default when no explicit value is supplied for a column; an explicitly supplied `NULL` remains `NULL` unless constrained by `NOT NULL`/conflict behavior. SQLite’s `DEFAULT` documentation says the default is used when no value is explicitly provided. ([SQLite][5])
* **Actual from source:** `build_row` initializes every column to `SqlValue::Null`, writes supplied expressions, then `build_default_values` replaces every `SqlValue::Null` with the column default. Omitted values and explicit `NULL` values are indistinguishable.
* **Why it matters:** This silently rewrites user data. It breaks nullable columns, migrations, ORMs, UPSERT logic, and SQLite conformance.
* **Suggested fix:** Store insert slots as tri-state:

  * `Omitted`
  * `Explicit(SqlValue)`
  * `DefaultKeyword`

  Apply defaults only to `Omitted` and explicit SQL `DEFAULT`, never to `Explicit(SqlValue::Null)`.
* **Tests to add:**

```sql
CREATE TABLE t(a INTEGER DEFAULT 7, b TEXT DEFAULT 'x');
INSERT INTO t(a) VALUES(NULL);
INSERT INTO t DEFAULT VALUES;
INSERT INTO t(a,b) VALUES(DEFAULT, NULL);
SELECT typeof(a), a, typeof(b), b FROM t ORDER BY rowid;
```

### Finding 3: SQL division/modulo by zero can panic

* **Severity:** P0

* **Area:** SQL execution, process safety, FFI safety

* **Files/lines:**

  * `crates/sql/src/exec/expr.rs:382-390`
  * `crates/sql/src/exec.rs:1165-1170`

* **Reproduction:**

```sql
SELECT 1 / 0;
SELECT 1 % 0;
```

* **Expected:** SQL execution must never panic the host process. For SQLite compatibility, division/modulo by zero should be handled as SQLite does, not as a Rust arithmetic panic.
* **Actual from source:** Integer division uses `a / b`; modulo uses `a % b`; there is no zero check.
* **Why it matters:** A database embedded in another process must treat SQL as untrusted input. A panic through FFI is especially dangerous.
* **Suggested fix:** Check zero before integer and real division/modulo. Return the SQLite-compatible SQL result or a database error, but never panic. Add `catch_unwind` boundaries at public Rust and C ABI entry points, but do not rely on `catch_unwind` as the primary fix.
* **Tests to add:** Rust API, SQL API, and C ABI tests for `1/0`, `1%0`, `1.0/0.0`, aggregate expressions, prepared statements, and recovery after the failed statement.

### Finding 4: Physical index mutations are repaired by best-effort SQL-side undo, not kernel transaction atomicity

* **Severity:** P0

* **Area:** Indexes, WAL, crash recovery, transaction atomicity

* **Files/lines:**

  * `crates/sql/src/session.rs:34-38`
  * `crates/sql/src/exec/index_dml.rs:28-33`
  * `crates/sql/src/connection.rs:370-386`
  * `crates/sql/src/exec.rs:268-327`
  * `crates/sql/src/exec.rs:332-379`

* **Reproduction:**

```sql
CREATE TABLE t(id INTEGER PRIMARY KEY, v TEXT);
CREATE UNIQUE INDEX ux_v ON t(v);

BEGIN;
INSERT INTO t VALUES(1, 'a');
-- inject failure after physical index insert but before commit publish/fsync success
COMMIT;

-- reopen/recover
SELECT * FROM t WHERE v = 'a';
PRAGMA integrity_check;
```

* **Expected:** If commit fails, neither heap nor index should expose the row. If commit is acknowledged, both heap and index must recover the row. Indexed query and table scan must match.
* **Actual from source:** Comments state that SQL DML mutates physical index pages immediately and that the kernel rollback does not undo those physical mutations. The repair path drains `session.index_undo`, opens a fresh repair transaction, replays inverse operations, and ignores repair failures with `let _ = engine.commit(repair_tx)`.
* **Why it matters:** A stale unique-index witness can reject valid future inserts. A stale dead mark can hide committed rows. A crash between mutation and best-effort repair can leave heap/index divergence.
* **Suggested fix:** Move index maintenance into the kernel transaction model. Two viable designs:

  1. **MVCC-tagged index entries:** store `{key, rowid, create_tx, delete_tx}` and make visibility checks snapshot-aware. Rollback only changes tx status, not physical bytes.
  2. **WAL-logged index intents:** record index insert/delete intents in the transaction WAL payload; apply them atomically during commit/recovery.

  Do not make committed index visibility depend on SQL-side best-effort undo.
* **Tests to add:** Failpoint tests after heap insert, after index insert, before WAL flush, after WAL flush, before publish, during repair, and during recovery. Every test should compare full table scan digest, index scan digest, and unique constraint digest.

### Finding 5: DDL index handles are published/removed before transaction commit

* **Severity:** P0/P1

* **Area:** DDL transactions, index lifecycle, concurrent visibility

* **Files/lines:**

  * `crates/kernel/src/engine/mod.rs:648-707`
  * `crates/kernel/src/engine/mod.rs:710-735`

* **Reproduction:**

```sql
CREATE TABLE t(a);
BEGIN;
CREATE INDEX ix_t_a ON t(a);
ROLLBACK;

-- Now inspect planner/executor behavior and internal index handle map.
EXPLAIN QUERY PLAN SELECT * FROM t WHERE a = 1;
```

For drop:

```sql
CREATE TABLE t(a);
CREATE INDEX ix_t_a ON t(a);
BEGIN;
DROP INDEX ix_t_a;
ROLLBACK;
EXPLAIN QUERY PLAN SELECT * FROM t WHERE a = 1;
```

* **Expected:** Index handles should become globally visible only after committed `CREATE INDEX`. A rolled-back `DROP INDEX` should not remove the live handle.
* **Actual from source:** `create_index` inserts the new `BtreeIndex` into `index_handles` before transaction commit. `drop_index` removes the handle before transaction commit.
* **Why it matters:** Other connections or later operations can observe a handle map inconsistent with the committed catalog. Even if the planner falls back safely in some cases, this creates stale handle leaks, missing handle behavior, and hard-to-debug DDL/concurrency bugs.
* **Suggested fix:** Stage handle-map changes inside the transaction and publish/remove them only during commit publish. On rollback, discard staged changes.
* **Tests to add:** Rollback `CREATE INDEX`, rollback `DROP INDEX`, concurrent read during uncommitted DDL, crash during DDL before publish, crash after publish.

### Finding 6: Conflict algorithms and explicit transaction failure semantics are not SQLite-compatible

* **Severity:** P0

* **Area:** SQL DML, transaction semantics, SQLite compatibility

* **Files/lines:**

  * `crates/sql/src/parser/dml.rs:222-230`
  * `crates/sql/src/exec/tail.rs:987-999`
  * `crates/sql/src/exec.rs:278-285`
  * `crates/sql/src/parser.rs:61-95`

* **Reproduction:**

```sql
CREATE TABLE t(x UNIQUE);
INSERT INTO t VALUES(1);

BEGIN;
INSERT INTO t VALUES(2);
INSERT OR ABORT INTO t VALUES(1);
INSERT INTO t VALUES(3);
COMMIT;

SELECT x FROM t ORDER BY x;
```

And:

```sql
CREATE TABLE t(x UNIQUE);
INSERT INTO t VALUES(1);
INSERT OR FAIL INTO t VALUES(2),(1),(3);
SELECT x FROM t ORDER BY x;
```

* **Expected:** SQLite distinguishes five conflict algorithms. `ABORT` backs out the current statement but keeps the transaction active; `FAIL` preserves prior row changes from the same statement; `ROLLBACK` rolls back the transaction; `IGNORE` skips the violating row; `REPLACE` deletes conflicting rows and continues. ([SQLite][6])
* **Actual from source:** The parser recognizes conflict actions, but execution treats `Abort`, `Fail`, `Rollback`, and `None` as ordinary constraint errors. In explicit transactions, `with_write_tx` marks the whole session failed on any statement error, requiring rollback. `SAVEPOINT`, `RELEASE`, and `ROLLBACK TO` are also absent; the parser only handles `BEGIN`, `BEGIN IMMEDIATE`, `BEGIN EXCLUSIVE`, `COMMIT`, and full `ROLLBACK`.
* **Why it matters:** SQLite conflict algorithms are heavily used by ORMs and application code. Incorrect transaction survival after `ABORT` is a major drop-in blocker.
* **Suggested fix:** Implement statement journals/savepoints first. Then express each conflict algorithm in terms of statement undo, row skip, delete-and-insert, or transaction rollback.
* **Tests to add:** Multi-row `INSERT`, `UPDATE`, `UPSERT`, `NOT NULL`, `UNIQUE`, and `CHECK` tests for `ABORT`, `FAIL`, `ROLLBACK`, `IGNORE`, and `REPLACE`, both inside and outside explicit transactions.

### Finding 7: Core expression semantics diverge materially from SQLite

* **Severity:** P0/P1

* **Area:** SQL expression evaluation, SQLite compatibility

* **Files/lines:**

  * `crates/sql/src/exec/expr.rs:686-713`
  * `crates/sql/src/exec/expr.rs:793-879`
  * `crates/sql/src/exec/expr.rs:881-908`
  * `crates/sql/src/exec/expr.rs:919-945`
  * `crates/sql/src/exec/expr.rs:958-965`

* **Reproduction:**

```sql
SELECT length(NULL), lower(NULL), upper(NULL), round(NULL), abs(NULL);
SELECT NULL || 'x';
SELECT CAST('123abc' AS INTEGER);
SELECT CAST('abc' AS INTEGER);
SELECT CAST('123e+5' AS INTEGER);
SELECT '5' + 1;
```

* **Expected:** SQLite preserves `NULL` through `CAST`, implements documented longest-prefix numeric casts, and applies dynamic type conversions according to its affinity/coercion rules. SQLite documents that scalar subqueries and casts preserve/convert values in specific ways; for integer casts, it extracts the longest integer prefix and returns `0` when no prefix exists. ([SQLite][7])
* **Actual from source:**

  * `length(NULL)` returns `0` because `value_to_string(NULL)` returns `""`.
  * `lower(NULL)` and `upper(NULL)` return empty text, not `NULL`.
  * `round(NULL)` returns `0` because `numeric_value(NULL)` returns `0.0`.
  * `abs(NULL)` returns a datatype mismatch.
  * `NULL || 'x'` returns `'x'`.
  * `CAST('123abc' AS INTEGER)` errors because Rust `parse::<i64>()` requires full-string parse.
  * Text numeric coercion is only attempted for text/text operands, not text/integer combinations.
* **Why it matters:** SQL compatibility lives in expression corner cases. These break application logic, CHECK constraints, generated columns, expression indexes, JSON path extraction, and ORMs.
* **Suggested fix:** Replace ad hoc conversion helpers with a SQLite-compatible coercion module:

  * `sqlite_cast_to_integer`
  * `sqlite_cast_to_real`
  * `sqlite_numeric_affinity`
  * `sqlite_truthiness`
  * `sqlite_concat`
  * per-function arity and NULL policy

  Add a scalar function registry rather than hard-coding loose behavior in one `match`.
* **Tests to add:** Import SQLite’s cast and scalar expression cases for the supported subset. Include result storage class, not just textual equality.

### Finding 8: `SELECT ALL`, qualified wildcards, grouped ordering, and some compound query outputs are wrong

* **Severity:** P0/P1

* **Area:** Parser/planner/executor correctness

* **Files/lines:**

  * `crates/sql/src/parser/select.rs:80-82`
  * `crates/sql/src/parser/select.rs:95-101`
  * `crates/sql/src/exec/expr.rs:13-17`
  * `crates/sql/src/parser/select.rs:264-339`
  * `crates/sql/src/exec.rs:986-1008`
  * `crates/sql/src/exec.rs:1076-1079`

* **Reproduction:**

```sql
CREATE TABLE t(x);
INSERT INTO t VALUES(1),(1);
SELECT ALL x FROM t;
```

```sql
CREATE TABLE a(x);
CREATE TABLE b(y);
INSERT INTO a VALUES(1);
INSERT INTO b VALUES(2);
SELECT a.* FROM a JOIN b;
```

```sql
SELECT 1 UNION ALL SELECT 2;
```

* **Expected:** `SELECT ALL` is equivalent to ordinary non-distinct SELECT. `a.*` should expand only columns from `a`. Compound query column metadata should reflect result columns. `ORDER BY` should follow requested expressions, directions, collations, and NULL ordering where supported.
* **Actual from source:**

  * `Distinct::All` is mapped to `true`, same as `DISTINCT`.
  * `QualifiedWildcard` is handled like wildcard, expanding all source columns.
  * Compound `UNION ALL` handling rejects parameters in branches/tails and clears output columns in some paths, risking `column_count == 0`.
  * DISTINCT/grouped order handling sorts projected rows or ignores requested ordering semantics.
* **Why it matters:** These are visible wrong-result bugs in common SQL.
* **Suggested fix:**

  * Map `Distinct::All` to `false`.
  * Preserve qualifier in wildcard expansion and expand only matching relation/alias.
  * Build compound-select metadata from the first SELECT projection and support parameters across all branches.
  * Represent `ORDER BY` as bound expressions evaluated against the proper row/projection context.
* **Tests to add:** SQLLogicTest cases for `ALL`, `DISTINCT`, `t.*`, joins with duplicate column names, compound SELECT metadata, `ORDER BY` aliases/ordinals/directions.

### Finding 9: Scalar subqueries and correlated subqueries do not match SQLite

* **Severity:** P0/P1

* **Area:** Query execution, name binding, SQLite compatibility

* **Files/lines:**

  * `crates/sql/src/exec/expr.rs:280-290`
  * `crates/sql/src/exec/expr.rs:493-510`

* **Reproduction:**

```sql
CREATE TABLE t(x);
INSERT INTO t VALUES(1),(2);

SELECT (SELECT x FROM t ORDER BY x);
SELECT x FROM t AS o
WHERE EXISTS (SELECT 1 FROM t AS i WHERE i.x = o.x);
```

* **Expected:** SQLite scalar subqueries use the first row of the enclosed SELECT and return `NULL` if it returns no rows. Correlated subqueries may reference outer query columns and are reevaluated as required. ([SQLite][7])
* **Actual from source:** Scalar subqueries error unless exactly one row and one column are returned. `evaluate_subquery_rows` binds and materializes the subquery without carrying an outer row context, so correlated references are not supported correctly.
* **Why it matters:** Subqueries are fundamental to SQL and common ORM output.
* **Suggested fix:** Add binder-resolved outer references and a chained `RowContext`. For scalar subqueries, reject only multi-column row-value cases; for multi-row scalar subqueries, use the first row.
* **Tests to add:** Empty scalar subquery, multi-row scalar subquery, correlated `EXISTS`, correlated `IN`, correlated aggregate subquery, nested correlation.

### Finding 10: Rowid semantics use non-negative `u64`, but SQLite rowid is signed 64-bit

* **Severity:** P0/P1

* **Area:** Storage identity, SQLite compatibility, C API behavior

* **Files/lines:**

  * `crates/sql/src/exec/tail.rs:1021-1040`
  * `crates/sql/src/exec/tail.rs:1260-1270`
  * `crates/sql/src/exec/expr.rs:1084-1090`

* **Reproduction:**

```sql
CREATE TABLE t(id INTEGER PRIMARY KEY, v TEXT);
INSERT INTO t(id, v) VALUES(-1, 'neg');
SELECT rowid, id, v FROM t;
```

* **Expected:** SQLite rowid tables use a unique, non-NULL, **signed 64-bit integer** rowid. The rowid is available as `rowid`, `oid`, or `_rowid_` unless those names are shadowed. ([SQLite][8])
* **Actual from source:** `choose_rowid_for_insert` rejects negative integer primary key aliases and converts accepted values to `u64`. Lookup casts `row.rowid.0 as i64`, which is dangerous once `u64` exceeds `i64::MAX`.
* **Why it matters:** Rowid behavior is central to SQLite compatibility, `last_insert_rowid`, ORMs, migrations, and rowid aliases.
* **Suggested fix:** Change `RowId` to wrap `i64` or introduce a SQLite rowid layer that preserves signed values. Audit page/key encoding and ordering. Implement rowid shadowing rules.
* **Tests to add:** Negative rowid insert/update, max/min `i64`, rowid alias columns, shadowed `rowid` column, `last_insert_rowid`.

### Finding 11: PRAGMAs are shallow or non-durable

* **Severity:** P1

* **Area:** SQLite compatibility, durability, tooling

* **Files/lines:**

  * `crates/sql/src/parser/pragma.rs:28-107`
  * `crates/sql/src/parser/pragma.rs:537-541`
  * `crates/sql/src/connection.rs:154`
  * `crates/sql/src/connection.rs:184`, `207`, `234`
  * `crates/sql/src/connection.rs:313-318`, `445-450`

* **Reproduction:**

```sql
PRAGMA user_version = 123;
-- close and reopen
PRAGMA user_version;
```

```sql
PRAGMA integrity_check;
```

```sql
PRAGMA foreign_keys = ON;
CREATE TABLE p(id PRIMARY KEY);
CREATE TABLE c(pid REFERENCES p(id));
INSERT INTO c VALUES(999);
```

* **Expected:** `user_version` is durable in SQLite. `integrity_check` should actually check database consistency. `foreign_keys = ON` should enforce foreign-key constraints when supported.
* **Actual from source:**

  * `user_version` is an in-memory `Mutex<i64>` initialized to `0` on create/open/recovery.
  * `integrity_check` always returns `"ok"`.
  * `foreign_keys` is a session boolean, while FK list returns empty and FK constraints are not meaningfully enforced.
* **Why it matters:** Migration frameworks rely on `user_version`. Users rely on `integrity_check` after crashes and corruption suspicion. FK PRAGMAs that appear to work but do not enforce constraints are dangerous.
* **Suggested fix:** Persist `user_version` in catalog/control metadata or WAL-logged catalog records. Replace `integrity_check` with a real kernel checker. Make unsupported foreign keys explicit: either reject `PRAGMA foreign_keys=ON` with “not supported” or implement FK parsing/enforcement.
* **Tests to add:** Reopen and crash-recover `user_version`; corrupt page/index fixtures for `integrity_check`; FK insert/update/delete enforcement tests.

### Finding 12: `sqlite3_prepare_v2`/`rldb_prepare_v2` mishandles `nByte`, tail, and multi-statement behavior

* **Severity:** P0

* **Area:** C ABI, memory safety, SQLite drop-in compatibility

* **Files/lines:**

  * `crates/ffi/src/lib.rs:369-417`
  * `crates/sql/src/parser.rs:101-106`

* **Reproduction:**

```c
const char sql[] = {
  'S','E','L','E','C','T',' ','1',';',
  'S','E','L','E','C','T',' ','2',';'
}; /* no NUL terminator */

sqlite3_stmt *stmt = 0;
const char *tail = 0;
int rc = sqlite3_prepare_v2(db, sql, sizeof(sql), &stmt, &tail);
```

* **Expected:** SQLite reads up to `nByte` bytes when `nByte` is positive, compiles only the first statement, sets `*pzTail` to the first byte past the first statement, and sets `*ppStmt = NULL` on errors or empty input. ([SQLite][9])
* **Actual from source:** RedlineDB calls `CStr::from_ptr(sql)` before applying `nbytes`, requiring a NUL-terminated input and risking over-read. It prepares the whole string and parser-level code rejects multiple statements. Tail is set to `sql_cstr.as_ptr() + sql_len`, not to the first uncompiled statement.
* **Why it matters:** This breaks many real C/C++ callers and is a memory-safety issue.
* **Suggested fix:** If `nbytes >= 0`, build a byte slice from the raw pointer and length without `CStr::from_ptr`; stop at first NUL within that slice. Parse only the first complete statement. Return tail into the original input buffer.
* **Tests to add:** C tests for non-NUL input, embedded NUL, empty string, comment-only string, multi-statement SQL, syntax error tail, and `ppStmt` nulling.

### Finding 13: Multiple C ABI entry points dereference null raw pointers

* **Severity:** P0

* **Area:** FFI memory safety, API misuse behavior

* **Files/lines:**

  * `crates/ffi/src/lib.rs:350-357`
  * `crates/ffi/src/lib.rs:421-424`

### Finding 14: `sqlite3_exec` is not SQLite-compatible

* **Severity:** P0/P1

* **Area:** C ABI, migration scripts, simple apps

* **Files/lines:** `crates/ffi/src/lib.rs:660-714`

* **Reproduction:**


* **Expected:** SQLite `sqlite3_exec` runs zero or more semicolon-separated statements and invokes the callback for result rows. ([SQLite][10])

* **Severity:** P1

* **Area:** C ABI, data typing

* **Files/lines:**

  * `crates/ffi/src/lib.rs:585-599`
  * `crates/ffi/src/lib.rs:646-655`

### Finding 16: Catalog save errors are ignored during commit publish

* **Severity:** P1

* **Area:** Catalog durability, error handling

* **Files/lines:** `crates/kernel/src/engine/mod.rs:547-550`, `565-570`

* **Reproduction:**

```sql
CREATE TABLE t(a);
```

* **Expected:** If a durable catalog snapshot save fails, commit handling should either rely explicitly and provably on WAL catalog snapshot recovery, or surface/record the error. It should not silently ignore I/O failures.

### Finding 17: Failpoint matrix currently verifies row count, not exact durability/integrity

* **Severity:** P1

* **Area:** Crash proof, benchmark certification

* **Files/lines:**

  * `crates/kernel/src/wal/manager.rs:767-783`
  * `crates/bench/src/failpoint_matrix.rs:464-505`

* **Reproduction:**

```bash
cargo run -p redlinedb-bench -- failpoint-matrix \
  --config crates/bench/bench/failpoint-matrix.toml \
  --out target/bench/failpoint-matrix.json \
  --seed 7
```

* **Expected:** A failpoint proof artifact should prove:

  * the failpoint fired,
  * the child died or continued as expected,
  * acknowledged transactions survived exactly,
  * unacknowledged transactions are handled according to the durability boundary,
  * table scan digest equals index scan digest,
  * catalog digest is valid,
  * `integrity_check` is real and passes.

* **Actual from source:** `wal::flush` has a failpoint that can skip fsync and report success, which is a useful negative scenario.   * ordered hash of `(k, tenant, version, payload_hash)`,
  * exact acked key set,
  * index-vs-table digest,
  * catalog hash,
  * real `integrity_check`,
  * failpoint fired count,
  * fsync/pwrite counters.

### Finding 18: Benchmark checksum and connection-limit workload can mislead

* **Severity:** P1/P2

* **Area:** Benchmark validity, performance claims

* **Files/lines:**

  * `crates/bench/src/engine/sqlite.rs:146-153`
  * `crates/bench/src/engine/redline.rs:120-127`
  * `crates/bench/src/workload.rs:300-350`

* **Reproduction:** Run the connection-limit certification lane and inspect the reported throughput and checksum fields.

* **Expected:** Checksums should detect lost rows, duplicate keys, wrong payloads, wrong versions, and wrong tenant assignment. Connection-limit throughput should use actual probe duration and the best stable probe, not an artificial elapsed interval.

* **Actual from source:**

  * Checksums use `COUNT(*)`, `MAX(k)`, `MAX(version)`, and `COUNT(*) WHERE tenant >= 0`; this misses many correctness failures.
  * Connection-limit uses a fixed high of `64`, one-second probes, very loose stability thresholds, and then computes elapsed from a fresh `Instant::now()` immediately before reporting, clamped to `1ms`. That can inflate throughput.

* **Why it matters:** This can produce impressive but invalid charts, especially on a 128-core node.

* **Suggested fix:**

  * Use strong ordered digests.
  * Record actual duration for every probe.
  * Report best stable probe metrics, not last probe metrics.
  * Raise the high bound dynamically to OS limits or a config value.
  * Tighten stability: near-zero correctness failures, separate busy/locked/timeout counts, p99/p999/max latency gates.

* **Tests to add:** Unit test the connection-limit reporter with synthetic metrics. Add a checksum negative-control fixture with same count/max values but wrong rows.

## Performance And Benchmark Review

### Harness issues

The benchmark harness is directionally useful. It has Redline and SQLite engines, Docker/remote scripts, failpoint matrix support, recovery lanes, process metrics, and some manifest fields. The SQLite engine configures WAL mode, cache size, auto-checkpoint behavior, and synchronous settings in `crates/bench/src/engine/sqlite.rs:207-229`. RedlineDB reports data/WAL byte stats and syscall counters through `crates/bench/src/engine/redline.rs:90-117`.

The serious issues are not the existence of the harness; they are the proof strength and claim discipline.

### Fairness concerns

Use this language until raw artifacts prove more:

> SQLite contention and tail-latency evidence.

Do not claim “faster than SQLite,” “lower memory than SQLite,” or “higher concurrency than SQLite” until the benchmark artifacts include:

* exact git SHA and dirty flag,
* binary hash,
* Docker image digest,
* host CPU/kernel/filesystem/mount options,
* SQLite version and compile options,
* RedlineDB version and feature flags,
* durability mode for both engines,
* raw latency samples or histograms,
* p50/p95/p99/p999/max,
* RSS/PSS,
* data bytes, WAL bytes, checkpoint bytes,
* fsync/fdatasync/pwrite counters,
* busy/locked/timeout split,
* integrity result,
* recovered digest after crash workloads.

### Specific benchmark flaws

1. **Checksum is too weak.** `COUNT`, `MAX(k)`, `MAX(version)`, and a count of non-negative tenant rows cannot detect many forms of corruption or wrong results.
2. **Connection-limit throughput is wrong.** `run_connection_limit` starts a fresh timer after the probes and clamps elapsed to `1ms`, so reported throughput can be inflated.
3. **Connection-limit search bound is too low for the target.** A fixed high of `64` is not enough for a 128-core benchmark node.
4. **Stability thresholds are too loose.** Allowing 5% errors, 50% busy/locked/timeout, and 100x p99 blowup is not “stable.”
5. **Failpoint verification is count-only.** Exact acked transaction digest and index/table equality are required.
6. **Warmup/measurement/post-check phases need separate timing.** Throughput should not accidentally include or exclude checkpoint/checksum work without labeling.

## Crash/Recovery/Corruption Review

### Invariants reviewed

1. **Acked commit durability:** if commit returns success, recovered state must include it.
2. **Failed commit atomicity:** if commit fails, heap and indexes must not expose partial transaction effects.
3. **Index/table equivalence:** every visible row has required index entries; every index entry points to a visible row.
4. **Unique durability:** no recovery path may produce duplicate committed unique keys.
5. **Catalog atomicity:** recovered schema is old or new, never mixed.
6. **Recovery idempotence:** repeated recovery does not change the database after the first successful recovery.
7. **Torn/corrupt input detection:** malformed WAL/page/catalog/tuple bytes are detected, not silently converted into rows.
8. **Checkpoint safety:** checkpoint/control updates do not make required WAL unreachable.

### Gaps

* SQL-side physical index undo is the largest crash-safety risk.
* `CREATE INDEX` backfill likely uses wrong record slots.
* `PRAGMA integrity_check` is a stub.
* Failpoint verification checks count, not exact content.
* Catalog snapshot save errors are ignored.
* DDL handle publication/removal is not commit-gated.
* FFI can segfault on null pointer misuse, so crash-resilience claims at the embedded boundary are weak.
* No evidence from this environment that recovery/failpoint matrices pass.

### New failpoints/tests

Add failpoints at these semantic boundaries:

* before WAL record encode,
* after WAL encode before write,
* after partial WAL write,
* after WAL write before fdatasync,
* after fdatasync before commit ack,
* after heap mutation before index mutation,
* after index mutation before commit,
* during SQL-side index undo repair,
* during `CREATE INDEX` backfill,
* after index handle insertion before commit,
* after index handle removal before commit,
* during catalog snapshot save,
* after catalog temp-file write before rename,
* after rename before parent-directory fsync,
* during checkpoint control-file update,
* during page flush,
* during transaction-status checkpoint.

Each test artifact should include fired count, child exit status, acked transaction digest, recovered digest, table scan digest, index scan digest, catalog digest, WAL/data bytes, fsync/pwrite counts, and real `integrity_check`.

## API/FFI/Tooling Review

### Rust API

The Rust facade should aim for a stable, SQLite-like subset first:

* `Database::open`, `open_with_options`, `open_readonly`
* `Connection::prepare`, `execute`, `query`, `query_row`
* `Statement::bind`, `reset`, `clear_bindings`
* `Transaction` and `Savepoint`
* `busy_timeout` and busy handler
* `last_insert_rowid`, `changes`, `total_changes`
* online backup/snapshot
* `interrupt`
* trace/profile hooks
* UDF/collation registration
* typed `Value`/`ValueRef`

The current API direction is useful, but it should not expose behaviors that contradict SQLite unless those APIs are explicitly Redline-specific.

### C ABI

Minimum API set needed for common SQLite-using C/C++ libraries:

* Connection: `sqlite3_open`, `sqlite3_open_v2`, `sqlite3_close`, `sqlite3_close_v2`
* Prepare/execute: `sqlite3_prepare_v2`, `sqlite3_prepare_v3`, `sqlite3_step`, `sqlite3_reset`, `sqlite3_finalize`, `sqlite3_exec`
* Errors: `sqlite3_errcode`, `sqlite3_extended_errcode`, `sqlite3_errmsg`, `sqlite3_errstr`, `sqlite3_extended_result_codes`
* Binds: `sqlite3_bind_null`, `bind_int`, `bind_int64`, `bind_double`, `bind_text`, `bind_text64`, `bind_blob`, `bind_zeroblob`, `bind_parameter_count`, `bind_parameter_index`, `bind_parameter_name`, `clear_bindings`
* Columns: `sqlite3_column_count`, `column_name`, `column_decltype`, `column_type`, `column_int`, `column_int64`, `column_double`, `column_text`, `column_blob`, `column_bytes`
* Metadata: `sqlite3_changes`, `sqlite3_total_changes`, `sqlite3_last_insert_rowid`, `sqlite3_get_autocommit`
* Busy/interrupt: `sqlite3_busy_timeout`, `sqlite3_busy_handler`, `sqlite3_interrupt`
* Memory/error strings: `sqlite3_malloc`, `sqlite3_free`, errmsg allocation
* Functions/collations: `sqlite3_create_function_v2`, `sqlite3_create_collation_v2`
* Backup: `sqlite3_backup_init`, `sqlite3_backup_step`, `sqlite3_backup_finish`, `sqlite3_backup_remaining`, `sqlite3_backup_pagecount`

## Major Upgrade Roadmap

### JSON / BJSON / JSONB

**Goal:** Beat SQLite’s JSON ergonomics while preserving compatibility where possible.

**API shape:**

```sql
CREATE TABLE events(
  id INTEGER PRIMARY KEY,
  doc JSONB,
  user_id TEXT GENERATED ALWAYS AS (json_extract(doc, '$.user.id')) STORED
);

CREATE INDEX events_user_id ON events(user_id);
CREATE INDEX events_doc_user_path ON events(json_extract(doc, '$.user.id'));

SELECT doc -> '$.user.id', doc ->> '$.user.name'
FROM events
WHERE json_extract(doc, '$.kind') = 'click';
```

**Storage format:**

* versioned binary JSON representation,
* typed node headers,
* varint lengths,
* offset table for O(log n) or bounded path seek,
* canonical number encoding,
* optional string dictionary,
* checksum coverage,
* text JSON round-trip functions.

SQLite now supports JSONB as a BLOB representation and documents it as its internal binary JSON representation, so RedlineDB should not stop at text JSON. ([SQLite][2])

**Indexing strategy:**

* expression indexes over `json_extract`,
* generated stored columns over JSON paths,
* path-value inverted indexes,
* per-page JSON path bloom filters for existence predicates.

**Backward compatibility:**

* accept text JSON and JSONB input,
* output canonical text JSON unless binary output explicitly requested,
* document duplicate-key semantics.

**Tests:**

* differential JSON tests against SQLite JSON1/JSONB for shared behavior,
* malformed JSONB fuzzing,
* path index consistency after update/delete/rollback/crash,
* generated-column JSON path tests.

**Performance risks:**

* binary format lock-in,
* path index write amplification,
* duplicate object-key behavior,
* number comparison semantics.

---

### Vector search and vectorized execution

**Vector type:**

```sql
CREATE TABLE docs(
  id INTEGER PRIMARY KEY,
  body TEXT,
  embedding VECTOR<F32, 768>
);

CREATE VECTOR INDEX docs_embedding_hnsw
ON docs(embedding)
USING hnsw
WITH (metric = 'cosine', m = 16, ef_construction = 200);

SELECT id, body
FROM docs
ORDER BY embedding <-> vector_bind(?)
LIMIT 10;
```

**Indexing strategy:**

1. Flat exact SIMD scan for small tables and correctness baseline.
2. HNSW for approximate nearest-neighbor search.
3. IVF-flat and IVF-PQ later for memory-constrained workloads.
4. Aligned vector sidecar pages to avoid decoding full SQL rows during vector search.
5. MVCC visibility checks separate from vector graph membership.

HNSW is a graph-based approximate nearest-neighbor index with hierarchical navigable small-world layers and is a strong baseline for embedded vector search. ([arXiv][3])

**Vectorized execution:**

Implement a hybrid executor:

* scalar path for point lookups,
* vectorized path for scans, predicates, projections, aggregates,
* 1024/2048 row batches,
* null bitmaps,
* selection vectors,
* late materialization,
* SIMD comparisons,
* columnar side caches for hot analytical columns.

DuckDB’s internal model is a strong reference: operators work on fixed-size vectors/DataChunks rather than row-at-a-time tuples. ([DuckDB][1])

**Tests:**

* exact vector distance tests,
* recall tests for HNSW with fixed seeds,
* crash/recovery of vector indexes,
* planner choice flat vs HNSW,
* memory cap tests.

---

### Higher concurrency

**Architecture upgrades:**

1. **Group commit:** multiple writers enqueue commit records; one committer assigns LSNs and fsyncs batches.
2. **MVCC-visible indexes:** entries carry create/delete transaction metadata.
3. **Reader epochs:** readers pin page generations; writers publish new generations after commit.
4. **Hot-key queues:** detect hot rows/unique keys and serialize only the contended key, not the whole database.
5. **Immutable delta pages:** append small deltas, compact in background, reduce write amplification.
6. **Lock wait telemetry:** every busy/locked timeout should identify table/index/key/waiter/holder class.
7. **Backpressure:** when WAL or checkpoint pressure exceeds limits, throttle writers before tail latency explodes.

**Novel concept worth prototyping:** a **semantic commit combiner** for opt-in hot counter workloads. If statements are planner-proven commutative, such as `UPDATE counters SET v = v + ? WHERE k = ?`, combine multiple increments into one physical page/index mutation while logging individual transaction effects. This is untested and must be opt-in or proof-backed, but it could produce major gains in hot-row storms.

## Bottom Line

RedlineDB has the right ambition and some promising infrastructure, especially around Rust implementation, physical indexes, WAL/failpoints, and benchmarking. But the current uploaded source has multiple **clear correctness blockers** that must be fixed before performance work or public SQLite-compatibility claims.

The immediate priority should be:

> Fix index correctness, SQL expression/default semantics, conflict/transaction behavior, and FFI safety; then prove crash recovery with exact acked digests and real integrity checks; then benchmark against SQLite under identical Docker/Linux durability modes.

Only after that should RedlineDB make stronger claims about being faster, lower-latency, lower-memory, or more concurrent than SQLite.
