# Engineering Spec: Replace global B-tree `structure_lock` with a B-link, page-latched concurrent index

**Recommendation:** upgrade the **B-tree index mutation path** first.

RedlineDB’s core pitch is already strong: safe Rust, SQLite-compatible ABI, MVCC, row-level write concurrency, group-commit WAL, and deterministic crash recovery. The live README positions SQLite’s single-writer WAL as the ceiling RedlineDB is designed to break, while RedlineDB keeps the SQLite API contract and replaces the storage core with MVCC, a concurrent B-tree, group-commit WAL, and crash recovery. ([GitHub][1]) SQLite’s own WAL documentation confirms the fundamental competing constraint: readers and a writer can proceed concurrently, but “there can only be one writer at a time.” ([SQLite][2])

The place I would upgrade is **not** the SQL parser, FFI layer, vector path, or even the WAL first. It is the **index concurrency layer**, specifically the current global B-tree `structure_lock`.

The reason: RedlineDB already beats SQLite dramatically on disjoint-writer and mixed-OLTP benchmarks, but the current numbers still show obvious room in index-heavy paths: `writers-disjoint` is 1,256 qps versus SQLite’s 79 qps, but `secondary-index-read` and `secondary-index-range` are still major losses versus SQLite in the published table. ([GitHub][1]) The uploaded spec also calls out that B-tree `structure_lock` serializes all inserts, even for logically disjoint keys, and explicitly names B-link trees as the mitigation.  The current code confirms the same pattern: `IndexInner` contains `structure_lock: Mutex<()>`, and `insert_tx_inner` locks it before descent, leaf modification, and split handling. ([GitHub][3]) ([GitHub][4])

So the highest-leverage upgrade is:

> **Convert RedlineDB’s B-tree from a globally serialized structure-lock index into a B-link-tree-style concurrent index with page-level latches, optimistic descent, move-right validation, structural modification operations, and redo-safe split publication.**

---

## 1. Why this is the right upgrade

### Current state

RedlineDB’s B-tree is already structurally close to a B-link tree:

The index page special region already has `left_sibling`, `right_sibling`, and `high_key` metadata, and range scans already follow `right_sibling` links.  The live code also has `PageHeader { left, right, high_key }`, and point lookup already walks right through sibling leaves to collect duplicate-key runs. ([GitHub][3]) ([GitHub][5])

But writes still serialize globally:

```rust
let _structure = self
    .inner
    .structure_lock
    .lock()
    .map_err(|_| Error::CorruptPage("index structure mutex poisoned"))?;
```

That means RedlineDB’s row-level MVCC/write-concurrency model can allow disjoint-row writes, but **every indexed insert/delete still queues behind one B-tree mutex**. The uploaded spec explicitly states that two writers inserting into different leaf pages serialize at the `structure_lock`. 

### Why this matters for queue workloads

Queue workloads are usually index-heavy:

```sql
CREATE INDEX jobs_ready_idx ON jobs(status, priority, created_at);

-- claim work
UPDATE jobs
SET status = 'running', worker_id = ?
WHERE id = (
  SELECT id
  FROM jobs
  WHERE status = 'ready'
  ORDER BY priority, created_at
  LIMIT 1
);
```

A database that wants to beat SQLite as an embedded queue engine needs to scale:

1. concurrent inserts into ready queues,
2. concurrent status updates that delete and reinsert secondary-index entries,
3. concurrent range scans over “ready” jobs,
4. concurrent point lookups by primary key,
5. hot-page behavior at the right edge or common queue-status prefix.

The global B-tree lock directly limits all five.

### Why not upgrade WAL first?

The WAL is also a serious future target. The uploaded spec notes a single WAL writer thread, one `VecDeque`, a 200 µs group-commit delay, and serialized append through the coordinator state lock.  But the WAL path is coupled to durability, crash certification, commit acknowledgement, and recovery. Changing it first risks touching the hardest correctness surface.

The B-tree upgrade can be staged more safely because:

1. SQL semantics do not change.
2. Tuple MVCC visibility does not change.
3. WAL commit durability does not change.
4. FFI ABI does not change.
5. Unique-key correctness remains protected by `UniqueKeyLockTable`.
6. Split correctness can be made redo-safe using page-image-set system records.

This is the better first “win on all fronts” upgrade.

## 2. Design goal

Replace:

```rust
BtreeIndex.inner.structure_lock: Mutex<()>
```

with:

```rust
page-local latches
+ optimistic descent
+ right-link/high-key move-right validation
+ redo-safe structural modification operations
+ optional parent-lag tolerance
```

The desired behavior:

| Operation                       |                                                Current behavior |                                   Target behavior |
| ------------------------------- | --------------------------------------------------------------: | ------------------------------------------------: |
| Point lookup                    | no global write lock, but page reads can race with page rewrite |      read-latched page copy, right-link traversal |
| Range scan                      |                                              follows leaf links |      read-latched leaf copy, no writer starvation |
| Insert into non-full leaf       |                                              global B-tree lock |                      only target leaf write latch |
| Insert into different leaves    |                                                      serialized |                                          parallel |
| Delete mark in different leaves |                                                      serialized |                                          parallel |
| Leaf split                      |                                              global B-tree lock |           local structural modification operation |
| Parent propagation              |                                                     global lock |   optimistic parent insert; parent may lag safely |
| Unique insert same key          |                                      unique-key lock serializes |                                         unchanged |
| Crash recovery                  |                                           redo existing records | redo index system records + existing user records |
| SQL/ABI compatibility           |                                                        existing |                                         unchanged |

---

## 3. Algorithmic basis

This should use the **Lehman-Yao B-link tree** pattern: every node has a right-link and high-key; searches move right when they discover the target key is beyond the current node; updates hold only a small number of locks at a time. The classic summary is exactly aligned with what RedlineDB already partially stores: a right-neighbor pointer plus a key naming the maximum range of the node; the scheme gives high concurrency with at most a small constant number of nodes locked by an update, and no read locks in the original paper model. ([Flux][6])

RedlineDB does not need to implement a fully lock-free/no-read-lock paper version. A safe-Rust implementation should use **short page read/write latches** because the current page code rewrites page contents in place. The critical win is eliminating the **global** B-tree lock.

---

## 4. Non-goals

This proposal deliberately avoids unrelated semantic changes.

1. **No SQL behavior change.** All SQLite-compatible behavior remains.
2. **No FFI ABI change.** `sqlite3_*` and `rldb_*` symbols remain untouched.
3. **No serializable isolation upgrade.** Snapshot isolation limitations remain as documented. 
4. **No B-tree merge on delete.** Keep tombstones and leaf compaction/vacuum. B-link deletion is much harder if pages can merge concurrently; even Lehman-Yao-style summaries note deletion/underflow is typically punted or handled by rebuild/maintenance. ([Flux][6])
5. **No WAL parallelization yet.** WAL remains the second major concurrency project.
6. **No variable page size.** Keep 16 KiB pages.
7. **No planner changes required.** Planner may benefit from better index runtime, but this is not a cost-model project.

## 5. Proposed architecture

### 5.1 Add page latches at the buffer-frame level

Do **not** create an unbounded `HashMap<PageId, RwLock<()>>`; that creates memory leaks and lifecycle complexity. Add latches to resident buffer frames.

Proposed frame-level additions:

```rust
pub(crate) struct Frame {
    page: Option<Page>,
    pin_count: AtomicUsize,
    dirty_lsn: AtomicU64,
    referenced: AtomicBool,

    // New:
    page_latch: RwLock<()>,
    page_epoch: AtomicU64,
}
```

`page_latch` protects in-memory page bytes while readers copy/decode and writers rewrite.

`page_epoch` increments after every structural rewrite. Optimistic descent can record observed epochs and restart cheaply if the path changed.

Memory cost is bounded by buffer-pool size. For example, a 1 GiB cache has about 65,536 16 KiB frames. Even a 64-byte latch/epoch overhead is roughly 4 MiB, which is acceptable relative to the cache.

### 5.2 Replace `structure_lock` with narrow root/meta coordination

Change `IndexInner` from:

```rust
pub(super) structure_lock: Mutex<()>,
```

to:

```rust
pub(super) root_update_lock: Mutex<()>,
pub(super) smo_epoch: AtomicU64,
```

`root_update_lock` is **not** taken for ordinary inserts/deletes. It is only used when installing a new root page or updating meta-root fields.

Most inserts should hold exactly one write latch: the target leaf.

### 5.3 Preserve existing key format

Keep:

```text
physical_key = logical_key || row_id || page_id || slot || generation
```

The uploaded spec already explains why this is important: the row locator suffix makes every physical key unique, avoids ambiguous duplicate runs, gives well-defined split midpoints, and lets range scans strip suffixes for logical comparisons. 

This format is a major advantage. Do not change it.

### 5.4 Preserve existing MVCC index entry visibility

Keep:

```rust
create_tx
delete_tx
```

inside leaf entries. Visibility stays snapshot-based and mirrors heap tuple visibility. 

This is why structural splits can be non-transactional while user entries remain transactional.

## 6. New operation model

## 6.1 Search / point lookup

Current point lookup already descends, scans a leaf, and follows right links when duplicates may continue. ([GitHub][5]) The upgraded version should add short read latches around page decoding.

Proposed algorithm:

```rust
fn point_lookup_visible(key, snapshot) -> Result<Vec<IndexRowRef>> {
    let mut page_id = optimistic_find_leaf(root(), key)?;

    loop {
        let guard = buffer.pin(page_id)?;
        let read = guard.read_latch();

        let header = read_page_header(&guard)?;
        let entries = read_leaf_entries(&guard)?;

        let first_key_past_target = first_logical_key(&entries)
            .is_some_and(|k| k > key);

        let right = header.right;

        let matches = entries
            .iter()
            .filter(|e| e.logical_key == key)
            .filter(|e| entry_visible(e, snapshot))
            .map(|e| e.row)
            .collect_into(out);

        drop(read);

        if first_key_past_target {
            break;
        }

        match right {
            Some(next) => page_id = next,
            None => break,
        }
    }

    Ok(out)
}
```

Reader behavior:

1. Pin page.
2. Acquire read latch.
3. Copy/decode the page contents.
4. Release read latch before heap fetches or expression evaluation.
5. Follow right links as needed.

This bounds latch hold time and avoids blocking writers during row materialization.

---

## 6.2 Range scan

Range scans should use the same short-latch pattern:

```rust
fn range_scan(start, end, snapshot) -> IndexCursor {
    let mut page_id = optimistic_find_leaf(root(), start)?;

    while let Some(id) = page_id {
        let guard = buffer.pin(id)?;
        let read = guard.read_latch();

        let header = read_page_header(&guard)?;
        let entries = read_leaf_entries(&guard)?;
        let right = header.right;
        let high_key = header.high_key.clone();

        let page_batch = entries
            .into_iter()
            .filter(|e| e.logical_key >= start)
            .take_while(|e| e.logical_key < end)
            .filter(|e| entry_visible(e, snapshot))
            .collect::<Vec<_>>();

        drop(read);

        yield_batch(page_batch);

        if !high_key.is_empty() && high_key.as_slice() >= end {
            break;
        }

        page_id = right;
    }
}
```

Important invariant: **a cursor never holds a page latch while yielding to the SQL executor.**

That prevents slow consumers from blocking writers.

## 6.3 Insert into non-full leaf

This is the fast path that should deliver the immediate benchmark gain.

Current behavior:

1. Take global `structure_lock`.
2. Descend.
3. Modify leaf.
4. Maybe split.
5. Append index delta.
6. Mark page dirty.

New behavior:

1. Build physical key.
2. Optimistically descend with read latches or unlocked page snapshots.
3. Acquire write latch only on target leaf.
4. Validate `key < high_key` or move right.
5. If leaf has capacity, rewrite leaf in place.
6. Append `IndexInsert` WAL delta.
7. Mark dirty with returned LSN.
8. Release latch.

Pseudo-code:

```rust
fn insert_tx_inner(tx_id, logical_key, row, emit_wal, recovery_lsn) -> Result<()> {
    let physical = encode_physical_key(logical_key, row);

    loop {
        let leaf_id = optimistic_find_leaf(root(), physical.as_slice())?;
        let guard = buffer.pin(leaf_id)?;
        let write = guard.write_latch();

        let header = read_page_header(&guard)?;

        if key_belongs_to_right_sibling(&header, physical.as_slice()) {
            let next = header.right.ok_or(Error::CorruptPage("missing right link"))?;
            drop(write);
            continue_from_page(next);
        }

        let mut entries = read_entries(&guard)?;
        let candidate = Entry::Leaf {
            logical_key: logical_key.to_vec(),
            row,
            physical: physical.as_slice().to_vec(),
            create_tx: tx_id,
            delete_tx: TxId::ZERO,
        };

        insert_sorted(&mut entries, candidate)?;

        if encoded_size(&entries) <= leaf_body_capacity {
            rewrite_leaf(&mut guard, entries, header.left, header.right, header.high_key)?;

            let lsn = if emit_wal {
                append_index_delta(IndexInsert { tx_id, index_id, logical_key, row })?
            } else {
                recovery_lsn
            };

            guard.mark_dirty(lsn)?;
            page_epoch.fetch_add(1, Release);
            return Ok(());
        }

        drop(write);

        split_leaf_smo(leaf_id)?;
        // Retry insert after structural split.
    }
}
```

Key design choice: **split first, then retry insert.**

Do not include the new user entry in the structural split. Splitting existing entries as a system operation makes crash recovery and rollback much cleaner.

## 6.4 Leaf split as a structural modification operation

A split is not a user transaction. It is a **system transaction** / **structural modification operation**.

### Why

If a user transaction fills a page, the tree may need to split. If the user later rolls back, the tree does **not** need to unsplit. The structural change can remain; the user’s inserted entry is what must disappear or remain invisible.

This mirrors common database index behavior: structural changes are physical maintenance, not logical user changes.

### Split-before-insert sequence

When a leaf is full:

1. Acquire write latch on leaf.
2. Re-read entries.
3. If no longer full, release and retry insert fast path.
4. Allocate right sibling.
5. Split existing entries only.
6. Compute separator = first physical key in right page.
7. Set right page:

   * `left = old_leaf`
   * `right = old_header.right`
   * `high_key = old_header.high_key`
8. Set left page:

   * `right = new_right`
   * `high_key = separator`
9. Append one atomic WAL structural page-image-set record.
10. Mark both pages dirty with the structural LSN.
11. Release latches.
12. Insert separator into parent asynchronously/optimistically.
13. Retry original user insert.

### New WAL payload

Add one WAL record kind/payload for atomic structural page image sets:

```rust
enum WalPayload {
    // existing:
    IndexInsert { tx_id, index_id, logical_key, row },
    IndexDelete { tx_id, index_id, logical_key, row },
    PageImage { page_id, page_lsn, page_bytes },

    // new:
    IndexPageImageSet {
        index_id: u64,
        reason: IndexImageSetReason,
        pages: Vec<IndexPageImage>,
    },
}

enum IndexImageSetReason {
    LeafSplit,
    InternalSplit,
    RootInstall,
    LeafCompact,
}

struct IndexPageImage {
    page_id: PageId,
    page_lsn: Lsn,
    page_bytes: Vec<u8>, // exactly PAGE_SIZE
}
```

Why one record?

A split modifies at least two pages. Recording the images in one CRC-covered WAL record prevents partial redo of “right page exists but left page does not link to it” cases. RedlineDB already uses page-image WAL records as redo safety nets; this extends that idea to multi-page structural operations. 

### Parent-lag invariant

After the leaf split, the parent may not yet point to the new right page. That is okay.

Searches that land on the old left page use:

```text
if key >= page.high_key:
    move right
```

This is the B-link core invariant. RedlineDB already has right-link/high-key metadata, and the B-link algorithm’s correctness relies on exactly that “link pointer + high key” pattern.  ([Flux][6])

Parent insertion can therefore lag without making the tree unsearchable.

## 6.5 Parent insertion

Parent insertion should be optimistic and retry-based.

Algorithm:

```rust
fn insert_parent_separator(path_hint, left_id, separator, right_id) -> Result<()> {
    loop {
        let parent_id = find_parent_or_use_path_hint(path_hint, left_id, separator)?;

        let guard = buffer.pin(parent_id)?;
        let write = guard.write_latch();

        let header = read_page_header(&guard)?;

        if separator_belongs_to_right_sibling(&header, &separator) {
            let next = header.right.ok_or(Error::CorruptPage("missing parent right link"))?;
            drop(write);
            continue_from_page(next);
        }

        let mut entries = read_internal_entries(&guard)?;

        if separator_already_present(&entries, right_id) {
            return Ok(()); // idempotent parent propagation
        }

        insert_internal_cell(&mut entries, separator.clone(), right_id)?;

        if encoded_size(&entries) <= internal_body_capacity {
            rewrite_internal(&mut guard, entries, header.left, header.right, header.high_key)?;
            log_index_page_image_set(InternalInsert, &[parent])?;
            guard.mark_dirty(lsn)?;
            return Ok(());
        }

        drop(write);
        split_internal_smo(parent_id)?;
        // Retry parent separator insertion.
    }
}
```

Important properties:

1. Parent insert is idempotent.
2. Parent insert may lag.
3. If parent is full, split parent as a system operation.
4. If root changes, take `root_update_lock`.

## 6.6 Root split / root install

A root split should also be structural and redo-safe.

Two safe options exist:

### Option A — old-root remains navigable, new root is an optimization

Because every internal page has a `right` pointer and `high_key`, the meta page can continue pointing at the old root temporarily. Searches can move right at the top level. A new root is installed later to shorten paths.

This is more B-link-pure but requires careful validation that `find_leaf_path()` handles right moves at every level. The current source already contains move-right logic during descent, but this should be explicitly tested. ([GitHub][3])

### Option B — install new root immediately under `root_update_lock`

This is simpler:

1. Split old root into left/right.
2. Allocate new root.
3. New root points to left and right.
4. Append `IndexPageImageSet { pages: [left, right, new_root, meta] }`.
5. Mark all dirty with same structural LSN.
6. Release `root_update_lock`.

This is safer for Phase 1. It costs more WAL on rare root splits, but root splits are rare.

**Recommendation:** implement Option B first.

---

## 6.7 Delete mark

Keep delete as a tombstone update. Do not merge pages.

Current design uses `delete_tx` and visibility filtering; that is compatible with MVCC and concurrent readers. 

New delete flow:

1. Build physical probe key.
2. Optimistically find leaf.
3. Acquire leaf write latch.
4. Validate key belongs; if not, move right.
5. Scan duplicate run if necessary.
6. Set `delete_tx = tx_id`.
7. Append `IndexDelete` WAL delta.
8. Mark dirty.
9. Release.

No page underflow handling. Vacuum/maintenance can compact leaves later under a write latch.

---

## 6.8 Unique keys

Do **not** replace `UniqueKeyLockTable`.

The uploaded spec correctly identifies the race:

> writer A sees no duplicate, writer B sees no duplicate, both insert same unique key.

The current `UniqueKeyLockTable` blocks by normalized key and rechecks after wake.  That remains the right mechanism.

With the new B-tree design:

```text
unique key conflict: serialized by UniqueKeyLockTable
different unique keys: parallel leaf-level insert
nonunique keys: parallel except same leaf/page contention
```

This preserves correctness while increasing concurrency.

## 7. WAL and recovery requirements

The most important rule:

> **No page modified by a structural operation may become flushable until the corresponding structural WAL record is appended and its LSN is assigned to every modified page.**

RedlineDB already has a durable-commit protocol and a failpoint/recovery matrix proving zero lost acked commits.  The live README also reports 36/36 recovery cases and 24/24 failpoint cases with zero lost acknowledged commits. ([GitHub][1]) This proposal must not weaken that.

### 7.1 User index records remain transactional

Ordinary insert/delete still append:

```rust
WalPayload::IndexInsert { tx_id, index_id, logical_key, row }
WalPayload::IndexDelete { tx_id, index_id, logical_key, row }
```

These remain tied to user `tx_id`.

### 7.2 Structural records are system records

Splits and root installs use:

```rust
tx_id = TxId::ZERO
```

or a new explicit system transaction ID.

They are redo-only and never rolled back.

### 7.3 Split-before-insert avoids rollback complexity

Because the split does **not** include the new user entry, rollback only has to undo the user entry. The split can remain forever.

This is the most important implementation simplification in the whole design.

### 7.4 Recovery idempotency

`IndexPageImageSet` redo is idempotent:

```rust
for page in pages {
    let current = read_page(page.page_id)?;
    if current.page_lsn < record.lsn {
        write_page(page.page_bytes);
    }
}
```

If the record CRC is invalid or torn, ignore it. If the record is valid, apply every page image in the set.

### 7.5 Crash windows to certify

Add failpoints:

| Failpoint                                          | Expected recovery result                              |
| -------------------------------------------------- | ----------------------------------------------------- |
| `index::smo::before_alloc_right`                   | no split, no lost committed rows                      |
| `index::smo::after_alloc_right_before_wal`         | orphan allocation harmless or reusable                |
| `index::smo::after_wal_before_dirty`               | redo applies split if WAL durable                     |
| `index::smo::after_left_right_dirty_before_parent` | search still works via right-link                     |
| `index::smo::after_parent_insert_before_root`      | parent lag or partial propagation is still searchable |
| `index::smo::after_root_install_before_meta_dirty` | old root still navigable, or image set restores all   |
| `index::insert::after_leaf_rewrite_before_wal`     | page not flushable; insertion not durable             |
| `index::delete::after_tombstone_before_wal`        | tombstone not durable unless WAL is durable           |

The existing certification harness already has queue, chaos, failpoint, recovery, and checksum concepts that fit this extension.

## 8. Invariants

Add these invariants to `BtreeIndex::validate()` and integrity tests.

### 8.1 Page-local invariants

For every leaf:

1. Entries sorted by full physical key.
2. `logical_key` prefix agrees with `physical`.
3. No duplicate physical keys.
4. If `right != None`, then `high_key` is non-empty.
5. If `high_key` is non-empty, every entry on the page is `< high_key`.
6. If `right != None`, the first key on `right` is `>= high_key`.
7. Every entry has valid `create_tx`.
8. `delete_tx == ZERO` or valid transaction marker.

### 8.2 Leaf-chain invariants

1. Starting from the leftmost leaf, following `right` visits all leaves exactly once.
2. Leaf-chain physical keys are globally nondecreasing.
3. Every visible index entry resolves to a heap tuple visible under the same snapshot.
4. Every visible heap tuple with indexed columns has exactly one visible index entry per relevant index.

### 8.3 Parent invariants

Parent pointers may lag, but:

1. Every parent separator points to a valid child.
2. A search from meta-root using move-right always reaches the correct leaf.
3. If a leaf is not reachable by parent descent, it must be reachable by right-link movement from a reachable page at the same level.
4. Parent separator duplication is allowed only if idempotent parent propagation can identify and ignore it.

### 8.4 Structural WAL invariants

1. A page image set is applied all-or-nothing at record granularity.
2. Every page in an image set has the same structural LSN.
3. Dirty pages cannot flush before their structural LSN is assigned.
4. Parent-lag states are valid states, not corruption.
5. Root install is either fully applied or old-root search remains valid.

## 9. Implementation plan

### Phase 0 — prove the bottleneck with telemetry

Add counters before changing semantics:

```rust
struct IndexStats {
    range_scan_leaves_visited: u64,

    // New:
    structure_lock_wait_ns: u64,
    structure_lock_hold_ns: u64,
    leaf_write_latch_wait_ns: u64,
    leaf_write_latch_hold_ns: u64,
    split_count: u64,
    root_split_count: u64,
    right_move_count: u64,
    optimistic_retry_count: u64,
}
```

Acceptance:

1. Expose in `rldb_stats_json`.
2. Bench `writers-disjoint`, `ChaosIndexHammer`, `secondary-index-read`, `secondary-index-range`.
3. Confirm `structure_lock` wait/hold is material under high thread counts.

### Phase 1 — leaf-local fast path, global split fallback

This is the safe first code change.

1. Add frame read/write latches.
2. For non-full leaf insert/delete, avoid global `structure_lock`.
3. If page is full, fall back to current `structure_lock` split path.
4. Keep old split algorithm unchanged.

Expected benefit: high, because many indexed writes do not split. Risk: low, because structural modification is still globally serialized.

Acceptance gate:

```text
All existing tests pass.
All recovery/failpoint cases pass.
writers-disjoint 64T improves or stays within ±3%.
single-thread insert does not regress by more than 3%.
point-read-pk does not regress by more than 3%.
```

### Phase 2 — split-before-insert structural operations

1. Add `IndexPageImageSet`.
2. Implement leaf split as system operation.
3. Retry original insert after split.
4. Add split failpoints.
5. Add validation for parent-lag searchability.

Acceptance gate:

```text
No lost acked commits.
No visible heap/index divergence.
ChaosIndexHammer passes at 1, 2, 4, 8, 16, 32, 64 threads.
Duplicate-key split tests pass.
Unique-key race tests pass.
```

### Phase 3 — parent propagation without global lock

1. Add optimistic parent insertion.
2. Implement internal page split as system operation.
3. Root install under `root_update_lock`.
4. Parent insert idempotency.

Acceptance gate:

```text
All generated random insert/delete workloads validate.
All range scans equal table-scan ground truth.
Parent-lag injected states validate and recover.
```

### Phase 4 — maintenance and vacuum compatibility

1. Leaf compaction uses leaf write latch.
2. Index vacuum never merges pages online.
3. Offline rebuild may reclaim sparse pages later.
4. Add a “sparse leaf ratio” metric.

Acceptance gate:

```text
Vacuum under concurrent reads does not corrupt cursors.
Vacuum under concurrent writes either waits or skips busy leaves.
Index checksum stable across crash/recovery.
```

### Phase 5 — remove `structure_lock`

After Phase 1–4 certification, delete or quarantine the old global lock behind a debug-only mode:

```rust
enum IndexConcurrencyMode {
    GlobalStructureLock, // debug/backcompat fallback
    PageLatchedBlink,    // default
}
```

Keep the fallback for one release cycle, then remove it once certification is stable.

## 10. Benchmark plan

The existing bench suite already includes the right starting points: `WritersDisjoint`, `MixedOLTP`, `SecondaryIndexRead`, `SecondaryIndexRange`, `HotRowUpdate`, and `ChaosIndexHammer`.  Add these targeted benches.

### 10.1 `IndexInsertDisjointLeaves`

Setup:

```sql
CREATE TABLE t(id INTEGER PRIMARY KEY, shard INTEGER, payload BLOB);
CREATE INDEX t_shard_id ON t(shard, id);
```

Preload enough rows to create at least 4× more leaves than worker threads.

Workload:

```text
thread i inserts only shard i
```

Measures:

1. qps
2. p50/p95/p99 insert latency
3. leaf latch wait
4. split count
5. WAL bytes per transaction
6. right-move count

Expected result:

Global lock version plateaus early. Page-latched version scales until WAL, allocator, or buffer-pool contention dominates.

### 10.2 `QueueClaimReady`

Setup:

```sql
CREATE TABLE jobs(
    id INTEGER PRIMARY KEY,
    status TEXT,
    priority INTEGER,
    created_at INTEGER,
    worker_id INTEGER,
    payload BLOB
);

CREATE INDEX jobs_ready_idx ON jobs(status, priority, created_at, id);
```

Workload mix:

1. 30% insert ready jobs
2. 50% claim jobs
3. 20% complete/delete jobs

This is the workload RedlineDB needs to win if the goal is “SQLite replacement that can be used as a queue service.”

### 10.3 `DuplicateKeyFanout`

Setup:

```sql
CREATE TABLE t(id INTEGER PRIMARY KEY, tenant INTEGER, payload BLOB);
CREATE INDEX t_tenant ON t(tenant);
```

All workers insert the same `tenant` value.

Purpose:

1. Stress duplicate logical keys.
2. Validate physical suffix ordering.
3. Force duplicate-key leaf splits.
4. Ensure right-link scans collect all matches.

### 10.4 `RightEdgeAppend`

Setup:

```sql
CREATE TABLE t(id INTEGER PRIMARY KEY AUTOINCREMENT, payload BLOB);
CREATE INDEX t_id_idx ON t(id);
```

Purpose:

This tests the hardest B-tree insert case: everyone targets the rightmost leaf. B-link latching will not make one hot leaf parallel, but it should reduce global side effects. Later, this can motivate right-edge append lanes or buffered leaf inserts.

## 11. Expected outcomes

These are engineering expectations, not measured results from this session.

### 11.1 Throughput

| Workload                | Expected impact                                                                                                              |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `writers-disjoint`      | Meaningful improvement at 32–64 threads because index writes on different leaves no longer serialize globally                |
| `mixed-95/5`            | Modest improvement; read-heavy workload already strong                                                                       |
| `mixed-80/20`           | Stronger improvement; more indexed writes                                                                                    |
| `mixed-50/50`           | Strong improvement until WAL or heap contention dominates                                                                    |
| `secondary-index-read`  | Some improvement under concurrent writes; pure read speed still needs separate cursor/layout work                            |
| `secondary-index-range` | Some improvement from read-copy/latch discipline, but SQLite gap likely also involves scan implementation and cache locality |
| `hot-row-update`        | Little to no improvement; row lock remains the correct bottleneck                                                            |
| `ChaosIndexHammer`      | Better p99 behavior, but same-leaf contention remains real                                                                   |
| queue claim workload    | Strong improvement for multi-shard queues; hot single-status queues still need queue-specific optimizations                  |

### 11.2 Memory

Expected memory cost:

```text
O(buffer_frames)
```

No per-page permanent heap map. No unbounded lock table. Per-frame latch overhead should be acceptable.

### 11.3 Latency

Low-concurrency inserts may pick up a small overhead from latch acquisition and validation. Target:

```text
single-thread insert regression <= 3%
point-read-pk regression <= 3%
```

High-concurrency p99 should improve because threads wait on leaf-local latches rather than a global structure mutex.

### 11.4 WAL size

Splits become more expensive because `IndexPageImageSet` logs full page images. But splits are rare relative to ordinary inserts, and RedlineDB already uses page images as a redo safety net. 

This is the correct trade for Phase 1:

```text
Rare split WAL amplification
in exchange for
safe, simple, idempotent structural recovery
```

Later, `IndexPageImageSet` can be replaced with smaller structural deltas once certification is stable.

## 12. Why this should not regress existing tests

### 12.1 SQLite ABI tests

No FFI symbols change. `sqlite3_open`, `sqlite3_prepare_v2`, `sqlite3_step`, binding, column access, and error mapping are untouched. The uploaded spec describes the FFI crate as a C ABI shim around the Rust facade, separate from kernel internals. 

### 12.2 SQL compatibility tests

No parser, planner, expression evaluator, statement cache, or result-shape behavior changes.

### 12.3 MVCC tests

Tuple visibility remains unchanged. Index entries still carry `create_tx` and `delete_tx`, and visibility is still evaluated against snapshot/owner transaction state. 

### 12.4 Unique constraint tests

Unique-key locking remains unchanged. The B-tree no longer serializes all unique inserts globally, but inserts of the same normalized unique key still serialize through `UniqueKeyLockTable`. 

### 12.5 Rollback tests

Rollback does not need to undo page splits. It only needs to remove or tombstone user-visible index entries. Structural splits are physical maintenance.

This is safer than trying to roll back splits.

### 12.6 Savepoint tests

Savepoint replay remains SQL-layer replay. This proposal does not change session journal behavior. Existing caveats around nondeterministic functions remain unchanged. 

### 12.7 Crash recovery tests

The proposal adds structural WAL records but keeps the existing durable-commit principle: committed transactions are acknowledged only after WAL durability. The uploaded spec’s fsynced-ack protocol already has the right oracle: recovered rows must be at least acknowledged rows, with zero tolerance for lost acknowledged commits. 

### 12.8 Range scan tests

Range scans should be tested more aggressively, but the design preserves the same logical traversal: descend to the first relevant leaf, scan entries, follow `right_sibling`, and stop based on `high_key`/upper bound. The uploaded spec already describes this exact range-scan shape.

## 14. Final design decision

**Upgrade target:** `crates/kernel/src/index/*`

**Primary change:** remove global B-tree write serialization from ordinary index DML.

**Design:** B-link-tree-style page-latched index.

**Core rule:** ordinary inserts/deletes lock only the target leaf; splits are redo-safe system operations; parent propagation may lag because right-link/high-key movement preserves search correctness.

**Why this is the right move:** RedlineDB’s biggest strategic advantage over SQLite is multi-writer concurrency. The current global B-tree `structure_lock` is the clearest remaining contradiction in that story: it serializes indexed writes even when MVCC and row locks would otherwise allow them to proceed in parallel. Removing it turns the existing architecture into the system it is trying to be: not just “SQLite-compatible with better writes,” but a genuinely concurrent embedded SQL engine.
