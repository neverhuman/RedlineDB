Not an LSM. Not a pure copy-on-write tree. Not SQLite WAL with nicer Rust wrappers.

The kernel should be designed around this invariant:

```text
Readers do not wait for writers.
```

# 1. The hard architectural decision

## Use clustered B+trees with undo MVCC

Each table is stored as a clustered B+tree:

```text
primary_key_or_hidden_rowid -> current row image
```

The current row image lives in the table leaf page. Older row versions live in undo segments.

```text
Current row:
    table B+tree leaf

Old versions:
    undo segment chain
```

This is the best middle ground between SQLite and PostgreSQL.

SQLite has a clean small-file architecture, but WAL mode has one writer. PostgreSQL has world-class MVCC, but its heap tuple model creates table/index bloat that is harder for an embedded replacement. So the better embedded design is closer to InnoDB’s shape:

```text
current row in clustered index
previous versions in undo
secondary indexes point back to primary key
```

That gives:

```text
Fast point reads
Fast primary-key range scans
Efficient updates
Bounded read path for recent snapshots
Good secondary-index behavior
Real multiwriter concurrency
```

# 2. Deployment model

There should be two real modes.

## Mode A: embedded single-process, multithreaded

This is the first-class mode.

```text
Application process
  ├── user threads call kernel directly
  ├── shared Rust buffer pool
  ├── shared lock manager
  ├── shared transaction table
  ├── WAL writer thread
  ├── checkpointer thread
  ├── undo purger thread
  └── deadlock detector thread
```

This is where you get maximum speed.

## Mode B: local broker mode for multiprocess

Do not try to make high-concurrency multiprocess file locking the primary architecture. It becomes a swamp.

For true PostgreSQL-level multiprocess concurrency, run a tiny local broker:

```text
Client process A ─┐
Client process B ─┼── local IPC ── oxide-broker ── database files
Client process C ─┘
```

The broker owns:

```text
buffer pool
WAL writer
lock table
transaction table
commit map
checkpointing
purge
```

This is the honest way to get PostgreSQL-like behavior across processes. PostgreSQL has a coordinating server. Your “embedded replacement” can still expose an embedded API, but broker mode should exist for serious multiprocess workloads.

# 5. Version stamp model

This is a critical correction.

Do **not** require commit to rewrite every row version from “pending” to “committed.” That is too slow for large transactions.

Instead, row headers store version stamps that can be either committed CSNs or pending TxIds.

```rust
#[repr(transparent)]
pub struct VersionStamp(u64);
```

Encoding:

```text
0                  = NONE
1..2^62-1           = committed CSN
high bit set        = TxId stamp
u64::MAX            = infinity
```

Visibility resolves as:

```rust
pub enum ResolvedStamp {
    None,
    Committed(Csn),
    Pending(TxId),
    Aborted(TxId),
    Infinity,
}
```

Commit does this:

```text
1. Assign commit CSN.
2. Append durable TX_COMMIT(txid, csn) WAL record.
3. Publish TxId -> CSN in commit map.
4. Release locks.
```

It does **not** rewrite all modified row headers.

A background freezer later rewrites old TxId stamps into CSNs when safe:

```text
TxId stamp -> committed CSN stamp
```

That allows the in-memory commit table to stay bounded.

# 6. Persistent commit map

You need this or the engine eventually forgets whether an old TxId committed.

```text
recent commit state:
    in-memory sharded commit table

older commit state:
    persistent commit-map pages

very old committed rows:
    frozen to CSN, commit-map entries removable
```

Commit state:

```rust
pub enum TxOutcome {
    InProgress,
    Committed(Csn),
    Aborted,
}
```

Visibility check:

```rust
fn resolve_stamp(stamp: VersionStamp, tx: &Transaction, commit_map: &CommitMap) -> ResolvedStamp {
    if stamp.is_infinity() {
        return ResolvedStamp::Infinity;
    }

    if stamp.is_csn() {
        return ResolvedStamp::Committed(stamp.as_csn());
    }

    let txid = stamp.as_txid();

    if txid == tx.id {
        return ResolvedStamp::Pending(txid); // own writes
    }

    match commit_map.lookup(txid) {
        TxOutcome::Committed(csn) => ResolvedStamp::Committed(csn),
        TxOutcome::Aborted => ResolvedStamp::Aborted(txid),
        TxOutcome::InProgress => ResolvedStamp::Pending(txid),
    }
}
```

Row visibility:

```rust
fn row_visible(row: &RowHeader, tx: &Transaction, commit_map: &CommitMap) -> bool {
    let begin = resolve_stamp(row.begin, tx, commit_map);
    let end = resolve_stamp(row.end, tx, commit_map);

    let begin_visible = match begin {
        ResolvedStamp::Committed(csn) => csn <= tx.read_csn,
        ResolvedStamp::Pending(txid) => txid == tx.id,
        ResolvedStamp::Aborted(_) => false,
        ResolvedStamp::None => false,
        ResolvedStamp::Infinity => false,
    };

    let end_visible = match end {
        ResolvedStamp::Committed(csn) => csn <= tx.read_csn,
        ResolvedStamp::Pending(txid) => txid == tx.id,
        ResolvedStamp::Aborted(_) => false,
        ResolvedStamp::None => false,
        ResolvedStamp::Infinity => false,
    };

    begin_visible && !end_visible
}
```

This is one of the most important pieces of the final design.

# 8. Undo storage

Undo is append-only, disk-backed, and chained both per-row and per-transaction.

```rust
#[repr(C)]

    pub prev_row_undo: UndoPtr;

    pub old_end: VersionStamp;
    pub old_schema_version: u32;

    pub payload_len: u32;
    pub checksum: u32;

    // key bytes
    // previous row payload or delta
}
```

Start with full before-images. Then optimize.

```text
v1: full previous row image
v2: column-level update deltas
v3: compressed varlen deltas
```

Read path:

```text
1. Find current row in clustered B+tree.
2. If current row visible, return it.
3. Else follow undo chain.
4. Reconstruct older versions until visible.
5. Return visible version or none.
```

Abort path:

```text
1. Walk transaction undo chain backward.
2. Restore old row/index state.
3. Emit compensation log records.
4. Mark transaction aborted.
5. Release locks.
```

Purge path:

```text
oldest_needed_csn = min(
    active transaction snapshots,
    replica replay horizon,
    backup horizon,
    open cursor horizon
)
```

Undo older than that horizon can be pruned.

# 10. Commit protocol

The final commit sequence must be brutally precise.

```rust
pub fn commit(tx: Transaction) -> Result<Csn> {
    // 1. Validate isolation-level constraints.
    validate_snapshot_conflicts(&tx)?;
    validate_ssi(&tx)?;

    // 2. Assign global commit sequence number.
    let csn = next_csn.fetch_add(1, Ordering::AcqRel) + 1;

    // 3. Append durable commit record.
    let commit_lsn = wal.append_tx_commit(tx.id, csn, tx.undo_head)?;

    // 4. Full durability requires WAL flush before visibility.
    wal.flush_to(commit_lsn, tx.commit_policy)?;

    // 5. Publish TxId -> CSN.
    commit_map.publish_commit(tx.id, csn, commit_lsn)?;

    // 6. Advance visible CSN in order.
    publish_csn_in_order(csn);

    // 7. Release locks after commit is visible.
    locks.release_all(tx.id);

    // 8. Queue background freeze/purge work.
    freezer.enqueue(tx.id, csn);
    purger.wake();

    Ok(csn)
}
```

The ordering is non-negotiable:

```text
WAL commit durable
    before
commit map says committed
    before
published_csn advances
    before
locks release
```

This prevents readers from seeing a commit that recovery cannot reproduce.

# 11. WAL architecture

## WAL insertion should not be a giant mutex

Use WAL space reservation:

```text
worker thread:
    reserve LSN range with atomic fetch_add
    write record bytes into WAL buffer
    mark reservation complete

wal writer:
    flushes contiguous completed records
    fsyncs for group commit
    advances durable_lsn
    wakes waiters
```

This lets many writers prepare WAL records concurrently while one writer enforces disk order.

# 12. Full-page images

On first page modification after checkpoint:

```text
emit WAL PageImage(page_id, full_page_bytes)
then emit logical/physical update record
```

This protects against torn pages and makes redo idempotent.

Rule:

```rust
if !page.dirtied_after_checkpoint {
    wal.append_full_page_image(page_id, page.bytes())?;
    page.dirtied_after_checkpoint = true;
}
```

Later optimization:

```text
doublewrite buffer
or partial-page checksummed sectors
```

But for v1, full-page images are the right safety choice.

# 13. Recovery

Startup recovery:

```text
1. Read both superblocks.
2. Choose newest valid checkpoint.
3. Scan WAL from checkpoint_lsn.
4. Rebuild:
   - transaction table
   - dirty page table
   - commit map updates
   - page allocation map
5. Redo all redoable records.
6. Identify loser transactions.
7. Undo losers using undo chains and compensation records.
8. Write recovery checkpoint.
9. Open database.
```

Redo test:

```rust
if page.header.page_lsn < record.lsn {
    apply_redo(page, record)?;
    page.header.page_lsn = record.lsn;
}
```

Undo loser transaction:

```rust
for undo in tx.undo_chain_rev() {
    apply_undo(undo)?;
    wal.append_compensation(tx.id, undo)?;
}
```

Crash-safe result:

```text
Committed transactions are present.
Aborted transactions are absent.
In-flight transactions are absent.
Indexes match clustered tables.
Commit map matches durable commits.
```

# 14. B+tree design

Use **B-link trees**, not naive B+trees.

Each page stores:

```rust
#[repr(C)]
pub struct BtreeSpecial {
    pub level: u16,          // 0 = leaf
    pub flags: u16,

    pub right_sibling: PageId,
    pub high_key_len: u16,

    pub prefix_base_len: u16,
}
```

Why B-link trees:

```text
Concurrent splits are survivable.
Readers can follow right siblings if they land on an old page.
Writers do not need to hold huge latch chains.
```

Search:

```text
1. Start from cached root.
2. Read page with optimistic latch.
3. Binary search separator keys.
4. If key > high_key, follow right_sibling.
5. Descend.
6. At leaf, verify page generation.
7. If generation changed badly, restart.
```

Insert:

```text
1. Lock logical key/range if needed.
2. Descend optimistically.
3. X-latch leaf.
4. If enough room, insert.
5. If full:
   - allocate right page
   - split records
   - set high keys
   - link siblings
   - WAL-log split
   - insert separator into parent
6. Release latches quickly.
```

Critical rule:

```text
Never wait on transaction locks while holding page latches.
```

# 18. Unique constraints

Unique insert must check committed, pending, and invisible-newer entries.

Algorithm:

```text
1. Acquire LockKey::IndexKey(unique_index, unique_key) in X/InsertIntent mode.
2. Search unique index.
3. If visible duplicate exists: constraint violation.
4. If pending duplicate by another tx: wait.
5. If pending tx commits: violation.
6. If pending tx aborts: continue.
7. Insert pending unique entry.
```

This prevents duplicate inserts racing through snapshots.

# 21. Checkpointing

Fuzzy checkpoint:

```text
1. Emit CHECKPOINT_BEGIN.
2. Snapshot dirty page table.
3. Snapshot active transaction table.
4. Snapshot commit-map horizon.
5. Flush dirty pages in background.
6. Flush commit-map pages.
7. Emit CHECKPOINT_END.
8. Update alternating superblock.
9. Recycle WAL segments older than checkpoint horizon.
```

Checkpoint must respect:

```text
WAL before data
commit map before forgetting TxIds
undo before row versions that reference undo
```

Dirty pressure:

```text
dirty pages > 70%: wake cleaner
dirty pages > 85%: throttle writers
dirty pages > 95%: force checkpoint assist
```

# 22. Purge and freeze

There are two background cleanup jobs.

## Purger

Deletes obsolete undo and old index entries.

```text
safe if version end_csn < oldest_active_read_csn
```

## Freezer

Converts old TxId stamps to CSN stamps.

```text
begin = TxId(100) where commit_map[100] = CSN(500)
becomes:
begin = CSN(500)
```

Only after all row/index references to a TxId are frozen can the commit-map entry be discarded.

This prevents unbounded memory growth and avoids PostgreSQL-style wraparound headaches.

# 25. Implementation order

## Phase 1: page, file, WAL primitives

```text
page headers
checksums
superblocks
WAL record encode/decode
WAL segment rotation
full-page images
```

Exit condition:

```text
Crash at any write point.
Recover exact page state.
Detect torn/corrupt pages.
```

## Phase 2: single-thread B+tree

```text
clustered B+tree
search
insert
split
range scan
delete marker
```

Exit condition:

```text
Random operations match BTreeMap model.
```

## Phase 3: transactions + undo MVCC

```text
TxId stamps
commit map
CSN snapshots
undo append
rollback
visibility reconstruction
```

Exit condition:

```text
Random transaction histories match MVCC model.
```

## Phase 4: real concurrency

```text
page latches
row locks
lock manager
deadlock detector
group commit
WAL reservation
```

Exit condition:

```text
N threads update disjoint keys concurrently.
Readers do not block writers.
Conflicting writers wait correctly.
```

## Phase 5: secondary indexes and uniqueness

```text
secondary B+trees
MVCC index entries
unique-key conflict protocol
index validator
```

Exit condition:

```text
No duplicate unique keys under adversarial concurrency.
Indexes always match table versions.
```

## Phase 6: checkpoint, purge, freeze

```text
fuzzy checkpoint
dirty-page cleaner
undo purger
commit freezer
WAL recycling
```

Exit condition:

```text
WAL, undo, and commit map remain bounded.
```

## Phase 7: Serializable SSI

```text
SIREAD locks
rw-dependency graph
dangerous structure detection
read-only deferrable snapshots
```

Exit condition:

```text
Write-skew workloads abort correctly.
Serializable histories validate against a serial model.
```

## Phase 8: broker mode

```text
local IPC
broker-owned buffer pool
broker-owned WAL
client session protocol
shared SQL/frontend compatibility
```

Exit condition:

```text
Multiple processes get PostgreSQL-like concurrency without unsafe file-lock gymnastics.
```
