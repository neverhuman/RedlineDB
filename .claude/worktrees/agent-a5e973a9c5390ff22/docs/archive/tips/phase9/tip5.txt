## Phase 9 only: build `redlinedb_bench` as a certification system, not a toy benchmark

For Phase 9, I would build a Rust crate whose job is to answer four questions with hard evidence:

1. **Correctness:** does RedlineDB return the same supported-SQL results as SQLite?
2. **Durability:** do acknowledged commits survive under the configured durability mode?
3. **Performance:** where does RedlineDB beat SQLite, tie SQLite, or lose to SQLite?
4. **Explainability:** when it wins or loses, can we attribute it to WAL fsync, checkpointing, page-cache behavior, planner choices, lock waits, memory pressure, or API overhead?

The important competitive reality is this: SQLite WAL allows readers and a writer to coexist, but SQLite still has only one writer at a time in WAL mode. SQLite’s own docs say that writers append to the WAL and readers can continue, but “there can only be one writer at a time.” ([SQLite][1]) SQLite’s isolation documentation says the same thing more directly: multiple connections may write, but they “have to take turns.” ([SQLite][2]) That is the exact axis where RedlineDB must demonstrate a real advantage: many sessions, disjoint writes, shared engine, shared buffer pool, group commit, and no SQLite-style global writer ceiling.

# 2. Benchmark philosophy

The benchmark must be hostile to flattering RedlineDB. It should give SQLite a fair, optimized configuration.

SQLite should not be punished by:

```text
using one shared connection across all threads
forgetting busy_timeout
using rollback journal when the comparison target is WAL
building SQL strings in the hot loop
creating statements repeatedly
letting SQLite use tiny cache defaults while RedlineDB gets a large buffer pool
measuring RedlineDB through Rust API but SQLite through a slow wrapper
comparing strict RedlineDB against unsafe SQLite, or vice versa
```

SQLite supports several threading modes. The fair concurrent test uses **one SQLite connection per worker thread**, not one shared connection, because SQLite’s multi-thread mode permits multiple threads as long as no single connection or derived object is used simultaneously by multiple threads. SQLite’s default is serialized mode, which is safe but can add mutex serialization around a connection. ([SQLite][3])

For SQLite WAL, explicitly set and verify:

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL | NORMAL | OFF;
PRAGMA busy_timeout = 30000;
PRAGMA wal_autocheckpoint = 0; -- for controlled checkpoint tests
PRAGMA cache_size = -N;        -- N KiB per connection
```

Verification matters because SQLite’s PRAGMA mechanism has sharp edges: the docs say unknown pragmas are ignored without error, so the adapter should read the setting back and fail if it did not stick. ([SQLite][4])

# 3. Durability matrix

Phase 9 must never mix durability modes.

| Class    | SQLite WAL config                                                       | RedlineDB config                                           | Claim allowed                                                                                                        |
| -------- | ----------------------------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `strict` | `journal_mode=WAL`, `synchronous=FULL`                                  | WAL durable before commit ack, checkpoint barriers enabled | No acknowledged commit disappears after process crash; power-loss semantics should be strict if storage honors fsync |
| `normal` | `journal_mode=WAL`, `synchronous=NORMAL`                                | group commit / relaxed per-commit fsync policy             | Database remains structurally safe; recent commits may be lost after power loss depending on policy                  |
| `unsafe` | `journal_mode=WAL`, `synchronous=OFF` or explicitly documented dev mode | no-fsync dev mode                                          | Speed-only, no durability claims                                                                                     |

SQLite’s WAL docs say writers sync the WAL on every transaction commit when `synchronous=FULL`, but omit that sync when `synchronous=NORMAL`. ([SQLite][1]) SQLite’s compile-option docs also note that in WAL mode `synchronous=NORMAL` preserves integrity but recent changes might roll back after power loss, while `FULL` is recommended for maximum safety. ([SQLite][5])

RedlineDB should mirror those semantics as closely as possible:

```rust
#[derive(Debug, Clone, Copy, serde::Serialize, serde::Deserialize)]
pub enum Durability {
    /// Commit acknowledged only after WAL records required for that commit
    /// are durable according to the configured sync method.
    Strict,

    /// Commit may rely on background or grouped sync. No torn/corrupt DB
    /// allowed, but recent acknowledged commits may be lost after power loss
    /// if this mode documents that behavior.
    Normal,

    /// Development mode. No durability guarantee.
    Unsafe,
}
```

# 5. Checkpoint fairness

Checkpointing is a huge source of misleading results.

SQLite WAL has automatic checkpoints. The docs say SQLite defaults to checkpointing when the WAL reaches about 1000 pages, and the committing thread may run the checkpoint, causing occasional slower commits. ([SQLite][1]) For fair measurements, run both engines in one of two explicit modes:

## Mode A: default checkpoint behavior

Use each engine’s default. This measures “what a normal user gets.”

```text
sqlite: wal_autocheckpoint default
redline: default checkpoint policy
```

## Mode B: controlled checkpoint behavior

Disable SQLite auto-checkpointing and run a benchmark-controlled checkpoint worker. SQLite documents `wal_autocheckpoint` and `sqlite3_wal_checkpoint_v2` for explicit control. ([SQLite][1])

```text
sqlite: PRAGMA wal_autocheckpoint=0
redline: disable auto checkpoint or set manual policy
bench: checkpoint every N WAL bytes or every T seconds
```

Then measure:

```text
checkpoint_count
checkpoint_ns_total
checkpoint_ns_p50/p95/p99
checkpoint_frames
checkpoint_bytes
wal_bytes_before
wal_bytes_after
stalls_observed_by_workers
```

SQLite’s checkpoint behavior is especially important under long readers: its docs explain that a checkpoint can run concurrently with readers but must stop when it reaches WAL content past the end mark of an active reader. ([SQLite][1]) RedlineDB’s checkpoint-pressure workload should reproduce this same scenario and show whether Redline’s horizon tracking, long snapshots, and WAL retention stay bounded.

# 7. Workloads

The workload suite should be deterministic, seeded, and explainable. Each workload has:

```rust
pub trait Workload {
    fn name(&self) -> &'static str;
    fn schema(&self) -> &'static str;
    fn setup(&self, engine: &mut dyn SetupConn, rows: u64, seed: u64) -> anyhow::Result<()>;
    fn make_worker_plan(&self, worker_id: usize, workers: usize, spec: &RunSpec) -> WorkerPlan;
    fn invariants(&self) -> Vec<Invariant>;
}
```

But in the hot loop, do **not** use `dyn Workload`. Monomorphize or dispatch once at the outer level.

## 7.1 Single-row insert, autocommit

Purpose:

```text
Measures commit path, WAL append, fsync/group-commit behavior, allocator overhead.
```

Schema:

```sql
CREATE TABLE kv (
    k INTEGER PRIMARY KEY,
    v INTEGER NOT NULL,
    pad BLOB
);
```

Key assignment:

```text
k = worker_id << 48 | local_sequence
```

That avoids accidental key conflicts. This test should be run under:

```text
threads = 1, 2, 4, 8, 16, 32
durability = strict, normal, unsafe
payload_bytes = 0, 32, 256, 1024
```

Expected diagnostic value:

```text
If Redline loses at 1 thread strict:
  likely WAL record overhead, fsync path, syscall count, SQL executor overhead.

If Redline loses at 16 threads normal:
  likely commit queue, WAL writer, transaction allocator, global latch, or planner/session lock.

If SQLite flatlines after a few writer threads:
  expected single-writer serialization axis.
```

## 7.2 Batched insert

Purpose:

```text
Separates per-row executor cost from per-transaction commit cost.
```

Batch sizes:



## 7.10 Concurrent readers

Shape:

```text
1 writer, N readers
N writers, N readers
long snapshot reader + writer storm
```

Measure:

```text
reader p99 latency during writer commits
writer commit p99 during active readers
checkpoint backlog
WAL growth
```

SQLite WAL provides snapshot isolation for readers: a read transaction sees an unchanging snapshot from when it began. ([SQLite][2]) RedlineDB should demonstrate the same semantic behavior while reducing writer contention.

## 7.11 Concurrent writers

This is the killer benchmark.

Shape:

```text
threads = 1,2,4,8,16,32,64
all workers write disjoint key ranges
transaction size = 1,10,100
durability = strict, normal
```

Report:

```text
aggregate txns/sec
per-worker txns/sec fairness
commit p99
lock wait p99
WAL writer queue depth
fsync batching efficiency
```

Expected RedlineDB advantage:

```text
SQLite serializes writers.
RedlineDB should allow disjoint writer transactions to run concurrently until the WAL writer, fsync policy, CPU, or storage device becomes the bottleneck.
```

## 7.12 Checkpoint pressure

Shape:

```text
preload 10M rows
start one long read transaction
writers update/insert continuously
checkpoint worker runs every N bytes
hold reader for 30s
release reader
continue writers
```

Measure:

```text
WAL growth while long reader is active
checkpoint attempts
checkpoint work completed
writer stalls
reader latency
post-release checkpoint catch-up time
database size
```

SQLite docs explicitly note long-running reads can prevent checkpoint progress. ([SQLite][1]) RedlineDB needs to prove it bounds WAL growth according to configured retention horizons, or at least reports why it cannot.

## 7.13 Crash recovery

Shape:

```text
parent process starts child
child runs workload
parent kills child at controlled points
parent reopens DB
parent verifies acknowledged commits
repeat for many seeds
```

Modes:

```text
process crash:
  SIGKILL child, OS remains alive

engine fault injection:
  RedlineDB failpoints simulate crashes around WAL append, commit ack, checkpoint, segment rotation

power-loss approximation:
  only valid with storage test rig or fsync fault model; do not overclaim from SIGKILL alone
```

## 7.14 Memory ceiling

Shape:

```text
dataset = 10x memory limit
memory_mib = 64, 128, 256, 512, 1024
threads = 1, 8, 32
workload = point_read, mixed_oltp, range_scan
```

Certification:

```text
RSS remains within configured bound plus documented overhead.
Throughput degrades predictably.
No unbounded statement cache, row materialization buffer, WAL cache, or checkpoint backlog.
```

# 8. Correctness and compatibility testing

Phase 9 must compare supported SQL against SQLite.

## 8.1 Result normalization

Define a canonical result type:

```rust
#[derive(Debug, Clone, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub enum SqlValue {
    Null,
    Integer(i64),
    Real(OrderedF64),
    Text(String),
    Blob(Vec<u8>),
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ResultSet {
    pub columns: Vec<String>,
    pub rows: Vec<Vec<SqlValue>>,
}
```

Rules:

```text
If SQL query has deterministic ORDER BY:
  compare rows in order.

If query has no ORDER BY:
  compare rows as a multiset.

If query uses floating point:
  avoid NaN in generator initially.
  compare exact bits for simple generated values, or epsilon only for functions documented as approximate.

If SQLite returns an error:
  RedlineDB may return the same error class for supported SQL.
  Unsupported SQL must be classified as unsupported, not silently different.
```

# 9. Crash oracle design

The oracle is the most important part of crash testing.

Inside each committed transaction, write a commit marker:

```sql
CREATE TABLE commit_log (
    txid INTEGER PRIMARY KEY,
    worker INTEGER NOT NULL,
    seq INTEGER NOT NULL,
    checksum INTEGER NOT NULL
);
```

Each transaction does:

```sql
BEGIN;
-- actual workload mutations
INSERT INTO commit_log(txid, worker, seq, checksum) VALUES (?, ?, ?, ?);
COMMIT;
```

The child sends an acknowledgment to the parent **after COMMIT returns**:

```text
child: COMMIT returned successfully
child -> parent pipe: Ack { txid, worker, seq, checksum }
parent: stores Ack in memory and in parent-side file
parent: may kill child after any ack
```

After crash:

```text
parent reopens DB
for each Ack:
  SELECT checksum FROM commit_log WHERE txid = ?
  verify row exists and checksum matches
  verify workload-specific effects exist
```

This avoids the classic bug where the benchmark cannot tell whether a transaction was actually acknowledged before the crash.

For `strict` durability:

```text
Every parent-observed ack must survive.
No corruption allowed.
Recovery must finish.
Database must accept new writes after recovery.
```

For `normal` durability:

```text
No corruption allowed.
Depending on documented RedlineDB normal semantics, acknowledged commits may or may not be required to survive simulated power loss.
For plain process kill, still record any losses as severe diagnostics.
```

For `unsafe`:

```text
No correctness certification beyond “database either recovers or reports unsupported unsafe recovery behavior.”
Do not use unsafe numbers in replacement claims.
```

# 10. Threading model for the benchmark harness

The harness itself must not become the bottleneck.

Use:

```text
one OS thread per worker
one DB connection/session per worker
one prepared-statement bundle per worker
thread-local RNG
thread-local histogram
thread-local counters
shared start barrier
shared atomic stop flag
no shared Vec push per operation
no logging per operation
no SQL string formatting in hot path
```

Use cache-padded atomics for global progress:

```rust
use crossbeam_utils::CachePadded;
use std::sync::atomic::{AtomicBool, AtomicU64, Ordering};

pub struct SharedRunState {
    pub stop: AtomicBool,
    pub started: AtomicBool,
    pub global_ops: CachePadded<AtomicU64>,
    pub global_errors: CachePadded<AtomicU64>,
}
```

Workers should merge results at the end:

```rust
pub struct WorkerResult {
    pub worker_id: usize,
    pub successful_ops: u64,
    pub failed_ops: u64,
    pub busy_errors: u64,
    pub retry_count: u64,
    pub latency: hdrhistogram::Histogram<u64>,
    pub engine_wait_ns: u64,
}
```

Do not sample RSS from every worker. Run one metrics sampler thread:

```text
sample every 100 ms or 1 second
read /proc/self/status on Linux
read DB/WAL file sizes
read engine stats
append compact MetricSample to Vec
```

# 13. Rust code: runner

```rust
use anyhow::Result;
use hdrhistogram::Histogram;
use std::sync::{
    atomic::{AtomicBool, AtomicU64, Ordering},
    Arc, Barrier,
};
use std::thread;
use std::time::{Duration, Instant};

pub trait WorkerDriver: Send + 'static {
    fn run_one(&mut self) -> Result<()>;
    fn name(&self) -> &'static str;
}

pub trait DriverFactory: Send + Sync + 'static {
    type Driver: WorkerDriver;

    fn make_driver(&self, worker_id: usize) -> Result<Self::Driver>;
}

pub struct ParallelRunResult {
    pub successful_ops: u64,
    pub failed_ops: u64,
    pub latency: Histogram<u64>,
}

pub fn run_parallel<F>(
    factory: Arc<F>,
    threads: usize,
    warmup: Duration,
    duration: Duration,
) -> Result<ParallelRunResult>
where
    F: DriverFactory,
{
    let start_barrier = Arc::new(Barrier::new(threads + 1));
    let warmup_done = Arc::new(AtomicBool::new(false));
    let stop = Arc::new(AtomicBool::new(false));
    let global_success = Arc::new(AtomicU64::new(0));
    let global_failed = Arc::new(AtomicU64::new(0));

    let mut handles = Vec::with_capacity(threads);

    for worker_id in 0..threads {
        let factory = factory.clone();
        let start_barrier = start_barrier.clone();
        let warmup_done = warmup_done.clone();
        let stop = stop.clone();
        let global_success = global_success.clone();
        let global_failed = global_failed.clone();

        handles.push(thread::spawn(move || -> Result<(u64, u64, Histogram<u64>)> {
            let mut driver = factory.make_driver(worker_id)?;
            let mut hist = Histogram::<u64>::new_with_max(3_600_000_000_000, 3)?;

            let mut local_success = 0_u64;
            let mut local_failed = 0_u64;

            start_barrier.wait();

            while !stop.load(Ordering::Relaxed) {
                let t0 = Instant::now();
                let res = driver.run_one();

                if warmup_done.load(Ordering::Relaxed) {
                    let ns = t0.elapsed().as_nanos().min(u64::MAX as u128) as u64;
                    let _ = hist.record(ns);

                    match res {
                        Ok(()) => {
                            local_success += 1;
                            if local_success % 1024 == 0 {
                                global_success.fetch_add(1024, Ordering::Relaxed);
                            }
                        }
                        Err(_) => {
                            local_failed += 1;
                            global_failed.fetch_add(1, Ordering::Relaxed);
                        }
                    }
                }
            }

            let unflushed_success = local_success % 1024;
            if unflushed_success != 0 {
                global_success.fetch_add(unflushed_success, Ordering::Relaxed);
            }

            Ok((local_success, local_failed, hist))
        }));
    }

    start_barrier.wait();

    thread::sleep(warmup);
    warmup_done.store(true, Ordering::Release);

    thread::sleep(duration);
    stop.store(true, Ordering::Release);

    let mut merged = Histogram::<u64>::new_with_max(3_600_000_000_000, 3)?;
    let mut success = 0_u64;
    let mut failed = 0_u64;

    for h in handles {
        let (s, f, hist) = h.join().expect("worker panicked")?;
        success += s;
        failed += f;
        merged.add(hist)?;
    }

    Ok(ParallelRunResult {
        successful_ops: success,
        failed_ops: failed,
        latency: merged,
    })
}
```

For very fast point-read microbenchmarks, `Instant::now()` per operation can become visible overhead. Use two modes:

```text
latency mode:
  measure every op

throughput mode:
  measure wall-clock total, sample 1/N operations for latency
```

The certification report should label which mode was used.

# 14. Rust code: SQLite raw FFI adapter

For official head-to-head numbers, I would use raw `libsqlite3-sys` for the SQLite adapter. `rusqlite` is excellent, but a raw adapter avoids wrapper overhead arguments.

```rust
use anyhow::{anyhow, bail, Result};
use libsqlite3_sys as ffi;
use std::ffi::{CStr, CString};
use std::os::raw::c_char;
use std::path::Path;
use std::ptr::{null, null_mut, NonNull};
use std::time::Duration;

pub struct SqliteDb {
    db: NonNull<ffi::sqlite3>,
}

// The handle is owned by one worker thread. It is movable before use,
// but do not share it concurrently.
unsafe impl Send for SqliteDb {}

impl Drop for SqliteDb {
    fn drop(&mut self) {
        unsafe {
            ffi::sqlite3_close_v2(self.db.as_ptr());
        }
    }
}

impl SqliteDb {
    pub fn open(path: &Path, no_mutex: bool) -> Result<Self> {
        let path = CString::new(path.to_string_lossy().as_bytes())?;
        let mut db: *mut ffi::sqlite3 = null_mut();

        let mut flags = ffi::SQLITE_OPEN_READ_WRITE | ffi::SQLITE_OPEN_CREATE;
        if no_mutex {
            flags |= ffi::SQLITE_OPEN_NOMUTEX;
        } else {
            flags |= ffi::SQLITE_OPEN_FULLMUTEX;
        }

        let rc = unsafe {
            ffi::sqlite3_open_v2(path.as_ptr(), &mut db, flags, null())
        };

        if rc != ffi::SQLITE_OK {
            let msg = if db.is_null() {
                "sqlite3_open_v2 failed".to_string()
            } else {
                unsafe { sqlite_errmsg(db) }
            };
            if !db.is_null() {
                unsafe { ffi::sqlite3_close_v2(db) };
            }
            bail!("{msg}");
        }

        Ok(Self {
            db: NonNull::new(db).expect("sqlite returned non-null db"),
        })
    }

    pub fn exec(&self, sql: &str) -> Result<()> {
        let sql = CString::new(sql)?;
        let mut err: *mut c_char = null_mut();

        let rc = unsafe {
            ffi::sqlite3_exec(
                self.db.as_ptr(),
                sql.as_ptr(),
                None,
                null_mut(),
                &mut err,
            )
        };

        if rc != ffi::SQLITE_OK {
            let msg = if err.is_null() {
                unsafe { sqlite_errmsg(self.db.as_ptr()) }
            } else {
                unsafe {
                    let s = CStr::from_ptr(err).to_string_lossy().into_owned();
                    ffi::sqlite3_free(err as *mut _);
                    s
                }
            };
            bail!("sqlite exec failed: {msg}");
        }

        Ok(())
    }

    pub fn busy_timeout(&self, d: Duration) -> Result<()> {
        let ms = d.as_millis().min(i32::MAX as u128) as i32;
        let rc = unsafe { ffi::sqlite3_busy_timeout(self.db.as_ptr(), ms) };
        self.check(rc)
    }

    pub fn prepare(&self, sql: &str) -> Result<SqliteStmt> {
        let sql = CString::new(sql)?;
        let mut stmt: *mut ffi::sqlite3_stmt = null_mut();

        let rc = unsafe {
            ffi::sqlite3_prepare_v2(
                self.db.as_ptr(),
                sql.as_ptr(),
                -1,
                &mut stmt,
                null_mut(),
            )
        };

        self.check(rc)?;

        Ok(SqliteStmt {
            db: self.db,
            stmt: NonNull::new(stmt).ok_or_else(|| anyhow!("null sqlite stmt"))?,
        })
    }

    pub fn query_one_text(&self, sql: &str) -> Result<String> {
        let mut stmt = self.prepare(sql)?;
        match stmt.step()? {
            StepResult::Row => stmt.column_text(0),
            StepResult::Done => bail!("query returned no rows: {sql}"),
        }
    }

    pub fn query_one_i64(&self, sql: &str) -> Result<i64> {
        let mut stmt = self.prepare(sql)?;
        match stmt.step()? {
            StepResult::Row => Ok(stmt.column_i64(0)),
            StepResult::Done => bail!("query returned no rows: {sql}"),
        }
    }

    fn check(&self, rc: i32) -> Result<()> {
        if rc == ffi::SQLITE_OK {
            Ok(())
        } else {
            bail!("sqlite error {rc}: {}", unsafe {
                sqlite_errmsg(self.db.as_ptr())
            })
        }
    }
}

unsafe fn sqlite_errmsg(db: *mut ffi::sqlite3) -> String {
    CStr::from_ptr(ffi::sqlite3_errmsg(db))
        .to_string_lossy()
        .into_owned()
}

pub enum StepResult {
    Row,
    Done,
}

pub struct SqliteStmt {
    db: NonNull<ffi::sqlite3>,
    stmt: NonNull<ffi::sqlite3_stmt>,
}

impl Drop for SqliteStmt {
    fn drop(&mut self) {
        unsafe {
            ffi::sqlite3_finalize(self.stmt.as_ptr());
        }
    }
}

impl SqliteStmt {
    #[inline]
    pub fn reset_clear(&mut self) -> Result<()> {
        unsafe {
            ffi::sqlite3_reset(self.stmt.as_ptr());
            ffi::sqlite3_clear_bindings(self.stmt.as_ptr());
        }
        Ok(())
    }

    #[inline]
    pub fn bind_i64(&mut self, idx: i32, value: i64) -> Result<()> {
        let rc = unsafe { ffi::sqlite3_bind_int64(self.stmt.as_ptr(), idx, value) };
        self.check(rc)
    }

    #[inline]
    pub fn bind_blob(&mut self, idx: i32, value: &[u8]) -> Result<()> {
        let rc = unsafe {
            ffi::sqlite3_bind_blob64(
                self.stmt.as_ptr(),
                idx,
                value.as_ptr() as *const _,
                value.len() as u64,
                ffi::SQLITE_TRANSIENT(),
            )
        };
        self.check(rc)
    }

    #[inline]
    pub fn step(&mut self) -> Result<StepResult> {
        let rc = unsafe { ffi::sqlite3_step(self.stmt.as_ptr()) };
        match rc {
            ffi::SQLITE_ROW => Ok(StepResult::Row),
            ffi::SQLITE_DONE => Ok(StepResult::Done),
            ffi::SQLITE_BUSY => bail!("SQLITE_BUSY"),
            ffi::SQLITE_LOCKED => bail!("SQLITE_LOCKED"),
            _ => bail!("sqlite step error {rc}: {}", unsafe {
                sqlite_errmsg(self.db.as_ptr())
            }),
        }
    }

    #[inline]
    pub fn step_done(&mut self) -> Result<()> {
        match self.step()? {
            StepResult::Done => Ok(()),
            StepResult::Row => bail!("expected SQLITE_DONE, got SQLITE_ROW"),
        }
    }

    #[inline]
    pub fn column_i64(&self, idx: i32) -> i64 {
        unsafe { ffi::sqlite3_column_int64(self.stmt.as_ptr(), idx) }
    }

    #[inline]
    pub fn column_text(&self, idx: i32) -> Result<String> {
        unsafe {
            let ptr = ffi::sqlite3_column_text(self.stmt.as_ptr(), idx);
            if ptr.is_null() {
                return Ok(String::new());
            }
            Ok(CStr::from_ptr(ptr as *const c_char)
                .to_string_lossy()
                .into_owned())
        }
    }

    #[inline]
    fn check(&self, rc: i32) -> Result<()> {
        if rc == ffi::SQLITE_OK {
            Ok(())
        } else {
            bail!("sqlite stmt error {rc}: {}", unsafe {
                sqlite_errmsg(self.db.as_ptr())
            })
        }
    }
}
```

```rust
use std::time::Duration;

pub fn configure_sqlite_for_bench(
    db: &SqliteDb,
    spec: &RunSpec,
    connections: usize,
) -> Result<()> {
    db.busy_timeout(Duration::from_millis(spec.busy_timeout_ms))?;

    // Must be set before data creation for page-size-sensitive tests.
    db.exec(&format!("PRAGMA page_size = {};", spec.page_size))?;

    let journal = db.query_one_text("PRAGMA journal_mode = WAL;")?;
    if journal.to_ascii_lowercase() != "wal" {
        bail!("failed to enter WAL mode; got journal_mode={journal}");
    }

    let sync = match spec.durability {
        Durability::Strict => "FULL",
        Durability::Normal => "NORMAL",
        Durability::Unsafe => "OFF",
    };

    db.exec(&format!("PRAGMA synchronous = {sync};"))?;

    let sync_readback = db.query_one_i64("PRAGMA synchronous;")?;
    let expected = match spec.durability {
        Durability::Strict => 2, // FULL
        Durability::Normal => 1, // NORMAL
        Durability::Unsafe => 0, // OFF
    };

    if sync_readback != expected {
        bail!("unexpected SQLite synchronous={sync_readback}, expected={expected}");
    }

    if spec.controlled_checkpoint {
        db.exec("PRAGMA wal_autocheckpoint = 0;")?;
    }

    // SQLite cache_size negative means KiB.
    // Divide memory budget by connections for matched global-memory comparison.
    let per_conn_kib = ((spec.memory_bytes() / 1024) / connections.max(1) as u64).max(1024);
    db.exec(&format!("PRAGMA cache_size = -{};", per_conn_kib))?;

    // Optional: keep mmap off for a cleaner page-cache comparison unless
    // RedlineDB also has an equivalent mmap mode.
    db.exec("PRAGMA mmap_size = 0;")?;

    Ok(())
}
```

```rust
    interval: Duration,

                log_frames: outcome.log_frames,

                busy: outcome.busy,

    })
```

```rust
use ordered_float::OrderedFloat;
use std::collections::BTreeMap;

#[derive(Debug, Clone, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub enum CanonValue {
    Null,
    Integer(i64),
    Real(OrderedFloat<f64>),
    Text(String),
    Blob(Vec<u8>),
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct CanonResult {
    pub columns: Vec<String>,
    pub rows: Vec<Vec<CanonValue>>,
}

#[derive(Debug, Clone, Copy)]
pub enum OrderSemantics {
    Ordered,
    UnorderedMultiset,
}

pub fn compare_results(
    sqlite: CanonResult,
    redline: CanonResult,
    order: OrderSemantics,
) -> anyhow::Result<()> {
    if sqlite.columns != redline.columns {
        anyhow::bail!(
            "column mismatch\nsqlite={:?}\nredline={:?}",
            sqlite.columns,
            redline.columns
        );
    }

    match order {
        OrderSemantics::Ordered => {
            if sqlite.rows != redline.rows {
                anyhow::bail!(
                    "ordered row mismatch\nsqlite={:?}\nredline={:?}",
                    sqlite.rows,
                    redline.rows
                );
            }
        }
        OrderSemantics::UnorderedMultiset => {
            let a = multiset(sqlite.rows);
            let b = multiset(redline.rows);
            if a != b {
                anyhow::bail!("unordered row mismatch\nsqlite={a:?}\nredline={b:?}");
            }
        }
    }

    Ok(())
}

fn multiset(rows: Vec<Vec<CanonValue>>) -> BTreeMap<Vec<CanonValue>, usize> {
    let mut out = BTreeMap::new();
    for row in rows {
        *out.entry(row).or_insert(0) += 1;
    }
    out
}
```

```rust
pub fn run_crash_child_and_kill(
    child_cmd: &mut Command,
    kill_after_acks: usize,
) -> Result<CrashRunResult> {
    let mut child = child_cmd
        .stdout(Stdio::piped())
        .stderr(Stdio::inherit())
        .spawn()?;

    let stdout = child.stdout.take().expect("child stdout");
    let reader = BufReader::new(stdout);

    let mut acks = Vec::new();

    for line in reader.lines() {
        let line = line?;
        if let Some(rest) = line.strip_prefix("ACK ") {
            let ack: Ack = serde_json::from_str(rest)?;
            acks.push(ack);

            if acks.len() >= kill_after_acks {
                kill_child(&mut child)?;
                break;
            }
        }
    }

    let _ = child.wait();

    Ok(CrashRunResult {
        killed_after_acks: acks.len(),
        acks,
    })
```

```rust
fn print_ack(ack: &Ack) {
    println!("ACK {}", serde_json::to_string(ack).unwrap());
    // stdout is line-buffered when terminal, but not always through pipe.
    // Flush explicitly.
    use std::io::Write;
    let _ = std::io::stdout().flush();
}
```

# 21. Release gates

I would define Phase 9 gates like this.

## Gate 1: compatibility correctness

```text
Required:
  0 failures on hand-written supported SQL corpus
  0 failures on generated SQL corpus for N seeds
  all failures produce shrinkable reproducers
  unsupported SQL is classified, not silently miscomputed
```

## Gate 2: strict crash durability

```text
Required:
  insert-autocommit strict crash test: 10,000 seeds pass
  batch-insert strict crash test: 10,000 seeds pass
  update/delete strict crash test: 10,000 seeds pass
  checkpoint-pressure crash test: 1,000 seeds pass
  every parent-observed ack is present after recovery
  database accepts new writes after recovery
```

## Gate 3: single-thread parity

```text
Required:
  RedlineDB within target range of SQLite on:
    point read
    insert autocommit
    batched insert
    update by primary key
    range scan

Suggested target:
  >= 90% of SQLite throughput for key single-thread OLTP paths before making replacement claims.

If RedlineDB loses:
  report reason and stats.
```

## Gate 4: concurrent writer advantage

```text
Required:
  On disjoint-key writes:
    RedlineDB throughput should scale beyond SQLite at 4, 8, 16 writer threads.
    RedlineDB p99 should not explode from a global writer lock.
    RedlineDB row-lock waits should remain near zero.
```

This is the benchmark that should validate RedlineDB’s architectural advantage over SQLite’s single-writer WAL design.

## Gate 5: memory discipline

```text
Required:
  RSS <= configured ceiling + documented overhead.
  No unbounded WAL growth in normal checkpoint conditions.
  No unbounded per-session statement/result/cache growth.
```

## Gate 6: checkpoint pressure

```text
Required:
  WAL growth is explained by active reader/recovery horizon.
  Once horizon advances, checkpoint catches up.
  Checkpoint p99 stalls remain within documented bounds.
```

# 23. RedlineDB-specific instrumentation I would add before trusting Phase 9

Phase 9 needs introspection hooks. Without them, you only know that RedlineDB is slower or faster, not why.

Make stats cheap:

```text

```

For histograms inside RedlineDB, avoid global histograms on hot paths. Use per-thread or per-shard histograms and merge on snapshot.

# 24. High-performance benchmarking details

## Avoid allocator distortion

Do:

```text
prepare statements once per worker
preallocate payload buffers
reuse bind buffers
reuse result row buffers where the API allows
avoid String formatting in loops
avoid Vec push per operation
avoid channel send per operation
```

Do not:

```text
println! in workers
create random distributions with heap allocation per op
prepare SQL per op
open/close connection per op
collect every latency into Vec<Duration>
```

## Use deterministic random streams

Each worker gets:

```rust
let worker_seed = spec.seed ^ ((worker_id as u64 + 1) * 0x9E37_79B9_7F4A_7C15);
```

Then deterministic keys:

```rust
pub struct KeyGen {
    state: rand_xoshiro::Xoshiro256PlusPlus,
    max_key: u64,
}

impl KeyGen {
    pub fn uniform(&mut self) -> u64 {
        use rand::Rng;
        self.state.gen_range(0..self.max_key)
    }
}
```

Use disjoint key ranges for scalability tests and shared hot ranges for conflict tests. Do not accidentally mix the two.

## Pinning

Thread pinning should be optional:

```text
--pin-threads=true
```

Record whether it was used. Pinning helps reduce noise, but some machines perform worse if pinning fights the OS scheduler.

## Warmup

Every run has:

```text
setup
warmup
measure
cooldown/checkpoint
verify
report
```

Never include setup in measured time unless the workload explicitly benchmarks bulk load.

## Repetition

For official certification:

```text
min_runs = 5
report median
report min/max
report MAD or confidence interval
randomize engine order
alternate SQLite/RedlineDB runs to reduce thermal/cache bias
```

# 26. The “beat SQLite” strategy for Phase 9

Do not try to beat SQLite everywhere on day one. Prove the architecture wins where it should.

## RedlineDB should win first on

```text
concurrent disjoint writers
mixed OLTP with many write sessions
normal durability group commit
shared-cache memory efficiency under many connections
checkpoint scheduling if background workers are better isolated
```

## RedlineDB must eventually match or approach SQLite on

```text
single-thread point lookup
single-thread insert
small range scan
prepared statement overhead
row decoding
B-tree cursor traversal
```

## RedlineDB may initially lose on

```text
SQLite’s extremely optimized single-thread VM path
tiny SELECT constants
very small in-cache point reads
COUNT(*) if SQLite uses specialized paths
single connection workloads where SQLite’s design is ideal
```

Losses are fine if they are visible, explained, and shrinking over time. The release claim should be based on measured supported workloads, not blanket marketing.

   * No measurements until configs are proven.

    * Parent/child kill testing.

    * SQLite-vs-Redline supported SQL corpus.

# 29. Final Phase 9 success definition

Phase 9 is done when RedlineDB has a reproducible report that says, with evidence:

```text
1. RedlineDB passes supported SQL differential tests against SQLite.
2. RedlineDB strict mode preserves every acknowledged commit in crash tests.
3. RedlineDB normal mode has documented and tested durability semantics.
4. RedlineDB single-thread OLTP is near SQLite on core paths.
5. RedlineDB beats SQLite WAL on concurrent disjoint writers.
6. RedlineDB maintains configured memory ceilings.
7. RedlineDB controls WAL/checkpoint growth under normal workloads.
8. Every benchmark is reproducible from a JSON manifest.
9. Every performance claim is backed by throughput, p99, memory, WAL bytes/op, checkpoint, and recovery metrics.
```

The “brilliant simplicity” version is this: **one benchmark crate, one deterministic workload model, one adapter per engine, one manifest format, one latency/metrics pipeline, one compatibility oracle, one crash oracle, and one honest report.**
