## Phase 9 target: build a certification system, not just a benchmark binary

Phase 9 should become a repeatable, adversarial, apples-to-apples certification harness that proves three things:

1. **Correctness:** supported SQL produces the same results as SQLite, or errors in a documented compatible way.
2. **Durability honesty:** strict, normal, and unsafe modes are compared only against equivalent SQLite durability modes.
3. **Performance truth:** RedlineDB wins where its architecture should win, especially concurrent writers, without hiding memory growth, WAL growth, checkpoint stalls, or tail latency.

SQLite’s official WAL docs give the central competitive point: WAL mode allows readers and a writer to run at the same time, but because there is only one WAL file, “there can only be one writer at a time.” That is the exact ceiling Phase 9 must expose with disjoint concurrent-writer workloads. SQLite also documents that WAL `synchronous=FULL` syncs the WAL on every commit, while `synchronous=NORMAL` avoids most transaction-commit syncs and trades away power-loss durability for speed. Those modes must be matched separately. ([SQLite][1])

SQLite’s WAL checkpoint behavior also matters for fair testing. SQLite defaults to checkpointing around 1000 WAL pages, and long/overlapping readers can prevent checkpoints from completing, causing WAL growth and degraded read performance. Phase 9 should therefore include both “SQLite default checkpoint behavior” and “controlled checkpoint behavior” runs, and it should measure WAL size, checkpoint progress, checkpoint stalls, and read degradation under long readers. ([SQLite][1])

# 2. Fundamental design rules

## Rule 1: separate benchmark truth from marketing truth

Every reported result must include:

```text
engine
engine version
git SHA
SQL path or raw API path
durability mode
checkpoint policy
page size
cache/buffer budget
thread count
worker count
background thread count
payload size
key distribution
transaction size
database size
whether DB fits in memory
warmup duration
measurement duration
SQLite PRAGMAs / RedlineDB config
OS
filesystem
CPU model
logical cores
physical cores if available
memory
kernel version
```

No single number like “RedlineDB is 5x faster” should exist without this context.

## Rule 2: compare modes, not vibes

The durability mapping should be explicit:

| Bench mode | SQLite config                                         | RedlineDB config                                                          | Claim allowed                                          |
| ---------- | ----------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------ |
| `strict`   | `PRAGMA journal_mode=WAL; PRAGMA synchronous=FULL;`   | commit returns only after WAL records are durable; group commit allowed   | power-loss durable commits                             |
| `normal`   | `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL;` | commit returns after WAL append/OS handoff or configured non-fsync policy | process-crash safe, not necessarily power-loss durable |
| `unsafe`   | `PRAGMA journal_mode=WAL; PRAGMA synchronous=OFF;`    | no sync guarantee                                                         | development/load speed only                            |

SQLite documents that WAL `FULL` is ACID, while WAL `NORMAL` remains consistent but may lose durable commits after power loss. The benchmark must never compare RedlineDB strict mode against SQLite normal mode, or RedlineDB normal mode against SQLite strict mode, unless the report labels it as intentionally mismatched. ([SQLite][3])

## Rule 3: use prepared statements everywhere

No serious benchmark should parse SQL in the hot path unless the workload is explicitly “prepare/parse overhead.” For normal OLTP benchmarks:

```text
prepare once per worker
bind each operation
step/execute
reset/reuse
```

For RedlineDB, this means your public API needs prepared statement reuse before replacement claims. For SQLite, the adapter should use prepared statements or `prepare_cached()` where Rust lifetimes make long-lived statements awkward.

## Rule 4: benchmark both SQL and API paths

You need two paths:

```text
redlinedb_bench --path sql
redlinedb_bench --path api
```

The **SQL path** is the replacement claim.

The **API path** tells you whether the kernel/storage engine is fast and the SQL layer is the bottleneck.

If API is fast and SQL is slow, optimize parser/binder/planner/executor. If both are slow, optimize storage/WAL/buffer/indexes.

# 3. Workload suite

## 3.1 Core schemas

Use a tiny KV table for OLTP micro-workloads:

```sql
CREATE TABLE kv (
    k       INTEGER PRIMARY KEY,
    v       BLOB NOT NULL,
    version INTEGER NOT NULL DEFAULT 0,
    tag     INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX kv_tag_idx ON kv(tag);
CREATE INDEX kv_version_idx ON kv(version);
```

Use a slightly richer schema for joins and planner tests:

```sql
CREATE TABLE users (
    user_id INTEGER PRIMARY KEY,
    name    TEXT NOT NULL,
    status  INTEGER NOT NULL,
    region  INTEGER NOT NULL
);

CREATE INDEX users_region_idx ON users(region);

CREATE TABLE orders (
    order_id INTEGER PRIMARY KEY,
    user_id  INTEGER NOT NULL,
    amount   INTEGER NOT NULL,
    state    INTEGER NOT NULL,
    created  INTEGER NOT NULL
);

CREATE INDEX orders_user_idx ON orders(user_id);
CREATE INDEX orders_state_created_idx ON orders(state, created);
```

## 3.2 Workloads to implement first

| Workload                 | Purpose                                    | RedlineDB advantage expected?            |
| ------------------------ | ------------------------------------------ | ---------------------------------------- |
| `single_row_insert`      | Commit overhead, WAL/fsync cost            | yes under concurrent strict group commit |
| `batched_insert`         | Sequential insert throughput               | maybe                                    |
| `point_read_pk`          | B-tree/index lookup latency                | must match SQLite eventually             |
| `range_scan_pk`          | ordered scan efficiency                    | must match SQLite eventually             |
| `update_disjoint`        | row-lock/write concurrency                 | yes                                      |
| `delete_disjoint`        | delete and vacuum pressure                 | yes after vacuum maturity                |
| `indexed_lookup`         | secondary-index point/range lookup         | must match SQLite eventually             |
| `join_indexed`           | planner/executor/indexed join              | later Phase 6/9                          |
| `readers_only`           | reader scalability                         | should scale well                        |
| `writers_disjoint`       | expose SQLite single-writer limit          | major yes                                |
| `mixed_oltp`             | realistic read/write pressure              | yes under write contention               |
| `checkpoint_pressure`    | checkpoint stall behavior                  | must be observable                       |
| `long_reader_wal_growth` | long snapshots vs WAL/checkpoint retention | must remain bounded by config            |
| `crash_recovery`         | recovery time and durability               | correctness gate                         |
| `memory_ceiling`         | bounded memory behavior                    | correctness/perf gate                    |

## 3.3 Key distributions

Do not use only sequential keys.

Use:

```text
sequential
uniform random
Zipfian / hot-key skew
disjoint writer ranges
append-only
read-mostly hot set
write-mostly hot set
```

Disjoint writer keying:

```text
worker 0: keys 0, 64, 128, ...
worker 1: keys 1, 65, 129, ...
...
worker N: keys N, N + worker_count, ...
```

This avoids logical conflicts and makes the database engine’s write-concurrency architecture the bottleneck, not application-level key contention.

Hotspot keying:

```text
90% of writes hit 1% of keys
10% of writes hit the rest
```

This proves lock/conflict behavior separately.

# 5. Threading model

Use **standard OS threads**, not Tokio, for the benchmark hot path.

Database operations are blocking, CPU-heavy, lock-heavy, or I/O-heavy. A Tokio runtime would add scheduler noise unless you are explicitly benchmarking an async server/wire layer. Tokio’s docs distinguish multithreaded worker runtimes and current-thread runtimes, but for embedded DB calls the cleanest benchmark is one OS worker thread per connection/session. ([Docs.rs][5])

Use:

```rust
std::thread
std::sync::Barrier
std::sync::atomic::AtomicBool
std::time::Instant
```

Avoid in the hot path:

```text
global logging
global atomic counters per operation
cross-thread channels per operation
heap allocation per operation
format! per operation
String creation per operation
Vec allocation per read row
```

Preferred hot-path structure:

```text
one worker thread
one DB connection/session
prepared statements created before measurement loop
one local RNG
one reusable payload buffer
one local latency histogram
one local counter block
merge metrics after join
```

HdrHistogram is a good fit for latency because it is designed for latency-sensitive measurements with fixed memory and constant recording cost; the Rust crate documents configurable precision and fixed footprint based on range/precision, not sample count. ([Docs.rs][6])

# 6. Memory strategy

The harness must not allocate in the measured loop.

## Payload generation

Do not allocate random payloads per operation. Reuse one buffer per worker:

```rust
pub fn fill_payload(buf: &mut [u8], key: u64, seed: u64) {
    let mut x = key ^ seed ^ 0x9E37_79B9_7F4A_7C15;
    for chunk in buf.chunks_mut(8) {
        x = splitmix64(x);
        let bytes = x.to_le_bytes();
        let n = chunk.len();
        chunk.copy_from_slice(&bytes[..n]);
    }
}

#[inline]
pub fn splitmix64(mut x: u64) -> u64 {
    x = x.wrapping_add(0x9E37_79B9_7F4A_7C15);
    let mut z = x;
    z = (z ^ (z >> 30)).wrapping_mul(0xBF58_476D_1CE4_E5B9);
    z = (z ^ (z >> 27)).wrapping_mul(0x94D0_49BB_1331_11EB);
    z ^ (z >> 31)
}
```

## Result reading

For SQLite, avoid pulling blobs into new `Vec<u8>` when only size/checksum is needed. Use borrowed value refs where possible:

```rust
use rusqlite::types::ValueRef;

let len = stmt.query_row([key], |row| {
    match row.get_ref(0)? {
        ValueRef::Blob(b) => Ok(b.len()),
        other => Err(rusqlite::Error::InvalidColumnType(
            0,
            "v".into(),
            other.data_type(),
        )),
    }
})?;
```

For RedlineDB, design the API so benchmark users can borrow column bytes during the row lifetime:

```rust
let row = stmt.query_one((&key,))?;
let value: &[u8] = row.get_blob_borrowed(0)?;
```

If RedlineDB forces heap allocation for every BLOB read, SQLite will punish it on point-read and range-scan benchmarks.

# 9. Metrics implementation

```rust
use hdrhistogram::Histogram;
use serde::Serialize;
use std::time::{Duration, Instant};

const MAX_LATENCY_US: u64 = 10 * 60 * 1_000_000; // 10 minutes

#[derive(Debug)]
pub struct WorkerMetrics {
    pub worker_id: usize,
    pub attempted: u64,
    pub succeeded: u64,
    pub failed: u64,
    pub busy_or_retry: u64,
    pub rows: u64,
    pub bytes_read: u64,
    pub bytes_written: u64,
    pub latency_us: Histogram<u64>,
}

impl WorkerMetrics {
    pub fn new(worker_id: usize) -> Self {
        Self {
            worker_id,
            attempted: 0,
            succeeded: 0,
            failed: 0,
            busy_or_retry: 0,
            rows: 0,
            bytes_read: 0,
            bytes_written: 0,
            latency_us: Histogram::new_with_max(MAX_LATENCY_US, 3)
                .expect("valid histogram config"),
        }
    }

    #[inline]
    pub fn record_latency_since(&mut self, start: Instant) {
        let elapsed = start.elapsed();
        let micros = duration_to_micros(elapsed).clamp(1, MAX_LATENCY_US);
        let _ = self.latency_us.record(micros);
    }
}

#[inline]
fn duration_to_micros(d: Duration) -> u64 {
    let us = d.as_micros();
    if us > u64::MAX as u128 {
        u64::MAX
    } else {
        us as u64
    }
}

#[derive(Debug, Clone, Serialize)]
pub struct LatencySummary {
    pub p50_us: u64,
    pub p95_us: u64,
    pub p99_us: u64,
    pub p999_us: u64,
    pub max_us: u64,
}

impl From<&Histogram<u64>> for LatencySummary {
    fn from(h: &Histogram<u64>) -> Self {
        Self {
            p50_us: h.value_at_percentile(50.0),
            p95_us: h.value_at_percentile(95.0),
            p99_us: h.value_at_percentile(99.0),
            p999_us: h.value_at_percentile(99.9),
            max_us: h.max(),
        }
    }
}

#[derive(Debug, Serialize)]
pub struct RunMetrics {
    pub attempted: u64,
    pub succeeded: u64,
    pub failed: u64,
    pub busy_or_retry: u64,
    pub rows: u64,
    pub bytes_read: u64,
    pub bytes_written: u64,
    pub elapsed_secs: f64,
    pub ops_per_sec: f64,
    pub rows_per_sec: f64,
    pub latency: LatencySummary,
}

impl RunMetrics {
    pub fn merge(workers: Vec<WorkerMetrics>, elapsed: Duration) -> anyhow::Result<Self> {
        let mut hist = Histogram::new_with_max(MAX_LATENCY_US, 3)?;
        let mut attempted = 0;
        let mut succeeded = 0;
        let mut failed = 0;
        let mut busy_or_retry = 0;
        let mut rows = 0;
        let mut bytes_read = 0;
        let mut bytes_written = 0;

        for w in workers {
            attempted += w.attempted;
            succeeded += w.succeeded;
            failed += w.failed;
            busy_or_retry += w.busy_or_retry;
            rows += w.rows;
            bytes_read += w.bytes_read;
            bytes_written += w.bytes_written;
            hist.add(w.latency_us)?;
        }

        let elapsed_secs = elapsed.as_secs_f64();

        Ok(Self {
            attempted,
            succeeded,
            failed,
            busy_or_retry,
            rows,
            bytes_read,
            bytes_written,
            elapsed_secs,
            ops_per_sec: succeeded as f64 / elapsed_secs,
            rows_per_sec: rows as f64 / elapsed_secs,
            latency: LatencySummary::from(&hist),
        })
    }
}
```

# 10. Runner implementation

The runner should create workers outside the measured interval, synchronize with a barrier, then run a tight loop.

```rust
use anyhow::{Context, Result};
use std::{
    sync::{Arc, Barrier},
    thread,
    time::{Duration, Instant},
};

pub struct WorkerCtx {
    pub worker_id: usize,
    pub worker_count: usize,
    pub seed: u64,
    pub start_at: Instant,
    pub deadline: Instant,
    pub barrier: Arc<Barrier>,
}

pub trait BenchWorker: Send + 'static {
    fn run(&mut self, ctx: WorkerCtx) -> Result<WorkerMetrics>;
}

pub fn run_workers<F>(
    worker_count: usize,
    seed: u64,
    measure: Duration,
    make_worker: F,
) -> Result<RunMetrics>
where
    F: Fn(usize) -> Result<Box<dyn BenchWorker>> + Send + Sync + 'static,
{
    anyhow::ensure!(worker_count > 0, "worker_count must be > 0");

    let barrier = Arc::new(Barrier::new(worker_count + 1));
    let make_worker = Arc::new(make_worker);

    let start_at = Instant::now() + Duration::from_millis(500);
    let deadline = start_at + measure;

    let mut handles = Vec::with_capacity(worker_count);

    for worker_id in 0..worker_count {
        let barrier = Arc::clone(&barrier);
        let make_worker = Arc::clone(&make_worker);

        let handle = thread::Builder::new()
            .name(format!("bench-worker-{worker_id}"))
            .spawn(move || -> Result<WorkerMetrics> {
                let mut worker = make_worker(worker_id)
                    .with_context(|| format!("create worker {worker_id}"))?;

                let ctx = WorkerCtx {
                    worker_id,
                    worker_count,
                    seed: seed ^ ((worker_id as u64) << 32),
                    start_at,
                    deadline,
                    barrier,
                };

                worker.run(ctx)
            })?;

        handles.push(handle);
    }

    barrier.wait();
    wait_until(start_at);
    let measured_start = Instant::now();

    let mut worker_metrics = Vec::with_capacity(worker_count);

    for handle in handles {
        let metrics = handle
            .join()
            .map_err(|_| anyhow::anyhow!("worker thread panicked"))??;
        worker_metrics.push(metrics);
    }

    let elapsed = measured_start.elapsed();
    RunMetrics::merge(worker_metrics, elapsed)
}

pub fn wait_until(t: Instant) {
    loop {
        let now = Instant::now();
        if now >= t {
            return;
        }

        let remaining = t - now;
        if remaining > Duration::from_millis(2) {
            thread::sleep(remaining / 2);
        } else {
            std::hint::spin_loop();
        }
    }
}
```

Inside each worker, do not call `Instant::now()` for loop termination every single operation if the operation is extremely cheap. Check every 64 or 256 ops:

```rust
#[inline]
pub fn should_stop(local_ops: u64, deadline: Instant) -> bool {
    local_ops & 0x3F == 0 && Instant::now() >= deadline
}
```

# 11. SQLite adapter

## 11.1 SQLite configuration

```rust
#[cfg(feature = "sqlite")]
pub mod sqlite_adapter {
    use crate::{DurabilityMode, RunConfig};
    use anyhow::{ensure, Result};
    use rusqlite::{Connection, OpenFlags};
    use std::{path::Path, time::Duration};

    pub fn open_sqlite_connection(path: &Path, cfg: &RunConfig) -> Result<Connection> {
        let flags = OpenFlags::SQLITE_OPEN_READ_WRITE
            | OpenFlags::SQLITE_OPEN_CREATE
            | OpenFlags::SQLITE_OPEN_NO_MUTEX;

        let conn = Connection::open_with_flags(path, flags)?;
        conn.busy_timeout(Duration::from_millis(cfg.busy_timeout_ms))?;

        let mode: String = conn.query_row("PRAGMA journal_mode=WAL", [], |row| row.get(0))?;
        ensure!(
            mode.eq_ignore_ascii_case("wal"),
            "SQLite refused WAL mode; got {mode:?}"
        );

        let sync = match cfg.durability {
            DurabilityMode::Strict => "FULL",
            DurabilityMode::Normal => "NORMAL",
            DurabilityMode::Unsafe => "OFF",
        };

        conn.execute_batch(&format!(
            "
            PRAGMA synchronous={sync};
            PRAGMA temp_store=MEMORY;
            PRAGMA cache_size=-{};
            PRAGMA wal_autocheckpoint={};
            PRAGMA locking_mode=NORMAL;
            ",
            cfg.cache_mib * 1024,
            cfg.wal_autocheckpoint_pages,
        ))?;

        Ok(conn)
    }

    pub fn sqlite_version() -> String {
        rusqlite::version().to_string()
    }
}
```

For strict mode, this maps to SQLite WAL `synchronous=FULL`. For normal mode, this maps to WAL `synchronous=NORMAL`, where SQLite documents that most transactions do not sync during commit, but may lose recent commits after power loss. ([SQLite][3])

## 11.2 SQLite setup

```rust
#[cfg(feature = "sqlite")]
pub fn setup_sqlite_kv(path: &std::path::Path, cfg: &RunConfig) -> anyhow::Result<()> {
    use rusqlite::params;

    remove_sqlite_files(path)?;

    let conn = sqlite_adapter::open_sqlite_connection(path, cfg)?;

    conn.execute_batch(
        "
        CREATE TABLE kv (
            k       INTEGER PRIMARY KEY,
            v       BLOB NOT NULL,
            version INTEGER NOT NULL DEFAULT 0,
            tag     INTEGER NOT NULL DEFAULT 0
        );

        CREATE INDEX kv_tag_idx ON kv(tag);
        CREATE INDEX kv_version_idx ON kv(version);
        ",
    )?;

    conn.execute_batch("BEGIN IMMEDIATE")?;

    {
        let mut stmt = conn.prepare(
            "INSERT INTO kv(k, v, version, tag) VALUES (?1, ?2, 0, ?3)"
        )?;

        let mut payload = vec![0_u8; cfg.payload_bytes];

        for k in 0..cfg.initial_rows {
            fill_payload(&mut payload, k, cfg.seed);
            let tag = (k % 1024) as i64;
            stmt.execute(params![k as i64, &payload[..], tag])?;
        }
    }

    conn.execute_batch("COMMIT")?;

    // Force a clean baseline. Useful before cloning/copying the DB for repeat runs.
    let _ = conn.execute_batch("PRAGMA wal_checkpoint(TRUNCATE)");

    Ok(())
}

pub fn remove_sqlite_files(path: &std::path::Path) -> anyhow::Result<()> {
    let _ = std::fs::remove_file(path);

    let wal = format!("{}-wal", path.display());
    let shm = format!("{}-shm", path.display());

    let _ = std::fs::remove_file(wal);
    let _ = std::fs::remove_file(shm);

    Ok(())
}
```

# 12. Workload example: single-row autocommit inserts

This measures per-transaction commit cost. In strict mode, this is brutal and important.

```rust
#[cfg(feature = "sqlite")]
pub struct SqliteSingleRowInsertWorker {
    conn: rusqlite::Connection,
    next_key: u64,
    payload: Vec<u8>,
    seed: u64,
}

#[cfg(feature = "sqlite")]
impl SqliteSingleRowInsertWorker {
    pub fn new(
        db_path: &std::path::Path,
        cfg: &RunConfig,
        worker_id: usize,
    ) -> anyhow::Result<Self> {
        let conn = sqlite_adapter::open_sqlite_connection(db_path, cfg)?;

        // Put inserts far above preloaded range.
        let next_key = 10_000_000_000_u64 + worker_id as u64;

        Ok(Self {
            conn,
            next_key,
            payload: vec![0_u8; cfg.payload_bytes],
            seed: cfg.seed ^ worker_id as u64,
        })
    }
}

#[cfg(feature = "sqlite")]
impl BenchWorker for SqliteSingleRowInsertWorker {
    fn run(&mut self, ctx: WorkerCtx) -> anyhow::Result<WorkerMetrics> {
        use rusqlite::params;

        let mut metrics = WorkerMetrics::new(ctx.worker_id);

        let worker_count = ctx.worker_count as u64;
        let mut key = self.next_key;

        let mut stmt = self.conn.prepare(
            "INSERT INTO kv(k, v, version, tag) VALUES (?1, ?2, 0, ?3)"
        )?;

        ctx.barrier.wait();
        wait_until(ctx.start_at);

        loop {
            if should_stop(metrics.attempted, ctx.deadline) {
                break;
            }

            fill_payload(&mut self.payload, key, self.seed);
            let tag = (key % 1024) as i64;

            metrics.attempted += 1;
            let start = std::time::Instant::now();

            match stmt.execute(params![key as i64, &self.payload[..], tag]) {
                Ok(_) => {
                    metrics.succeeded += 1;
                    metrics.rows += 1;
                    metrics.bytes_written += self.payload.len() as u64;
                }
                Err(e) if is_sqlite_busy(&e) => {
                    metrics.failed += 1;
                    metrics.busy_or_retry += 1;
                }
                Err(e) => return Err(e.into()),
            }

            metrics.record_latency_since(start);
            key = key.wrapping_add(worker_count);
        }

        Ok(metrics)
    }
}

#[cfg(feature = "sqlite")]
fn is_sqlite_busy(e: &rusqlite::Error) -> bool {
    matches!(
        e,
        rusqlite::Error::SqliteFailure(err, _)
            if err.code == rusqlite::ErrorCode::DatabaseBusy
                || err.code == rusqlite::ErrorCode::DatabaseLocked
    )
}
```

For a fair “application throughput” benchmark, do not just count SQLite `BUSY` as failure. Run two variants:

```text
--retry-policy none
--retry-policy busy-timeout
```

The `busy-timeout` variant should count the full wait/retry time inside operation latency.

# 13. Workload example: point reads without allocation

```rust
#[cfg(feature = "sqlite")]
pub struct SqlitePointReadWorker {
    conn: rusqlite::Connection,
    max_key: u64,
    rng_state: u64,
}

#[cfg(feature = "sqlite")]
impl SqlitePointReadWorker {
    pub fn new(
        db_path: &std::path::Path,
        cfg: &RunConfig,
        worker_id: usize,
    ) -> anyhow::Result<Self> {
        let conn = sqlite_adapter::open_sqlite_connection(db_path, cfg)?;
        Ok(Self {
            conn,
            max_key: cfg.initial_rows,
            rng_state: cfg.seed ^ ((worker_id as u64) << 32),
        })
    }

    #[inline]
    fn next_key(&mut self) -> i64 {
        self.rng_state = splitmix64(self.rng_state);
        (self.rng_state % self.max_key) as i64
    }
}

#[cfg(feature = "sqlite")]
impl BenchWorker for SqlitePointReadWorker {
    fn run(&mut self, ctx: WorkerCtx) -> anyhow::Result<WorkerMetrics> {
        use rusqlite::types::ValueRef;

        let mut metrics = WorkerMetrics::new(ctx.worker_id);
        let mut stmt = self.conn.prepare("SELECT v FROM kv WHERE k = ?1")?;

        ctx.barrier.wait();
        wait_until(ctx.start_at);

        loop {
            if should_stop(metrics.attempted, ctx.deadline) {
                break;
            }

            let key = self.next_key();

            metrics.attempted += 1;
            let start = std::time::Instant::now();

            let len: usize = stmt.query_row([key], |row| {
                match row.get_ref(0)? {
                    ValueRef::Blob(b) => Ok(b.len()),
                    other => Err(rusqlite::Error::InvalidColumnType(
                        0,
                        "v".into(),
                        other.data_type(),
                    )),
                }
            })?;

            metrics.succeeded += 1;
            metrics.rows += 1;
            metrics.bytes_read += len as u64;
            metrics.record_latency_since(start);
        }

        Ok(metrics)
    }
}
```

This style matters. If RedlineDB copies every blob into a new `Vec`, SQLite may win because the benchmark is measuring RedlineDB allocation policy instead of index/page performance.

# 14. Workload example: disjoint concurrent updates

This is one of the most important Phase 9 workloads because it exposes the SQLite writer ceiling.

```rust
#[cfg(feature = "sqlite")]
pub struct SqliteUpdateDisjointWorker {
    conn: rusqlite::Connection,
    payload: Vec<u8>,
    seed: u64,
    next_key: u64,
    max_key: u64,
}

#[cfg(feature = "sqlite")]
impl SqliteUpdateDisjointWorker {
    pub fn new(
        db_path: &std::path::Path,
        cfg: &RunConfig,
        worker_id: usize,
    ) -> anyhow::Result<Self> {
        let conn = sqlite_adapter::open_sqlite_connection(db_path, cfg)?;

        Ok(Self {
            conn,
            payload: vec![0_u8; cfg.payload_bytes],
            seed: cfg.seed ^ worker_id as u64,
            next_key: worker_id as u64,
            max_key: cfg.initial_rows,
        })
    }
}

#[cfg(feature = "sqlite")]
impl BenchWorker for SqliteUpdateDisjointWorker {
    fn run(&mut self, ctx: WorkerCtx) -> anyhow::Result<WorkerMetrics> {
        use rusqlite::params;

        let mut metrics = WorkerMetrics::new(ctx.worker_id);
        let mut stmt = self.conn.prepare(
            "UPDATE kv SET v = ?1, version = version + 1 WHERE k = ?2"
        )?;

        let stride = ctx.worker_count as u64;
        let mut key = self.next_key;

        ctx.barrier.wait();
        wait_until(ctx.start_at);

        loop {
            if should_stop(metrics.attempted, ctx.deadline) {
                break;
            }

            if key >= self.max_key {
                key = ctx.worker_id as u64;
            }

            fill_payload(&mut self.payload, key, self.seed);

            metrics.attempted += 1;
            let start = std::time::Instant::now();

            match stmt.execute(params![&self.payload[..], key as i64]) {
                Ok(changed) => {
                    metrics.succeeded += 1;
                    metrics.rows += changed as u64;
                    metrics.bytes_written += self.payload.len() as u64;
                }
                Err(e) if is_sqlite_busy(&e) => {
                    metrics.failed += 1;
                    metrics.busy_or_retry += 1;
                }
                Err(e) => return Err(e.into()),
            }

            metrics.record_latency_since(start);
            key = key.wrapping_add(stride);
        }

        Ok(metrics)
    }
}
```

Run this with:

```text
threads = 1, 2, 4, 8, 16, 32, 64
durability = strict, normal, unsafe
payload = 16, 64, 256, 1024 bytes
initial_rows = 1M, 10M
cache = 64MiB, 256MiB, 1GiB
```

The expected RedlineDB win is not “all updates are faster.” The expected win is:

```text
SQLite throughput flattens early because writes serialize.
RedlineDB throughput continues scaling until WAL/device/CPU/latch limits.
RedlineDB p99 remains controlled until saturation.
```

SQLite’s own WAL docs support that concurrency expectation: readers can coexist with a writer in WAL mode, but only one writer exists at a time. ([SQLite][1])

For RedlineDB:

```rust
pub fn redline_file_sizes(dir: &Path) -> anyhow::Result<FileSizeSnapshot> {
    let mut main = 0;
    let mut wal = 0;

    for entry in std::fs::read_dir(dir)? {
        let entry = entry?;
        let path = entry.path();
        let len = entry.metadata()?.len();

        let name = path.file_name().and_then(|s| s.to_str()).unwrap_or("");

        if name.ends_with(".wal") || name.contains("wal") {
            wal += len;
        } else if name.ends_with(".db") || name.contains("data") {
            main += len;
        }
    }

    Ok(FileSizeSnapshot {
        main_bytes: main,
        wal_bytes: wal,
        shm_bytes: 0,
        total_bytes: main + wal,
    })
}
```

## 19.4 Oracle state

For mutation-heavy tests, track an in-memory oracle for simple tables:

```rust
use std::collections::BTreeMap;

#[derive(Clone, Debug)]
pub struct KvOracle {
    rows: BTreeMap<i64, Vec<u8>>,
}

impl KvOracle {
    pub fn insert(&mut self, k: i64, v: Vec<u8>) -> anyhow::Result<()> {
        anyhow::ensure!(!self.rows.contains_key(&k), "duplicate key");
        self.rows.insert(k, v);
        Ok(())
    }

    pub fn update(&mut self, k: i64, v: Vec<u8>) {
        if let Some(old) = self.rows.get_mut(&k) {
            *old = v;
        }
    }

    pub fn delete(&mut self, k: i64) {
        self.rows.remove(&k);
    }

    pub fn checksum(&self) -> u64 {
        let mut h = 0xcbf2_9ce4_8422_2325_u64;
        for (k, v) in &self.rows {
            h ^= *k as u64;
            h = h.wrapping_mul(0x100_0000_01B3);
            for b in v {
                h ^= *b as u64;
                h = h.wrapping_mul(0x100_0000_01B3);
            }
        }
        h
    }
}
```

For concurrent workloads, do not rely only on SQLite as the oracle because SQLite serializes writers differently. Use invariant checks:

```text
row count expected
no duplicate primary keys
version never decreases
checksum matches acknowledged operations for disjoint keys
all committed operation IDs are visible
rolled-back operation IDs are absent
```

# 20. Crash recovery certification

Phase 9 needs crash tests even though Phase 1 already did storage correctness, because end-to-end benchmark claims must include recovery time and persisted SQL/API state.

## 20.1 Crash test architecture

Use a parent controller and child workload process:

```text
parent:
  create DB
  spawn child
  read ACK lines from child stdout
  kill child at random or configured point
  reopen DB
  verify acknowledged commits
  measure recovery time
  repeat many seeds

child:
  open DB
  run deterministic transactions
  after each commit returns, print ACK(seq, checksum)
  flush stdout
```

In strict mode:

```text
every acknowledged commit must be present after reopen
```

In normal mode:

```text
database must not corrupt
a suffix of acknowledged commits may be absent after simulated power-loss style crash
application-process crash should generally preserve more, but the benchmark should not overclaim
```

SQLite documents that WAL `FULL` is durable/ACID, while WAL `NORMAL` may lose durability after power loss but remains consistent. That is the same semantic split RedlineDB should expose. ([SQLite][3])

## 20.2 ACK record table

```sql
CREATE TABLE crash_log (
    seq      INTEGER PRIMARY KEY,
    checksum INTEGER NOT NULL,
    payload  BLOB NOT NULL
);
```

Child transaction:

```sql
BEGIN;
INSERT INTO crash_log(seq, checksum, payload) VALUES (?1, ?2, ?3);
COMMIT;
```

Parent expects all ACKed `seq` values in strict mode.

## 20.3 Parent pseudocode

```rust
pub fn run_crash_trial(cfg: &RunConfig, engine: EngineKind, seed: u64) -> anyhow::Result<()> {
    let child = std::process::Command::new(std::env::current_exe()?)
        .arg("crash-child")
        .arg("--engine")
        .arg(format!("{engine:?}"))
        .arg("--durability")
        .arg(format!("{:?}", cfg.durability))
        .arg("--seed")
        .arg(seed.to_string())
        .stdout(std::process::Stdio::piped())
        .spawn()?;

    // Read ACKs until randomized kill point.
    // Then kill child, wait, reopen DB, verify.
    //
    // Keep this in a separate process. Thread panic is not a crash.
    Ok(())
}
```

# 21. Memory ceiling certification

Memory ceiling tests should deliberately create pressure:

```text
cache/buffer budget: 32MiB, 64MiB, 128MiB
DB size: 10x cache
workload: 80% point read, 20% update
payload: 256B / 1KiB
threads: 8 / 16 / 32
duration: 5–15 min in nightly
```

The gate should fail if:

```text
peak RSS > configured budget + allowed engine overhead
WAL grows beyond configured retention without active long reader
checkpoint cannot make progress after reader gap
latency collapses from unbounded eviction stalls
```

Linux RSS sampler:

```rust
pub fn linux_vm_hwm_bytes() -> Option<u64> {
    let s = std::fs::read_to_string("/proc/self/status").ok()?;

    for line in s.lines() {
        if let Some(rest) = line.strip_prefix("VmHWM:") {
            let mut parts = rest.split_whitespace();
            let kib: u64 = parts.next()?.parse().ok()?;
            return Some(kib * 1024);
        }
    }

    None
}

pub fn linux_vm_rss_bytes() -> Option<u64> {

            let mut parts = rest.split_whitespace();

        }
    }

    None
}
```

# 22. Checkpoint-pressure workload

This workload is mandatory because many databases look fast until checkpointing starts.

## Setup

```text
initial rows: 1M
payload: 256B
threads: 8 writers + 8 readers
durability: strict and normal
checkpoint target: small enough to trigger frequently
long-reader variant: one reader holds snapshot for 30s
```

## Operations

Writers:

```sql
UPDATE kv SET v = ?, version = version + 1 WHERE k = ?;
```

Readers:

```sql
SELECT v FROM kv WHERE k = ?;
```

Long reader:

```sql
BEGIN;
SELECT COUNT(*) FROM kv WHERE tag BETWEEN ? AND ?;
-- hold transaction open
COMMIT;
```

## Required output

```text
ops/sec before checkpoint pressure
ops/sec during checkpoint pressure
p99 before/during/after
WAL bytes over time
checkpoint progress over time
reader stall count
writer stall count
oldest snapshot age
```

SQLite’s docs explicitly call out checkpoint starvation: if there are many overlapping readers and always at least one active reader, checkpoints may not complete and the WAL can grow without bound. RedlineDB’s long-reader retention behavior needs to be measured against that same class of pressure. ([SQLite][1])

# 23. Open-loop latency mode

Closed-loop benchmarks answer:

```text
How many ops/sec can N client threads push?
```

Open-loop benchmarks answer:

```text
What is p99 latency at a fixed offered load?
```

Both are needed.

Closed-loop hides coordinated omission: when the database stalls, clients stop issuing new work, so the histogram underreports the pain.

Open-loop runner shape:

```rust
pub struct RateLimiter {
    next: std::time::Instant,
    interval: std::time::Duration,
}

impl RateLimiter {
    pub fn new(start: std::time::Instant, ops_per_sec: f64) -> Self {
        Self {
            next: start,
            interval: std::time::Duration::from_secs_f64(1.0 / ops_per_sec),
        }
    }

    pub fn wait_next(&mut self) {
        wait_until(self.next);
        self.next += self.interval;
    }
}
```

Use open-loop sweeps:

```text
50% of max throughput
70% of max throughput
85% of max throughput
95% of max throughput
110% of max throughput
```

The 110% overload run is useful because it reveals queue buildup, tail-latency collapse, and backpressure behavior.

# 25. Release gates

I would define gates in layers.

## Gate A: correctness

Must pass:

```text
SQL compatibility for supported subset
transaction commit/rollback tests
constraint tests
prepared statement invalidation tests
crash recovery strict mode
reopen consistency
result canonicalization tests
```

No performance claim can override this.

## Gate B: durability honesty

For each durability mode:

```text
strict: no acknowledged commit disappears
normal: no corruption; durability caveat documented
unsafe: no corruption guarantee claimed
```

## Gate C: single-thread parity

Minimum for replacement claims:

```text
point_read_pk: RedlineDB >= 90% SQLite throughput
single_row_insert normal: RedlineDB >= 90% SQLite throughput
update_disjoint 1 thread: RedlineDB >= 80–90% SQLite throughput
range_scan_pk: RedlineDB >= 80–90% SQLite throughput
```

The exact thresholds can be tuned after early data, but the release gate should exist. Without single-thread parity, concurrent wins may look like niche wins.

## Gate D: concurrent-writer advantage

For disjoint writers:

```text
threads >= 8
durability = strict and normal
RedlineDB throughput >= 2x SQLite
RedlineDB p99 <= SQLite p99 at equivalent achieved throughput
no unbounded memory growth
no unbounded WAL growth after reader gaps
```

A stronger goal:

```text
16 writers, strict mode:
RedlineDB >= 4x SQLite on single-row transactions
```

This is where RedlineDB should win because SQLite WAL admits only one writer at a time. ([SQLite][1])

## Gate E: memory discipline

```text
peak RSS <= configured cache/buffer budget + fixed overhead
no per-operation allocation growth
no unbounded prepared statement cache
no unbounded WAL retention without active horizon
```

## Gate F: reporting honesty

Every release report must include:

```text
all failed workloads
all unsupported SQL features
all skipped tests
all configs
all raw JSON
SQLite version
RedlineDB git SHA
hardware and filesystem
```

# 26. How to make RedlineDB win without cheating

## 26.1 Use disjoint writer workloads

If all writers update the same row, RedlineDB should not scale. That is conflict behavior, not engine write scalability.

Run both:

```text
writers_disjoint: architecture scalability
writers_hotspot: conflict behavior
```

## 26.2 Let group commit work, but measure its latency

In strict mode, RedlineDB can group multiple concurrent commits into one WAL fsync if each commit only returns after its record is durable. That is legitimate.

But report:

```text
group commit batch size
group commit wait time
fsync count
fsync duration
commit p99
```

SQLite WAL `FULL` syncs the WAL on each transaction commit, according to the official PRAGMA docs. RedlineDB’s strict group commit can be a real advantage if it preserves the same “acknowledged commit is durable” contract. ([SQLite][3])

## 26.3 Do not give RedlineDB a bigger cache

If RedlineDB gets 1 GiB and SQLite gets 64 MiB, the result is useless.

Use:

```text
RedlineDB buffer pool = X
SQLite cache_size = X
```

Also report RSS because SQLite may rely on OS page cache beyond SQLite’s own page cache.

## 26.4 Do not hide checkpoint cost

Run:

```text
with default checkpoint behavior
with controlled checkpoint worker
with long reader
with post-run checkpoint
```

Report both pre-checkpoint and post-checkpoint DB size.

## 26.5 Include p99 and p99.9

A database that gets 2x throughput with 100x p99 latency is not a clean win.

# 31. The key strategic point

Phase 9 should be designed to prove RedlineDB’s architectural thesis:

```text
SQLite is extremely optimized for embedded single-writer workloads.
RedlineDB must first match SQLite on single-thread key OLTP paths.
Then RedlineDB must clearly beat SQLite on concurrent disjoint writers by avoiding SQLite’s single-writer WAL ceiling.
```

The benchmark should make that impossible to fake. If RedlineDB wins because it is genuinely concurrent, memory-bounded, durable in strict mode, and correct against SQLite’s supported SQL subset, Phase 9 becomes the release certificate.
